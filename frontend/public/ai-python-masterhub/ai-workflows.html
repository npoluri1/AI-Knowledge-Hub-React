AI Workflows — Designing Reliable LLM Pipelines

Compose prompts, models, tools and human checkpoints into deterministic, observable, resumable pipelines

How to Use This Chapter

An AI workflow is a structured sequence of steps — calls to models, tools, retrievers, validators and humans — composed into a pipeline with defined inputs, outputs and failure handling. Workflows are the difference between a demo and a product: deterministic where it must be, flexible where it can be, and always observable.

Part I · FoundationsTier 1 — the atomic unit: a step

1Workflow vs Agent: When to Use Which

What & why. A workflow is a fixed graph of steps; an agent is a loop that decides its own next action. Anthropic's guidance: start with the simplest workflow that works; use agents only when open-ended decisions are genuinely required. Predictable tasks belong in workflows.

# Workflow: fixed path, every run identical shape
#   input -> [classify] -> [translate] -> [validate] -> output

# Agent: loop with model-chosen next step
#   input -> think -> act(tool) -> observe -> think -> ... -> done

# Decision guide
#   Fixed steps, known order?      -> workflow (chain, router)
#   Steps vary by input?           -> router or dynamic workflow
#   Free-form problem, tools, loop? -> agent

# Cost & reliability:
#   Workflows: predictable latency/cost, easy to test
#   Agents:    flexible, but non-deterministic and harder to eval
Where you'll use itEvery architecture review. The default should be a workflow; agents are the escape hatch for open-ended tasks.
Under the hoodThis mirrors AI Design Patterns: chains, routers, and orchestrator-worker are workflows; the evaluator-optimizer loop is a mini-agent.

2The Linear Chain: Your First Workflow

What & why. The simplest workflow chains steps where each output feeds the next input. Each step wraps one LLM call plus parsing and validation, so failures are caught at the step boundary, not mid-pipeline.

from dataclasses import dataclass, field
from typing import Callable, Any

@dataclass
class Step:
    name: str
    fn: Callable[[dict], dict]
    retries: int = 2

class Chain:
    def __init__(self, steps):
        self.steps = steps

    def run(self, state: dict) -> dict:
        for step in self.steps:
            print(f"[workflow] running {step.name}")
            state = step.fn(state)          # step boundary
        return state

# --- example: summarize -> extract -> grade ---
summarize = Step("summarize", lambda s: {
    **s, "summary": call_llm(f"Summarize: {s['text']}")
})
extract = Step("extract", lambda s: {
    **s, "keywords": parse_json(call_llm(
        f"Extract keywords as JSON from: {s['summary']}"))
})
def grade(s):
    if not s["keywords"]:
        raise ValueError("extraction produced no keywords")
    return {**s, "grade": "ok"}
grade_step = Step("grade", grade)

pipeline = Chain([summarize, extract, grade_step])
result = pipeline.run({"text": "..."})
Where you'll use itETL of text, document triage, translation, and every place a fixed sequence of LLM operations is needed.
Under the hoodThis is LCEL-style composition (LangChain) and LangGraph chains — same idea, more tooling: |, RunnableSequence, pydantic output parsers.

3Structured Output as a Contract

What & why. Free-form LLM text breaks pipelines. Every step that produces data should return validated, typed structures — using JSON mode / function calling plus Pydantic validation — so downstream steps never guess.

from pydantic import BaseModel, Field

class Extract(BaseModel):
    sentiment: str = Field(description="positive|neutral|negative")
    score: float = Field(ge=0, le=1)
    topics: list[str]

# OpenAI-style tool/JSON-mode call
def call_llm_json(prompt, schema):
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_object"},  # JSON mode
        tools=[{"type": "function",
                "function": {"name": "extract",
                             "parameters": schema.model_json_schema()}}],
    )
    return Extract.model_validate_json(
        response.choices[0].message.tool_calls[0].function.arguments)

out = call_llm_json("The product is great but support is slow.", Extract)
print(out.sentiment, out.score, out.topics)

# Validation failure = retry with error feedback:
#   Extract.model_validate_json(raw)  -> raises ValidationError
Where you'll use itEvery step that must hand data to another step or store it: extraction, routing decisions, evals, database writes.
Under the hoodDeep dive in Tool Calling: schema-driven generation is the same mechanism as function calling, just used for data contracts.

Part II · Control FlowTier 2 — making workflows smart

4Routing: Let the Input Choose the Path

What & why. A router classifies the input and dispatches to a specialized sub-pipeline. This keeps each path simple while the system as a whole covers many cases — the single most common production workflow pattern.

from pydantic import BaseModel

class Route(BaseModel):
    path: str  # one of: billing, engineering, account, sales

def route_step(state):
    decision = call_llm_json(
        f"Classify this ticket to a path: {state['ticket']}",
        Route)
    return {**state, "path": decision.path}

def billing_handler(state):  return {**state, "answer": call_llm(f"Billing reply: {state['ticket']}")}
def eng_handler(state):      return {**state, "answer": call_llm(f"Engineering triage: {state['ticket']}")}
def account_handler(state):  return {**state, "answer": call_llm(f"Account reply: {state['ticket']}")}
def sales_handler(state):    return {**state, "answer": call_llm(f"Sales reply: {state['ticket']}")}

HANDLERS = {
    "billing": billing_handler,
    "engineering": eng_handler,
    "account": account_handler,
    "sales": sales_handler,
}

def router_workflow(ticket):
    state = {"ticket": ticket}
    state = route_step(state)
    return HANDLERS[state["path"]](state)

# Router choice matters:
#   LLM router: flexible, needs eval on edge cases
#   Keyword router: cheap, deterministic, no latency
Where you'll use itSupport triage, content classification, model selection ("route to GPT-4 vs Haiku"), and intent-based dispatch.
Under the hoodThe routing pattern is one of the core AI Design Patterns; production systems add a fallback path and log every route decision.

5Parallel Steps and Map-Reduce

What & why. Many workflows fan out: chunk a document and summarize each chunk, then combine. Parallel fan-out cuts latency; map-reduce tames long inputs that exceed context windows.

from concurrent.futures import ThreadPoolExecutor

def fan_out(inputs, step_fn, workers=8):
    with ThreadPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(step_fn, inputs))

# Example: summarize a long document by chunks
def chunk(text, n=1500):
    words = text.split()
    return [" ".join(words[i:i+n]) for i in range(0, len(words), n)]

def summarize_chunk(chunk_text):
    return call_llm(f"Summarize in 2 sentences: {chunk_text[:1500]}")

def summarize_long(text):
    summaries = fan_out(chunk(text), summarize_chunk)
    combined = "\n".join(f"- {s}" for s in summaries)
    return call_llm(f"Write an executive summary from:\n{combined}")

# Safety: cap parallelism, set per-call timeouts, dedupe inputs
# map-reduce also works for: extraction, classification, scoring
Where you'll use itLong-document processing, batch extraction, bulk classification, and any embarrassingly-parallel LLM work.
Under the hoodLangGraph's Send API implements map-reduce over nodes; production systems also use queues (Celery/Redis) when fan-out is huge.

6Retries, Timeouts and Fallbacks

What & why. LLM providers fail: rate limits, timeouts, 5xx, malformed JSON. A resilient workflow retries with backoff, switches models on failure, and degrades gracefully when everything fails.

import time, random

def with_retries(fn, retries=3, backoff=1.5, fallback=None):
    for attempt in range(retries):
        try:
            return fn()
        except Exception as e:
            print(f"attempt {attempt+1} failed: {e}")
            if attempt == retries - 1:
                return fallback if fallback else fn  # degrade
            time.sleep(backoff * (2 ** attempt) + random.uniform(0, 0.5))

def call_with_fallback(prompt):
    providers = [call_gpt4, call_claude, call_local]
    for provider in providers:
        try:
            return provider(prompt, timeout=20)
        except Exception:
            continue
    raise RuntimeError("all providers failed")

# Policy essentials
#   timeout per call:         20-60s
#   max retries:              3 (exponential backoff + jitter)
#   retry on:                 429, 5xx, timeouts, parse errors
#   never retry on:           4xx auth/validation (fix config)
Where you'll use itEvery production LLM integration. Retry policies are the #1 difference between demo and production pipelines.
Under the hoodSee Agent Gateway for provider-level fallbacks, load balancing, and circuit breakers; this pattern composes with it.

Part III · OrchestrationTier 3 — stateful DAGs

7State, Checkpoints and Resumability

What & why. Long workflows must survive crashes. Persist workflow state after every step so a run can resume from the last checkpoint instead of restarting — critical for cost and reliability on multi-minute pipelines.

import json, os

class CheckpointedWorkflow:
    def __init__(self, run_id, steps, store_dir="runs"):
        self.run_id = run_id
        self.steps = steps
        self.store = os.path.join(store_dir, f"{run_id}.json")
        self.state = self._load() or {}

    def _load(self):
        if os.path.exists(self.store):
            with open(self.store) as f:
                return json.load(f)
        return None

    def _save(self):
        os.makedirs(os.path.dirname(self.store), exist_ok=True)
        with open(self.store, "w") as f:
            json.dump(self.state, f, indent=2)

    def run(self, initial):
        self.state = {**initial, **self.state}
        for name, fn in self.steps:
            if self.state.get(f"done_{name}"):
                continue                      # already finished
            self.state.update(fn(self.state))  # run step
            self.state[f"done_{name}"] = True
            self._save()                      # checkpoint after step
        return self.state

# run_id ties retries to the same state file; a new attempt
# simply skips completed steps. Combine with idempotent steps.
Where you'll use itLong document jobs, batch pipelines, agent runs that take minutes, and any workflow with human approval steps.
Under the hoodLangGraph checkpointer, Temporal, and Prefect all do this — the principle is the same: durable state + step-level idempotency.

8Human-in-the-Loop Checkpoints

What & why. High-stakes steps (approving a payment, publishing content, emailing a customer) need a human gate. The workflow pauses, emits a review request, and resumes when the decision arrives — never auto-executes irreversible actions.

from enum import Enum

class Approval(str, Enum):
    APPROVE = "approve"
    EDIT = "edit"
    REJECT = "reject"

def human_review(state, review_channel="review-queue"):
    # 1. Publish a review task with the pending action
    publish(review_channel, {
        "run_id": state["run_id"],
        "action": state["draft_action"],
        "context": state["evidence"],
    })
    # 2. BLOCK until a human responds (long-poll / webhook)
    decision = wait_for_decision(state["run_id"], timeout="24h")
    # 3. Apply the decision
    if decision == Approval.APPROVE:
        return {**state, "status": "approved"}
    if decision == Approval.EDIT:
        return {**state, "status": "needs_edit",
                "feedback": decision.feedback}
    return {**state, "status": "rejected", "reason": decision.reason}

# Design rules
#   - irreversible actions ALWAYS need approval
#   - attach evidence so the human can verify fast
#   - enforce decision timeouts (escalate, don't block forever)
#   - audit-log who approved what, when
Where you'll use itFinance, healthcare, publishing, email automation, code-gen review — anywhere a mistake is expensive.
Under the hoodLangGraph interrupts implement exactly this: the graph pauses at a node, serializes state, and resumes from a saved snapshot after the human answers.

9Building a Workflow with LangGraph

What & why. LangGraph gives you stateful graphs with conditional edges, checkpointing, and human-in-the-loop out of the box. The canonical example: an agentic research workflow with router, tools and a guard.

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, END

class State(TypedDict):
    question: str
    plan: str
    answer: str
    needs_tools: bool

def plan_node(state):       # step 1: plan
    return {"plan": call_llm(f"Plan for: {state['question']}"),
            "needs_tools": True}

def route_after_plan(state) -> Literal["tools", "answer"]:
    return "tools" if state["needs_tools"] else "answer"

def tools_node(state):      # step 2: use tools
    return {"plan": state["plan"] + " [searched]"}

def answer_node(state):     # step 3: synthesize
    return {"answer": call_llm(f"Answer given: {state['plan']}")}

g = StateGraph(State)
g.add_node("plan", plan_node)
g.add_node("tools", tools_node)
g.add_node("answer", answer_node)
g.set_entry_point("plan")
g.add_conditional_edges("plan", route_after_plan)
g.add_edge("tools", "answer")
g.add_edge("answer", END)

app = g.compile(checkpointer=MemorySaver())  # resumable
result = app.invoke({"question": "..."},
                    config={"configurable": {"thread_id": "1"}})
Where you'll use itAny multi-step LLM app that needs state, branching, or resumption. Full framework coverage in LangGraph.
Under the hoodThe graph is compiled to an executable; the checkpointer persists state per thread_id, enabling interrupt/resume and even time-travel debugging.

Part IV · ProductionTier 4 — scale and operate

10Event-Driven and Asynchronous Workflows

What & why. For long or bursty workloads, don't hold a process open. Model steps as messages on a queue (SQS, Redis, Kafka): a worker consumes a message, runs a step, and emits the next message. This gives you durability, retries, and horizontal scaling for free.

# Message-based workflow: each step is a consumer
#   ingest.queue -> [extract] -> extract.queue -> [grade] -> results

# Worker pseudocode (Celery / SQS / Redis Streams)
@worker.consumer("extract.queue")
def extract_worker(message):
    try:
        data = extract(message["doc_id"])
    except TransientError:
        message.retry(delay=30)          # redeliver later
        return
    publish("grade.queue", {"doc_id": message["doc_id"], "data": data})

# Why async wins for production:
#   - workers scale independently per step
#   - failed messages are redelivered, not lost
#   - steps can be replaced without touching the pipeline
#   - bursts buffer in the queue instead of 5xxing

# Add: DLQ (dead-letter queue) for poison messages,
#      idempotency keys per message, delivery at-least-once.
Where you'll use itDocument processing at scale, nightly enrichment jobs, ingestion pipelines, and any workflow with variable load.
Under the hoodAt-least-once delivery means your steps must be idempotent: same input twice must produce the same stored result.

11Observability and Cost Control

What & why. You cannot operate what you cannot see. Trace every step: which model, tokens in/out, latency, cost, retries, and the input/output of each step — then alert on regressions. Cost per workflow run is a product metric, not an afterthought.

# Trace a step with OpenTelemetry-style spans
def traced_step(name, fn, state):
    span = tracer.start_span(name)
    span.set_attribute("input_len", len(str(state)))
    start = time.time()
    try:
        result = fn(state)
        span.set_attribute("status", "ok")
    except Exception as e:
        span.set_attribute("status", "error")
        span.record_exception(e)
        raise
    finally:
        span.set_attribute("duration_ms", (time.time() - start) * 1000)
        span.end()
    return result

# Per-run metrics to capture
#   tokens_in, tokens_out, cost_usd = f(tokens, model)
#   step_duration_ms, total_duration_ms, retries, route_decision
# Alert when: cost/run > X, error rate > Y%, p95 latency > Zs

# Tools: Langfuse, LangSmith, Phoenix, OpenTelemetry
# Full method in the Observability chapter.
Where you'll use itEvery shipped workflow. Cost regressions appear the day after a prompt change; tracing catches them first.
Under the hoodFull coverage in Observability (spans, metrics, sessions) and Evaluations (regression gates on workflow outputs).

12Workflow Evaluation as CI

What & why. Workflows are software: prompt or step changes should be tested before deploy. Build a golden dataset of (input, expected) pairs, run the workflow, score outputs, and gate deploys on regression thresholds.

GOLDEN = [
    {"input": "Refund for order 123", "path": "billing"},
    {"input": "App crashes on login", "path": "engineering"},
    # ... 50-200 representative cases
]

def eval_workflow(pipeline):
    results = []
    for case in GOLDEN:
        out = pipeline(case["input"])
        ok = out["path"] == case["path"]
        results.append({"case": case["input"], "ok": ok,
                        "got": out["path"]})
    acc = sum(r["ok"] for r in results) / len(results)
    return acc, results

# CI gate: block merge if accuracy drops below threshold
acc, results = eval_workflow(router_workflow)
assert acc >= 0.95, f"router regression: {acc:.2f}"

# Beyond exact-match:
#   - LLM-as-judge on answer quality (rubric)
#   - assert on structure (schema validation)
#   - assert on safety (no PII, no harmful content)
#   - cost budget assertions
Where you'll use itAny workflow you ship more than once. Evals convert "it works in my notebook" into a deployable contract.
Under the hoodDeep dive: Evaluations (judges, rubrics, pairwise) and MLOps (CI/CD for prompts and models).

15Project 3 — Guardrailed Agent Workflow

What & why. A workflow that looks like an agent: plan, call tools with approval gates, synthesize, and validate output before delivery. This is the pattern most production "agents" actually are.

def production_agent(question):
    state = {"question": question}
    state = sanitize_input(state)        # guardrail: injection/PII
    state = plan_node(state)             # decompose into steps
    for step in state["plan"]:
        if step.requires_tool:
            state = human_review(state)  # approval for risky tools
            state = tools_node(state)
    state = answer_node(state)
    state = validate_output(state)       # guardrail: schema+safety
    return state
