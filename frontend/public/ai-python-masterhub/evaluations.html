1Why Evaluations Differ from Unit Tests

What & why. Traditional unit tests assert deterministic outputs: given input X, expect output Y. LLM systems are non-deterministic â€” the same prompt can return semantically equivalent but lexically different answers across runs. Evaluations therefore measure quality distributions rather than exact correctness, requiring statistical thinking, tolerance bands, and multiple runs per test case.

# Traditional test: deterministic pass/fail
def test_add():
    assert add(2, 3) == 5  # always passes

# LLM eval: non-deterministic, needs tolerance
import statistics

def test_llm_summary_quality():
    scores = []
    for _ in range(5):  # run N times
        output = llm.generate("Summarize: The Earth orbits the Sun.")
        score = grade_relevance(output, reference)
        scores.append(score)
    mean = statistics.mean(scores)
    assert mean >= 0.8, f"Mean relevance {mean:.2f} below threshold"
Where you'll use itEvery team shipping LLM features needs evals. Without them, prompt changes silently degrade quality and regressions reach production undetected for weeks.
Under the hoodLLM non-determinism stems from temperature sampling, floating-point arithmetic on GPUs, and provider-side infrastructure changes. Temperature 0 reduces but does not eliminate variance.

2Golden Dataset Creation: Your First 20 Examples

What & why. A golden dataset is a curated set of input-output pairs where you have expert-verified reference answers. Start with 20 examples covering your most critical use cases: happy paths, edge cases, and known failure modes. Each example needs an input prompt, expected output (or acceptable range), and a difficulty label for stratified sampling.

3Exact-Match and Contains Assertions

What & why. Exact-match checks whether the LLM output is character-identical to the reference. Contains checks whether the reference string appears anywhere in the output. These are the simplest assertion types and are appropriate for factual answers, classification labels, and structured output validation where there is a single correct form.

def exact_match(output: str, reference: str) -> bool:
    return output.strip().lower() == reference.strip().lower()

def contains(output: str, reference: str) -> bool:
    return reference.strip().lower() in output.strip().lower()

# Usage in eval loop
test_cases = [
    {"input": "What is 2+2?", "expected": "4"},
    {"input": "Name a prime number", "expected_contains": "2"},
]

for case in test_cases:
    result = llm.generate(case["input"])
    if "expected" in case:
        score = exact_match(result, case["expected"])
    elif "expected_contains" in case:
        score = contains(result, case["expected_contains"])
    print(f"{case['input']}: {'PASS' if score else 'FAIL'}")
Where you'll use itExact-match works for classification tasks, JSON schema validation, and API response format checks. Use it as a first gate before more expensive semantic evaluation.
Under the hoodNormalization (lowercase, strip whitespace, remove articles) is critical. Without it, "The 4" vs "4" causes false negatives. Most eval frameworks apply configurable normalization pipelines.

4LLM-as-Judge: Basic Rubric Scoring

What & why. Instead of checking exact text, you use a powerful LLM (typically GPT-4 or Claude) to score the output against a rubric. The judge receives the input, the reference answer, and the system output, then returns a numeric score. This captures semantic quality that exact-match misses entirely.

judge_prompt = """Rate the following answer on a scale of 1-5.

Input: {input}
Reference: {reference}
System Output: {output}

Scoring rubric:
5 - Perfectly accurate and complete
4 - Accurate with minor omissions
3 - Mostly accurate but missing key details
2 - Partially accurate with significant gaps
1 - Incorrect or irrelevant

Respond with JSON: {{"score": int, "reasoning": "..."}}"""

from openai import OpenAI
client = OpenAI()

def judge_score(input_text, reference, output):
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": judge_prompt.format(
            input=input_text, reference=reference, output=output
        )}],
        response_format={"type": "json_object"}
    )
    return json.loads(response.choices[0].message.content)
Where you'll use itLLM-as-judge is the standard approach for evaluating summarization, translation, creative writing, and any task where "correct" has a semantic range rather than a single answer.
Under the hoodThe judge model must be more capable than the system being evaluated. Using the same model to judge itself produces inflated scores â€” always use a stronger or equal-capability model as judge.

5Pairwise A/B Preference Judging

What & why. Instead of scoring individual outputs on an absolute scale, pairwise judging presents two outputs side by side and asks the judge which one is better. This reduces score calibration issues and is more reliable when comparing model versions, prompt variants, or RAG configurations. The Elo-style rating system converts pairwise wins into relative rankings.

pairwise_prompt = """Compare these two responses to the same input.

Input: {input}
Response A: {output_a}
Response B: {output_b}

Which response is better? Consider accuracy, completeness, and clarity.
Respond with JSON: {{"winner": "A" | "B" | "tie", "reasoning": "..."}}"""

def pairwise_judge(input_text, output_a, output_b):
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": pairwise_prompt.format(
            input=input_text, output_a=output_a, output_b=output_b
        )}],
        response_format={"type": "json_object"}
    )
    return json.loads(response.choices[0].message.content)

# Aggregate into ratings
def elo_update(rating_a, rating_b, winner, k=32):
    expected_a = 1 / (1 + 10 ** ((rating_b - rating_a) / 400))
    expected_b = 1 - expected_a
    if winner == "A":
        return rating_a + k * (1 - expected_a), rating_b + k * (0 - expected_b)
    elif winner == "B":
        return rating_a + k * (0 - expected_a), rating_b + k * (1 - expected_b)
    return rating_a, rating_b
Where you'll use itPairwise judging is the backbone of Chatbot Arena-style evaluation. Use it when comparing prompt versions or model upgrades where relative improvement matters more than absolute score.
Under the hoodPosition bias â€” judges favoring the response presented first â€” is mitigated by running each pair twice with swapped order and requiring agreement. See Tier 3 for detailed bias mitigation.

6Regression Suites: Run-on-Change Testing

What & why. Regression suites are eval sets that run automatically whenever you change a prompt, switch a model, or modify a RAG pipeline. They act as quality gates: if any score drops below the threshold, the change is blocked. This is the LLM equivalent of CI test suites in traditional software engineering.

# eval_suite.py â€” runs on every prompt change
import json, sys

THRESHOLDS = {
    "summarization": 0.85,
    "factual_qa": 0.90,
    "classification": 0.95,
}

def load_golden(path="golden_dataset.jsonl"):
    with open(path) as f:
        return [json.loads(line) for line in f]

def run_eval_suite(dataset, system_fn):
    results = []
    for example in dataset:
        output = system_fn(example["input"])
        score = judge_score(
            example["input"], example["reference"], output
        )
        results.append({
            "id": example["id"],
            "category": example["category"],
            "score": float(score["score"]) / 5.0,
        })
    return results

def check_thresholds(results):
    failures = []
    for r in results:
        threshold = THRESHOLDS.get(r["category"], 0.80)
        if r["score"] < threshold:
            failures.append(f"{r['id']}: {r['score']:.2f} < {threshold}")
    return failures

if __name__ == "__main__":
    dataset = load_golden()
    results = run_eval_suite(dataset, my_system.generate)
    failures = check_thresholds(results)
    if failures:
        print("EVAL REGRESSION DETECTED:")
        for f in failures:
            print(f"  FAIL: {f}")
        sys.exit(1)
    print("All evals passed.")
Where you'll use itRegression suites are triggered by git hooks, CI pipelines, or pre-deploy checks. They prevent prompt engineers from accidentally degrading quality while optimizing for one metric.
Under the hoodThe threshold-setting process is empirical: run the suite on known-good and known-bad outputs, find the decision boundary, then add a 5-10% safety margin.

7Metrics Cheat Sheet: Accuracy, F1, BLEU, ROUGE and Their Limits

What & why. Different evaluation metrics capture different aspects of quality. Accuracy measures exact correctness, F1 balances precision and recall for classification, BLEU measures n-gram overlap for translation, and ROUGE measures recall-oriented overlap for summarization. Each has blind spots: BLEU penalizes valid paraphrases, ROUGE rewards verbose output, and accuracy ignores confidence calibration.

from collections import Counter

def accuracy(predictions, references):
    correct = sum(1 for p, r in zip(predictions, references) if p == r)
    return correct / len(predictions)

def f1_score_binary(tp, fp, fn):
    precision = tp / (tp + fp) if (tp + fp) > 0 else 0
    recall = tp / (tp + fn) if (tp + fn) > 0 else 0
    if precision + recall == 0:
        return 0
    return 2 * precision * recall / (precision + recall)

def rouge_l(output, reference):
    output_tokens = output.split()
    reference_tokens = reference.split()
    lcs = _lcs_length(output_tokens, reference_tokens)
    recall = lcs / len(reference_tokens) if reference_tokens else 0
    precision = lcs / len(output_tokens) if output_tokens else 0
    if precision + recall == 0:
        return 0
    return 2 * precision * recall / (precision + recall)

def _lcs_length(a, b):
    m, n = len(a), len(b)
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if a[i-1] == b[j-1]:
                dp[i][j] = dp[i-1][j-1] + 1
            else:
                dp[i][j] = max(dp[i-1][j], dp[i][j-1])
    return dp[m][n]
Where you'll use itUse accuracy for classification, F1 for information extraction, ROUGE for summarization recall, and LLM-as-judge for everything else. Never rely on a single metric â€” use a metric panel.
Under the hoodBLEU and ROUGE were designed for machine translation and summarization in the pre-LLM era. They reward surface-level overlap and miss semantic equivalence. Modern eval practice supplements them with embedding-based similarity (BERTScore) and LLM-as-judge.

9Sampling N Runs and Measuring Variance

What & why. Because LLM outputs vary between runs, a single evaluation pass is insufficient. You must sample N runs (typically 3-10) per test case and measure the variance. High variance means the system is unstable for that input â€” even if the mean score is acceptable, individual runs may fail.

import statistics

def eval_with_variance(system_fn, example, n_runs=5):
    scores = []
    outputs = []
    for _ in range(n_runs):
        output = system_fn(example["input"])
        score = grade(output, example["reference"])
        scores.append(score)
        outputs.append(output)

    mean = statistics.mean(scores)
    stdev = statistics.stdev(scores) if len(scores) > 1 else 0
    return {
        "id": example["id"],
        "mean_score": mean,
        "stdev": stdev,
        "min_score": min(scores),
        "max_score": max(scores),
        "n_runs": n_runs,
        "stable": stdev < 0.1,
    }

def batch_eval(dataset, system_fn, n_runs=5):
    results = []
    for example in dataset:
        result = eval_with_variance(system_fn, example, n_runs)
        results.append(result)
        status = "STABLE" if result["stable"] else "UNSTABLE"
        print(f"{result['id']}: {result['mean_score']:.2f} "
              f"(+/-{result['stdev']:.3f}) [{status}]")
    return results
Where you'll use itVariance analysis identifies prompt fragility. If a test case has high variance, the prompt needs clarification or the model needs temperature reduction for that use case.
Under the hoodSetting temperature to 0 reduces but does not eliminate variance. GPU floating-point non-determinism and provider-side batching introduce irreducible noise. Accept stdev < 0.1 as "stable."

10Pass/Fail Thresholds and Quality Gates

What & why. Thresholds convert continuous quality scores into binary pass/fail decisions for CI gates. Setting thresholds too high blocks all changes; too low lets regressions through. The right approach is data-driven: measure your current baseline, determine the minimum acceptable quality, and set the threshold at baseline minus a small margin.

import json

class QualityGate:
    def __init__(self, thresholds_file="thresholds.json"):
        with open(thresholds_file) as f:
            self.thresholds = json.load(f)

    def evaluate(self, eval_results):
        """Returns (passed, report)"""
        failures = []
        warnings = []
        for category, results in eval_results.items():
            mean_score = sum(r["score"] for r in results) / len(results)
            threshold = self.thresholds.get(category, {}).get("min", 0.8)
            warn_threshold = self.thresholds.get(category, {}).get("warn", 0.85)
            if mean_score < threshold:
                failures.append(
                    f"{category}: {mean_score:.3f} < {threshold} (FAIL)"
                )
            elif mean_score < warn_threshold:
                warnings.append(
                    f"{category}: {mean_score:.3f} near threshold (WARN)"
                )
        return len(failures) == 0, {"failures": failures, "warnings": warnings}

# thresholds.json
# {
#   "summarization": {"min": 0.80, "warn": 0.85},
#   "factual_qa": {"min": 0.90, "warn": 0.93},
#   "classification": {"min": 0.95, "warn": 0.97}
# }
Where you'll use itQuality gates run in CI pipelines. A failed gate blocks the PR merge. Warnings appear as review comments, giving authors visibility without blocking.
Under the hoodDual thresholds (min + warn) create a buffer zone. When scores drift into the warn zone, the team knows to investigate before a hard failure occurs.

11Recording Results in JSONL for Analysis

What & why. Every eval run should produce a structured log with timestamps, model versions, prompt hashes, scores, and raw outputs. JSONL (one JSON object per line) is the standard format because it is append-friendly, streamable, and trivially loadable into pandas, BigQuery, or Databricks for longitudinal analysis.

import json, hashlib, datetime

def log_eval_result(result, metadata=None):
    record = {
        "timestamp": datetime.datetime.utcnow().isoformat(),
        "eval_id": result["id"],
        "score": result["score"],
        "model": result.get("model", "unknown"),
        "prompt_hash": hashlib.sha256(
            result.get("prompt", "").encode()
        ).hexdigest()[:16],
        "output": result.get("output", ""),
        "reference": result.get("reference", ""),
        "metadata": metadata or {},
    }
    with open("eval_log.jsonl", "a") as f:
        f.write(json.dumps(record) + "\n")
    return record

def run_and_log(dataset, system_fn, model_name="gpt-4o"):
    results = []
    for example in dataset:
        output = system_fn(example["input"])
        score = grade(output, example["reference"])
        record = log_eval_result({
            "id": example["id"],
            "score": score,
            "model": model_name,
            "prompt": example["input"],
            "output": output,
            "reference": example["reference"],
        })
        results.append(record)
    passed = sum(1 for r in results if r["score"] >= 0.8)
    print(f"Eval complete: {passed}/{len(results)} passed")
    return results
Where you'll use itJSONL logs enable trend analysis: detect quality drift over weeks, compare model versions, and identify which prompt changes improved or degraded scores.
Under the hoodPrompt hashing captures the exact prompt variant used. When you later see a score change, you can diff the prompts by hash to identify the triggering change.

13RAGAS: Faithfulness, Answer Relevancy, Context Precision

What & why. RAGAS (Retrieval Augmented Generation Assessment) is an open-source framework that evaluates RAG systems using four core metrics: faithfulness (is the answer grounded in context?), answer relevancy (does the answer address the question?), context precision (are retrieved chunks relevant?), and context recall (were all needed chunks retrieved?). Each metric uses LLM-as-judge under the hood.

from ragas import evaluate
from ragas.metrics import (
    faithfulness, answer_relevancy,
    context_precision, context_recall
)
from datasets import Dataset

eval_data = Dataset.from_dict({
    "question": [
        "What is the refund policy?",
        "How do I reset my password?",
    ],
    "answer": [
        "You can request a refund within 30 days.",
        "Go to Settings > Security > Reset Password.",
    ],
    "contexts": [
        ["Our refund policy allows returns within 30 days of purchase."],
        ["To reset: navigate to Settings, select Security, click Reset."],
    ],
    "ground_truth": [
        "Refunds accepted within 30 days.",
        "Password reset via Settings > Security.",
    ],
})

result = evaluate(
    eval_data,
    metrics=[faithfulness, answer_relevancy,
             context_precision, context_recall],
)
print(result)
# {'faithfulness': 0.95, 'answer_relevancy': 0.92,
#  'context_precision': 0.88, 'context_recall': 0.90}
Where you'll use itRAGAS metrics decompose RAG quality into retrieval vs. generation problems. Low faithfulness means the generator hallucinates; low context precision means the retriever fetches noise.
Under the hoodRAGAS faithfulness works by decomposing the answer into claims, then verifying each claim against the context using an NLI (natural language inference) model. This is more robust than whole-answer similarity.

16Judge Prompt Engineering: Role, Rubric, Scale

What & why. The quality of LLM-as-judge evaluation depends entirely on the judge prompt. A well-crafted judge prompt defines: (1) the judge's role and expertise, (2) a rubric with clearly differentiated levels, (3) the scoring scale, and (4) explicit criteria for each level. Poor judge prompts produce noisy, unreliable scores.

JUDGE_PROMPT = """You are an expert evaluator of customer support responses.

Rate the system output on these criteria:
1. ACCURACY: Is the information factually correct?

17Position Bias and Swap-Order Mitigation

What & why. When comparing two outputs side by side, LLM judges tend to favor whichever response appears first (position bias). The mitigation strategy is to run each comparison twice â€” once with A first, once with B first â€” and only count a preference if both runs agree. Disagreements are marked as ties.

def debiased_pairwise_judge(input_text, output_a, output_b):
    # Run comparison twice with swapped order
    result_ab = pairwise_judge(input_text, output_a, output_b)
    result_ba = pairwise_judge(input_text, output_b, output_a)

    # Normalize: map second result back to A/B notation
    result_ba["winner"] = {"A": "B", "B": "A", "tie": "tie"}[
        result_ba["winner"]
    ]

    if result_ab["winner"] == result_ba["winner"]:
        # Both agree â€” trustworthy result
        return {
            "winner": result_ab["winner"],
            "confidence": "high",
            "both_agree": True,
        }
    else:
        # Disagreement â€” treat as tie (position bias detected)
        return {
            "winner": "tie",
            "confidence": "low",
            "both_agree": False,
            "note": "Position bias detected, treating as tie",
        }

def full_debiased_eval(dataset, system_a, system_b):
    results = {"a_wins": 0, "b_wins": 0, "ties": 0}
    for example in dataset:
        out_a = system_a(example["input"])
        out_b = system_b(example["input"])
        result = debiased_pairwise_judge(
            example["input"], out_a, out_b
        )
        if result["winner"] == "A":
            results["a_wins"] += 1
        elif result["winner"] == "B":
            results["b_wins"] += 1
        else:
            results["ties"] += 1
    return results

18Verbosity Bias and Length Control

What & why. LLM judges tend to rate longer responses higher, conflating verbosity with quality. A 200-word answer is not inherently better than a 50-word answer that covers the same information. Length control techniques include: adding explicit length instructions to the judge prompt, normalizing scores by length, and including a "conciseness" criterion.

JUDGE_PROMPT_LENGTH_CONTROLLED = """You are an expert evaluator.

    output_len = len(output.split())
    reference_len = len(reference.split())
    length_ratio = output_len / max(reference_len, 1)
    # Penalize if output is more than 2x reference length

        return max(0, raw_score - penalty)
    return raw_score

What & why. Reference-based evaluation compares LLM output to a known-good reference answer. Reference-free evaluation judges output quality without a reference, using criteria like coherence, safety, and format compliance. # Reference-based: needs a reference answer

23Agent Trajectory Evaluations: Steps, Tool Choice, Success

What & why. Agent evaluation goes beyond output quality to assess the trajectory: which tools were called, in what order, whether unnecessary steps were taken, and whether the agent reached the goal. A trajectory eval captures the full execution trace and scores each step for correctness, efficiency, and tool selection appropriateness.

def evaluate_trajectory(trajectory, ground_truth_trajectory=None):
    """Score an agent trajectory on multiple dimensions."""
    steps = trajectory["steps"]
    scores = {}

    # Goal achievement: did the agent reach the correct final answer?
    scores["goal_achieved"] = (
        1.0 if trajectory["final_answer"] == trajectory["expected"]
        else 0.0
    )

    # Tool appropriateness: were the right tools called?
    tool_calls = [s["tool"] for s in steps if s["type"] == "tool_call"]
    expected_tools = set(trajectory.get("expected_tools", []))
    if expected_tools:
        scores["tool_precision"] = (
            len(set(tool_calls) & expected_tools) / len(tool_calls)
            if tool_calls else 0
        )
        scores["tool_recall"] = (
            len(set(tool_calls) & expected_tools) / len(expected_tools)
        )

    # Step efficiency: fewer steps is better
    max_steps = trajectory.get("max_steps", 10)
    scores["efficiency"] = max(0, 1.0 - (len(steps) / max_steps))

    # Error recovery: did the agent handle failures gracefully?
    error_steps = [s for s in steps if s.get("error")]
    recovery_steps = [s for s in steps if s.get("recovery")]
    if error_steps:
        scores["error_recovery"] = (
            len(recovery_steps) / len(error_steps)
        )
    else:
        scores["error_recovery"] = 1.0

    # Weighted composite
    weights = {"goal_achieved": 0.4, "tool_precision": 0.2,
               "efficiency": 0.2, "error_recovery": 0.2}
    scores["composite"] = sum(
        scores[k] * weights[k] for k in weights
    )
    return scores
Where you'll use itAgent trajectory evaluation is essential for production agents where efficiency matters. An agent that reaches the right answer in 20 steps when 3 would suffice wastes compute and time.
Under the hoodGround-truth trajectories are expensive to create (you need expert traces). Use them for your critical paths and fall back to LLM-as-judge evaluation for the rest.

24Task Success Rate vs Step Efficiency Tradeoffs

What & why. Optimizing purely for task success rate encourages agents to take more steps "just in case." Optimizing purely for efficiency encourages agents to take shortcuts that occasionally fail. The Pareto frontier between these two objectives reveals the optimal operating point for your use case, and tracking it over time prevents drift in either direction.

def pareto_analysis(eval_runs):
    """Find Pareto-optimal configurations."""
    runs = []
    for run in eval_runs:
        runs.append({
            "config": run["config_name"],
            "success_rate": run["success_rate"],
            "avg_steps": run["avg_steps"],
            "cost": run["avg_cost"],
        })

    pareto_front = []
    for r in runs:
        dominated = False
        for other in runs:
            if (other["success_rate"] >= r["success_rate"] and
                other["avg_steps"] <= r["avg_steps"] and
                (other["success_rate"] > r["success_rate"] or
                 other["avg_steps"] < r["avg_steps"])):
                dominated = True
                break
        if not dominated:
            pareto_front.append(r)
    return pareto_front

def recommend_config(eval_runs, min_success_rate=0.90):
    """Find cheapest config meeting success threshold."""
    eligible = [r for r in eval_runs
                if r["success_rate"] >= min_success_rate]
    if not eligible:
        return None
    return min(eligible, key=lambda r: r["avg_cost"])

26Interleaved A/B Experiments with Statistical Rigor

What & why. Interleaved A/B testing presents both system versions to the same user in a single session, rather than splitting users into groups. This eliminates user-segment bias and requires smaller sample sizes. Statistical analysis uses bootstrap confidence intervals rather than p-values to measure the magnitude and certainty of differences.

import numpy as np

def interleaved_assignment(query_hash, seed=42):
    """Deterministic assignment based on query hash."""
    np.random.seed(seed + hash(query_hash) % 2**32)
    return np.random.choice(["A", "B"])

def bootstrap_ci(differences, n_bootstrap=10000, ci=0.95):
    """Compute bootstrap confidence interval for mean difference."""
    differences = np.array(differences)
    bootstrap_means = []
    for _ in range(n_bootstrap):
        sample = np.random.choice(
            differences, size=len(differences), replace=True
        )
        bootstrap_means.append(np.mean(sample))
    bootstrap_means = np.array(bootstrap_means)
    lower = np.percentile(bootstrap_means, (1 - ci) / 2 * 100)
    upper = np.percentile(bootstrap_means, (1 + ci) / 2 * 100)
    return {
        "mean_difference": np.mean(differences),
        "ci_lower": lower,
        "ci_upper": upper,
        "significant": not (lower <= 0 <= upper),
    }

def analyze_interleaved_results(results):
    """Analyze interleaved A/B experiment results."""
    a_scores = [r["score_a"] for r in results]
    b_scores = [r["score_b"] for r in results]
    differences = [b - a for a, b in zip(a_scores, b_scores)]
    return bootstrap_ci(differences)

27Statistical Significance: P-values vs Bootstrap CIs

What & why. P-values answer "is there a difference?" but not "how big is the difference?" Bootstrap confidence intervals answer both. For LLM evals with small sample sizes (50-200 examples), bootstrap methods are more robust than parametric tests because they make no assumptions about the underlying score distribution.

import numpy as np

def welch_t_test(group_a, group_b):
    """Welch's t-test for unequal variances."""
    a, b = np.array(group_a), np.array(group_b)
    n_a, n_b = len(a), len(b)
    mean_a, mean_b = np.mean(a), np.mean(b)
    var_a, var_b = np.var(a, ddof=1), np.var(b, ddof=1)
    se = np.sqrt(var_a / n_a + var_b / n_b)
    t_stat = (mean_a - mean_b) / se
    # Approximate degrees of freedom (Welch-Satterthwaite)
    df = (var_a / n_a + var_b / n_b) ** 2 / (
        (var_a / n_a) ** 2 / (n_a - 1) +
        (var_b / n_b) ** 2 / (n_b - 1)
    )
    return {"t_statistic": t_stat, "df": df, "mean_diff": mean_a - mean_b}

def bootstrap_effect_size(group_a, group_b, n_bootstrap=10000):
    """Bootstrap Cohen's d with confidence interval."""
    a, b = np.array(group_a), np.array(group_b)
    pooled_std = np.sqrt(
        ((len(a) - 1) * np.var(a, ddof=1) +
         (len(b) - 1) * np.var(b, ddof=1)) /
        (len(a) + len(b) - 2)
    )
    if pooled_std == 0:
        return {"cohens_d": 0, "ci_lower": 0, "ci_upper": 0}

    effects = []
    for _ in range(n_bootstrap):
        boot_a = np.random.choice(a, size=len(a), replace=True)
        boot_b = np.random.choice(b, size=len(b), replace=True)
        d = (np.mean(boot_a) - np.mean(boot_b)) / pooled_std
        effects.append(d)

    return {
        "cohens_d": np.mean(effects),
        "ci_lower": np.percentile(effects, 2.5),
        "ci_upper": np.percentile(effects, 97.5),
    }

28Inter-Rater Agreement: Humans vs Judge, Cohen's Kappa

What & why. Before trusting an LLM judge, you must measure how well it agrees with human experts. Cohen's kappa measures agreement corrected for chance: kappa=1 is perfect agreement, kappa=0 is chance-level, kappa<0 is worse than chance. If the judge-human kappa is below 0.6, the judge prompt needs revision.

def cohens_kappa(rater_a_scores, rater_b_scores):
    """Compute Cohen's kappa for two raters."""
    assert len(rater_a_scores) == len(rater_b_scores)
    n = len(rater_a_scores)
    categories = set(rater_a_scores) | set(rater_b_scores)

    # Observed agreement
    agree = sum(1 for a, b in zip(rater_a_scores, rater_b_scores)
                if a == b)
    po = agree / n

    # Expected agreement by chance
    pe = 0
    for cat in categories:
        freq_a = rater_a_scores.count(cat) / n

        return 1.0
    return (po - pe) / (1 - pe)

What & why. Test set contamination occurs when your golden dataset examples appear in the training data of the model you're evaluating. This inflates scores and makes evaluations meaningless. Contamination detection involves checking for exact and near-duplicate matches between eval data and model training corpora, and monitoring for score anomalies that suggest memorization.

import hashlib
from difflib import SequenceMatcher

def detect_exact_contamination(eval_data, training_samples):
    """Check for exact matches between eval and training data."""
    training_hashes = set()
    for sample in training_samples:
        h = hashlib.sha256(sample.encode()).hexdigest()
        training_hashes.add(h)

    contaminated = []
    for example in eval_data:
        h = hashlib.sha256(example["input"].encode()).hexdigest()
        if h in training_hashes:
            contaminated.append(example["id"])
    return contaminated

def detect_near_contamination(eval_data, training_samples,
                               threshold=0.85):
    """Check for near-duplicates using sequence matching."""
    contaminated = []
    for example in eval_data:
        for sample in training_samples:
            ratio = SequenceMatcher(
                None, example["input"], sample
            ).ratio()
            if ratio >= threshold:
                contaminated.append({
                    "id": example["id"],
                    "similarity": ratio,
                    "training_sample_preview": sample[:100],
                })
                break
    return contaminated

def contamination_report(eval_data, training_samples):
    exact = detect_exact_contamination(eval_data, training_samples)
    near = detect_near_contamination(eval_data, training_samples)
    print(f"Exact contamination: {len(exact)}/{len(eval_data)} "
          f"({len(exact)/len(eval_data)*100:.1f}%)")
    print(f"Near contamination: {len(near)}/{len(eval_data)} "
          f"({len(near)/len(eval_data)*100:.1f}%)")
    return {"exact": exact, "near": near}

32Cost-Normalized Quality: Quality per Dollar

What & why. Raw quality scores are incomplete without cost context. A system that scores 0.95 at $0.10/query is worse than one scoring 0.92 at $0.001/query for most applications. Cost-normalized quality metrics â€” quality per dollar, cost-adjusted Pareto frontiers â€” enable rational model selection and budget allocation.

def cost_normalized_quality(scores, costs):
    """Compute quality per dollar for each configuration."""
    results = []
    for name, score in scores.items():
        cost = costs[name]
        qpd = score / cost if cost > 0 else float("inf")
        results.append({
            "config": name,
            "quality": score,
            "cost_per_query": cost,
            "quality_per_dollar": qpd,
        })
    return sorted(results, key=lambda r: r["quality_per_dollar"],
                  reverse=True)

def budget_allocation(total_budget, configs, target_quality):
    """Allocate budget across configs to maximize coverage."""
    affordable = [c for c in configs if c["cost_per_query"] <= total_budget]
    allocation = {}
    remaining = total_budget

    for config in sorted(affordable,
                         key=lambda c: c["quality_per_dollar"],
                         reverse=True):
        if config["quality"] >= target_quality:
            queries = int(remaining / config["cost_per_query"])
            allocation[config["config"]] = queries
            remaining -= queries * config["cost_per_query"]
    return allocation

34Eval Registry: Versioning Datasets and Prompts

What & why. An eval registry tracks versions of your golden datasets, judge prompts, and evaluation configurations. When you update a judge prompt, the old scores are no longer comparable to new scores. Versioning ensures reproducibility: you can re-run any historical evaluation with the exact same configuration.

import json, hashlib
from datetime import datetime

class EvalRegistry:
    def __init__(self, registry_path="eval_registry.json"):
        self.path = registry_path
        self.entries = self._load()

    def _load(self):
        try:
            with open(self.path) as f:
                return json.load(f)
        except FileNotFoundError:
            return {"datasets": {}, "prompts": {}, "configs": {}}

    def _save(self):
        with open(self.path, "w") as f:
            json.dump(self.entries, f, indent=2)

    def register_dataset(self, name, version, data, metadata=None):
        content_hash = hashlib.sha256(
            json.dumps(data, sort_keys=True).encode()
        ).hexdigest()[:16]
        key = f"{name}:v{version}"
        self.entries["datasets"][key] = {
            "name": name,
            "version": version,
            "hash": content_hash,
            "size": len(data),
            "registered_at": datetime.utcnow().isoformat(),
            "metadata": metadata or {},
        }
        self._save()
        return key

    def register_judge_prompt(self, name, version, prompt_text):
        content_hash = hashlib.sha256(
            prompt_text.encode()
        ).hexdigest()[:16]
        key = f"{name}:v{version}"
        self.entries["prompts"][key] = {
            "name": name,
            "version": version,
            "hash": content_hash,
            "preview": prompt_text[:200],
            "registered_at": datetime.utcnow().isoformat(),
        }
        self._save()
        return key

    def get_experiment_config(self, dataset_key, judge_key):
        return {
            "dataset": self.entries["datasets"].get(dataset_key),
            "judge": self.entries["prompts"].get(judge_key),
            "experiment_id": f"{dataset_key}+{judge_key}",
        }

import json, hashlib, sys
from pathlib import Path

class EvalGate:
    def __init__(self, baseline_path="baseline_scores.json",
                 thresholds_path="thresholds.json"):
        self.baseline_path = Path(baseline_path)
        self.thresholds = json.loads(
            Path(thresholds_path).read_text()
        )
        self.baseline = self._load_baseline()

    def _load_baseline(self):
        if self.baseline_path.exists():
            return json.loads(self.baseline_path.read_text())
        return {}

    def run_gate(self, eval_results):
        regressions = []
        improvements = []
        for metric, score in eval_results.items():
            base = self.baseline.get(metric, score)
            threshold = self.thresholds.get(metric, 0.05)
            diff = score - base
            if diff < -threshold:
                regressions.append({
                    "metric": metric, "baseline": base,
                    "current": score, "diff": diff,
                })
            elif diff > threshold:
                improvements.append({
                    "metric": metric, "baseline": base,
                    "current": score, "diff": diff,
                })

        if regressions:
            return {
                "passed": False,
                "regressions": regressions,
                "improvements": improvements,
            }
        self.baseline.update(eval_results)
        self.baseline_path.write_text(
            json.dumps(self.baseline, indent=2)
        )
        return {"passed": True, "improvements": improvements}
