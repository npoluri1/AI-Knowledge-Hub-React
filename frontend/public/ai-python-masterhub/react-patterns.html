ReAct (Reasoning + Acting) is the pattern of interleaving explicit reasoning traces with tool-calling actions. The LLM thinks about what to do, takes an action, observes the result, and reasons again. This grounds outputs in real data rather than hallucinated facts. Part I · FoundationsTier 1 — Thought-Action-Observation grammar, parsing, basic tools

1ReAct Paper Origin: Reasoning Traces Help

What & why. The ReAct paper (Yao et al., 2022) demonstrated that interleaving reasoning traces (Thought) with actions (Action) and observations (Observation) significantly improves LLM performance on complex tasks. The key insight: reasoning traces make the LLM's decision process explicit and auditable, while actions ground the reasoning in real data. Pure chain-of-thought reasoning hallucinates facts; pure action-taking lacks strategic planning. ReAct combines both.



Where you'll use itReAct is the foundational pattern for all tool-using LLM agents. It appears in search-augmented QA, code generation with debugging, data analysis with validation, and any task where the LLM needs to ground its reasoning in external data.


Under the hoodReAct works by giving the LLM a structured prompt template that constrains output to the Thought-Action-Observation format. The loop extracts actions, executes tools, feeds observations back, and continues until a final answer is produced. The reasoning trace enables debugging and auditing.







2Thought-Action-Observation Grammar


What & why. The ReAct grammar defines a strict format for LLM output: each step must contain a Thought (reasoning about the current state and next action), an Action (tool to invoke), an Action Input (parameters for the tool), and an Observation (result from the tool). This structured format makes parsing reliable and ensures the LLM follows a disciplined reasoning process rather than generating free-form text.


# ReAct grammar in a prompt template
REACT_PROMPT = """Answer the question using the tools available.

You must follow this exact format for each step:

Thought: [Analyze the current situation and plan the next action]
Action: [The tool name to use - must be one of: {tool_names}]
Action Input: [The input to pass to the tool]
Observation: [This will be filled in by the system after action]

When you have enough information, provide:
Thought: I now have enough information to answer
Final Answer: [Your complete answer to the question]

Question: {question}
"""

# Example conversation following the grammar:
# Thought: I need to find the population of France
# Action: search
# Action Input: population of France 2024
# Observation: France population: 68.17 million (2024 est.)
# Thought: I now have the information needed
# Final Answer: The population of France is approximately 68.17 million.

# The grammar constrains the LLM to a predictable output format
# which enables reliable parsing and tool execution


Where you'll use itThe TAO grammar is the standard format for ReAct implementations. Use it in custom prompt templates when building ReAct agents from scratch. Frameworks like LangChain abstract this grammar, but understanding it is essential for debugging and customization.


Under the hoodThe grammar is enforced through the system prompt. The LLM is instructed to follow the format, and parsing code extracts actions and inputs using regex. The Observation field is injected by the system after tool execution, creating a feedback loop that guides the LLM's reasoning.







3Handwritten Prompt Template


What & why. A handwritten ReAct prompt template gives you full control over the reasoning format, tool descriptions, and behavioral instructions. While frameworks provide built-in templates, understanding how to write your own enables customization for specific domains. The template must include: role definition, tool descriptions, the TAO format, and termination instructions.

Under the hoodThe prompt template is the entire mechanism for enforcing ReAct behavior. The LLM follows the format because the system prompt instructs it to. There is no code-level enforcement of the grammar; it relies on the LLM's instruction-following capability.







4Parsing the Action Line: Regex


What & why. Parsing the Action and Action Input lines from the LLM's response is critical for reliable ReAct execution. Regex-based parsing extracts tool names and parameters from the structured output. The parser must handle variations: extra whitespace, missing colons, or slightly different formatting. Robust parsing prevents execution failures due to minor LLM output variations.


import re

def parse_react_response(response):
    """Parse a ReAct-format response into components."""
    result = {
        "thought": "",
        "action": None,
        "action_input": None,
        "final_answer": None,
    }
    
    # Extract Thought
    thought_match = re.search(r"Thought:\s*(.+?)(?:\nAction:|\nFinal Answer:|\Z)", response, re.DOTALL)
    if thought_match:
        result["thought"] = thought_match.group(1).strip()
    
    # Check for Final Answer
    final_match = re.search(r"Final Answer:\s*(.+)", response, re.DOTALL)
    if final_match:
        result["final_answer"] = final_match.group(1).strip()
        return result
    
    # Extract Action
    action_match = re.search(r"Action:\s*(.+)", response)
    if action_match:
        result["action"] = action_match.group(1).strip()
    
    # Extract Action Input (everything after Action Input: until Observation or end)
    input_match = re.search(r"Action Input:\s*(.+?)(?:\nObservation:|\Z)", response, re.DOTALL)
    if input_match:
        result["action_input"] = input_match.group(1).strip()
    
    return result

Under the hoodThe parser uses regex with flexible patterns to handle output variations. The non-greedy .*? with re.DOTALL handles multi-line fields. The parser checks for Final Answer first (termination) before looking for Action (continuation).







5Executing Against Toy Tools


What & why. Toy tools demonstrate the ReAct loop without external dependencies. Simple tools like calculator, string reversal, or list operations let you test the reasoning loop, parsing, and observation injection. This is the fastest way to validate a ReAct implementation before connecting real tools.


import re

# Toy tool implementations
tools = {

    "upper": lambda s: s.upper(),
    "word_count": lambda s: str(len(s.split())),

}

def run_react_step(prompt, llm_call):
    """Execute one ReAct step."""
    response = llm_call(prompt)
    
    # Parse action
    action_match = re.search(r"Action:\s*(\w+)", response)
    input_match = re.search(r"Action Input:\s*(.+?)(?:\n|$)", response)
    
    if "Final Answer:" in response:
        answer = response.split("Final Answer:")[-1].strip()
        return None, answer
    
    if action_match and input_match:
        tool_name = action_match.group(1)
        tool_input = input_match.group(1).strip()
        
        if tool_name in tools:
            observation = tools[tool_name](tool_input)
        else:
            observation = f"Error: Unknown tool '{tool_name}'"
        
        new_prompt = prompt + f"\n{response}\nObservation: {observation}\n"
        return new_prompt, None
    
    return prompt + f"\n{response}\n", None

Under the hoodToy tools follow the same interface as production tools: string input, string output. The ReAct loop does not distinguish between toy and production tools; only the tool implementations differ. This makes upgrading from toy to production tools straightforward.







6Observation Truncation Hygiene


What & why. Tool observations can be very large: web search returns full pages, database queries return thousands of rows, and code execution outputs can be lengthy. Large observations consume context window tokens and can cause the LLM to lose focus. Observation truncation keeps the context manageable by summarizing or truncating large outputs to a fixed size.


def truncate_observation(observation, max_chars=2000):
    """Truncate long observations to fit context window."""
    if len(observation) <= max_chars:
        return observation
    
    truncated = observation[:max_chars]
    # Try to truncate at a sentence boundary
    last_period = truncated.rfind(".")
    if last_period > max_chars * 0.8:  # At least 80% utilized
        truncated = truncated[:last_period + 1]
    
    return truncated + f"\n... [truncated, {len(observation)} total chars]"

def summarize_observation(observation, max_chars=2000):
    """Summarize long observations instead of truncating."""
    if len(observation) <= max_chars:
        return observation
    
    # For web pages: extract key sentences
    sentences = observation.split(". ")
    key_sentences = []
    current_len = 0
    for sentence in sentences:
        if current_len + len(sentence) > max_chars:
            break
        key_sentences.append(sentence)
        current_len += len(sentence)
    
    return ". ".join(key_sentences) + "."

# Usage in ReAct loop
def process_observation(obs):
    """Standard observation processing."""
    obs = truncate_observation(obs, max_chars=2000)
    return obs


Where you'll use itObservation truncation is essential for production ReAct. Without it, a single large observation can consume most of the context window, leaving little room for reasoning. Set max_chars based on your model's context window and typical observation sizes.


Under the hoodTruncation strategies include: hard truncation at character count, sentence-aware truncation (preserving complete sentences), and summarization (using the LLM to compress the observation). Hard truncation is fastest; summarization preserves the most information.







7Stopping on Final Answer


What & why. The ReAct loop must terminate when the LLM produces a Final Answer. Without a clear termination signal, the loop continues indefinitely. The standard approach: instruct the LLM to end with "Final Answer: [answer]" and check for this pattern after each response. Additional termination guards include max steps limit and timeout to prevent runaway loops.


import re
import time

def react_loop(query, tools, llm_call, max_steps=10, timeout=60):
    """ReAct loop with proper termination."""
    start_time = time.time()
    prompt = f"""Answer: {query}

Thought: [your reasoning]
Action: [tool_name]
Action Input: [input]
Observation: [result]
...
Thought: I have the answer
Final Answer: [answer]
"""
    
    for step in range(max_steps):
        # Timeout check
        if time.time() - start_time > timeout:
            return "Timeout exceeded", prompt
        
        response = llm_call(prompt)
        
        # Final Answer check (primary termination)
        if "Final Answer:" in response:
            answer = response.split("Final Answer:")[-1].strip()
            return answer, response
        
        # Parse and execute action
        action_match = re.search(r"Action:\s*(\w+)", response)
        input_match = re.search(r"Action Input:\s*(.+?)(?:\n|$)", response)
        
        if not action_match or not input_match:
            prompt += f"\n{response}\nObservation: Please use the correct format.\n"
            continue
        
        tool_name = action_match.group(1)
        tool_input = input_match.group(1).strip()
        
        if tool_name not in tools:
            observation = f"Unknown tool: {tool_name}. Available: {list(tools.keys())}"
        else:
            observation = tools[tool_name](tool_input)
        
        prompt += f"\n{response}\nObservation: {observation}\n"
    
    return "Max steps reached", prompt


Where you'll use itAlways implement multiple termination safeguards: Final Answer detection, max steps limit, and timeout. Without these, a confused LLM can loop indefinitely, consuming tokens and time.


Under the hoodThe termination check happens after each LLM response, before tool execution. If Final Answer is detected, the loop returns immediately. The max_steps guard prevents infinite loops even if the LLM never produces a Final Answer.







8Worked Example: Hotpot-Style Question


What & why. HotpotQA-style questions require multi-hop reasoning: the answer depends on information from multiple sources. ReAct handles this naturally: the agent searches for the first fact, reasons about what else is needed, searches for the second fact, and combines them. This worked example demonstrates the full ReAct loop with multiple tool calls and progressive reasoning.


# Worked example: Multi-hop question
# Q: "What is the capital of the country where the 2024 Olympics were held?"

# Step 1: Initial reasoning and search
# Thought: I need to find where the 2024 Olympics were held
# Action: search
# Action Input: 2024 Olympics host city
# Observation: The 2024 Summer Olympics were held in Paris, France

# Step 2: Reasoning about the next step
# Thought: The 2024 Olympics were in Paris, France. Now I need the capital
# Action: search
# Action Input: capital of France
# Observation: The capital of France is Paris

# Thought: I now have both facts
# Final Answer: The 2024 Olympics were held in Paris, France, which is also the capital of France

}

        if key in query.lower():
            return value

tools = {"search": search}

# 1. Find fact A (host city)
# 2. Use fact A to search for fact B (capital)
# 3. Combine facts into final answer


Where you'll use itMulti-hop reasoning is ReAct's killer feature. It handles questions that require combining information from multiple sources: "Who directed the movie that won Best Picture at the ceremony where Halle Berry won Best Actress?" The agent decomposes the question and searches iteratively.


Under the hoodEach Thought step reasons about what information is missing and what action would provide it. The observation from the previous step feeds into the next Thought, enabling progressive information gathering. This is fundamentally different from single-step retrieval.







9ReAct vs Plain Chain-of-Thought


What & why. Chain-of-Thought (CoT) reasoning asks the LLM to "think step by step" without tool access. ReAct adds tool-calling actions to CoT, grounding reasoning in real data. CoT can hallucinate facts because it relies entirely on the LLM's internal knowledge. ReAct prevents hallucination by checking facts against external tools. The tradeoff: ReAct is slower (multiple LLM calls + tool executions) but more accurate for fact-dependent tasks.




Where you'll use itUse CoT for tasks that rely on reasoning about known facts: logic puzzles, math problems, and code review. Use ReAct for tasks that require current or specific information: research, data analysis, and fact-checking. The key distinction: does the task need external data?


Under the hoodCoT is a single LLM call with a "think step by step" instruction. ReAct is a loop of multiple LLM calls, each producing a Thought and Action. ReAct's accuracy advantage comes from tool-grounded facts; CoT's speed advantage comes from fewer LLM calls.







10Failure Mode: Hallucinated Observation


What & why. A common ReAct failure is the hallucinated observation: the LLM generates an Observation without actually calling a tool. This happens when the LLM is confident in its answer and skips the Action step, fabricating an observation that confirms its belief. This defeats the purpose of ReAct. Prevention: always validate that the Observation was produced by a real tool call.


import re

def validate_react_step(response, tools):
    """Check for hallucinated observations."""
    # Check if LLM skipped Action and went straight to Observation
    has_action = bool(re.search(r"Action:\s*\w+", response))
    has_observation = bool(re.search(r"Observation:\s*.+", response))
    has_final = bool(re.search(r"Final Answer:", response))
    
    if has_observation and not has_action and not has_final:
        return False, "Hallucinated observation: no Action found before Observation"
    
    # Check if Action name is valid
    if has_action:
        action_match = re.search(r"Action:\s*(\w+)", response)
        tool_name = action_match.group(1)
        if tool_name not in tools:
            return False, f"Invalid tool: {tool_name}"
    
    return True, "Valid step"

# Example of hallucinated observation:
# "Thought: I know the answer is 42
#  Observation: The answer is 42"
# (No Action was called; observation is fabricated)

# Prevention: inject reminder after each step
REACT_REMINDER = """
Remember: You MUST call a tool using Action and Action Input.
Do not write Observation yourself - the system fills that in.
If you know the answer, use Final Answer instead.
"""


Where you'll use itHallucinated observations are a critical failure mode in production ReAct. Always validate that actions precede observations. Inject reminders in the prompt to reinforce the grammar. Monitor for hallucination patterns in production logs.


Under the hoodThe hallucination occurs because the LLM generates the entire response at once, including the Observation field. Without code-level validation, a fabricated observation looks identical to a real one. The only difference is that a real observation was produced by tool execution.







11Iteration Cap Defaults


What & why. ReAct loops need iteration caps to prevent runaway execution. The cap depends on task complexity: simple lookup tasks need 2-3 steps, research tasks need 5-8, and complex analysis may need 10-15. Setting the cap too low causes premature termination; too high wastes tokens. Default to 5 for general use, adjust based on task type.


# Iteration cap guidelines by task type
ITERATION_CAPS = {
    "simple_lookup": 3,    # "What is X?" -> search -> answer
    "factual_qa": 5,       # "What is X and how does Y relate?" -> 2 searches
    "research": 8,         # "Analyze X in context of Y" -> multiple searches + analysis
    "complex_analysis": 12, # "Compare X, Y, Z across dimensions" -> many steps
    "code_generation": 10,  # Write -> test -> debug -> verify
}

def adaptive_react_loop(query, tools, llm_call, task_type="factual_qa"):
    """ReAct loop with adaptive iteration cap."""
    max_steps = ITERATION_CAPS.get(task_type, 5)
    steps_used = 0
    
    prompt = f"Answer: {query}\n\n"
    
    for step in range(max_steps):
        steps_used += 1
        response = llm_call(prompt)
        
        if "Final Answer:" in response:
            answer = response.split("Final Answer:")[-1].strip()
            return {
                "answer": answer,
                "steps": steps_used,
                "max_steps": max_steps,
                "efficiency": steps_used / max_steps,
            }
        
        # ... execute action and continue
    
    return {
        "answer": "Max iterations reached",
        "steps": steps_used,
        "max_steps": max_steps,
        "efficiency": 1.0,
    }


Where you'll use itAdaptive iteration caps balance thoroughness with efficiency. Simple tasks should complete quickly; complex tasks deserve more steps. Monitor actual step counts in production to calibrate defaults over time.


Under the hoodThe iteration cap is a hard limit on the number of LLM calls + tool executions. Each step typically costs one LLM call (for Thought + Action) plus one tool execution. The total cost is approximately (steps * LLM_cost) + (tool_executions * tool_cost).

13Function-Calling Modern ReAct: No Text Parsing


What & why. Modern LLMs support native function calling, eliminating the need for text parsing. Instead of extracting "Action: search" from the response text, the LLM returns structured tool calls that the runtime executes directly. This is more reliable than regex parsing: no formatting errors, no hallucinated actions, and automatic parameter validation. LangChain and LlamaIndex abstract this into tool-calling agents.


# Modern ReAct with function calling (no text parsing)
from langchain_openai import ChatOpenAI
from langchain.agents import AgentExecutor, create_tool_calling_agent
from langchain_core.tools import tool
from langchain_core.prompts import ChatPromptTemplate

@tool
def search(query: str) -> str:
    """Search for information on the web."""
    return f"Search results for '{query}': [simulated results]"

@tool
def calculate(expression: str) -> str:
    """Calculate a mathematical expression."""
    try:
        return str(eval(expression))
    except Exception as e:
        return f"Error: {e}"

llm = ChatOpenAI(model="gpt-4o", temperature=0)

# Prompt still uses Thought pattern, but tools are called via function calling

Where you'll use itFunction-calling ReAct is the standard for production. It eliminates parsing failures, handles parameter types correctly, and integrates cleanly with LangChain/LlamaIndex. Use it for all new ReAct implementations unless you need custom parsing for specific reasons.


Under the hoodThe LLM generates structured function calls (tool invocations) instead of free-form text. The runtime extracts the function name and arguments, executes the tool, and feeds the result back. No regex parsing is needed because the tool calls are structured data.







14Strict Tool Schemas Improve Reliability


What & why. Tool schemas define the expected parameters, types, and descriptions for each tool. Strict schemas with Pydantic models improve reliability: the LLM receives clear parameter specifications, the runtime validates inputs, and type coercion handles edge cases. Vague schemas produce incorrect tool calls; strict schemas with descriptions and examples produce correct calls consistently.


from pydantic import BaseModel, Field
from langchain_core.tools import tool

class SearchInput(BaseModel):
    query: str = Field(description="The search query to find information")
    num_results: int = Field(default=3, description="Number of results to return")

class CalculateInput(BaseModel):
    expression: str = Field(description="Mathematical expression to evaluate, e.g. '2 + 3 * 4'")

@tool(args_schema=SearchInput)
def search(query: str, num_results: int = 3) -> str:
    """Search the web for information. Returns search results matching the query."""
    return f"Found {num_results} results for: {query}"

@tool(args_schema=CalculateInput)
def calculate(expression: str) -> str:
    """Evaluate a mathematical expression. Supports +, -, *, /, **, and parentheses."""
    allowed = set("0123456789+-*/.() ")
    if not all(c in allowed for c in expression):
        return "Error: expression contains invalid characters"
    try:
        return str(eval(expression))
    except Exception as e:
        return f"Error: {e}"

# Strict schemas produce more reliable tool calls
# The LLM knows exactly what parameters to provide


Where you'll use itInvest in tool schema quality. Clear descriptions, typed parameters, and default values reduce LLM errors. For complex tools, add examples in the description. Use Pydantic models for automatic validation and documentation generation.


Under the hoodTool schemas are sent to the LLM as part of the function definition. The LLM uses these schemas to generate correctly structured calls. Pydantic validation runs after the LLM generates the call, catching type errors before execution.

def summarize_observation(observation, llm=None, max_tokens=500):

    if len(observation) < 1000:

20Success Detection Heuristics


What & why. Detecting whether a ReAct run succeeded is not trivial. The agent may produce an answer that looks correct but is actually hallucinated, or it may produce a partial answer. Success heuristics check for: tool call count (did it use tools?), answer specificity (is the answer concrete?), and tool result quality (did tools return useful data?). Combine these heuristics for reliable success detection.


import re

class SuccessDetector:
    """Detect ReAct run success with multiple heuristics."""
    
    def __init__(self):
        self.min_tool_calls = 1
        self.min_answer_length = 20
    
    def detect(self, trajectory):
        """Analyze trajectory for success signals."""
        steps = [s for s in trajectory if s.get("action")]
        final = [s for s in trajectory if s.get("step") == "final"]
        
        if not final:
            return {"success": False, "reason": "No final answer produced"}
        
        answer = final[0].get("answer", "")
        
        # Heuristic 1: Did the agent use tools?
        tool_calls = len(steps)
        if tool_calls < self.min_tool_calls:
            return {"success": False, "reason": f"Only {tool_calls} tool calls"}
        
        # Heuristic 2: Is the answer substantive?
        if len(answer) < self.min_answer_length:
            return {"success": False, "reason": "Answer too short"}
        
        # Heuristic 3: Did tools return useful data?
        observations = [s.get("observation", "") for s in steps]
        error_count = sum(1 for o in observations if "error" in o.lower())
        if error_count > len(observations) * 0.5:
            return {"success": False, "reason": "Too many tool errors"}
        
        # Heuristic 4: Answer doesn't contain error messages
        if "error" in answer.lower() or "unable" in answer.lower():
            return {"success": False, "reason": "Answer indicates failure"}
        
        return {"success": True, "tool_calls": tool_calls, "answer_length": len(answer)}

def detect_dead_end(observation, previous_observations):
    """Detect if the current approach has hit a dead end."""
    dead_end_signals = [
        "no results",
        "not found",
        "error",
        "unable to",
        "empty",

    ]

    return False

27LATS: Lookahead Search Brief


What & why. LATS (Language Agent Tree Search) combines Monte Carlo Tree Search (MCTS) with LLM agents. It expands reasoning branches, simulates outcomes, and backpropagates evaluation scores to select the best path. LATS is the most sophisticated exploration strategy: it balances exploration (trying new paths) with exploitation (following proven paths). It is expensive but produces high-quality results for complex tasks.


# LATS: MCTS applied to LLM reasoning
# 1. Selection: Choose a node to expand (UCT algorithm)
# 2. Expansion: Generate child thoughts
# 3. Simulation: Evaluate the thought (LLM or heuristic)
# 4. Backpropagation: Update node values

# Conceptual LATS implementation
class LATNode:
    def __init__(self, state, parent=None):
        self.state = state
        self.parent = parent
        self.children = []
        self.visits = 0
        self.value = 0.0
    
    def uct(self, exploration_weight=1.4):
        """Upper Confidence Bound for Trees."""
        if self.visits == 0:
            return float("inf")
        return self.value / self.visits + exploration_weight * (
            (2 * (self.parent.visits or 1) / self.visits) ** 0.5
        )

29Confidence-Aware Stopping Thresholds


What & why. Not all ReAct runs need the same number of steps. Confidence-aware stopping lets the agent terminate early when it is confident in its answer, or continue when uncertainty is high. The agent assesses confidence after each step and decides whether to stop or continue. This optimizes the cost-quality tradeoff: confident answers save tokens; uncertain answers get more investigation.


def confidence_check(answer, evidence, threshold=0.8):
    """Assess confidence in the current answer."""
    # Simple heuristic confidence scoring
    confidence_signals = {
        "has_evidence": len(evidence) >= 2,
        "consistent": answer not in str(evidence),  # Not just repeating evidence
        "specific": len(answer.split()) >= 5,  # Detailed answer
        "no_uncertainty_markers": not any(w in answer.lower() for w in ["maybe", "possibly", "unclear"]),
        "used_tools": len(evidence) > 0,
    }
    
    score = sum(confidence_signals.values()) / len(confidence_signals)
    return score >= threshold, score

31Theory: Interleaving Rationale Grounding Acting Distributions


What & why. The theoretical foundation of ReAct is that interleaving rationale (Thought) with acting (Action) creates a grounded reasoning distribution. Without actions, the LLM's reasoning distribution drifts from reality (hallucination). With actions, each observation anchors the reasoning in factual data. The interleaving prevents distributional drift: each action resets the reasoning to a grounded state. This explains why ReAct outperforms both pure CoT (no grounding) and pure action-taking (no planning).


# Theoretical insight:
# P(answer | query) is estimated differently by CoT vs ReAct

# CoT: P(answer | query) = LLM generates answer from internal knowledge
#   Risk: Distribution drift (hallucination)
#   The LLM's internal representation may not match reality

# ReAct: P(answer | query, obs1, obs2, ...) where observations are real data
#   Each observation grounds the distribution
#   Risk: Tool errors or misleading data (but at least it's grounded)

# The interleaving creates a Markov chain:
# state_0 = query
# state_1 = query + thought_1 + action_1 + observation_1
# state_2 = state_1 + thought_2 + action_2 + observation_2
# ...
# Each state is grounded by the observation

# This is why observation quality matters:
# Bad observation -> wrong grounding -> wrong reasoning -> wrong answer
# Good observation -> correct grounding -> correct reasoning -> correct answer


Where you'll use itUnderstanding the theoretical basis helps you debug and optimize ReAct systems. When the agent produces wrong answers, check whether observations are grounding the reasoning correctly. Bad grounding (wrong tools, misleading data) is the primary failure mode.


Under the hoodThe theory explains ReAct's empirical success: it constrains the LLM's reasoning to be consistent with observed data. Each observation acts as a checkpoint that prevents the reasoning from drifting into hallucination. The quality of the final answer depends on the quality of the observations.







32When ReAct Hurts: Overthinking Simple Tasks


What & why. ReAct is not always the best pattern. For simple tasks (direct questions, simple calculations, single-lookup Q&A), ReAct adds unnecessary overhead: extra LLM calls for thoughts, tool execution latency, and token costs. A direct LLM call may produce the same answer faster and cheaper. Use a router to detect task complexity and route simple tasks to direct LLM calls, complex tasks to ReAct.

            for line in f:
                data = json.loads(line)
                if data.get("step") != "final":

                        action=data.get("action", ""),
                        action_input=data.get("action_input", ""),
                        observation=data.get("observation", ""),
                        timestamp=data.get("timestamp", 0),
                        tokens=data.get("tokens", 0),
                    ))
        return steps

        return {
            "total_steps": len(self.steps),
            "total_tokens": sum(s.tokens for s in self.steps),
            "tool_calls": len([s for s in self.steps if s.action]),
            "avg_thought_length": sum(len(s.thought) for s in self.steps) / max(len(self.steps), 1),
            "total_time": self.steps[-1].timestamp if self.steps else 0,
        }
