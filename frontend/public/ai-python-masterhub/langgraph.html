1Why Graphs for LLM Applications

What & why. Linear chains break down when an application requires loops (retry on failure), branching (route by classifier output), or multiple coordinated actors. Graphs model these patterns explicitly: nodes are computation units, edges define execution order, and state is a first-class object flowing through the graph. LangGraph turns these conceptual graphs into executable, checkpointable, and debuggable runtimes.

# A linear chain cannot express "retry if the tool fails"
# A graph makes this explicit and inspectable

# Conceptual comparison:
# Chain:    A -> B -> C          (one path, no loops)
# Graph:    A -> B --retry--> A  (cycle on failure)
#           A -> C               (success path)

from langgraph.graph import StateGraph, END
from typing import TypedDict

class AppState(TypedDict):
    input: str
    output: str
    attempts: int

def process(state: AppState) -> dict:
    return {"output": f"Processed: {state['input']}", "attempts": state.get("attempts", 0) + 1}

graph = StateGraph(AppState)
graph.add_node("process", process)
graph.add_edge("__start__", "process")
graph.add_edge("process", "__end__")
app = graph.compile()
result = app.invoke({"input": "hello", "attempts": 0})
print(result["output"])
Where you'll use itGraphs are the standard pattern for any LLM application beyond simple prompt-response: customer support routers, multi-step research agents, code generation pipelines with self-correction, and approval workflows.
Under the hoodLangGraph compiles your graph definition into an optimized execution plan using a Pregel-like model. Nodes execute sequentially or in parallel based on topology, and the runtime manages state serialization, checkpointing, and error recovery automatically.

2StateGraph and TypedDict State

What & why. StateGraph is the primary entry point for building graphs. You define a TypedDict to represent the graph state schema: every field is accessible to every node, and nodes return dictionaries of partial updates. TypedDict provides static type checking for state fields, catching misspellings and type mismatches at development time rather than runtime.

from typing import TypedDict
from langgraph.graph import StateGraph

class GraphState(TypedDict):
    question: str
    context: str
    answer: str
    iterations: int

# StateGraph enforces the TypedDict schema
graph = StateGraph(GraphState)

# Every node receives the full state and returns a partial update
def retrieve(state: GraphState) -> dict:
    return {"context": f"Retrieved docs for: {state['question']}"}

def answer(state: GraphState) -> dict:
    return {"answer": f"Based on {state['context']}", "iterations": state.get("iterations", 0) + 1}

graph.add_node("retrieve", retrieve)
graph.add_node("answer", answer)
graph.add_edge("__start__", "retrieve")
graph.add_edge("retrieve", "answer")
graph.add_edge("answer", "__end__")

app = graph.compile()
result = app.invoke({"question": "What is LangGraph?", "context": "", "answer": "", "iterations": 0})
print(result["answer"])
Where you'll use itEvery LangGraph application starts with StateGraph. The TypedDict approach makes state visible and testable, unlike opaque context objects. It is the single most important pattern in the framework.
Under the hoodStateGraph validates that your TypedDict has no mutable default values and that all node return types are compatible with the state schema. The compiled graph stores a flattened version of state for efficient serialization to checkpoints.

3Nodes as Functions

What & why. Nodes are the computational units of a graph. Each node is a Python function that receives the current state and returns a dictionary of partial state updates. The runtime merges these updates into the shared state. Nodes can call LLMs, execute tools, transform data, or perform any computation. Keeping nodes as pure functions makes them easy to test in isolation.

from typing import TypedDict
from langgraph.graph import StateGraph
from langchain_openai import ChatOpenAI

class ChatState(TypedDict):
    messages: list
    next_action: str

model = ChatOpenAI(model="gpt-4o", temperature=0)

def chatbot(state: ChatState) -> dict:
    response = model.invoke(state["messages"])
    return {"messages": state["messages"] + [response]}

def classifier(state: ChatState) -> dict:
    last = state["messages"][-1].content
    action = "respond" if "question" in last.lower() else "end"
    return {"next_action": action}

graph = StateGraph(ChatState)
graph.add_node("chatbot", chatbot)
graph.add_node("classifier", classifier)
graph.add_edge("__start__", "chatbot")
graph.add_edge("chatbot", "classifier")

app = graph.compile()
result = app.invoke({"messages": [{"role": "user", "content": "Hello"}], "next_action": ""})
print(result["next_action"])
Where you'll use itNode-as-function is the universal pattern. LLM calls, tool executions, data transforms, validations, and external API calls are all nodes. This uniformity makes graph logic easy to reason about and debug.
Under the hoodLangGraph wraps your function in a RunnableNode that handles state extraction, partial update merging, error propagation, and checkpoint serialization. The original function signature is preserved for testing.

4add_node and add_edge

What & why. add_node registers a function with a string name. add_edge defines a directed edge between two named nodes. Together they compose the graph topology. Nodes can be referenced by name in multiple edges, and edges can connect any two registered nodes. The graph must be a directed acyclic graph (DAG) at compile time unless cycles are intentional and properly bounded.

from typing import TypedDict
from langgraph.graph import StateGraph, END

class PipelineState(TypedDict):
    data: str
    enriched: str
    result: str

def fetch(state: PipelineState) -> dict:
    return {"data": "raw data"}

def enrich(state: PipelineState) -> dict:
    return {"enriched": f"enriched({state['data']})"}

def transform(state: PipelineState) -> dict:
    return {"result": f"final({state['enriched']})"}

def validate(state: PipelineState) -> dict:
    return state  # pass-through node

graph = StateGraph(PipelineState)
graph.add_node("fetch", fetch)
graph.add_node("enrich", enrich)
graph.add_node("transform", transform)
graph.add_node("validate", validate)

graph.add_edge("__start__", "fetch")
graph.add_edge("fetch", "enrich")
graph.add_edge("enrich", "transform")
graph.add_edge("transform", "validate")
graph.add_edge("validate", END)

app = graph.compile()
print(app.invoke({"data": "", "enriched": "", "result": ""}))
Where you'll use itadd_node and add_edge are called in the graph-building phase, typically in a dedicated build function. The pattern is: create StateGraph, add all nodes, wire edges, then compile.
Under the hoodLangGraph validates the graph topology at compile time: it checks for unreachable nodes, missing start/end edges, and (for non-cyclic graphs) verifies acyclicity. Invalid graphs raise GraphValidationError with specific node references.

5START and END Constants

What & why. LangGraph defines two special constants: START (the entry point, aliased as "__start__") and END (the terminal point). Every graph must have at least one edge from START and one edge to END. These constants make the graph's entry and exit points explicit, eliminating ambiguity about where execution begins and terminates.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class SimpleState(TypedDict):
    value: int

def increment(state: SimpleState) -> dict:
    return {"value": state["value"] + 1}

graph = StateGraph(SimpleState)
graph.add_node("increment", increment)

# START and END are explicit constants
graph.add_edge(START, "increment")
graph.add_edge("increment", END)

app = graph.compile()
print(app.invoke({"value": 0}))  # {'value': 1}

# You can use the string "__start__" or "__end__" too
# But START/END constants are preferred for readability
graph2 = StateGraph(SimpleState)
graph2.add_node("inc", increment)
graph2.add_edge("__start__", "inc")
graph2.add_edge("inc", "__end__")
app2 = graph2.compile()
print(app2.invoke({"value": 10}))  # {'value': 11}
Where you'll use itSTART and END appear in every graph definition. Using the constants instead of strings prevents typos and makes the graph structure immediately clear to readers.
Under the hoodSTART and END are sentinel values that LangGraph's runtime uses to identify the initial state projection and the termination condition. The compiled graph maps them to internal scheduler hooks.

6Conditional Edges with Branch Functions

What & why. Conditional edges route execution dynamically based on state. You provide a function that inspects the state and returns a string naming the next node. This enables branching logic: classifier routes to different nodes, retry loops, or early termination. The routing function is pure and deterministic given the same state.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class RouteState(TypedDict):
    input: str
    category: str
    result: str

def classify(state: RouteState) -> dict:
    cat = "greeting" if "hello" in state["input"].lower() else "question"
    return {"category": cat}

def handle_greeting(state: RouteState) -> dict:
    return {"result": "Hello! How can I help?"}

def handle_question(state: RouteState) -> dict:
    return {"result": f"Answering: {state['input']}"}

def route_after_classify(state: RouteState) -> str:
    if state["category"] == "greeting":
        return "greeting"
    return "question"

graph = StateGraph(RouteState)
graph.add_node("classify", classify)
graph.add_node("greeting", handle_greeting)
graph.add_node("question", handle_question)

graph.add_edge(START, "classify")
graph.add_conditional_edges("classify", route_after_classify, {"greeting": "greeting", "question": "question"})
graph.add_edge("greeting", END)
graph.add_edge("question", END)

app = graph.compile()
print(app.invoke({"input": "hello there", "category": "", "result": ""}))
print(app.invoke({"input": "what is recursion?", "category": "", "result": ""}))
Where you'll use itConditional edges are the core mechanism for agent routing, error handling loops, human-in-the-loop branching, and any decision point in your graph. Most graphs have at least one conditional edge.
Under the hoodThe routing function's return value is looked up in the path_map dictionary. If no path_map is provided, the return value must exactly match a node name. LangGraph validates that all possible return values have corresponding edges at compile time.

7compile and invoke

What & why. The compile() method validates and optimizes the graph definition into an executable Runnable. invoke() runs the graph synchronously with an initial state dict and returns the final state. Compilation catches errors early: missing edges, invalid routing, unreachable nodes. The compiled graph is reusable and thread-safe.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class EchoState(TypedDict):
    input: str
    output: str

def echo(state: EchoState) -> dict:
    return {"output": f"Echo: {state['input']}"}

# Build
graph = StateGraph(EchoState)
graph.add_node("echo", echo)
graph.add_edge(START, "echo")
graph.add_edge("echo", END)

# Compile (validates graph, optimizes execution)
app = graph.compile()

# Invoke (runs the graph)
result = app.invoke({"input": "hello", "output": ""})
print(result)  # {'input': 'hello', 'output': 'Echo: hello'}

# The compiled app can be invoked many times
for word in ["alpha", "beta", "gamma"]:
    print(app.invoke({"input": word, "output": ""})["output"])
Where you'll use itcompile is called once during application setup. invoke is called per request. The separation ensures graph validation happens at startup, not on every user request, catching configuration errors before they reach production.
Under the hoodcompile() performs topological analysis, builds an adjacency matrix, validates routing completeness, and creates an optimized execution scheduler. The returned CompiledGraph implements the Runnable interface, making it composable with LangChain LCEL chains.

8Streaming Updates

What & why. The stream() method yields state updates as each node completes, enabling real-time progress reporting and token-by-token display. Unlike invoke() which waits for full completion, stream() gives you incremental visibility into the graph's execution. This is critical for user-facing applications where perceived responsiveness matters.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class StreamState(TypedDict):
    step: str
    progress: list

def step_a(state: StreamState) -> dict:
    return {"step": "a", "progress": state.get("progress", []) + ["a done"]}

def step_b(state: StreamState) -> dict:
    return {"step": "b", "progress": state.get("progress", []) + ["b done"]}

def step_c(state: StreamState) -> dict:
    return {"step": "c", "progress": state.get("progress", []) + ["c done"]}

graph = StateGraph(StreamState)
graph.add_node("a", step_a)
graph.add_node("b", step_b)
graph.add_node("c", step_c)
graph.add_edge(START, "a")
graph.add_edge("a", "b")
graph.add_edge("b", "c")
graph.add_edge("c", END)

app = graph.compile()

# stream() yields updates per node
for event in app.stream({"step": "", "progress": []}):
    for node_name, update in event.items():
        print(f"Node '{node_name}' produced: {update}")

# Final state
final = app.invoke({"step": "", "progress": []})
print("Final:", final["progress"])
Where you'll use itStreaming is essential for chat interfaces where users expect to see responses appear incrementally. It also enables progress bars for long-running multi-step pipelines and real-time monitoring dashboards.
Under the hoodstream() wraps the Pregel execution loop to emit intermediate state snapshots after each super-step. Each yield contains a dictionary keyed by node name with the partial state update from that node's execution.

10Simple Chatbot Graph

What & why. The canonical first LangGraph application is a chatbot: a single node that calls an LLM, with state holding the message list. This demonstrates the minimal viable graph and introduces the message accumulation pattern where each node appends to a shared messages list rather than replacing it.

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, AIMessage

class ChatState(TypedDict):
    messages: list

model = ChatOpenAI(model="gpt-4o", temperature=0)

def chatbot(state: ChatState) -> dict:
    response = model.invoke(state["messages"])
    return {"messages": state["messages"] + [response]}

graph = StateGraph(ChatState)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)

app = graph.compile()

# Multi-turn conversation
state = {"messages": [HumanMessage(content="Hi, I'm building a LangGraph app")]}
result = app.invoke(state)
print(result["messages"][-1].content)

# Add follow-up
result = app.invoke({"messages": result["messages"] + [HumanMessage(content="What state management does it use?")]})
print(result["messages"][-1].content)
Where you'll use itThis minimal chatbot is the starting point for every LangGraph application. From here you add tool nodes, routing logic, memory persistence, and human-in-the-loop controls.
Under the hoodThe messages list grows with each invocation. Without a reducer (covered in Tier 2), each node must manually concatenate new messages to the existing list. This pattern is simple but has O(n) growth per turn.

11recursion_limit Guard

What & why. LangGraph defaults to 25 recursion steps to prevent infinite loops in cyclic graphs. The recursion_limit config parameter sets the maximum number of node executions before raising GraphRecursionError. This is a safety net for graphs with conditional cycles: retry loops, reflection patterns, or agent loops that might not terminate.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class RetryState(TypedDict):
    value: int
    attempts: int

def process(state: RetryState) -> dict:
    return {"attempts": state["attempts"] + 1}

def should_continue(state: RetryState) -> str:
    if state["attempts"] < 3:
        return "process"
    return END

graph = StateGraph(RetryState)
graph.add_node("process", process)
graph.add_edge(START, "process")
graph.add_conditional_edges("process", should_continue, {"process": "process", END: END})

app = graph.compile()

# Default recursion_limit is 25
result = app.invoke({"value": 0, "attempts": 0})
print(f"Completed in {result['attempts']} attempts")

# Set a lower limit for safety
try:
    result = app.invoke(
        {"value": 0, "attempts": 0},
        config={"recursion_limit": 2}
    )
except Exception as e:
    print(f"Hit limit: {type(e).__name__}")
Where you'll use itEvery graph with cycles must set an appropriate recursion_limit. For agent loops, set it to max_iterations + 1. For simple retries, set it to max_retries + 1. This prevents runaway costs from infinite LLM calls.
Under the hoodThe recursion counter increments after each node execution in the Pregel loop. When it exceeds recursion_limit, the runtime raises GraphRecursionError with the current state, allowing cleanup and logging before failure.

12When LangGraph vs Plain Chains

What & why. Use plain LangChain chains (LCEL) when your pipeline is linear: prompt | model | parser. Use LangGraph when you need cycles (retry loops), conditional routing (classifier-based paths), multiple coordinated actors (subgraphs), human-in-the-loop interrupts, or persistent checkpointing. LangGraph adds complexity; only use it when the features justify the overhead.

# Plain chain: linear, simple, sufficient
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

simple_chain = (
    ChatPromptTemplate.from_template("Answer: {question}")
    | ChatOpenAI(model="gpt-4o")
    | (lambda x: x.content)
)
# Result: simple_chain.invoke({"question": "hi"})

# LangGraph: needed when you have cycles, routing, or state persistence
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class AgentState(TypedDict):
    question: str
    answer: str
    attempts: int

def try_answer(state: AgentState) -> dict:
    return {"answer": "draft answer", "attempts": state["attempts"] + 1}

def is_good(state: AgentState) -> str:
    return END if state["attempts"] >= 2 else "try_answer"

graph = StateGraph(AgentState)
graph.add_node("try_answer", try_answer)
graph.add_edge(START, "try_answer")
graph.add_conditional_edges("try_answer", is_good, {"try_answer": "try_answer", END: END})
agent = graph.compile()
Where you'll use itThis decision point comes up in every project. Simple RAG? Chains. Self-correcting RAG with retry and human approval? LangGraph. The threshold is: do you need a loop or a branch?
Under the hoodLangChain LCEL chains are DAGs compiled into a RunnableSequence. LangGraph extends this with cycle support, checkpointing, streaming per-node, and state management. The execution model is fundamentally different: LCEL is a pipeline, LangGraph is a state machine.

13Annotated Reducers with operator.add

What & why. By default, state fields are overwritten by each node. Annotated reducers change this behavior: Annotated[list, operator.add] means list fields accumulate via concatenation rather than replacement. This is essential for message histories, log streams, and any state that grows over multiple node executions without manual list management.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class LogState(TypedDict):
    logs: Annotated[list, operator.add]
    current_step: str

def step_one(state: LogState) -> dict:
    return {"logs": ["step one executed"], "current_step": "one"}

def step_two(state: LogState) -> dict:
    return {"logs": ["step two executed"], "current_step": "two"}

def step_three(state: LogState) -> dict:
    return {"logs": ["step three executed"], "current_step": "three"}

graph = StateGraph(LogState)
graph.add_node("step_one", step_one)
graph.add_node("step_two", step_two)
graph.add_node("step_three", step_three)
graph.add_edge(START, "step_one")
graph.add_edge("step_one", "step_two")
graph.add_edge("step_two", "step_three")
graph.add_edge("step_three", END)

app = graph.compile()
result = app.invoke({"logs": [], "current_step": ""})
print(result["logs"])
# ['step one executed', 'step two executed', 'step three executed']
print(result["current_step"])  # 'three' (overwritten, no reducer)
Where you'll use itAnnotated reducers are critical for any state that accumulates: conversation messages, tool call histories, error logs, intermediate results. Without them, you must manually concatenate in every node return.
Under the hoodWhen a node returns a partial update for a field with a reducer, LangGraph calls the reducer function with the existing value and the new value. For operator.add on lists, this is list concatenation. For sets, you could use a union reducer.

14Messages State and add_messages

What & why. LangGraph provides a pre-built MessagesState TypedDict with a messages field using the add_messages reducer. This handles message accumulation, deduplication by ID, and merging automatically. It is the standard state type for chat applications and replaces manual message list management.

from langgraph.graph import StateGraph, START, END, MessagesState
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, AIMessage

model = ChatOpenAI(model="gpt-4o", temperature=0)

def chatbot(state: MessagesState) -> dict:
    response = model.invoke(state["messages"])
    return {"messages": [response]}

graph = StateGraph(MessagesState)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")
graph.add_edge("chatbot", END)

app = graph.compile()

# Messages accumulate automatically via add_messages reducer
result = app.invoke({"messages": [HumanMessage(content="Hi")]})
print(len(result["messages"]))  # 2 (human + ai)

# Second turn: pass full message history
result = app.invoke({"messages": result["messages"] + [HumanMessage(content="Follow up")]})
print(len(result["messages"]))  # 3 (human + ai + human)
print(result["messages"][-1].content)
Where you'll use itMessagesState is the standard starting point for chat-based LangGraph applications. It eliminates the most common bug: accidentally overwriting the message history instead of appending to it.
Under the hoodadd_messages merges new messages by ID. If a returned message has the same ID as an existing message, it updates rather than duplicates. This enables node functions to modify existing messages (e.g., tool call results) without creating duplicates.

15Pydantic State Schemas

What & why. Instead of TypedDict, you can use Pydantic BaseModel for state schemas. Pydantic provides runtime validation, default values, and richer type constraints. This is useful when state must conform to strict schemas for API contracts, when you need computed fields, or when integrating with systems that expect validated data.

from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END

class AnalysisState(BaseModel):
    query: str = Field(description="The user query")
    result: str = Field(default="", description="Analysis result")
    confidence: float = Field(default=0.0, ge=0.0, le=1.0)
    tags: list[str] = Field(default_factory=list)

def analyze(state: AnalysisState) -> dict:
    return {
        "result": f"Analyzed: {state.query}",
        "confidence": 0.85,
        "tags": ["analysis", "complete"],
    }

def summarize(state: AnalysisState) -> dict:
    return {"result": f"Summary ({state.confidence}): {state.result}"}

graph = StateGraph(AnalysisState)
graph.add_node("analyze", analyze)
graph.add_node("summarize", summarize)
graph.add_edge(START, "analyze")
graph.add_edge("analyze", "summarize")
graph.add_edge("summarize", END)

app = graph.compile()
result = app.invoke({"query": "analyze market trends"})
print(result["confidence"], result["tags"])
Where you'll use itPydantic schemas are preferred when state fields have constraints (ranges, required patterns), when integrating with FastAPI request/response models, or when you need automatic documentation of the state shape.
Under the hoodLangGraph detects Pydantic models and uses model_validate for state construction. Validation errors are raised before node execution, catching invalid state transitions at the boundary rather than deep in node logic.

16Parallel Fan-Out and Fan-In Joins

What & why. When multiple edges leave a node, LangGraph executes the successor nodes in parallel (fan-out). When multiple edges converge on a single node (fan-in join), that node waits for all predecessors to complete before executing. This enables concurrent LLM calls, parallel tool execution, and aggregation patterns without explicit threading.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END
from concurrent.futures import ThreadPoolExecutor

class ParallelState(TypedDict):
    topic: str
    summaries: Annotated[list, operator.add]
    combined: str

def research_news(state: ParallelState) -> dict:
    return {"summaries": [f"News on {state['topic']}: breakthrough in AI"]}

def research_papers(state: ParallelState) -> dict:
    return {"summaries": [f"Papers on {state['topic']}: 3 new papers"]}

def research_social(state: ParallelState) -> dict:
    return {"summaries": [f"Social on {state['topic']}: trending discussions"]}

def combine(state: ParallelState) -> dict:
    return {"combined": " | ".join(state["summaries"])}

graph = StateGraph(ParallelState)
graph.add_node("research_news", research_news)
graph.add_node("research_papers", research_papers)
graph.add_node("research_social", research_social)
graph.add_node("combine", combine)

graph.add_edge(START, "research_news")
graph.add_edge(START, "research_papers")

Where you'll use itFan-out/fan-in is the standard pattern for parallel data enrichment: querying multiple APIs simultaneously, running multiple analysis perspectives, or generating drafts from multiple viewpoints before synthesis.

17Send API for Map-Reduce Dynamic Dispatch

What & why. The Send function enables dynamic fan-out: instead of static edges, a node can emit multiple Send messages to the same node with different inputs. This is the map-reduce pattern for LangGraph: one node maps inputs, multiple parallel invocations process them, and a join node reduces results. The number of parallel tasks is determined at runtime, not compile time.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.constants import Send

class MapReduceState(TypedDict):
    documents: list[str]
    summaries: Annotated[list, operator.add]
    final_summary: str

def distribute(state: MapReduceState) -> list[Send]:
    return [
        Send("summarize", {"doc": doc, "doc_index": i})
        for i, doc in enumerate(state["documents"])
    ]

def summarize(state: dict) -> dict:
    return {"summaries": [f"Summary #{state['doc_index']}: {state['doc'][:20]}..."]}

def aggregate(state: MapReduceState) -> dict:
    return {"final_summary": " | ".join(state["summaries"])}

graph = StateGraph(MapReduceState)
graph.add_node("summarize", summarize)
graph.add_node("aggregate", aggregate)
graph.add_conditional_edges(START, distribute, ["summarize"])
graph.add_edge("summarize", "aggregate")
graph.add_edge("aggregate", END)

app = graph.compile()
result = app.invoke({
    "documents": ["Doc one about AI", "Doc two about ML", "Doc three about NLP"],
    "summaries": [],
    "final_summary": "",
})
print(result["final_summary"])
Where you'll use itSend is essential for processing variable-length lists: summarizing N documents, analyzing N data points, or generating N variations. The parallelism count scales with input size without code changes.
Under the hoodSend creates a dynamic message that the Pregel runtime routes to the named node. Each Send creates an independent state instance for the target node. The join node (aggregate) collects all results via the reducer before executing.

18Command goto + update Pattern

What & why. The Command object combines a goto (next node) with a state update in a single return value from a node. This replaces the need for separate conditional edges when the routing decision and state mutation are tightly coupled. Commands are especially useful in agent loops where the node decides both what to do next and updates scratchpad state.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]
    next_tool: str
    tool_result: str

def decide(state: AgentState) -> Command:
    last_msg = state["messages"][-1].content if state["messages"] else ""
    if "search" in last_msg.lower():
        return Command(goto="search_tool", update={"next_tool": "search"})
    return Command(goto="respond", update={"next_tool": "none"})

def search_tool(state: AgentState) -> dict:
    return {"messages": [{"role": "assistant", "content": "Search results found"}], "tool_result": "results"}

def respond(state: AgentState) -> dict:
    return {"messages": [{"role": "assistant", "content": "Here is my response"}]}

graph = StateGraph(AgentState)
graph.add_node("decide", decide)
graph.add_node("search_tool", search_tool)
graph.add_node("respond", respond)
graph.add_edge(START, "decide")
graph.add_edge("search_tool", END)
graph.add_edge("respond", END)

app = graph.compile()
result = app.invoke({"messages": [{"role": "user", "content": "search for LangGraph"}], "next_tool": "", "tool_result": ""})
print(result["next_tool"])
Where you'll use itCommand is the preferred pattern in ReAct-style agent loops where the reasoning node both updates the scratchpad and chooses the next action. It keeps routing logic inside the node rather than externalizing it to conditional edges.
Under the hoodCommand is a typed return value that the runtime inspects after node execution. If a node returns a Command, the runtime applies the state update and follows the goto target instead of following static edges. This gives nodes direct control over execution flow.

21interrupt human-in-the-loop (approve)

What & why. The interrupt() function pauses graph execution at a specific point and returns control to the caller with the current state. This enables human-in-the-loop patterns: a node calls interrupt() before a sensitive action (sending an email, making a payment), and the graph suspends until a human approves or rejects via Command(resume=...).

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END, MessagesState

    return {"messages": [{"role": "assistant", "content": "Action cancelled by user"}]}

graph.add_node("execute", execute)

graph.add_edge("review", "execute")
graph.add_edge("execute", END)

23Subgraphs and Composition

What & why. Subgraphs allow you to compose graphs hierarchically: a parent graph's node can be an entire compiled child graph. This enables modular design where complex subsystems (a tool-use agent, a retrieval pipeline) are developed and tested independently, then composed into larger workflows. State is shared between parent and child via schema compatibility.

import operator
from langgraph.graph import StateGraph, START, END

    processed: str

    result: str

What & why. The supervisor pattern assigns a coordinator LLM that inspects each task and routes it to the most appropriate specialist agent. from typing import TypedDict, Annotated

34Plan-and-Execute Graph

What & why. Plan-and-execute separates reasoning into two phases: a planner node creates a list of steps, and an executor node processes them sequentially. The planner uses a powerful model for strategy, while the executor can use a faster, cheaper model for individual steps. The graph loops: execute a step, re-evaluate the plan, adjust if needed.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class PlanExecute(TypedDict):
    input: str
    plan: list[str]
    past_steps: Annotated[list[tuple[str, str]], operator.add]
    response: str

def planner(state: PlanExecute) -> dict:
    return {"plan": ["Step 1: Research topic", "Step 2: Outline structure", "Step 3: Write draft"]}

def executor(state: PlanExecute) -> dict:
    step = state["plan"][0]
    remaining = state["plan"][1:]
    return {
        "past_steps": [(step, f"Completed: {step}")],
        "plan": remaining,

def should_continue(state: PlanExecute) -> str:
    return "executor" if state["plan"] else "responder"

def responder(state: PlanExecute) -> dict:
    summary = " | ".join([s for _, s in state["past_steps"]])
    return {"response": f"Done: {summary}"}

graph = StateGraph(PlanExecute)
graph.add_node("planner", planner)
graph.add_node("executor", executor)
graph.add_node("responder", responder)
graph.add_edge(START, "planner")
graph.add_edge("planner", "executor")
graph.add_conditional_edges("executor", should_continue, {"executor": "executor", "responder": "responder"})
graph.add_edge("responder", END)

app = graph.compile()
result = app.invoke({"input": "Write a report on AI graphs", "plan": [], "past_steps": [], "response": ""})
print(result["response"])
Where you'll use itPlan-and-execute is ideal for complex multi-step tasks: research reports, data pipelines, migration plans. It provides visibility into the plan and allows mid-course correction between steps.
Under the hoodThe plan is stored in state and mutated by the executor (remove completed step) and planner (add/modify steps on re-plan). The loop continues until the plan is empty or a stopping condition is met.

35Reflection and Critic Loops

What & why. Reflection graphs add a critic node that evaluates the output of a generator node. If the critic finds issues, the graph loops back to the generator with feedback. This produces higher-quality outputs through iterative refinement: write, critique, revise, critique again, until quality thresholds are met.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class ReflectState(TypedDict):
    topic: str
    draft: str
    critique: str
    revisions: Annotated[list[str], operator.add]
    iteration: int

def generate(state: ReflectState) -> dict:
    iteration = state.get("iteration", 0) + 1
    critique = state.get("critique", "")
    if critique:
        return {"draft": f"Revised draft v{iteration} addressing: {critique}", "revisions": [f"v{iteration}"], "iteration": iteration}
    return {"draft": f"Initial draft on {state['topic']}", "revisions": ["v1"], "iteration": iteration}

def critique(state: ReflectState) -> dict:
    if state["iteration"] >= 3:
        return {"critique": "APPROVED"}
    return {"critique": f"Issue in iteration {state['iteration']}: needs more detail"}

def should_continue(state: ReflectState) -> str:
    return END if state.get("critique") == "APPROVED" else "generate"

graph = StateGraph(ReflectState)
graph.add_node("generate", generate)
graph.add_node("critique", critique)
graph.add_edge(START, "generate")
graph.add_edge("generate", "critique")
graph.add_conditional_edges("critique", should_continue, {"generate": "generate", END: END})

app = graph.compile()
result = app.invoke({"topic": "AI agents", "draft": "", "critique": "", "revisions": [], "iteration": 0})
print(f"Final: {result['draft']} after {result['iteration']} iterations")
Where you'll use itReflection loops produce publication-quality content, validated code, and reviewed analyses. They are used in content generation, code review automation, and any domain where iterative improvement outperforms single-shot generation.
Under the hoodThe critique node is typically an LLM call with a quality-focused prompt. The loop termination is controlled by either a max-iteration guard, an approval signal from the critic, or a quality score threshold. Each iteration adds a checkpoint for comparison.

37Durable Execution: At-Least-Once Semantics

What & why. LangGraph's durable execution guarantees that each node executes at least once per checkpoint. If a process crashes mid-execution, the runtime resumes from the last successful checkpoint and re-executes pending nodes. This at-least-once semantic means nodes must be idempotent: calling them twice with the same state should produce the same result.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class DurableState(TypedDict):
    items: list[str]
    processed: Annotated[list[str], operator.add]
    total_cost: float

def process_item(state: DurableState) -> dict:
    # Must be idempotent: same input produces same output
    unprocessed = [i for i in state["items"] if i not in state.get("processed", [])]
    results = [f"done({item})" for item in unprocessed]
    return {"processed": results, "total_cost": sum(len(r) for r in results) * 0.01}

graph = StateGraph(DurableState)
graph.add_node("process", process_item)
graph.add_edge(START, "process")
graph.add_edge("process", END)

# On crash recovery, process_item re-runs but idempotency
# prevents duplicate processing
app = graph.compile()  # with production checkpointer
result = app.invoke({"items": ["a", "b", "c"], "processed": [], "total_cost": 0.0})
Where you'll use itDurable execution is critical for long-running workflows: data pipelines, approval chains, and multi-day agent tasks. Without idempotency, crash recovery would duplicate side effects like sending emails or charging credit cards.
Under the hoodThe checkpointer stores a pending writes list after each node execution. On recovery, the runtime compares the checkpoint's node versions with the current graph and re-executes only nodes whose state has changed. This is similar to event sourcing replay.

40Functional vs Pregel Execution Model

What & why. LangGraph's execution is Pregel-inspired: the graph is divided into super-steps where all nodes in a step execute, then barriers synchronize before the next step. The functional API (v0.2+) provides a decorator-based alternative where each function is a standalone unit with explicit state passing. Understanding both models helps choose the right abstraction for different problem domains.

# Pregel model (graph-based):
# Super-step 1: nodes A, B execute in parallel
# Barrier: synchronize
# Super-step 2: node C executes (fan-in from A, B)
# Each super-step produces a checkpoint

# Functional API (decorator-based):
from langgraph.func import entrypoint, task

@task
def process_data(data: str) -> str:
    return f"processed: {data}"

@task
def summarize(processed: str) -> str:
    return f"summary of {processed}"

@entrypoint
def pipeline(raw_data: str) -> str:
    processed = process_data(raw_data).result()
    return summarize(processed).result()

# result = pipeline.invoke("raw input")

Where you'll use itPregel (graph API) is best for complex topologies with fan-out/fan-in and conditional routing. Functional API is best for linear pipelines and when you prefer Python-native control flow over graph declarations.
Under the hoodBoth APIs compile to the same Pregel runtime internally. The functional API generates a graph under the hood: each @entrypoint becomes a linear graph, and @task calls within it become nodes. Checkpointing and streaming work identically.

44Latency Optimization and Parallelism Design

What & why. Graph latency is dominated by LLM calls. Optimize by parallelizing independent LLM invocations (fan-out), using faster models for routing decisions, streaming for perceived responsiveness, and caching for repeated inputs. Design graphs with critical path awareness: minimize the longest sequential chain of LLM calls.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class OptimizedState(TypedDict):
    query: str
    context: Annotated[list, operator.add]
    answer: str

def fast_route(state: OptimizedState) -> dict:
    # Use small/fast model for routing (GPT-4o-mini)
    return {"context": [f"Route decision for: {state['query']}"]}

def parallel_retrieve_a(state: OptimizedState) -> dict:
    return {"context": [f"Source A results for: {state['query']}"]}

def parallel_retrieve_b(state: OptimizedState) -> dict:
    return {"context": [f"Source B results for: {state['query']}"]}

def synthesize(state: OptimizedState) -> dict:
    return {"answer": f"Synthesized from {len(state['context'])} sources"}

graph = StateGraph(OptimizedState)
graph.add_node("route", fast_route)
graph.add_node("retrieve_a", parallel_retrieve_a)
graph.add_node("retrieve_b", parallel_retrieve_b)
graph.add_node("synthesize", synthesize)

graph.add_edge(START, "route")
graph.add_edge("route", "retrieve_a")
graph.add_edge("route", "retrieve_b")
graph.add_edge("retrieve_a", "synthesize")
graph.add_edge("retrieve_b", "synthesize")
graph.add_edge("synthesize", END)

# With fan-out, retrieve_a and retrieve_b run concurrently
# Total latency: route + max(retrieve_a, retrieve_b) + synthesize
app = graph.compile()

Customer Support Triage Bot with HITL Escalation

Build a customer support system that classifies incoming tickets, routes to the appropriate specialist, and escalates to a human when confidence is low or the customer requests it.

Architecture steps.

  1. Define a MessagesState with Annotated[list, operator.add] for conversation history and ticket metadata fields (category, priority, confidence)
  2. Create a triage node that classifies the ticket into billing, technical, or general categories using an LLM with structured output
  3. Add a confidence check node that evaluates the classifier's certainty and routes low-confidence tickets to human review via interrupt()
  4. Build specialist subgraphs for each category (billing_agent, tech_agent, general_agent) using create_react_agent with category-specific tools
  5. Implement a supervisor node that orchestrates the triage-to-specialist handoff and tracks resolution progress
  6. Add a HITL approval gate before any external action (refunds, account changes) using interrupt() with Command(resume=...)
  7. Configure PostgresSaver for production persistence and set recursion_limit to 25 for the agent loop
  8. Add streaming support for real-time ticket status updates to the support dashboard
from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.prebuilt import create_react_agent
from langgraph.types import interrupt, Command
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

class TicketState(TypedDict):
    messages: Annotated[list, operator.add]
    category: str
    priority: str
    confidence: float
    resolution: str

model = ChatOpenAI(model="gpt-4o", temperature=0)

def triage(state: TicketState) -> dict:
    last = state["messages"][-1].content
    category = "billing" if "refund" in last.lower() else "technical" if "error" in last.lower() else "general"
    return {"category": category, "confidence": 0.9, "priority": "medium"}

def needs_human(state: TicketState) -> str:
    if state["confidence"] < 0.7:
        return "escalate"
    return state["category"]

def escalate(state: TicketState) -> dict:
    decision = interrupt("Human review needed for this ticket")
    return {"resolution": f"Escalated and {decision}"}

def handle_billing(state: TicketState) -> dict:
    return {"resolution": "Billing issue resolved: refund processed"}

def handle_technical(state: TicketState) -> dict:
    return {"resolution": "Technical issue resolved: workaround provided"}

def handle_general(state: TicketState) -> dict:
    return {"resolution": "General inquiry answered"}

graph = StateGraph(TicketState)
graph.add_node("triage", triage)
graph.add_node("escalate", escalate)
graph.add_node("billing", handle_billing)
graph.add_node("technical", handle_technical)
graph.add_node("general", handle_general)
graph.add_edge(START, "triage")
graph.add_conditional_edges("triage", needs_human, {"escalate": "escalate", "billing": "billing", "technical": "technical", "general": "general"})
graph.add_edge("escalate", END)
graph.add_edge("billing", END)
graph.add_edge("technical", END)
graph.add_edge("general", END)

app = graph.compile(checkpointer=MemorySaver())

Research Team: Supervisor + Writer + Critic

Build a multi-agent research system where a supervisor coordinates a research agent, a writer agent, and a critic agent to produce high-quality research reports through iterative refinement.

Architecture steps.

  1. Define ResearchState with Annotated fields for messages, research notes, draft, critique, and iteration count
  2. Create a research_agent subgraph using create_react_agent with search and paper_lookup tools
  3. Create a writer_agent subgraph that takes research notes and produces structured draft sections
  4. Create a critic_agent subgraph that evaluates the draft against quality criteria and provides specific feedback
  5. Build a supervisor node that orchestrates the research-write-critique loop and tracks progress
  6. Implement the loop with conditional routing: critic approval routes to END, rejection routes back to writer with feedback
  7. Add a max_iterations guard (recursion_limit) to prevent infinite refinement loops
  8. Stream intermediate results: research findings, draft versions, and critique comments in real time
from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END

class ResearchState(TypedDict):
    topic: str
    research_notes: Annotated[list[str], operator.add]
    draft: str
    critique: str
    iteration: int
    final_report: str

def research(state: ResearchState) -> dict:
    return {"research_notes": [f"Finding 1 about {state['topic']}", f"Finding 2 about {state['topic']}"]}

def write(state: ResearchState) -> dict:
    notes = " ".join(state.get("research_notes", []))
    iteration = state.get("iteration", 0) + 1
    critique = state.get("critique", "")
    if critique:
        return {"draft": f"Revised draft v{iteration} incorporating: {critique}", "iteration": iteration}
    return {"draft": f"Initial draft on {state['topic']} based on: {notes}", "iteration": iteration}

def critique(state: ResearchState) -> dict:
    if state.get("iteration", 0) >= 3:
        return {"critique": "APPROVED", "final_report": state["draft"]}
    return {"critique": "Needs more specific data points and citations"}

def should_continue(state: ResearchState) -> str:
    return END if state.get("critique") == "APPROVED" else "write"

graph = StateGraph(ResearchState)
graph.add_node("research", research)
graph.add_node("write", write)
graph.add_node("critique", critique)
graph.add_edge(START, "research")
graph.add_edge("research", "write")
graph.add_edge("write", "critique")
graph.add_conditional_edges("critique", should_continue, {"write": "write", END: END})

app = graph.compile()
result = app.invoke({"topic": "AI agent architectures", "research_notes": [], "draft": "", "critique": "", "iteration": 0, "final_report": ""})
print(f"Iterations: {result['iteration']}, Report length: {len(result['final_report'])}")

Resilient Data Pipeline Graph with Replay

Build a data processing pipeline that handles failures gracefully with automatic retries, supports time-travel debugging, and can replay from any checkpoint to recover from errors or test alternative processing logic.

Architecture steps.

  1. Define PipelineState with Annotated fields for source data, processed chunks, errors, and output
  2. Create an extract node that reads data from multiple sources (simulated with sleep and occasional failures)
  3. Add a RetryPolicy with max_attempts=3 and exponential backoff for the extract node
  4. Create transform nodes for cleaning, enriching, and aggregating data with individual error handling
  5. Implement a validate node that checks data quality and routes invalid records to an error correction path
  6. Configure PostgresSaver for production persistence and enable checkpoint listing for debugging
  7. Add a replay function that takes a checkpoint_id and re-runs the pipeline from that point with modified parameters
  8. Build a monitoring node that logs processing metrics (record count, error rate, latency) at each stage
from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langgraph.retry import RetryPolicy

class PipelineState(TypedDict):
    source_data: list[str]
    cleaned: Annotated[list[str], operator.add]
    enriched: Annotated[list[str], operator.add]
    output: str
    errors: Annotated[list[str], operator.add]
    metrics: Annotated[list[str], operator.add]

def extract(state: PipelineState) -> dict:
    return {"cleaned": [f"clean({d})" for d in state["source_data"]], "metrics": ["extract complete"]}

def enrich(state: PipelineState) -> dict:
    return {"enriched": [f"enrich({c})" for c in state.get("cleaned", [])], "metrics": ["enrich complete"]}

def aggregate(state: PipelineState) -> dict:
    enriched = state.get("enriched", [])
    return {"output": f"Aggregated {len(enriched)} records", "metrics": ["aggregate complete"]}

def validate(state: PipelineState) -> dict:
    return {"metrics": [f"validated {len(state.get('enriched', []))} records"]}

graph = StateGraph(PipelineState)
graph.add_node("extract", extract, retry=RetryPolicy(max_attempts=3))
graph.add_node("enrich", enrich)
graph.add_node("aggregate", aggregate)
graph.add_node("validate", validate)
graph.add_edge(START, "extract")
graph.add_edge("extract", "enrich")
graph.add_edge("enrich", "aggregate")
graph.add_edge("aggregate", "validate")
graph.add_edge("validate", END)

memory = MemorySaver()
app = graph.compile(checkpointer=memory)
config = {"configurable": {"thread_id": "pipeline-001"}}
result = app.invoke({"source_data": ["record1", "record2", "record3"], "cleaned": [], "enriched": [], "output": "", "errors": [], "metrics": []}, config)
print(result["output"])

# List checkpoints for debugging
checkpoints = list(memory.list({"configurable": {"thread_id": "pipeline-001"}}))
print(f"Checkpoints saved: {len(checkpoints)}")
