Part I · FoundationsTier 1 — the edge stack

1The IoT Reference Architecture

What & why. Every IoT system is a four-layer stack: devices (sensors/actuators) → connectivity (protocols) → edge/gateway (local compute) → cloud (storage, ML, dashboards). Where intelligence runs — device, edge, or cloud — is the central architecture decision.

# Reference architecture
#   [Devices]      sensors, actuators, MCUs, cameras
#       |  MQTT / CoAP / BLE / LoRaWAN
#   [Gateways]     protocol translation, buffering, local AI
#       |  HTTPS / MQTT-over-TLS
#   [Cloud]        ingestion, time-series DB, ML training,
#                  dashboards, OTA fleet management
#
# Intelligence placement:
#   Device:  real-time, offline-safe, privacy-first
#            (wake words, anomaly detection)
#   Edge:    aggregation, low-latency decisions
#            (gateway rules, local inferencing)
#   Cloud:   training, big-data analytics, heavy models
#
# Latency/bandwidth/power triangle:
#   more edge = less latency/bandwidth but less compute
#   more cloud = more compute but latency + data cost

# Example: industrial vibration monitoring
#   MCU reads accelerometer @ 1kHz, runs tiny anomaly model,
#   only sends anomalies + summaries to the cloud.
Where you'll use itEvery IoT design. Decide where each decision lives before writing any code — moving intelligence later is expensive.
Under the hoodThe "edge" is not one place: it's a spectrum from the MCU to the on-prem server. Edge AI usually means inference within a few ms of the sensor.

2Communication Protocols: MQTT, CoAP, BLE

What & why. IoT devices are constrained, intermittent and numerous. MQTT (publish/subscribe over TCP, QoS levels) is the default for sensor telemetry; CoAP (UDP, REST-like) suits very constrained nodes; BLE suits short-range battery devices; LoRaWAN suits kilometers at low rate.

# MQTT essentials
#   broker = central hub (Mosquitto, EMQX, HiveMQ)
#   topics = hierarchical:  factory/line1/temp
#   QoS 0: fire-and-forget     QoS 1: at-least-once
#   QoS 2: exactly-once        (2x round trips)
#   retained messages: last value kept for new subscribers
#   will messages: broker publishes if device dies

# Mosquitto CLI example
# mosquitto_pub -h broker -t factory/line1/temp -m 22.5
# mosquitto_sub -h broker -t factory/+/temp   # wildcard

# Python with paho-mqtt
import paho.mqtt.client as mqtt

def on_message(client, userdata, msg):
    print(f"{msg.topic}: {msg.payload.decode()}")

client = mqtt.Client()
client.on_message = on_message
client.connect("broker.local", 1883)
client.subscribe("factory/+/temp")
client.loop_forever()

# When to use what:
#   MQTT:    reliable telemetry, fleet of devices
#   CoAP:    tiny MCUs over UDP (DTLS security)
#   BLE:     wearables, phones, short range
#   LoRaWAN: agriculture, metering, km range, low rate
Where you'll use itChoosing transport for any device fleet. MQTT + TLS + JSON/Protobuf covers 80% of production IoT.
Under the hoodMQTT QoS 1/2 trade throughput for delivery guarantees; brokers retain session state, so reconnect is seamless — ideal for flaky radio links.

3Sensors, Sampling and Data Realities

What & why. Real IoT data is messy: missing samples, out-of-order timestamps, drift, and units confusion. Understanding your sensors (rate, resolution, noise) determines what the ML pipeline can achieve.

# Sensor pipeline from raw to feature
raw = read_adc(channel=0, samples=256, rate=1000)  # 1kHz
#   -> calibrate (offset/gain from datasheet or factory cal)
#   -> filter (moving average / median for spikes)
#   -> downsample (1kHz -> 100Hz)
#   -> features: mean, rms, peak, fft bands, zero crossings
#   -> window: 1-2s windows with overlap for streaming models

import numpy as np

def extract_features(window):
    return {
        "mean": window.mean(),
        "rms": np.sqrt((window**2).mean()),
        "peak": np.abs(window).max(),
        "crest": np.abs(window).max() / np.sqrt((window**2).mean()),
        "std": window.std(),
    }

# Data-quality rules
#   - timestamp at the DEVICE (not at ingestion)
#   - store raw + derived; never overwrite raw
#   - treat gaps explicitly (null, not zero)
#   - log calibration + firmware version with every batch
#   - watch for sensor drift -> periodic recalibration
Where you'll use itAny ML on sensor data. Garbage sensors in = garbage models out; feature extraction is often more valuable than a fancier model.
Under the hoodADC sampling obeys Nyquist: sample at ≥2x the highest frequency you care about. Aliased high-frequency noise looks like real signal — filter first.

Part II · SystemsTier 2 — pipelines and gateways

4Building a Sensor-to-Dashboard Pipeline

What & why. The canonical IoT project: device publishes MQTT → broker → ingestion service → time-series database → dashboard/alerts. This is the skeleton every product builds on.

# Stack (all open source)
#   Device:      ESP32 + sensor, publishes JSON via MQTT
#   Broker:      Mosquitto (or EMQX for scale)
#   Ingestion:   FastAPI + paho subscriber -> TimescaleDB
#   Storage:     TimescaleDB (Postgres + time-series)
#   Dashboard:   Grafana; alerts via Alertmanager

# Ingestion subscriber (FastAPI + paho)
import json
import psycopg2

def on_message(client, userdata, msg):
    payload = json.loads(msg.payload)
    with psycopg2.connect(DB_URL) as conn:
        conn.execute(
            "INSERT INTO telemetry(device, ts, temp, rms) "
            "VALUES (%s, to_timestamp(%s), %s, %s)",
            (payload["device"], payload["ts"],
             payload["temp"], payload["rms"]))

# Time-series modeling
#   - hypertable partitioned by time (TimescaleDB)
#   - downsampling/continuous aggregates for long retention
#   - retention policy: raw 30d, hourly 1y, daily 5y

# Grafana: panel per device + threshold alert when temp > 80
Where you'll use itEvery telemetry product. Keep the pipeline idempotent (device_id + ts as dedup key) — MQTT redelivery will duplicate otherwise.
Under the hoodTime-series DBs win over generic stores via columnar compression and time partitioning; continuous aggregates precompute rollups so dashboards stay instant.

5Edge vs Cloud: The Decision Framework

What & why. "Send everything to the cloud" fails at scale: bandwidth, latency, power, privacy, cost. The framework: process where it is cheapest in total — device for real-time, edge for aggregation, cloud for training and heavy analytics.

# Decision framework
#   Q1. Latency budget?  <50ms?  -> device/edge (no round trip)
#   Q2. Connectivity?    offline safe needed? -> edge
#   Q3. Data volume?     GB/day of raw? -> summarize at edge
#   Q4. Privacy?         PII/sensitive? -> keep at edge
#   Q5. Model size?      >100MB? -> cloud (unless quantized)
#   Q6. Power?           battery years? -> tiny MCU models

# A typical hybrid split (video analytics)
#   Device/camera:  motion detection (cheap CNN, 1-5 TOPS NPU)
#   Edge gateway:   object tracking, dedup, crop interesting
#   Cloud:          fine-tuned model on crops, training, evals

# Cost reality
#   cellular data $/MB vs edge compute $/hour decides everything;
#   "summarize at the edge, archive in the cloud" is the norm
Where you'll use itArchitecting any IoT product. Write the data-flow budget (bytes/day per tier) before choosing hardware.
Under the hoodEdge AI economics: a $2 MCU doing local anomaly detection can beat a $0.10/MB cellular bill — the unit economics decide the architecture.

6Microcontrollers and Boards: ESP32, RP2040, Jetson

What & why. The hardware ladder: MCUs (ESP32, RP2040) for sensors/actuators at ~$2-10; application processors (Raspberry Pi, Jetson) for gateways and real AI at $35-250+. Pick by compute, RAM, and power envelope.

# Hardware ladder
# ESP32-S3:  240MHz dual-core Xtensa, 512KB SRAM, WiFi+BLE
#            -> sensors, MQTT clients, TinyML (300KB model)
# RP2040:    133MHz dual-core, 264KB SRAM, no radio
#            -> hobbyist, low-power sensing
# Raspberry Pi 5: quad A76, 8GB, full Linux
#            -> gateway, video, heavy processing
# Jetson Orin Nano: 1024-core GPU, 8GB, 40 TOPS
#            -> real-time vision AI at the edge

# ESP32 MicroPython sensor + MQTT (sketch)
from machine import Pin, ADC
import time, network, ujson
from umqtt.simple import MQTTClient

wlan = network.WLAN(network.STA_IF); wlan.active(True)
wlan.connect("ssid", "pass")
adc = ADC(Pin(34)); adc.atten(ADC.ATTN_11DB)

def publish():
    temp = adc.read() / 4095 * 3.3 * 100 - 50  # crude linear
    c = MQTTClient("dev-7", "broker.local")
    c.connect(); c.publish("factory/line1/temp",
                           ujson.dumps({"v": round(temp, 2)}))
    c.disconnect()

while True:
    publish(); time.sleep(30)

# Power: deep sleep (ESP32) draws ~10uA -> years on battery
Where you'll use itChoosing hardware for each tier of the architecture. Match the MCU to the task: don't run Linux where a 300KB model suffices.
Under the hoodMCU RAM (KB) is the hard constraint: models must fit in flash (MB) and run with activations in RAM — hence quantization to 4-8 bits is mandatory for TinyML.

Part III · TinyMLTier 3 — AI on microcontrollers

7TinyML: From TensorFlow to Microcontroller

What & why. TinyML runs ML on devices with KB of RAM: train in TensorFlow, convert with TensorFlow Lite, quantize to int8, and deploy with TFLite Micro on any MCU. The whole flow is designed around the memory ceiling.

# Flow: train -> quantize -> convert -> deploy
import tensorflow as tf

# 1. Train a small model (keep it TINY by design)
model = tf.keras.Sequential([
    tf.keras.layers.Dense(16, activation="relu", input_shape=(8,)),
    tf.keras.layers.Dense(4, activation="relu"),
    tf.keras.layers.Dense(3, activation="softmax"),
])
model.compile(optimizer="adam", loss="sparse_categorical_crossentropy")
model.fit(X_train, y_train, epochs=10)

# 2. Convert + quantize (int8) for MCU
converter = tf.lite.TFLiteConverter.from_keras_model(model)
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.representative_dataset = lambda: gen_rep_data()  # sample
tflite_model = converter.convert()

# 3. Deploy via TFLite Micro C++ on ESP32/STM32
#    or on-device inference via TensorFlow Lite Python/RPi

# Budget rules of thumb (8-bit quantized)
#   params  <  200K   (200KB flash)
#   activations < 32KB RAM
#   latency < 50ms per inference on MCU @ 240MHz
Where you'll use itWake-word detection, gesture recognition, vibration anomaly detection, predictive maintenance on the device.
Under the hoodQuantization-aware training (QAT) recovers accuracy after int8 conversion: simulate quantization during training so the model learns to tolerate it.

8On-Device Inference Runtimes

What & why. Beyond TFLite Micro: ONNX Runtime (Edge/Web), ExecuTorch (PyTorch on edge), MediaPipe (vision pipelines), and vendor SDKs (STM32Cube.AI, NXP eIQ, Qualcomm QNN). Choose by model source and target hardware.

# Runtime selection guide
# TFLite Micro:  TF-trained, MCUs (ESP32, STM32) - de facto
# ExecuTorch:    PyTorch-trained, mobile+edge (llama.cpp too)
# ONNX Runtime:  any framework -> ONNX, x86/ARM/GPU/Web
# llama.cpp:     LLM inference on CPU/NPU (edge LLMs)
# QNN / NNAPI:   vendor NPU acceleration on phones

# ONNX on Raspberry Pi (gateway AI)
import onnxruntime as ort
sess = ort.InferenceSession("model.onnx",
                            providers=["CPUExecutionProvider"])
result = sess.run(None, {"input": window_np})   # (1, 8)
print(result[0])   # class probabilities

# llama.cpp for edge LLMs
# llama-cli -m llama-3.2-1b-q4_k_m.gguf -p "hello"
#   1B @ 4-bit ~ 1-2 GB RAM -> runs on Pi 5 / phones

# Deploy + validate:
#   - run on the TARGET device (not the laptop)
#   - measure: RAM peak, latency p95, accuracy vs fp32
#   - golden test set on-device before fleet rollout
Where you'll use itShipping models beyond the laptop. The runtime choice is dictated by training framework + target silicon; benchmark both before committing.
Under the hoodRuntimes differ in kernel coverage: a model that runs on x86 may hit unsupported ops on MCU — test the converted artifact, not the source model.

9Edge Computer Vision Pipelines

What & why. Cameras are the most common "sensor" at the edge. A production vision pipeline is a chain: capture → preprocessing (resize/normalize) → detection → tracking → region-of-interest crop → optional cloud. Latency and power are engineered, not hoped for.

# Pipeline (Jetson / RPi + camera)
#   1. Capture @ 30fps, skip frames by motion
#   2. Preprocess: BGR->RGB, resize 640, /255 (NPP/CUDA)
#   3. Detect: YOLOv8n (~6M params) @ 20-60 fps on Orin
#   4. Track: ByteTrack/DeepSORT -> stable IDs across frames
#   5. Act:   crop person, run face/OCR model on crop only
#   6. Cloud: send only detections + crops (Kafka/MQTT)

import cv2
from ultralytics import YOLO

model = YOLO("yolov8n.pt")
cap = cv2.VideoCapture(0)

while True:
    ok, frame = cap.read()
    if not ok: break
    results = model(frame, verbose=False)     # detect
    for r in results:
        for box in r.boxes.xyxy.cpu().numpy():
            x1, y1, x2, y2 = map(int, box)
            if r.boxes.cls[0] == 0:           # person
                crop = frame[y1:y2, x1:x2]    # ROI
                # embed -> compare -> count/alert
    cv2.imshow("edge", results[0].plot())
    if cv2.waitKey(1) & 0xFF == ord("q"): break

# Power budget: 24/7 cameras at the edge need NPU
# (Jetson ~7-15W total vs cloud upload cost per hour)
Where you'll use itSecurity, retail analytics, industrial QA, traffic monitoring — every vision product follows this chain.
Under the hoodTracking removes duplicate detections and enables counting; cropping to ROIs lets a small, cheap model do what a giant model would do in the cloud.

Part IV · Fleet & SecurityTier 4 — operate at scale

10IoT Security: The Attack Surface

What & why. Default passwords and plaintext MQTT have powered some of the biggest botnets (Mirai). A secure IoT device covers: secure boot, encrypted storage, TLS everywhere, per-device certificates, key rotation, and no hardcoded secrets.

# Security checklist
#   Device
#     - unique per-device identity (secure element / TPM)
#     - secure boot: signed firmware only
#     - encrypted flash (keys in secure element, not flash)
#     - no default credentials; forced setup flow
#   Transport
#     - TLS 1.2+ for MQTT/HTTPS; cert pinning on gateways
#     - CoAP -> DTLS; BLE -> pairing + encryption
#   Cloud
#     - per-device certificates (X.509), not shared tokens
#     - revocation list / device quarantine
#     - audit logs of every control command
#   Ops
#     - signed, staggered OTA updates
#     - rate limiting + anomaly detection on traffic

# Example: AWS IoT / Azure IoT provisioning
#   device -> register -> issue cert -> connect over TLS
#   policy: device may only publish to its own topics

# Red-team mindset: assume physical access + network access.
# If the secret is in the firmware, it is public.
Where you'll use itEvery device you ship. Security is a design property; retrofitting it to a fleet is orders of magnitude more expensive.
Under the hoodHardware root of trust (secure element) means even full flash readout yields no keys — the difference between a breach and a nuisance.

11OTA Updates and Fleet Management

What & why. You will find bugs after shipping. Over-the-air updates must be signed, atomic (A/B partitions), staggered, and rollback-safe. Fleet management = inventory + health + config-as-code for thousands of devices.

# OTA design
#   1. Build firmware, sign with private key (code signing)
#   2. Upload to OTA server, tag by fleet/channel (stable/beta)
#   3. Devices poll, verify signature against public key
#   4. A/B partitions: write new image to inactive slot,
#      reboot into it, report health; auto-rollback on failure
#   5. Stagger rollout: 1% -> 10% -> 100% with health gates

# Fleet health signals
#   - connectivity rate (heartbeats expected vs received)
#   - firmware version distribution
#   - memory/CPU/error counters from devices
#   - model metrics when edge AI is deployed (drift!)

# Config as code
#   device config in git -> rendered per device -> OTA'd
#   every change is a release with a rollback path

# Monitoring golden rule:
#   you cannot fix a fleet you cannot see;
#   telemetry comes FIRST, features second.
Where you'll use itAny fleet beyond a handful of devices. Design OTA before the first device ships; retrofitting is painful.
Under the hoodA/B partition layout trades flash space for atomicity: if the new firmware fails to boot, the bootloader flips back automatically.

12Digital Twins and 5G/Private Networks

What & why. A digital twin is a live software model of a physical system, fed by IoT data, used to simulate "what if". Private 5G / Wi-Fi 6 / LoRaWAN give factories the deterministic, low-latency connectivity industrial edge AI needs.

# Digital twin loop
#   physical asset --(telemetry)--> twin model --(simulate)--> 
#   insights --(actuate/plan)--> physical asset

# Value
#   - predictive maintenance: run failure scenarios in sim
#   - what-if: change setpoint in twin, not the plant
#   - operator training on a safe simulation
#   - as-built vs as-designed reconciliation (BIM/GIS)

# Connectivity for industrial IoT
#   Wi-Fi 6:   ~1-2 Gbps indoor, fine for cameras
#   Private 5G: deterministic latency (1-10ms), slicing
#   LoRaWAN:   km range, low rate, battery years (metering)
#   TSN:       time-synchronized ethernet for control loops

# Implementation stack
#   OPC-UA / Modbus for machines
#   MQTT-Sparkplug B for industrial telemetry
#   TimescaleDB + Grafana + simulation engine
#   (e.g. pyomo/Modelica for physics simulation)
Where you'll use itManufacturing, energy, smart cities. Twins are where IoT data becomes decision-making infrastructure.
Under the hoodDigital twins fail when the model and reality diverge: continuous reconciliation (Kalman filters, drift detection) between telemetry and simulation is the hard part.

# Rule engine (simple, readable, testable)

    {"when": "door/front", "and": {"night": True},
     "then": "alert/security", "value": "open"},

def evaluate(rules, state):
    actions = []
    for rule in rules:
        if state.get(rule["when"]) and all(
                check(state[k], op, v)
                for k, (op, v) in rule["and"].items()):
            actions.append(rule["then"])
    return actions

14Project 2 — Vibration Anomaly Detection (Predictive Maintenance)

What & why. A motor's vibration signature changes before failure. Build: MCU samples accelerometer → feature extraction → tiny model flags anomalies → only anomalies go to the cloud.

# 1. Collect: normal vs faulty vibration windows (1s @ 1kHz)
# 2. Features: rms, peak, crest, fft energy bands, skew
# 3. Model: isolation forest / small autoencoder (TinyML)
#    - autoencoder: reconstruction error > threshold = anomaly
import numpy as np
from sklearn.ensemble import IsolationForest

def featurize(windows):  # (n, 1000) -> (n, 8)
    out = []
    for w in windows:
        f = np.abs(np.fft.rfft(w))
        out.append([w.mean(), w.std(), np.abs(w).max(),
                    np.sqrt((w**2).mean()),
                    f[1:20].sum(), f[50:100].sum(),
                    f[100:200].sum(), f[200:400].sum()])
    return np.array(out)

model = IsolationForest(contamination=0.05)
model.fit(featurize(normal_windows))

def is_anomaly(window):
    return model.predict(featurize([window]))[0] == -1
