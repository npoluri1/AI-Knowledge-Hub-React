1What an LLM Gateway Is: Unified Ingress for Model Traffic

What & why. An LLM gateway is a proxy server that sits between your application code and every LLM provider (OpenAI, Anthropic, Google, AWS Bedrock). Instead of each service embedding provider API keys and calling providers directly, all traffic routes through the gateway. This centralizes authentication, routing, observability, and policy enforcement in one place.

# Application code points to ONE endpoint
import openai

client = openai.OpenAI(
    base_url="https://gateway.internal/v1",
    api_key="virtual-key-team-alpha"
)

# The gateway handles which real provider receives the call
resp = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Summarize this report."}]
)
Where you'll use itAny organization running more than one LLM model or provider benefits from a gateway. It eliminates per-service key management and gives platform teams a single control point for all AI traffic.
Under the hoodThe gateway translates virtual keys into real provider credentials, applies routing logic, and returns the response. Your application code never sees real API keys or provider-specific quirks.

2Problems a Gateway Solves: Key Sprawl, Lock-in, No Visibility

What & why. Without a gateway, each team manages its own provider keys, costs are invisible at the org level, switching providers requires code changes, and there is no central place to enforce rate limits or audit usage. Key sprawl means dozens of API keys scattered across env files, secret managers, and developer machines.

# Without gateway: every service hard-codes provider details
# service-a/.env
OPENAI_API_KEY=sk-real-key-1
OPENAI_MODEL=gpt-4o

# service-b/.env
ANTHROPIC_API_KEY=sk-ant-real-key-2
ANTHROPIC_MODEL=claude-sonnet-4-20250514

# With gateway: all services point to one endpoint
# All services use:
GATEWAY_URL=https://gateway.internal/v1
VIRTUAL_KEY=virtual-key-team-alpha
Where you'll use itKey sprawl is the most common driver for gateway adoption. Once keys leak into logs, CI configs, or developer environments, revoking them requires chasing every copy. A gateway eliminates this attack surface.
Under the hoodThe gateway stores real provider credentials encrypted at rest. Applications receive short-lived virtual tokens scoped to specific models and budgets. Revoking a virtual key instantly cuts off access without touching provider dashboards.

3Direct Call vs. Gateway Architecture

What & why. In a direct-call architecture, each application embeds provider keys and calls provider APIs directly. In a gateway architecture, all calls flow through a proxy that owns the provider credentials. The trade-off is added network hop (typically 2-10ms) versus centralized control, auditability, and credential isolation.

# Direct call: app talks to provider
# [App] -----> [OpenAI API]
# [App] -----> [Anthropic API]
# [App] -----> [Google API]

# Gateway: app talks to gateway, gateway talks to providers
# [App] -----> [Gateway] -----> [OpenAI API]
# [App] -----> [Gateway] -----> [Anthropic API]
# [App] -----> [Gateway] -----> [Google API]

# Benefits accumulated at the gateway:
# - One place for logging, auth, rate limits, fallbacks
# - Provider credentials never leave the gateway
# - Swapping providers requires zero application changes
Where you'll use itDirect calls work for prototypes with a single provider. The gateway pattern becomes necessary when you hit two providers, two teams, or any compliance requirement for credential management.
Under the hoodThe gateway introduces a single point of failure. Production deployments must be highly available (multi-instance, health checks, graceful degradation) to avoid becoming a bottleneck.

4LiteLLM Proxy: Quickstart Configuration

What & why. LiteLLM provides an open-source proxy that exposes an OpenAI-compatible API and routes to 100+ LLM providers. A single YAML config file defines your model catalog, virtual keys, and routing rules. The proxy can run as a Python process or Docker container.

# litellm_config.yaml
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
  - model_name: claude-sonnet
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514
      api_key: os.environ/ANTHROPIC_API_KEY

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY

litellm_settings:
  drop_params: ["stop"]
  set_verbose: false
Where you'll use itLiteLLM proxy is the fastest path to a working gateway. Deploy it in under 10 minutes and immediately gain model aliasing, key management, and usage tracking across providers.
Under the hoodLiteLLM translates between provider-specific API formats (Anthropic messages, Google Gemini, Bedrock Converse) and the OpenAI chat/completions format, so your application code only needs to speak one API.

5Model Aliasing: Map Logical Names to Real Models

What & why. Model aliasing lets you define logical names (like "primary" or "fast") that map to actual provider models. When you upgrade from GPT-4o to a newer model, you update the alias in one place and all consumers pick it up. This decouples application code from specific model versions.

# LiteLLM alias config
model_list:
  - model_name: primary
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
  - model_name: primary
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514
      api_key: os.environ/ANTHROPIC_API_KEY
      api_base: https://api.anthropic.com

  - model_name: fast
    litellm_params:
      model: openai/gpt-4o-mini
      api_key: os.environ/OPENAI_API_KEY

  - model_name: cheap
    litellm_params:
      model: openai/gpt-4.1-nano-2025-04-14
      api_key: os.environ/OPENAI_API_KEY

# Application code uses aliases:
# model="primary" -> gateway routes to configured model
# model="fast" -> lightweight model for simple tasks
Where you'll use itAliasing is critical for zero-downtime model upgrades. When a new model drops, you update the alias mapping and test with a canary before shifting all traffic.
Under the hoodThe gateway maintains a model catalog with metadata (context window, pricing tier, capabilities). Alias resolution happens at request time, allowing dynamic re-routing without redeploying consumers.

6OpenAI-Compatible /chat/completions Surface

What & why. The gateway exposes a standard OpenAI-compatible /v1/chat/completions endpoint. This means any SDK, library, or tool that works with OpenAI can talk to your gateway without modification. The compatibility layer translates requests and responses between provider-specific formats.

# Any OpenAI-compatible client works with the gateway
import openai

client = openai.OpenAI(
    base_url="https://gateway.internal/v1",
    api_key="virtual-key-team-alpha"
)

# Standard OpenAI call - gateway handles provider translation
response = client.chat.completions.create(
    model="claude-sonnet",  # alias mapped by gateway
    messages=[{"role": "user", "content": "Hello"}],
    temperature=0.7,
    max_tokens=1024
)

# Streaming also works identically
stream = client.chat.completions.create(
    model="primary",
    messages=[{"role": "user", "content": "Tell me a story"}],
    stream=True
)
Where you'll use itOpenAI compatibility is the de facto standard. LangChain, LlamaIndex, CrewAI, and virtually every agent framework speaks this protocol. A gateway that implements it gets instant ecosystem compatibility.
Under the hoodThe gateway must handle subtle differences: Anthropic uses "system" as a top-level parameter (not a message role), Google uses "parts" instead of "content", and Bedrock wraps everything in a Converse API. The compatibility layer normalizes all of these.

7Virtual Keys: Per-Team Scoped Credentials

What & why. Virtual keys are gateway-issued credentials that map to a specific team, project, or environment. They carry embedded policies: which models are allowed, what budget limits apply, and what rate caps are enforced. Revoking a virtual key instantly cuts off access without touching provider dashboards.

    "max_budget": 500,
    "budget_duration": "30d",
    "rpm_limit": 100,
    "tpm_limit": 100000,
    "max_parallel_requests": 5
}

# List keys with usage data
# GET /key/info?key=sk-virtual-xxx
{
    "key": "sk-virtual-xxx",
    "metadata": {"team": "ml-research"},
    "models": ["gpt-4o", "claude-sonnet"],
    "spend": 127.43,
    "max_budget": 500

Where you'll use itVirtual keys replace the pattern of sharing a single provider key across teams. Each team gets its own key with scoped access, making cost attribution and access control trivial.
Under the hoodVirtual keys are typically JWT tokens or database-stored records with embedded policies. The gateway validates the key on every request, enforces limits, and logs usage against the key's metadata.

8Basic Fallback Chain: Provider Failover

What & why. A fallback chain defines an ordered list of providers to try if the primary fails. If OpenAI returns a 503, the gateway automatically retries on Anthropic or Google. This provides resilience against provider outages without any application-level logic.

# LiteLLM fallback configuration
model_list:
  - model_name: primary
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
  - model_name: primary
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514
      api_key: os.environ/ANTHROPIC_API_KEY

router_settings:
  routing_strategy: simple-shuffle
  num_retries: 2
  retry_after: 5
  allowed_fails: 3
  cooldown_time: 30

# When openai/gpt-4o fails, gateway tries anthropic/claude-sonnet
# automatically, transparent to the calling application
Where you'll use itFallback chains are essential for production reliability. Provider outages happen regularly; a well-configured chain keeps your application running with minimal latency impact.
Under the hoodThe gateway tracks provider health with circuit breakers. After multiple consecutive failures, a provider enters cooldown and is skipped for subsequent requests until it recovers.

10Simple Rate Limiting Per Key

What & why. Rate limiting protects both your budget and the gateway itself. Limits can be expressed as requests per minute (RPM), tokens per minute (TPM), or requests per day (RPD). When a key exceeds its limit, the gateway returns a 429 Too Many Requests with a Retry-After header.

# Virtual key with rate limits
{
    "key": "sk-virtual-key-abc",
    "models": ["primary", "fast"],
    "rpm_limit": 60,
    "tpm_limit": 90000,
    "max_budget": 200,
    "budget_duration": "30d"
}

# 429 response when limit exceeded:
# {
#   "error": {
#     "type": "rate_limit_error",
#     "message": "Rate limit reached for key sk-virtual-xxx. "
#                "Retry after 12 seconds.",
#     "param": null,
#     "code": "rate_limit_exceeded"
#   }
# }
Where you'll use itRate limits prevent runaway loops, abuse, and budget overruns. Set conservative limits for development keys and higher limits for production workloads.
Under the hoodMost gateways implement sliding-window rate limiters using Redis. The counter decrements as the window slides, providing smooth rate enforcement without the burstiness of fixed windows.

11Logging All Requests Through the Gateway

What & why. The gateway captures every request's full lifecycle: incoming payload, routing decision, provider call, response, latency, token counts, and cost. Structured logs (JSON lines) enable post-hoc analysis, debugging, and compliance auditing. Logs can be streamed to external systems for real-time monitoring.

Where you'll use itRequest logging is mandatory for compliance (SOC 2, GDPR) and essential for debugging. The gateway is the only place you get a complete picture of every LLM interaction across all services.
Under the hoodLogs are typically written to stdout as JSON lines and collected by a log shipper (Fluentd, Vector, Datadog Agent). For sensitive data, the gateway can redact message content while preserving metadata.

12When You Need a Gateway: Decision Criteria

What & why. Not every project needs a gateway. You likely need one when you hit two or more of these triggers: multiple LLM providers in use, multiple teams sharing provider accounts, compliance requirements for credential management, cost visibility needs beyond provider dashboards, or the need for fallback routing during outages.

# Decision checklist - if you answer yes to 2+, you need a gateway

checklist = {
    "multiple_providers": True,       # Using 2+ LLM providers
    "multiple_teams": True,           # 3+ teams share provider keys
    "compliance_required": False,     # SOC2 / GDPR / audit needs
    "cost_visibility": True,          # Need org-wide cost breakdown
    "need_fallback": True,            # Provider outage resilience
    "production_agents": True,        # Agents in prod serving users
    "evaluation_pipeline": False,     # Need to compare models
}

triggers = sum(checklist.values())
if triggers >= 2:
    print("Gateway recommended. Start with LiteLLM proxy.")
else:
    print("Direct provider calls are fine for now.")
    print("Revisit when you hit 2+ triggers.")
Where you'll use itTeams often add a gateway after their second provider outage or their first monthly bill surprise. The decision criteria help you time the adoption correctly without premature complexity.
Under the hoodMost organizations adopt a gateway between 2-5 LLM models in production. Earlier adoption (prototyping) adds unnecessary latency. Later adoption means retrofitting key management across existing services.

13Routing Policies: Cheapest-First and Latency-Based

What & why. Routing policies determine which provider or model handles a request. Cheapest-first routes to the lowest-cost model that satisfies the task. Latency-based routing selects the provider with the fastest response time. These policies can be combined with weighted round-robin for gradual traffic shifts.

# LiteLLM routing strategies
router_settings:
  routing_strategy: latency-based-routing
  num_retries: 2
  allowed_fails: 3
  cooldown_time: 30

model_list:
  - model_name: smart
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY
  - model_name: smart
    litellm_params:
      model: anthropic/claude-sonnet-4-20250514
      api_key: os.environ/ANTHROPIC_API_KEY

# latency-based: gateway pings providers, routes to fastest
# cheapest-first: gateway uses pricing table, routes to lowest cost
# usage-based: routes based on current provider utilization
Where you'll use itLatency-based routing is critical for real-time applications (chat, voice). Cheapest-first is ideal for batch workloads and background tasks where cost optimization matters more than speed.
Under the hoodThe gateway maintains a latency heatmap per provider, updated with each request's response time. Routing decisions use a sliding window average (typically 30-60 seconds) to smooth out transient spikes.

14Retries with Provider Failover

What & why. Retries handle transient failures: rate limits (429), server errors (500/503), and timeouts. The gateway implements exponential backoff with jitter, retries on the same provider first, then fails over to the next provider in the chain. This is transparent to the calling application.

# Retry configuration in LiteLLM router
router_settings:
  num_retries: 3
  retry_after: 5           # seconds between retries
  allowed_fails: 3         # circuit breaker threshold
  cooldown_time: 60        # seconds to skip failed provider

# Retry behavior:
# Attempt 1: openai/gpt-4o -> 429 rate limited
# Wait 5s
# Attempt 2: openai/gpt-4o -> 429 rate limited
# Wait 10s (exponential backoff)
# Attempt 3: openai/gpt-4o -> 500 server error
# Failover: anthropic/claude-sonnet -> success

# Status code routing
retry_status_codes = [408, 429, 500, 502, 503, 504]
Where you'll use itTransient failures are common. A well-tuned retry policy eliminates 95% of user-visible errors. Without retries, every provider hiccup becomes a user-facing failure.
Under the hoodJitter prevents thundering herd when multiple clients retry simultaneously. The gateway tracks failure rates per provider and automatically opens circuit breakers when failure rates exceed thresholds.

15Budgets and Quota Enforcement Per Key

What & why. Budgets cap spending per virtual key over a time period. Quotas limit the number of requests or tokens. The gateway enforces these limits at request time, rejecting calls that would exceed the budget. This prevents runaway costs from loops, bugs, or abuse.

Under the hoodBudget tracking uses a token bucket or sliding window counter in Redis. The gateway updates the counter after each request completes (using actual token counts), not before (which would be speculative).

16Semantic Router: Intent-to-Model Mapping

What & why. A semantic router analyzes the user's input and selects the most appropriate model based on task complexity. Simple questions go to fast/cheap models, complex reasoning goes to powerful/expensive models. This optimizes cost without sacrificing quality where it matters.

from sentence_transformers import SentenceTransformer
import numpy as np

# Define route examples for each model tier
routes = {
    "fast": [
        "What is 2+2?", "Convert 100 USD to SGD",
        "What time is it in Tokyo?", "Define machine learning"
    ],
    "standard": [
        "Summarize this article about climate change",
        "Explain how transformers work in NLP",
        "Write a Python function for data validation"
    ],
    "powerful": [
        "Analyze the ethical implications of this policy",
        "Design a distributed system architecture",
        "Debug this complex multi-threaded race condition"
    ]
}

model = SentenceTransformer("all-MiniLM-L6-v2")
route_embeddings = {k: model.encode(v) for k, v in routes.items()}

def select_model(user_query: str) -> str:
    query_emb = model.encode([user_query])[0]
    best_route, best_score = "standard", -1
    for route_name, embeddings in route_embeddings.items():
        similarity = max(np.dot(query_emb, e) for e in embeddings)
        if similarity > best_score:
            best_route, best_score = route_name, similarity
    return {"fast": "fast", "standard": "primary", "powerful": "smart"}[best_route]
Where you'll use itSemantic routing can reduce costs by 60-80% for workloads with many simple queries. It's most effective when task complexity varies widely within a single application.
Under the hoodThe router uses embedding similarity between the query and route examples. More examples per route improve accuracy. The classification adds ~5ms latency (one small embedding call).

17Caching: Identical Prompts and Prefix Caching

What & why. Caching stores responses for repeated identical prompts, avoiding redundant provider calls. Prefix caching (supported by OpenAI, Anthropic, and Google) caches the KV cache for prompt prefixes, reducing latency and cost for requests that share common system prompts or context.

# LiteLLM caching configuration
litellm_settings:
  cache: true
  cache_params:
    type: "redis"
    host: "redis.internal"
    port: 6379
    ttl: 3600           # cache for 1 hour
    suffix: "litellm"

# Cache behavior:
# Request 1: "Summarize this 10-page report" -> cache MISS, call provider
# Request 2: "Summarize this 10-page report" -> cache HIT, return stored

# Prefix caching (provider-side):
# Long system prompt + short user query
# Provider caches the system prompt KV cache
# Subsequent requests reuse cached prefix
# OpenAI: automatic for prompts > 1024 tokens
# Anthropic: prompt_caching=True on messages
Where you'll use itCaching is highest-impact for repeated system prompts and identical user queries. Agent loops with fixed system instructions benefit greatly from prefix caching, reducing both latency and token costs.
Under the hoodRedis-backed caching uses content hashing for cache keys. Non-deterministic outputs (temperature > 0) should only cache based on the prompt hash. Provider-side prefix caching is transparent and managed by the provider's infrastructure.

18Streaming Passthrough: SSE Relay

What & why. The gateway must relay streaming responses (Server-Sent Events) without buffering. Each token chunk flows through the gateway to the client in real time. The gateway can still log token counts and costs even for streaming responses by accumulating usage data from the final chunk.

# Gateway streaming passthrough
import httpx

async def stream_with_gateway(query: str):
    async with httpx.AsyncClient() as client:
        async with client.stream(
            "POST",
            "https://gateway.internal/v1/chat/completions",
            json={
                "model": "primary",
                "messages": [{"role": "user", "content": query}],
                "stream": True
            },
            headers={"Authorization": "Bearer sk-virtual-key-xxx"}
        ) as resp:
            async for line in resp.aiter_lines():
                if line.startswith("data: "):
                    chunk = line[6:]
                    if chunk == "[DONE]":
                        yield chunk
                        break
                    # Each chunk relayed in real time
                    yield f"data: {chunk}\n\n"

# Usage logging happens after stream completes
# Gateway accumulates token counts from final usage chunk
Where you'll use itStreaming is required for responsive chat interfaces. The gateway must not add latency to individual chunks, which means no buffering. Each chunk should pass through within 1-2ms.
Under the hoodThe gateway opens a streaming connection to the provider and a streaming connection to the client, piping bytes between them. Usage data is extracted from the final [DONE] chunk's usage field when available.

19Authentication: API Keys and JWT for Agents

What & why. The gateway authenticates callers using virtual API keys or JWT tokens. API keys are simpler; JWTs carry embedded policies (allowed models, budget, expiry) and don't require a lookup on every request. For machine-to-machine agent communication, JWTs with short TTLs provide better security.

# Virtual API key (simple auth)
curl -H "Authorization: Bearer sk-virtual-key-xxx" \
  https://gateway.internal/v1/chat/completions

# JWT token (richer, self-contained)
import jwt, time

payload = {
    "sub": "agent-orchestrator",
    "team": "ml-platform",
    "models": ["primary", "fast"],
    "max_cost": 50,
    "iat": int(time.time()),
    "exp": int(time.time()) + 3600  # 1 hour TTL
}
token = jwt.encode(payload, gateway_secret, algorithm="HS256")

# Gateway validates JWT on every request:
# 1. Check signature
# 2. Check expiry
# 3. Extract policies from claims
# 4. Enforce model allowlist and budget
Where you'll use itJWT tokens are preferred for agent-to-agent communication because they're self-contained and short-lived. API keys work well for human-developed services with longer lifecycles.
Under the hoodJWT validation adds ~1ms overhead per request. The gateway caches validation results for the token's TTL to avoid repeated signature verification.

PII_PATTERNS = {
    "email": r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b",
    "phone": r"\b(?:\+65\s?)?\d{4}\s?\d{4}\b",

def scrub_pii(text: str) -> tuple[str, list[str]]:
    """Redact PII from text, return scrubbed text and list of redacted types."""

            redacted.append(pii_type)
    return text, redacted

26Circuit Breakers and Provider Health Checks

What & why. Circuit breakers prevent the gateway from repeatedly calling a failing provider. After a threshold of consecutive failures, the circuit opens and all requests are routed elsewhere. Periodic health checks detect when the provider recovers. This prevents cascading failures and reduces latency during outages.

import time
from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"      # Normal operation
    OPEN = "open"          # Failing, skip this provider
    HALF_OPEN = "half_open" # Testing recovery

class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=60):
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.last_failure_time = 0

    def record_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = CircuitState.OPEN

    def record_success(self):
        self.failure_count = 0
        self.state = CircuitState.CLOSED

    def should_allow(self) -> bool:
        if self.state == CircuitState.CLOSED:
            return True
        if self.state == CircuitState.OPEN:
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = CircuitState.HALF_OPEN
                return True  # Allow one test request
            return False
        return True  # HALF_OPEN: allow test request
Where you'll use itCircuit breakers are essential for multi-provider setups. Without them, a failing provider causes cascading timeouts as every request waits for a provider that will never respond.
Under the hoodThe circuit breaker uses a state machine: CLOSED (normal), OPEN (failing), HALF_OPEN (testing recovery). The half-open state allows a single test request to verify the provider has recovered before resuming traffic.

27Request Hedging for Tail-Latency Mitigation

What & why. Request hedging sends the same request to multiple providers simultaneously and uses the first complete response. This eliminates tail-latency outliers caused by slow GC pauses, network jitter, or provider queuing. The extra cost is offset by consistently low latency.

  enable_request_hedging: true
  hedge_latency_threshold_ms: 3000
  # If first response takes > 3s, send to backup provider
  # Use whichever response arrives first

import asyncio, time

async def hedged_request(query: str, providers: list):
    """Send to multiple providers, return first complete response."""
    async def call_with_timeout(provider, timeout):
        start = time.time()
        try:
            result = await provider.complete(query)
            return result, time.time() - start
        except Exception:
            return None, time.time() - start

    # Send to primary and backup simultaneously
    tasks = [call_with_timeout(p, 5) for p in providers[:2]]
    done, pending = await asyncio.wait(
        tasks, timeout=5, return_when=asyncio.FIRST_COMPLETED
    )

    for task in pending:
        task.cancel()

    return done.pop().result()
Where you'll use itHedging is used by latency-sensitive applications (real-time chat, voice agents) where P99 latency matters more than cost. It typically adds 30-50% cost but eliminates tail-latency spikes.
Under the hoodThe gateway sends identical requests to 2-3 providers concurrently. The first response wins; others are discarded. This is effective because provider latency distributions have long tails caused by queuing, GC, and network issues.

40Key Vault and HSM Integration for Secret Rotation

What & why. Provider API keys must never be stored in plaintext configuration files. The gateway integrates with a key vault (AWS Secrets Manager, Azure Key Vault, HashiCorp Vault) for secure storage and automatic rotation. HSM (Hardware Security Module) integration provides FIPS 140-2 compliant key protection.

# AWS Secrets Manager integration
import boto3
import json

class KeyVault:
    def __init__(self):
        self.client = boto3.client("secretsmanager")
        self.cache = {}

    def get_provider_key(self, provider: str) -> str:
        if provider in self.cache:
            return self.cache[provider]

        secret = self.client.get_secret_value(
            SecretId=f"gateway/providers/{provider}/api-key"
        )
        key = json.loads(secret["SecretString"])["api_key"]
        self.cache[provider] = key
        return key

    def rotate_key(self, provider: str, new_key: str):
        """Update key in vault and refresh cache."""
        self.client.update_secret(
            SecretId=f"gateway/providers/{provider}/api-key",
            SecretString=json.dumps({"api_key": new_key})
        )
        self.cache.pop(provider, None)

# Automatic rotation schedule:
# - Rotate provider keys every 90 days
# - Gateway fetches new keys on TTL expiry
# - Zero-downtime rotation: old and new keys both valid during transition
Where you'll use itKey vault integration eliminates hardcoded secrets. Automatic rotation reduces operational burden and limits the blast radius of key compromise.
Under the hoodSecrets are fetched on startup and cached in memory with a TTL. On cache miss or expiry, the gateway re-fetches from the vault. HSM-backed keys never leave the hardware boundary.

42FinOps Unit Economics: Per-Feature Team Costs

# Per-feature cost tracking
class FeatureCostTracker:
    def __init__(self):
        self.feature_costs = defaultdict(list)

    def track(self, feature: str, cost: float, tokens: int, latency: int):
        self.feature_costs[feature].append({
            "cost": cost,
            "tokens": tokens,
            "latency_ms": latency,
            "timestamp": time.time()
        })

    def report(self, feature: str) -> dict:
        records = self.feature_costs[feature]
        costs = [r["cost"] for r in records]
        return {
            "feature": feature,
            "total_calls": len(records),
            "total_cost_usd": sum(costs),
            "avg_cost_per_call": statistics.mean(costs),
            "p95_latency_ms": sorted([r["latency_ms"] for r in records])[int(len(records) * 0.95)],
            "cost_per_1k_calls": statistics.mean(costs) * 1000
        }
