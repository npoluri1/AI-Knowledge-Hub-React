LlamaIndex — Data Framework for LLMs

A specialized framework for connecting LLMs with external data through structured indexing, retrieval, and query engines, purpose-built for RAG and data-augmented applications.

Part I · FoundationsTier 1 — Framework purpose, core model, indexing, query, persistence

1Framework Purpose vs Raw Code

What & why. LlamaIndex provides structured abstractions (Document, Node, Index, QueryEngine) that eliminate the boilerplate of building RAG systems from scratch. While raw OpenAI + ChromaDB code works for simple cases, LlamaIndex adds automatic chunking, metadata extraction, multi-index routing, and evaluation hooks that become essential as complexity grows.

# Raw RAG: ~30 lines of manual orchestration
# LlamaIndex: ~5 lines with the same functionality
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

# Load documents from a directory
documents = SimpleDirectoryReader("./data").load_data()

# Build vector index (handles chunking, embedding, storage automatically)
index = VectorStoreIndex.from_documents(documents)

# Query the index
query_engine = index.as_query_engine()
response = query_engine.query("What is the refund policy?")
print(response)
print(f"Sources: {[n.metadata for n in response.source_nodes]}")
Where you'll use itLlamaIndex is the default choice when your application is primarily about querying data: knowledge bases, document search, data analysis chatbots, and any system where the core value is connecting LLMs to structured or unstructured data.
Under the hoodLlamaIndex's simplicity hides a sophisticated pipeline: documents are parsed into Nodes (chunks with metadata and relationships), embedded with a configurable model, stored in a configurable backend, and retrieved via configurable similarity search with automatic prompt construction.

2Document and Node Model

What & why. LlamaIndex models data as Documents (raw source files with metadata) and Nodes (chunked pieces with relationships to other Nodes). Documents are the input; Nodes are the indexed units. Each Node carries metadata, a reference to its source Document, and relationships (next, previous, parent, child) that enable traversal and context assembly.

from llama_index.core import Document

# Create a Document directly
doc = Document(
    text="The refund policy allows returns within 30 days of purchase.",
    metadata={"source": "policy.pdf", "page": 1, "department": "legal"},
    id_="policy_doc_1",
)

# Documents get split into Nodes during indexing
# Each Node inherits metadata and adds positional info
# Node.text = chunk of the document text
# Node.metadata = parent document metadata + chunk info
# Node.relationships = {NEXT: node_2, PREVIOUS: None, SOURCE: doc}

print(f"Document: {doc.id_}, text length: {len(doc.text)}")
print(f"Metadata: {doc.metadata}")
Where you'll use itThe Document/Node model is the foundation of all LlamaIndex operations. Understanding it is essential for custom metadata handling, relationship traversal, and building multi-document architectures.
Under the hoodDocuments and Nodes are Pydantic models with built-in serialization, embedding storage, and hash-based deduplication. The relationship graph enables parent-child retrieval (small-to-big) and sibling traversal (getting surrounding context).

3SimpleDirectoryReader: Loading Documents

What & why. SimpleDirectoryReader is the quickest way to load documents from a local directory. It auto-detects file types (PDF, TXT, Markdown, DOCX) and delegates to appropriate parsers. For custom file types or remote sources, use the 160+ data connectors available through LlamaHub.

from llama_index.core import SimpleDirectoryReader

# Load all files from a directory
documents = SimpleDirectoryReader("./knowledge_base").load_data()
print(f"Loaded {len(documents)} documents")

# Filter by file type
pdf_docs = SimpleDirectoryReader(
    "./docs",
    required_exts=[".pdf", ".txt"],
).load_data()

# Load with metadata extraction
docs = SimpleDirectoryReader(
    "./docs",
    recursive=True,
    exclude=["**/temp/*", "**/.git/*"],
).load_data()

# Each document has auto-extracted metadata
for doc in docs[:3]:
    print(f"File: {doc.metadata.get('file_name', 'unknown')}, "
          f"Size: {len(doc.text)} chars")
Where you'll use itSimpleDirectoryReader covers 90% of document loading needs for prototypes. For production systems with remote sources (S3, GCS, Confluence, Notion), use LlamaHub readers instead.
Under the hoodSimpleDirectoryReader uses a registry of file-type handlers: PdfReader for PDFs, DocxReader for DOCX, MarkdownReader for Markdown. Each handler extracts text and metadata, returning Document objects ready for indexing.

4VectorStoreIndex Creation

What & why. VectorStoreIndex is the most common index type in LlamaIndex. It chunks documents, embeds each chunk, and stores them in a vector store for similarity search. The index handles chunking strategy, embedding model selection, and storage backend configuration through a single creation call.

from llama_index.core import VectorStoreIndex, Settings
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding

# Configure global settings
Settings.llm = OpenAI(model="gpt-4o", temperature=0)
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")

# Create index from documents
documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(
    documents,
    chunk_size=600,
    chunk_overlap=60,
    show_progress=True,
)

# The index is now ready for querying
print(f"Index contains {len(index.docstore.data)} nodes")
Where you'll use itVectorStoreIndex is the default starting point for any LlamaIndex application. It handles the full ingest-chunk-embed-store pipeline with sensible defaults that can be customized at every step.
Under the hoodVectorStoreIndex uses an IngestionPipeline that runs documents through a text splitter, embeds each node with the configured embedding model, and upserts into the configured vector store (default: in-memory SimpleVectorStore).

5query_engine.query Flow

What & why. The query engine is LlamaIndex's primary retrieval-and-generation interface. Calling query_engine.query() executes the full pipeline: embed the query, retrieve top-k similar nodes, assemble them into a prompt with a template, send to the LLM, and return a structured Response object with the answer and source nodes.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(documents)
query_engine = index.as_query_engine(similarity_top_k=5)

# Execute a query
response = query_engine.query("What are the payment methods?")

# Response object contains:
print(f"Answer: {response.response}")         # The generated text
print(f"Sources: {len(response.source_nodes)}")  # Number of source nodes
for node in response.source_nodes:
    print(f"  Score: {node.score:.3f} | {node.text[:80]}...")

# The response object is also a string
print(str(response))
Where you'll use itquery_engine.query() is the entry point for every user-facing interaction. Understanding the Response object is essential for building citation tracking, feedback loops, and debugging tools.
Under the hoodThe query flow: (1) embed query, (2) similarity search in vector store returning top-k Nodes, (3) format nodes into a context string using the template, (4) send context + query to LLM, (5) parse LLM output into Response with source_node tracking for citations.

6storage_context Persistence

What & why. LlamaIndex indexes must be persisted to disk or a database for production use. The storage_context manages serialization of the index, document store, and vector store. Persisting avoids re-ingesting and re-embedding documents on every application restart, reducing startup time from minutes to seconds.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, StorageContext
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.vector_stores.chroma import ChromaVectorStore
import chromadb

# Create index with ChromaDB persistence
chroma_client = chromadb.PersistentClient(path="./chroma_db")
chroma_collection = chroma_client.get_or_create_collection("my_docs")
vector_store = ChromaVectorStore(chroma_collection=chroma_collection)

storage_context = StorageContext.from_defaults(vector_store=vector_store)
documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(documents, storage_context=storage_context)

# Persist to disk
index.storage_context.persist(persist_dir="./index_storage")

# Reload from disk (no re-embedding needed)
from llama_index.core import load_index_from_storage
storage_context = StorageContext.from_defaults(persist_dir="./index_storage")
index = load_index_from_storage(storage_context)
query_engine = index.as_query_engine()
Where you'll use itPersistent storage is essential for production. Always persist your index after building, and reload it on application startup. ChromaDB and Qdrant provide persistent backends that survive process restarts.
Under the hoodThe storage_context serializes three components: the docstore (Node objects), the vector_store (embeddings + metadata), and the index_store (index configuration). Each can be backed by different storage backends.

7Settings Global Configuration

What & why. LlamaIndex uses a global Settings object to configure the LLM, embedding model, chunk size, and other defaults across all components. Setting these once ensures consistent behavior throughout your application without passing configuration to every component.

from llama_index.core import Settings
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding

# Configure once, use everywhere
Settings.llm = OpenAI(model="gpt-4o", temperature=0, max_tokens=2048)
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")
Settings.chunk_size = 600
Settings.chunk_overlap = 60
Settings.chunk_window_size = 1  # number of surrounding chunks to include

# All subsequent index creation and querying uses these defaults
documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(documents)
query_engine = index.as_query_engine()  # uses Settings.llm and Settings.embed_model

# Override per-component when needed
custom_llm = OpenAI(model="gpt-4o-mini", temperature=0.5)
local_query_engine = index.as_query_engine(llm=custom_llm)
Where you'll use itSettings configuration is the first step in any LlamaIndex application. Set it early to avoid inconsistent behavior between index creation and querying.
Under the hoodSettings is a Pydantic model with global scope. Components that accept an llm or embed_model parameter override the global setting. This pattern enables per-component customization while maintaining application-wide defaults.

8Response Object and Source Nodes

What & why. Every query returns a Response object containing the generated text, the source Nodes used, their similarity scores, and metadata. The source_nodes list enables citation tracking, answer verification, and debugging. Each Node includes the original text chunk, its metadata, and the retrieval score.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(documents)
response = index.as_query_engine().query("How do I contact support?")

# Inspect the Response object
print(f"Answer type: {type(response.response)}")
print(f"Answer length: {len(response.response)} chars")
print(f"Source nodes: {len(response.source_nodes)}")

# Examine each source node
for i, node in enumerate(response.source_nodes):
    print(f"\n--- Source {i+1} ---")
    print(f"Score: {node.score:.4f}")
    print(f"Text: {node.text[:150]}...")
    print(f"Metadata: {node.metadata}")
    print(f"Node ID: {node.node_id}")

# The response also stores the query
print(f"\nOriginal query: {response.query}")
Where you'll use itSource node inspection is essential for building citation UIs, debugging retrieval quality, and implementing feedback loops. Always log source_nodes alongside the answer for production observability.
Under the hoodSource nodes are populated during the retrieve step. The score represents cosine similarity between the query embedding and the node embedding. Higher scores indicate stronger semantic matches, though score distributions vary by embedding model.

9chunk_size and chunk_overlap Settings

What & why. LlamaIndex's chunk_size and chunk_overlap parameters control how documents are split into Nodes during indexing. chunk_size sets the maximum token count per Node. chunk_overlap creates overlapping context between adjacent Nodes to prevent information loss at boundaries. These are the most impactful parameters for retrieval quality.

from llama_index.core import Settings

# Default: 1024 tokens, 200 overlap
Settings.chunk_size = 1024
Settings.chunk_overlap = 200

# For precise retrieval: smaller chunks
Settings.chunk_size = 400
Settings.chunk_overlap = 40

# For context-rich retrieval: larger chunks
Settings.chunk_size = 1200
Settings.chunk_overlap = 120

# Override per-index when different documents need different sizes
from llama_index.core import VectorStoreIndex
from llama_index.core.node_parser import SentenceSplitter

# Custom splitter for this specific index
splitter = SentenceSplitter(chunk_size=500, chunk_overlap=50)
index = VectorStoreIndex.from_documents(
    documents,
    transformations=[splitter],
)

# Compare chunk counts
Settings.chunk_size = 300
index_small = VectorStoreIndex.from_documents(docs)
Settings.chunk_size = 1000
index_large = VectorStoreIndex.from_documents(docs)
print(f"Small chunks: {len(index_small.docstore.data)}")
print(f"Large chunks: {len(index_large.docstore.data)}")
Where you'll use itChunk size tuning is the highest-leverage optimization in LlamaIndex. Start with 600 tokens and adjust based on retrieval quality experiments.
Under the hoodLlamaIndex's default splitter is SentenceSplitter, which tries to split at sentence boundaries while respecting the chunk_size limit. This produces semantically coherent chunks that are better for retrieval than arbitrary word-boundary splits.

10Quickstart: Full Mini Application

What & why. A complete LlamaIndex application in under 20 lines: configure settings, load documents, build a vector index, and query it. This demonstrates the full workflow from data ingestion to answer generation with source attribution.

from llama_index.core import (
    VectorStoreIndex, SimpleDirectoryReader, Settings
)
from llama_index.llms.openai import OpenAI
from llama_index.embeddings.openai import OpenAIEmbedding

# Configure
Settings.llm = OpenAI(model="gpt-4o", temperature=0)
Settings.embed_model = OpenAIEmbedding(model="text-embedding-3-small")
Settings.chunk_size = 600

# Load
documents = SimpleDirectoryReader("./data").load_data()
print(f"Loaded {len(documents)} documents")

# Index
index = VectorStoreIndex.from_documents(documents, show_progress=True)

# Query
engine = index.as_query_engine(similarity_top_k=5)
response = engine.query("What is the main topic of these documents?")
print(f"\nAnswer: {response.response}")
for node in response.source_nodes:
    print(f"  [{node.score:.3f}] {node.text[:100]}...")
Where you'll use itThis mini application is the starting point for every LlamaIndex project. Copy it, point it at your data directory, and you have a working RAG system in seconds.
Under the hoodUnder the hood, these 5 lines execute: file discovery, PDF/TXT/MD parsing, sentence splitting, OpenAI embedding API calls (batched), vector store creation, query embedding, similarity search, prompt construction, and LLM generation.

11When to Choose LlamaIndex

What & why. LlamaIndex excels when your application's primary function is querying data: document search, knowledge base Q&A, data analysis chatbots. Choose it over raw code when you need multiple index types, metadata extraction, or evaluation. Choose LangChain when you need broader orchestration (agents, chains, tools) beyond data querying.

# Decision framework for LLM app frameworks

# Choose LlamaIndex when:
# - Core task is querying documents/data
# - You need multiple index types (vector, summary, knowledge graph)
# - You want built-in evaluation (faithfulness, relevancy)
# - You need sophisticated data connectors (160+ readers)
# - Your app is primarily RAG with minimal orchestration

# Choose raw code when:
# - Simple single-document Q&A
# - You need maximum control over every step
# - Minimal dependencies are critical

# Example: LlamaIndex shines for multi-source routing
from llama_index.core import VectorStoreIndex
from llama_index.core.query_engine import RouterQueryEngine
from llama_index.core.selectors import PydanticSingleSelector

# Build indices for different document types
policy_index = VectorStoreIndex.from_documents(load_policies())
technical_index = VectorStoreIndex.from_documents(load_docs())
faq_index = VectorStoreIndex.from_documents(load_faqs())

# Router automatically selects the right index per query
router = RouterQueryEngine(
    selector=PydanticSingleSelector.from_defaults(
        query_tools=[
            QueryTool(description="Policies", query_engine=policy_index.as_query_engine()),
            QueryTool(description="Technical docs", query_engine=technical_index.as_query_engine()),
            QueryTool(description="FAQs", query_engine=faq_index.as_query_engine()),
        ]
    )
)
Where you'll use itLlamaIndex is the right choice for data-centric applications where the value comes from connecting LLMs to diverse data sources with sophisticated retrieval strategies.
Under the hoodLlamaIndex's specialization in data querying means its abstractions (Index, Retriever, QueryEngine) are more deeply optimized for this use case than general-purpose frameworks. The 160+ data connectors and multiple index types provide capabilities that take significant effort to build from scratch.

14Text Splitters: SentenceSplitter and TokenTextSplitter

What & why. LlamaIndex provides multiple text splitter implementations. SentenceSplitter splits at sentence boundaries while respecting the token limit, producing semantically coherent chunks. TokenTextSplitter works at the token level for precise size control. The choice affects retrieval quality because sentence boundaries align with semantic units.

from llama_index.core.node_parser import SentenceSplitter, TokenTextSplitter
from llama_index.core import Document

doc = Document(text="FastAPI is a modern Python web framework. It provides automatic API documentation. Django is another popular framework. It includes an ORM and admin panel. React is a JavaScript library for building user interfaces. It uses a virtual DOM for efficient updates.")

# SentenceSplitter: respects sentence boundaries
sentence_splitter = SentenceSplitter(chunk_size=50, chunk_overlap=10)
sentence_nodes = sentence_splitter.get_nodes_from_documents([doc])
for node in sentence_nodes:
    print(f"SentenceSplitter: '{node.text[:80]}'")

# TokenTextSplitter: precise token-level splitting
token_splitter = TokenTextSplitter(chunk_size=30, chunk_overlap=5)
token_nodes = token_splitter.get_nodes_from_documents([doc])
for node in token_nodes:
    print(f"TokenSplitter: '{node.text[:80]}'")

# Custom splitter with Markdown awareness
from llama_index.core.node_parser import MarkdownNodeParser
# markdown_parser = MarkdownNodeParser()
# md_nodes = markdown_parser.get_nodes_from_documents([markdown_doc])
Where you'll use itSentenceSplitter is the default for most use cases. Use TokenTextSplitter when you need precise token counts (e.g., staying under strict API limits). MarkdownNodeParser preserves document structure for Markdown-heavy corpora.
Under the hoodSentenceSplitter uses a tokenizer to count tokens and a sentence boundary detector (period, newline) to find optimal split points. It will split mid-sentence only when a single sentence exceeds the chunk_size limit.

15MetadataExtractors: Auto-Summarization

What & why. LlamaIndex's MetadataExtractor nodes automatically enrich chunks with LLM-generated metadata: summaries, keywords, questions, and entity extraction. This enriched metadata improves retrieval by providing additional semantic signals and enables metadata-based filtering and citation enhancement.

from llama_index.core.extractors import (
    SummaryExtractor, QuestionsAnsweredExtractor, TitleExtractor
)
from llama_index.core.ingestion import IngestionPipeline

# Define metadata extraction pipeline
extractors = [
    SummaryExtractor(summaries=["self"]),
    QuestionsAnsweredExtractor(questions=3),
    TitleExtractor(),
]

pipeline = IngestionPipeline(transformations=[
    SentenceSplitter(chunk_size=600, chunk_overlap=60),
    *extractors,
])

# Process documents
documents = SimpleDirectoryReader("./data").load_data()
nodes = pipeline.run(documents=documents, show_progress=True)

# Each node now has enriched metadata
for node in nodes[:2]:
    print(f"Title: {node.metadata.get('document_title')}")
    print(f"Summary: {node.metadata.get('section_summary', '')[:100]}")
    print(f"Questions: {node.metadata.get('questions_this_excerpt_can_answer')}")
    print()
Where you'll use itMetadata extraction improves retrieval quality for complex documents. Summaries enable summary-based retrieval, and generated questions match user query formulations that differ from the document text.
Under the hoodEach extractor makes an LLM call per Node to generate the metadata. The QuestionsAnsweredExtractor generates questions that the chunk answers, creating semantic anchors that improve retrieval for diverse query formulations.

16Multiple Index Types: Summary, Tree, KG

What & why. LlamaIndex supports multiple index types beyond vectors: SummaryIndex concatenates all nodes for comprehensive summarization. TreeIndex builds a hierarchical tree of summaries for multi-level aggregation. KnowledgeGraphIndex extracts entities and relationships for graph-based queries. Each type excels at different query patterns.

from llama_index.core import (
    VectorStoreIndex, SummaryIndex, TreeIndex, KnowledgeGraphIndex,
    SimpleDirectoryReader
)

documents = SimpleDirectoryReader("./data").load_data()

# VectorStoreIndex: semantic similarity search
vector_index = VectorStoreIndex.from_documents(documents)

# SummaryIndex: concatenates all nodes, good for "summarize all"
summary_index = SummaryIndex.from_documents(documents)
summary_engine = summary_index.as_query_engine()
response = summary_engine.query("Give me a comprehensive summary")
print(f"Summary: {response.response[:200]}")

# TreeIndex: hierarchical summarization
tree_index = TreeIndex.from_documents(documents)
tree_engine = tree_index.as_query_engine()
response = tree_engine.query("What are the main themes?")

# KnowledgeGraphIndex: entity-relationship queries
kg_index = KnowledgeGraphIndex.from_documents(documents)
kg_engine = kg_index.as_query_engine()
response = kg_engine.query("What entities are related to revenue?")
Where you'll use itDifferent query types need different index types. Use VectorStore for specific fact retrieval, SummaryIndex for overviews, TreeIndex for hierarchical questions, and KnowledgeGraphIndex for relationship queries.
Under the hoodSummaryIndex inserts a "summary" prompt at the start that instructs the LLM to synthesize all nodes. TreeIndex builds a tree bottom-up by summarizing node groups, then traverses the tree at query time. KnowledgeGraphIndex uses LLM-based entity extraction to build a graph stored in a triples format.

17Retrievers API and similarity_top_k

What & why. Retrievers are the retrieval layer between the index and the query engine. They control how many nodes to fetch (similarity_top_k), apply filters, and optionally rerank results. The Retriever API is decoupled from the QueryEngine, enabling custom retrieval strategies without reimplementing generation.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(documents)

# Default retriever with top-k
retriever = index.as_retriever(similarity_top_k=10)
nodes = retriever.retrieve("What is the refund policy?")
print(f"Retrieved {len(nodes)} nodes")

for node in nodes:
    print(f"  [{node.score:.3f}] {node.text[:80]}...")

# Vector index retriever with metadata filter
from llama_index.core.vector_stores import MetadataFilters, MetadataFilter
filters = MetadataFilters(filters=[
    MetadataFilter(key="department", value="engineering"),
])
filtered_retriever = index.as_retriever(
    similarity_top_k=5,
    filters=filters,
)
filtered_nodes = filtered_retriever.retrieve("deployment process")
print(f"Filtered: {len(filtered_nodes)} nodes")
Where you'll use itRetrievers enable fine-grained control over the retrieval step. Use metadata filters for multi-tenant or departmental scoping. Use similarity_top_k tuning to balance recall against context window limits.
Under the hoodThe VectorIndexRetriever embeds the query, performs similarity search in the vector store, and returns the top-k Nodes with scores. Metadata filtering happens at the vector store level before similarity search, reducing the search space.

18NodePostprocessor: Reranking and Filtering

What & why. NodePostprocessors transform retrieved nodes after the initial similarity search but before they are passed to the LLM. Common postprocessors include reranking (cross-encoder), keyword filtering, and score threshold filtering. They improve precision by refining the initial retrieval results.

from llama_index.core.postprocessor import SimilarityPostprocessor, KeywordNodePostprocessor
from llama_index.postprocessor.cohere_rerank import CohereRerank
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

documents = SimpleDirectoryReader("./data").load_data()
index = VectorStoreIndex.from_documents(documents)

# Score threshold: only keep nodes above a minimum similarity
score_filter = SimilarityPostprocessor(similarity_cutoff=0.7)

# Keyword filter: require or exclude specific keywords
keyword_filter = KeywordNodePostprocessor(
    required_keywords=["Python", "API"],
    exclude_keywords=["deprecated", "legacy"],
)

# Cross-encoder reranking (Cohere)
reranker = CohereRerank(model="rerank-v3.5", top_n=5)

# Chain postprocessors on the query engine
query_engine = index.as_query_engine(
    similarity_top_k=20,
    node_postprocessors=[score_filter, keyword_filter, reranker],
)

response = query_engine.query("FastAPI middleware patterns")
print(f"Answer: {response.response[:200]}")
Where you'll use itNodePostprocessors are the production refinement layer. Start with a wide retrieval (top_k=20), then apply reranking and filtering to select the best 3-5 nodes for the LLM.
Under the hoodPostprocessors run in sequence: the output of one is the input to the next. Score filtering removes low-quality matches, keyword filtering ensures topical relevance, and reranking reorders by cross-encoder relevance score.

What & why. RouterQueryEngine automatically selects the best data source for each query. Given multiple indices (different departments, document types, or data sources), the router analyzes the query and routes it to the most relevant index, avoiding the need for the user to specify which source to search.

Under the hoodThe router uses the LLM to analyze the query against tool descriptions, selecting the best match. It then delegates retrieval and generation to the selected index, returning a unified Response object regardless of the underlying source.

20SubQuestionQueryEngine for Query Decomposition

What & why. Complex questions often require information from multiple documents or sub-queries. SubQuestionQueryEngine decomposes a complex question into simpler sub-queries, executes each against the appropriate data source, and synthesizes the results into a comprehensive answer. This handles multi-hop reasoning without explicit agent loops.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.query_engine import SubQuestionQueryEngine
from llama_index.core.tools import QueryTool

    SimpleDirectoryReader("./reviews").load_data()

        description="Product specifications, pricing, features",
    ),
    QueryTool.from_defaults(
        query_engine=reviews.as_query_engine(),

Under the hoodThe engine uses the LLM to decompose the query into sub-questions, determines which tool answers each sub-question, executes them in dependency order, and synthesizes the sub-answers into a final response. It handles up to 3 levels of decomposition.

21ChatEngine with Condense and React Modes

What & why. ChatEngine wraps a query engine with conversation memory, enabling multi-turn dialogues. Condense mode rewrites follow-up questions using chat history before retrieval. React mode uses an LLM agent that can call the retriever as a tool, deciding dynamically when to search and when to answer from chat history.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

Under the hoodCondense mode prepends chat history to the query, asking the LLM to rewrite it as a standalone question, then retrieves and generates. React mode uses a ReAct agent loop where the LLM decides whether to call the retriever tool or answer from memory at each turn.

25Agents + Tools from Query Engines

What & why. Any LlamaIndex query engine can be wrapped as a tool that an agent can call. This converts a data query into a function the agent can invoke when it determines the query requires external knowledge. The agent orchestrates multiple tools, handles multi-step reasoning, and synthesizes results.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.agent import ReActAgent
from llama_index.core.tools import QueryTool, FunctionTool

# Build a knowledge index
documents = SimpleDirectoryReader("./docs").load_data()
knowledge_index = VectorStoreIndex.from_documents(documents)

# Wrap as a tool
knowledge_tool = QueryTool.from_defaults(
    query_engine=knowledge_index.as_query_engine(),
    description="Search the company knowledge base for policies, procedures, and technical docs",
)

# Add a custom function tool

    """Calculate the R&D budget as 15% of annual revenue."""
    budget = annual_revenue * 0.15
    return f"R&D budget: ${budget:,.0f}"

budget_tool = FunctionTool.from_defaults(fn=calculate_budget)

# Create agent with multiple tools
agent = ReActAgent.from_tools(
    tools=[knowledge_tool, budget_tool],
    verbose=True,
)

# Agent decides which tool to use per query
response = agent.chat("What is our API rate limit and what should the R&D budget be for $10M revenue?")
print(response)
Where you'll use itAgents from query engines enable complex workflows where the LLM decides which knowledge source to query, when to compute values, and how to combine results from multiple tools.
Under the hoodReActAgent uses a reasoning-action loop: it thinks about what the user needs, selects a tool, observes the result, and repeats until it has enough information to answer. QueryTool wrappers handle the embedding-retrieve-generate pipeline transparently.

26Multi-Document Agent Architecture

What & why. Multi-document agents maintain separate indices per document or document group, with a coordinator agent that routes queries to the appropriate sub-agent. This architecture scales to hundreds of documents while maintaining retrieval precision, because each sub-agent has a focused, smaller index.

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.agent import ReActAgent
from llama_index.core.tools import QueryTool
from pathlib import Path

def build_multi_doc_agent(docs_dir: str) -> ReActAgent:
    """Build an agent with one tool per document."""
    tools = []
    for doc_path in Path(docs_dir).glob("*.pdf"):
        docs = SimpleDirectoryReader(input_files=[doc_path]).load_data()
        doc_index = VectorStoreIndex.from_documents(docs)
        tool = QueryTool.from_defaults(
            query_engine=doc_index.as_query_engine(),
            description=f"Information from {doc_path.stem}",
        )
        tools.append(tool)

    return ReActAgent.from_tools(tools=tools, verbose=True)

agent = build_multi_doc_agent("./documents/")
# Agent routes to the right document per query
response = agent.chat("What does the Q3 report say about revenue growth?")
Where you'll use itMulti-document agents scale to large document collections without degrading retrieval quality. Each sub-agent operates on a small, focused index, maintaining precision while the coordinator handles routing.
Under the hoodThe coordinator agent uses tool descriptions to determine which document to query. Each sub-agent performs retrieval independently, and the coordinator synthesizes results when queries require information from multiple documents.

27Evaluation Module: Faithfulness, Relevancy, Correctness

What & why. LlamaIndex provides built-in evaluation metrics that measure RAG quality without ground-truth labels. Faithfulness checks if the answer is grounded in the retrieved context. Answer relevancy checks if the answer addresses the query. Context relevancy checks if the retrieved context is relevant to the query. Together they provide a comprehensive quality assessment.

from llama_index.core.evaluation import (
    FaithfulnessEvaluator, RelevancyEvaluator, CorrectnessEvaluator
)
from llama_index.llms.openai import OpenAI

llm = OpenAI(model="gpt-4o")

# Create evaluators
faithfulness_eval = FaithfulnessEvaluator(llm=llm)
relevancy_eval = RelevancyEvaluator(llm=llm)
correctness_eval = CorrectnessEvaluator(llm=llm)

# Evaluate a query-response pair
query = "What is the refund policy?"
response = query_engine.query(query)

# Faithfulness: is the answer grounded in context?
faith_result = faithfulness_eval.evaluate_response(
    query=query,
    response=response,
    contexts=[node.text for node in response.source_nodes],
)
print(f"Faithful: {faith_result.passing}, Score: {faith_result.score}")

# Relevancy: does the answer address the query?
rel_result = relevancy_eval.evaluate_response(
    query=query, response=response,
    contexts=[node.text for node in response.source_nodes],
)
print(f"Relevant: {rel_result.passing}, Score: {rel_result.score}")

# Batch evaluation over a dataset
from llama_index.core.evaluation import batch_evaluate
eval_results = batch_evaluate(
    eval_fn=faithfulness_eval.evaluate_response,
    queries=sample_queries,
    responses=sample_responses,
)
Where you'll use itEvaluation is mandatory before production deployment. Run faithfulness, relevancy, and correctness on a sample set of 50+ queries to establish baseline quality and detect regressions after changes.
Under the hoodEach evaluator uses the configured LLM as a judge to assess the quality dimension. Faithfulness checks each claim against context. Relevancy generates synthetic questions from the answer and checks alignment. Correctness compares against a reference answer when available.

31Workflow Events Architecture (Beta)

What & why. LlamaIndex Workflows provide a declarative way to define multi-step pipelines using events and handlers. Each step emits events that trigger downstream handlers, creating a reactive architecture. This replaces complex agent loops with explicit, testable pipeline definitions.

# Workflows are in beta as of 2024
# from llama_index.core.workflow import Workflow, step, StartEvent, StopEvent

# Conceptual workflow for RAG pipeline
class RAGWorkflow(Workflow):
    @step
    async def ingest(self, event: StartEvent) -> StopEvent:
        # Step 1: load and index documents
        docs = SimpleDirectoryReader(event.data_dir).load_data()
        index = VectorStoreIndex.from_documents(docs)
        return StopEvent(result=index)

    @step
    async def query(self, index, query: str) -> str:
        # Step 2: retrieve and generate
        engine = index.as_query_engine()
        response = engine.query(query)
        return response.response

# Workflows provide:
# - Explicit step definitions (easier to debug than agent loops)
# - Event-driven execution (steps run when events arrive)
# - Built-in observability (step timing, error tracking)
# - Testability (each step can be tested independently)
Where you'll use itWorkflows are the future of LlamaIndex pipeline orchestration. They provide the explicitness of code with the flexibility of event-driven architecture, replacing complex agent chains with testable, observable steps.
Under the hoodWorkflows use Python async generators and event dispatching. Each @step decorator registers a handler for specific event types. The workflow engine routes events to handlers, manages state, and handles errors with retries and timeouts.

33Cost Control: Token Accounting per Component

What & why. LlamaIndex operations consume tokens at multiple stages: embedding during indexing, LLM calls during metadata extraction, and LLM calls during querying. Tracking token usage per component reveals cost drivers and enables targeted optimization. LlamaIndex provides built-in token counting through callbacks.

from llama_index.core import Settings
from llama_index.core.callbacks import CallbackManager, TokenCountingHandler
from llama_index.llms.openai import OpenAI

token_counter.print_total_token_counts()
# Shows: embedding tokens, LLM prompt tokens, LLM completion tokens
# Enables cost calculation:
# Embedding: $0.02/1M tokens (text-embedding-3-small)
# LLM input: $2.50/1M tokens (gpt-4o)
# LLM output: $10.00/1M tokens (gpt-4o)

Where you'll use itToken accounting is essential for budgeting and cost optimization. Track tokens per query to identify expensive operations and set per-user token budgets.

34Production Checklist: Caching, Retries, Timeouts

What & why. Production LlamaIndex deployments need resilience patterns: caching LLM responses to avoid redundant calls, retry logic for transient API failures, and timeouts to prevent hung requests. These patterns prevent cascading failures and reduce costs from repeated API calls.

from llama_index.core import Settings
from llama_index.llms.openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_exponential

# LLM with built-in caching (OpenAI SDK caches automatically)
Settings.llm = OpenAI(model="gpt-4o", temperature=0)

# Custom retry wrapper for LlamaIndex operations
@retry(stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=2, max=10))
def robust_query(query_engine, query: str):
    """Query with automatic retry on transient failures."""
    try:
        return query_engine.query(query)
    except Exception as e:
        if "rate_limit" in str(e).lower():
            raise  # retry on rate limits
        if "timeout" in str(e).lower():
            raise  # retry on timeouts
        raise  # don't retry on permanent errors

# Timeout configuration
import httpx
Settings.timeout = 30  # seconds

# Health check with index validation
def health_check(query_engine) -> dict:
    try:
        response = query_engine.query("test")
        return {"status": "healthy", "source_nodes": len(response.source_nodes)}
    except Exception as e:
        return {"status": "unhealthy", "error": str(e)}
Where you'll use itRetry logic and timeouts are mandatory for production. OpenAI's API has rate limits and occasional timeouts; without retries, user-facing errors spike during traffic surges.
Under the hoodThe OpenAI Python SDK includes automatic retries with exponential backoff for 429 (rate limit) and 500 (server error) responses. Tenacity provides application-level retries for LlamaIndex operations that wrap the SDK.

35Upgrading LlamaIndex: Breaking Changes Playbook

What & why. LlamaIndex evolves rapidly with frequent breaking changes between versions. A structured upgrade playbook prevents production surprises: pin versions, test in staging, handle import path changes, and validate index compatibility. The most common breaking changes are import reorganization and API signature changes.

# Version pinning in requirements.txt
# llama-index-core==0.10.68
# llama-index-llms-openai==0.1.22
# llama-index-embeddings-openai==0.1.10
# llama-index-vector-stores-chroma==0.1.8

# Common import path changes (v0.9 -> v0.10):
# OLD: from llama_index import VectorStoreIndex
# NEW: from llama_index.core import VectorStoreIndex

# OLD: from llama_index.llms import OpenAI
# NEW: from llama_index.llms.openai import OpenAI

# OLD: from llama_index.vector_stores import ChromaVectorStore
# NEW: from llama_index.vector_stores.chroma import ChromaVectorStore

# Upgrade validation script
def validate_upgrade():
    """Check that all imports resolve after upgrade."""
    imports = [
        ("llama_index.core", "VectorStoreIndex"),
        ("llama_index.core", "SimpleDirectoryReader"),
        ("llama_index.core", "Settings"),
        ("llama_index.llms.openai", "OpenAI"),
        ("llama_index.embeddings.openai", "OpenAIEmbedding"),
    ]
    for module, attr in imports:
        try:
            mod = __import__(module, fromlist=[attr])
            getattr(mod, attr)
            print(f"OK: {module}.{attr}")
        except (ImportError, AttributeError) as e:
            print(f"BREAKING: {module}.{attr} - {e}")

validate_upgrade()

Company-Wiki Chat with Department Router

Build a chatbot that routes employee questions to the correct department's knowledge base using RouterQueryEngine, with conversation memory and department-scoped access control.

Architecture steps.

  1. Ingest department wikis from Notion/Confluence exports using LlamaHub readers into separate indices
  2. Apply department metadata to all chunks during ingestion for access control
  3. Build a RouterQueryEngine with PydanticSingleSelector that routes based on query content
  4. Add metadata filtering to each retriever to enforce department-level access control
  5. Wrap the router in a ChatEngine with condense mode for multi-turn conversations
  6. Deploy as a FastAPI service with JWT-based department claim extraction
  7. Add streaming responses with token-by-token output to the frontend
  8. Implement evaluation suite with 20 queries per department measuring faithfulness and relevancy
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.query_engine import RouterQueryEngine
from llama_index.core.selectors import PydanticSingleSelector
from llama_index.core.tools import QueryTool
from llama_index.core.vector_stores import MetadataFilters, MetadataFilter

departments = ["engineering", "hr", "finance", "marketing"]
tools = []

for dept in departments:
    docs = SimpleDirectoryReader(f"./{dept}_wiki").load_data()
    for doc in docs:
        doc.metadata["department"] = dept
    index = VectorStoreIndex.from_documents(docs)
    
    # Scoped retriever
    filters = MetadataFilters(filters=[
        MetadataFilter(key="department", value=dept),
    ])
    engine = index.as_query_engine(
        similarity_top_k=5,
        filters=filters,
    )
    tools.append(QueryTool.from_defaults(
        query_engine=engine,
        description=f"{dept.capitalize()} department policies and procedures",
    ))

router = RouterQueryEngine(
    selector=PydanticSingleSelector.from_defaults(query_tools=tools),
)

# Chat engine with memory
chat = router.as_chat_engine(chat_mode="condense", streaming=True)

Architecture steps.

  1. Parse financial PDFs with LlamaParse in markdown mode to preserve table structure and formatting
  2. Split parsed markdown into chunks that respect table boundaries using MarkdownNodeParser
  3. Extract financial entity metadata (company name, fiscal year, metric type) using MetadataExtractor
  4. Build a VectorStoreIndex with 400-token chunks for precise financial data retrieval
  5. Implement a custom prompt template that requires the LLM to cite specific table cells
  6. Add a comparison tool that retrieves the same metric across multiple fiscal years
  7. Build a Gradio interface with document upload, query input, and formatted citation display
  8. Evaluate on 30 financial questions with ground-truth answers using CorrectnessEvaluator
from llama_parse import LlamaParse
from llama_index.core import VectorStoreIndex
from llama_index.core.node_parser import MarkdownNodeParser
from llama_index.core import PromptTemplate

# Parse complex financial PDFs
parser = LlamaParse(api_key="...", result_mode="markdown")
docs = parser.load_data("./annual_report_2024.pdf")

# Parse markdown preserving table structure
md_parser = MarkdownNodeParser()
nodes = md_parser.get_nodes_from_documents(docs)

# Custom financial QA prompt
finance_qa = PromptTemplate(
    template=(
        "You are a financial analyst. Answer using ONLY the context below.\n"
        "For numerical claims, cite the specific table or section.\n\n"
        "Context:\n{context_str}\n\n"
        "Question: {query_str}\n\n"
        "Answer with citations:"
    ),
)

index = VectorStoreIndex(nodes)
engine = index.as_query_engine(text_qa_template=finance_qa, similarity_top_k=5)

# Financial comparison tool
def compare_fiscal_years(metric: str) -> str:
    """Compare a financial metric across fiscal years."""
    results = []
    for year in ["2022", "2023", "2024"]:
        response = engine.query(f"What was {metric} in fiscal year {year}?")
        results.append(f"FY{year}: {response.response}")
    return "\n".join(results)
