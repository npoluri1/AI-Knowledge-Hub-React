Part I · FoundationsTier 1 — Schemas, tools param, dispatchers, round-trips, validation

1Function Calling Concept: Model Outputs Intent, Not Execution

What & why. When you give an LLM a function schema, it does not execute the function. Instead, it outputs a structured JSON object describing which function to call and with what arguments. Your code is responsible for executing the function and returning the result. This separation keeps the model sandboxed while giving it access to real-world actions.

import openai, json

client = openai.OpenAI()

tools = [{"type": "function", "function": {
    "name": "get_weather",
    "description": "Get current weather for a city",
    "parameters": {"type": "object", "properties": {
        "city": {"type": "string", "description": "City name"}
    }, "required": ["city"]}
}}]

resp = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "What is the weather in Tokyo?"}],
    tools=tools
)
msg = resp.choices[0].message
if msg.tool_calls:
    args = json.loads(msg.tool_calls[0].function.arguments)
    print(f"Model wants to call: {msg.tool_calls[0].function.name}")
    print(f"With arguments: {args}")
    # YOUR code executes the function
    result = {"temp": 22, "condition": "sunny"}
Where you'll use itEvery tool-using agent relies on this pattern. The model decides WHAT to call; your code handles HOW. This keeps the LLM away from direct system access while enabling rich functionality.
Under the hoodThe model has been trained on function-calling examples and understands JSON Schema. It selects the best function based on the user's request and generates compliant arguments.

2JSON Schema Describing a Function

What & why. A JSON schema defines the function's name, description, parameters, and their types. The schema is the contract between your code and the model. Clear descriptions and well-typed parameters are the primary lever for making the model call tools correctly.

search_tool_schema = {
    "type": "function",
    "function": {
        "name": "search_products",
        "description": "Search for products in the catalog. Returns matching products with prices.",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {
                    "type": "string",
                    "description": "Search terms, e.g. 'wireless headphones'"
                },
                "max_price": {
                    "type": "number",
                    "description": "Maximum price filter in USD. Omit for no limit."
                },
                "category": {
                    "type": "string",
                    "enum": ["electronics", "clothing", "books", "home"],
                    "description": "Product category filter"
                }
            },
            "required": ["query"]
        }
    }
}
Where you'll use itEvery tool needs a schema. The quality of the schema directly determines how often the model generates correct arguments. Invest time in clear descriptions and examples.
Under the hoodThe schema follows JSON Schema Draft 7 with OpenAI extensions (the "function" wrapper). Anthropic and Google use similar but slightly different formats for their tool definitions.

3OpenAI tools Param and tool_choice auto

What & why. The tools parameter accepts a list of tool schemas. The tool_choice parameter controls whether the model may choose any tool (auto), must use a specific tool (by name), or must not use tools (none). This gives you control over the model's tool-selection behavior.

# Default: model decides whether to use a tool
resp = client.chat.completions.create(
    model="gpt-4o", messages=messages, tools=tools, tool_choice="auto"
)

# Force the model to use a specific tool
resp = client.chat.completions.create(
    model="gpt-4o", messages=messages, tools=tools,
    tool_choice={"type": "function", "function": {"name": "get_weather"}}
)

# Force the model to use any tool (not respond with text)
resp = client.chat.completions.create(
    model="gpt-4o", messages=messages, tools=tools, tool_choice="required"
)

# Disable tool calling
resp = client.chat.completions.create(
    model="gpt-4o", messages=messages, tools=tools, tool_choice="none"
)
Where you'll use ittool_choice="required" is useful when you know the user's request needs a tool. tool_choice with a specific tool name forces the model into a particular workflow.
Under the hoodWhen tool_choice="none", the model behaves as if no tools are defined. When "required", the model must call at least one tool but can choose which one.

4Reading Response: tool_calls and Arguments

What & why. When the model decides to use a tool, the response contains tool_calls: an array of objects each with an id, function name, and arguments string. The arguments are a JSON string that must be parsed. Reading this structure correctly is essential for dispatching tool calls.

resp = client.chat.completions.create(
    model="gpt-4o", messages=messages, tools=tools
)

choice = resp.choices[0]
msg = choice.message

if choice.finish_reason == "tool_calls":
    for tc in msg.tool_calls:
        print(f"ID: {tc.id}")              # unique call ID
        print(f"Function: {tc.function.name}")  # function name
        print(f"Args (raw): {tc.function.arguments}")  # JSON string
        args = json.loads(tc.function.arguments)  # parsed dict
        print(f"Args (parsed): {args}")
elif choice.finish_reason == "stop":
    print(f"Final answer: {msg.content}")
Where you'll use itEvery tool-calling loop must handle the tool_calls structure. The finish_reason tells you whether the model wants to use tools or is done.
Under the hoodThe arguments field is always a string (not a dict), even if the function takes no arguments. Always use json.loads() to parse it safely.

5Executing Dispatcher: if/elif Registry Pattern

What & why. A dispatcher maps tool names to functions. The if/elif pattern is the simplest: check the tool name and call the corresponding function. For many tools, a dictionary registry is cleaner. The dispatcher handles execution and catches errors for each tool independently.

def get_weather(city: str) -> str:
    return f"Weather in {city}: 22C sunny"

def get_stock_price(ticker: str) -> str:
    return f"{ticker} price: $150.25"

# Dictionary registry
TOOL_REGISTRY = {
    "get_weather": get_weather,
    "get_stock_price": get_stock_price,
}

def dispatch_tool(tool_name: str, arguments: str) -> str:
    args = json.loads(arguments)
    func = TOOL_REGISTRY.get(tool_name)
    if func is None:
        return f"Error: unknown tool '{tool_name}'"
    try:
        result = func(**args)
        return str(result)
    except Exception as e:
        return f"Error executing {tool_name}: {e}"

# Usage in loop
for tc in msg.tool_calls:
    result = dispatch_tool(tc.function.name, tc.function.arguments)
    messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
Where you'll use itThe dictionary registry pattern scales to dozens of tools without growing if/elif chains. It also makes adding new tools a one-line operation.
Under the hoodUsing **args unpacking means the function signature must match the JSON schema parameter names exactly. Mismatches cause KeyError at runtime.

6Returning role: tool Result Message

What & why. After executing a tool, the result must be returned as a message with role="tool" and the matching tool_call_id. This lets the model correlate the result with its original request. Without the tool_call_id, the model cannot determine which result corresponds to which call.

def execute_and_respond(msg, messages):
    """Execute all tool calls and append results to messages."""
    for tc in msg.tool_calls:
        result = dispatch_tool(tc.function.name, tc.function.arguments)
        messages.append({
            "role": "tool",
            "tool_call_id": tc.id,
            "content": str(result)
        })

# Complete round-trip
messages = [{"role": "user", "content": "Weather in Tokyo and NYC"}]
resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
messages.append(resp.choices[0].message)

if resp.choices[0].finish_reason == "tool_calls":
    execute_and_respond(resp.choices[0].message, messages)
    # Model now sees both results and can compose the answer
    resp2 = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
Where you'll use itThe tool_call_id linking is mandatory for all OpenAI-compatible APIs. It enables parallel tool calls where multiple results arrive simultaneously.
Under the hoodThe OpenAI API enforces that tool result messages follow the corresponding assistant message. Skipping or reordering tool results causes API errors.

7Complete Round-Trip Example: Calculator

What & why. A calculator tool demonstrates the complete function-calling round-trip: schema definition, model call, argument parsing, execution, result return, and final answer generation. It is the minimal end-to-end example for learning tool calling.

import openai, json

client = openai.OpenAI()

def calculator(expression: str) -> str:
    try:
        result = eval(expression, {"__builtins__": {}})
        return str(result)
    except Exception as e:
        return f"Error: {e}"

calc_tool = {"type": "function", "function": {
    "name": "calculator", "description": "Evaluate a math expression",
    "parameters": {"type": "object", "properties": {
        "expression": {"type": "string", "description": "Math expression, e.g. '2+2*3'"}
    }, "required": ["expression"]}
}}

messages = [{"role": "user", "content": "What is 15 * 7 + 3?"}]
tools = [calc_tool]

resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
msg = resp.choices[0].message
messages.append(msg)

if resp.choices[0].finish_reason == "tool_calls":
    tc = msg.tool_calls[0]
    result = calculator(json.loads(tc.function.arguments)["expression"])
    messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
    final = client.chat.completions.create(model="gpt-4o", messages=messages)
    print(final.choices[0].message.content)  # "15 * 7 + 3 = 108"
Where you'll use itCalculator is the canonical tool-calling demo. It verifies the full cycle without external dependencies.
Under the hoodUsing eval() for a calculator is unsafe in production. A proper calculator would use ast.literal_eval or a math parser. This example prioritizes simplicity.

8Pydantic Args Validation

What & why. Pydantic models validate tool arguments at runtime, catching malformed inputs before they reach your tool logic. When the model generates invalid arguments, Pydantic raises a ValidationError that you can return as a tool error message, letting the model self-correct.

from pydantic import BaseModel, Field, ValidationError

class WeatherArgs(BaseModel):
    city: str = Field(description="City name")
    units: str = Field(default="celsius", pattern="^(celsius|fahrenheit)$")

def validated_weather(arguments: str) -> str:
    try:
        args = WeatherArgs.model_validate_json(arguments)
    except ValidationError as e:
        return f"Invalid arguments: {e.errors()[0]['msg']}"
    return get_weather(args.city, args.units)

# Schema with Pydantic
from pydantic import TypeAdapter

def get_weather_schema() -> dict:
    schema = TypeAdapter(WeatherArgs).json_schema()
    return {"type": "function", "function": {
        "name": "get_weather", "description": "Get weather for a city",
        "parameters": schema
    }}
Where you'll use itPydantic validation prevents tools from receiving unexpected argument types. It catches enum violations, missing required fields, and type mismatches before execution.
Under the hoodPydantic v2 generates JSON Schema from Python type hints automatically. This means you define validation once in Python and it becomes the tool schema for the model.

9Enum-Constrained Parameters

What & why. Enum constraints restrict a parameter to a fixed set of values. This prevents the model from generating invalid options (e.g., a misspelled sort order). Enums also generate cleaner schema definitions that the model follows more reliably.

from enum import Enum
from pydantic import BaseModel

class SortOrder(str, Enum):
    ASC = "asc"
    DESC = "desc"

class Priority(str, Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"

class SearchArgs(BaseModel):
    query: str
    sort_by: SortOrder = SortOrder.DESC
    priority: Priority = Priority.MEDIUM

search_tool = {"type": "function", "function": {
    "name": "search_tasks",
    "description": "Search and filter tasks",
    "parameters": {
        "type": "object",
        "properties": {
            "query": {"type": "string"},
            "sort_by": {"type": "string", "enum": ["asc", "desc"]},
            "priority": {"type": "string", "enum": ["low", "medium", "high"]}
        },
        "required": ["query"]
    }
}}
Where you'll use itEnum constraints are essential for tools that interface with APIs expecting exact string values. They prevent the model from inventing values that the downstream system rejects.
Under the hoodThe "enum" keyword in JSON Schema tells the model the exact allowed values. The model almost always respects enum constraints because they appear in its training data as valid patterns.

10Docstring as Spec: Quality Tips

What & why. The tool description is the model's primary guide for when and how to use a tool. Clear, specific descriptions with examples dramatically improve tool selection accuracy. A good description answers: when should the model use this tool, what inputs are expected, and what does the output look like?

excellent_tool_schema = {
    "type": "function", "function": {
        "name": "query_database",
        "description": (
            "Execute a read-only SQL query against the company database. "
            "Use this when the user asks about business data: sales figures, "
            "customer counts, inventory levels, or any data stored in tables. "
            "Do NOT use for simple calculations (use calculator instead) or "
            "for checking system status (use health_check instead). "
            "Returns query results as a list of rows."
        ),
        "parameters": {"type": "object", "properties": {
            "sql": {"type": "string", "description": "SELECT query only. Max 1000 rows."},
            "database": {"type": "string", "enum": ["analytics", "crm", "inventory"],
                         "description": "Which database to query"}
        }, "required": ["sql", "database"]}
    }
}
Where you'll use itTool descriptions are the most important factor in tool-selection accuracy. Invest time in writing descriptions that clearly distinguish each tool's purpose from similar tools.
Under the hoodThe model uses the description to decide which tool matches the user's intent. Vague descriptions lead to wrong tool selection; specific descriptions with exclusions ("Do NOT use for...") reduce false positives.

11Error Message Returns for Model Self-Correction

What & why. When a tool fails, returning a descriptive error message as the tool result lets the model understand what went wrong and try a different approach. This self-correction loop is more resilient than crashing on tool errors.

def safe_tool_execution(tool_name: str, arguments: str) -> str:
    func = TOOL_REGISTRY.get(tool_name)
    if func is None:
        return f"Error: tool '{tool_name}' does not exist. Available: {list(TOOL_REGISTRY.keys())}"
    try:
        args = json.loads(arguments)
    except json.JSONDecodeError as e:
        return f"Error: invalid JSON in arguments: {e}"
    try:
        result = func(**args)
        return str(result)
    except TypeError as e:
        return f"Error: wrong argument types. {e}. Check the schema."
    except ValueError as e:
        return f"Error: invalid value. {e}. Please use valid input."
    except Exception as e:
        return f"Error: {type(e).__name__}: {e}"

# Model sees the error and adjusts
messages.append({"role": "tool", "tool_call_id": tc.id,
                 "content": "Error: wrong argument types. 'city' must be a string, got int."})
# Model will retry with correct types
Where you'll use itSelf-correction via error messages is a core agent pattern. The model learns from the error and retries with corrected arguments, improving robustness without human intervention.
Under the hoodSpecific error messages are better than generic ones. "city must be a string" tells the model exactly what to fix; "invalid input" does not.

12When NOT to Give a Tool

What & why. Not every capability should be a tool. Giving the model unnecessary tools increases prompt size, dilutes tool-selection accuracy, and wastes tokens. Tools should be provided only when the model cannot accomplish the task from its own knowledge or when real-time data access is needed.

# GOOD: Tool for real-time data the model cannot know
weather_tool = {"name": "get_weather", "description": "Real-time weather data"}

# GOOD: Tool for actions the model cannot perform
send_email_tool = {"name": "send_email", "description": "Send an email to a recipient"}

# BAD: Tool for something the model already knows
capital_tool = {"name": "get_capital", "description": "Get capital of a country"}
# The model already knows capitals; this wastes a tool slot

# BAD: Tool that duplicates existing functionality
calc_tool = {"name": "add", "description": "Add two numbers"}
# The model can do arithmetic; only use a calculator for complex expressions

# Rule of thumb
PROVIDE_TOOL_IF = [
    "Real-time or frequently changing data",
    "Actions with side effects (send, create, delete)",
    "Access to private/proprietary data",
    "Computation too complex for the model",
]
SKIP_TOOL_IF = [
    "General knowledge the model already has",
    "Simple arithmetic the model can do",
    "Text transformation the model can perform",
]
Where you'll use itTool proliferation is a common anti-pattern. Each tool adds tokens to every API call; 20+ tools degrade performance. Keep the tool set minimal and purposeful.
Under the hoodModels select tools more accurately with fewer options. The tool-selection accuracy drops measurably when the count exceeds 15-20 tools per call.

13Multiple Tools: Registry Dict Pattern

What & why. A tool registry organizes multiple tools in a dictionary mapping names to functions and schemas. This pattern scales cleanly: adding a tool means one dict entry. The registry also provides tool enumeration for schema generation and validation.

@dataclass
class Tool:
    name: str
    description: str
    function: Callable
    schema: dict

class ToolRegistry:
    def __init__(self):
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool):
        self._tools[tool.name] = tool

    def get_schemas(self) -> list[dict]:
        return [{"type": "function", "function": {
            "name": t.name, "description": t.description, "parameters": t.schema
        }} for t in self._tools.values()]

    def dispatch(self, name: str, arguments: str) -> str:
        tool = self._tools.get(name)
        if not tool:
            return f"Unknown tool: {name}"
        args = json.loads(arguments)
        return str(tool.function(**args))

registry = ToolRegistry()
registry.register(Tool("get_weather", "Get weather", get_weather, weather_schema))
registry.register(Tool("search", "Search catalog", search_products, search_schema))
schemas = registry.get_schemas()  # pass to OpenAI tools param
Where you'll use itThe registry pattern is the standard for production agents with 5+ tools. It provides a single source of truth for tool definitions and dispatch logic.
Under the hoodFrameworks like LangChain and CrewAI use similar registry patterns under the hood. Understanding the raw pattern helps when debugging framework internals.

14Parallel Tool Calls: Parsing Arrays

What & why. The model may return multiple tool_calls in a single response when it determines that several tools need to be called independently. Each tool call has its own id, function name, and arguments. All must be executed and their results appended before the next LLM call.

def handle_parallel_calls(msg, messages):
    """Execute all tool calls from a single response."""
    if not msg.tool_calls:
        return
    for tc in msg.tool_calls:
        result = dispatch_tool(tc.function.name, tc.function.arguments)
        messages.append({
            "role": "tool",
            "tool_call_id": tc.id,
            "content": str(result)
        })

# Full loop with parallel support
for i in range(MAX_ITER):
    resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=schemas)
    msg = resp.choices[0].message
    messages.append(msg)
    if resp.choices[0].finish_reason == "stop":
        return msg.content
    handle_parallel_calls(msg, messages)
Where you'll use itParallel calls reduce round-trips. A query like "weather in Tokyo and NYC" produces two tool_calls in one response instead of two sequential LLM calls.
Under the hoodOpenAI enables parallel tool calls by default. The model has been trained to batch independent calls, reducing latency and cost.

15Strict Mode: Guaranteed Schema Compliance

What & why. OpenAI's strict mode ensures the model's tool-call arguments exactly match the JSON schema. Without strict mode, the model may generate extra fields or omit required ones. Strict mode uses grammar-constrained decoding to guarantee compliance.

# Strict mode tool definition
strict_tool = {
    "type": "function",
    "function": {
        "name": "create_order",
        "description": "Create a customer order",
        "strict": True,  # enables strict schema compliance
        "parameters": {
            "type": "object",
            "properties": {
                "item_id": {"type": "string"},
                "quantity": {"type": "integer", "minimum": 1},
                "shipping": {"type": "string", "enum": ["standard", "express", "overnight"]}
            },
            "required": ["item_id", "quantity", "shipping"],
            "additionalProperties": False  # mandatory with strict mode
        }
    }
}

# With strict mode, the model ALWAYS generates valid arguments
resp = client.chat.completions.create(
    model="gpt-4o", messages=messages, tools=[strict_tool]
)
# Arguments are guaranteed to match the schema exactly
Where you'll use itStrict mode is essential for tools that interface with rigid APIs. It eliminates argument validation errors at the cost of slightly higher latency.
Under the hoodStrict mode uses constrained decoding: the model's token probabilities are masked to only allow tokens that maintain valid JSON according to the schema. This guarantees syntactic and semantic compliance.

16Anthropic tool_use Block Format

What & why. Anthropic's tool-use format differs from OpenAI's. Tool calls arrive as content blocks with type="tool_use" inside the assistant message. Tool results are sent as type="tool_result" blocks within a user message, not as separate tool-role messages.

import anthropic

aclient = anthropic.Anthropic()

tools = [{"name": "get_weather", "description": "Get weather",
          "input_schema": {"type": "object", "properties": {
              "city": {"type": "string"}}, "required": ["city"]}}]

resp = aclient.messages.create(model="claude-sonnet-4-20250514", max_tokens=4096,
                                messages=[{"role": "user", "content": "Weather in Tokyo?"}],
                                tools=tools)

# Parse tool_use blocks
for block in resp.content:
    if block.type == "tool_use":
        result = execute_tool(block.name, block.input)

# Return results as user message with tool_result blocks
result_blocks = [{"type": "tool_result", "tool_use_id": block.id, "content": str(result)}]
resp2 = aclient.messages.create(model="claude-sonnet-4-20250514", max_tokens=4096,
    messages=[{"role": "user", "content": "Weather in Tokyo?"},
              {"role": "assistant", "content": resp.content},
              {"role": "user", "content": result_blocks}], tools=tools)
Where you'll use itClaude's tool_use format is used by all Anthropic API consumers. Understanding the content-block structure is essential for Claude-based tool-calling agents.
Under the hoodAnthropic's approach keeps the message structure flat (only user/assistant roles) by using content blocks for tool interactions. This differs from OpenAI's dedicated tool role.

17Gemini Function Declarations Mapping

What & why. Google's Gemini API uses function_declarations with a slightly different schema format. Parameters use "type": "STRING" instead of "type": "string", and the response format includes functionCall and functionResponse parts.

import google.generativeai as genai

genai.configure(api_key="your-key")
model = genai.GenerativeModel(model_name="gemini-2.0-flash")

# Gemini tool declaration
weather_func = {"function_declarations": [{
    "name": "get_weather",
    "description": "Get weather for a city",
    "parameters": {"type": "OBJECT", "properties": {
        "city": {"type": "STRING", "description": "City name"}
    }, "required": ["city"]}
}]}

# Call with tools
response = model.generate_content(
    "Weather in Tokyo?",
    tools=weather_func
)

# Parse function call
for part in response.parts:
    if hasattr(part, "function_call"):
        fc = part.function_call
        result = execute_tool(fc.name, dict(fc.args))
        # Return function response
        response2 = model.generate_content(
            [{"function_response": {"name": fc.name, "response": {"result": result}}}],
            tools=weather_func
        )
Where you'll use itGemini function declarations follow the same concept as OpenAI/Anthropic but with different naming conventions. Multi-provider agents must handle all three formats.
Under the hoodGemini uses uppercase type names (OBJECT, STRING) matching Protocol Buffer conventions. The functionCall/functionResponse parts keep tool interactions within the content stream.

18Nested Object Schemas: Pitfalls

What & why. Nested objects in tool schemas (e.g., address: {street, city, zip}) are valid but risky. Models sometimes flatten them, generate extra nesting, or omit required nested fields. Flat schemas with explicit field names (address_street, address_city) are more reliable.

# PITFALL: nested schema often fails
nested_tool = {"type": "function", "function": {
    "name": "create_contact",
    "parameters": {"type": "object", "properties": {
        "name": {"type": "string"},
        "address": {"type": "object", "properties": {
            "street": {"type": "string"},
            "city": {"type": "string"},
            "zip": {"type": "string"}
        }}
    }}
}}

# BETTER: flat schema with prefixed names
flat_tool = {"type": "function", "function": {
    "name": "create_contact",
    "parameters": {"type": "object", "properties": {
        "name": {"type": "string"},
        "street": {"type": "string"},
        "city": {"type": "string"},
        "zip_code": {"type": "string"}
    }, "required": ["name", "city"]}
}}

# ACCEPTABLE: single nested object with strict mode
strict_nested = {**nested_tool, "function": {**nested_tool["function"],
    "strict": True, "parameters": {**nested_tool["function"]["parameters"],
    "additionalProperties": False}}}
Where you'll use itNested schemas are common in real-world APIs. The tradeoff is clean schema design vs. model reliability. Use strict mode if nesting is necessary.
Under the hoodModels are trained on flat parameter examples more than nested ones. The training distribution bias makes flat schemas produce more reliable arguments.

19Optional vs Required Fields and Defaults

What & why. Correctly marking fields as required vs optional affects what the model generates. Required fields must always appear; optional fields may be omitted if defaults are provided. Missing required fields cause tool failures; unnecessary required fields cause the model to invent values.

send_email_tool = {"type": "function", "function": {
    "name": "send_email",
    "description": "Send an email",
    "parameters": {"type": "object", "properties": {
        "to": {"type": "string", "description": "Recipient email address"},
        "subject": {"type": "string", "description": "Email subject line"},
        "body": {"type": "string", "description": "Email body text"},
        "cc": {"type": "string", "description": "CC address. Optional."},
        "priority": {"type": "string", "enum": ["low", "normal", "high"],
                     "default": "normal"}

20Streaming Tool-Call Deltas: Accumulation

What & why. When streaming, tool calls arrive as deltas across multiple chunks. The function name may come in one chunk and arguments in subsequent chunks. Accumulating these deltas into complete tool-call objects is essential for streaming agent loops.

def accumulate_tool_calls(stream) -> list[dict]:
    """Accumulate streaming tool-call deltas into complete objects."""
    tool_calls = {}
    for chunk in stream:
        delta = chunk.choices[0].delta
        if delta.tool_calls:
            for tc_delta in delta.tool_calls:
                idx = tc_delta.index
                if idx not in tool_calls:
                    tool_calls[idx] = {"id": "", "name": "", "args": ""}
                if tc_delta.id:
                    tool_calls[idx]["id"] = tc_delta.id
                if tc_delta.function and tc_delta.function.name:
                    tool_calls[idx]["name"] += tc_delta.function.name
                if tc_delta.function and tc_delta.function.arguments:
                    tool_calls[idx]["args"] += tc_delta.function.arguments
    return list(tool_calls.values())

stream = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools, stream=True)
completed_calls = accumulate_tool_calls(stream)
for tc in completed_calls:
    result = dispatch_tool(tc["name"], tc["args"])
Where you'll use itStreaming accumulation is needed for responsive UIs that show tool-call progress. Without it, the UI must wait for the full response before processing any tool call.
Under the hoodDeltas are fragmented because the API sends tokens as they are generated. The function name and arguments are generated token-by-token, arriving in separate chunks.

23Dynamic Tool Selection: RAG-over-Tools Catalog

What & why. When an agent has hundreds of tools, sending all schemas to the model is impractical. RAG-over-tools selects the most relevant tools for each query by embedding tool descriptions and retrieving the top matches. Only relevant tools are included in the API call.

import numpy as np

class ToolCatalog:
    def __init__(self, tools: list[dict]):
        self.tools = tools
        self.vectors = self._embed_tools()

    def _embed_tools(self) -> list[list[float]]:
        descriptions = [t["function"]["description"] for t in self.tools]
        resp = client.embeddings.create(model="text-embedding-3-small", input=descriptions)
        return [d.embedding for d in resp.data]

    def select_tools(self, query: str, top_k: int = 5) -> list[dict]:
        resp = client.embeddings.create(model="text-embedding-3-small", input=query)
        q_vec = np.array(resp.data[0].embedding)
        scores = [(i, float(np.dot(q_vec, np.array(v)))) for i, v in enumerate(self.vectors)]
        scores.sort(key=lambda x: x[1], reverse=True)
        return [self.tools[i] for i, _ in scores[:top_k]]

catalog = ToolCatalog(all_tools)
relevant = catalog.select_tools("what is the weather in Singapore")
Where you'll use itRAG-over-tools is essential for platforms with 50+ tools. It reduces prompt size and improves tool-selection accuracy by presenting only relevant options.
Under the hoodThe embedding similarity between the user query and tool descriptions determines relevance. This works because tool descriptions are typically short and semantically clear.

24Permission Layers: Role-Based Tool Allowlists

What & why. Not all users should have access to all tools. Permission layers restrict which tools each role can use. An admin might have database-write tools; a viewer only has read tools. The permission check runs before including tools in the API call.

ROLE_PERMISSIONS = {
    "admin": ["read_data", "write_data", "delete_user", "send_email", "deploy"],
    "analyst": ["read_data", "run_query", "export_report"],
    "viewer": ["read_data"],
}

class PermissionedToolRegistry:
    def __init__(self, all_tools: dict):
        self.tools = all_tools

    def get_tools_for_role(self, role: str) -> list[dict]:
        allowed = ROLE_PERMISSIONS.get(role, [])
        return [self.tools[name] for name in allowed if name in self.tools]

    def is_allowed(self, role: str, tool_name: str) -> bool:
        return tool_name in ROLE_PERMISSIONS.get(role, [])

    def execute_with_permission(self, role: str, tool_name: str, arguments: str) -> str:
        if not self.is_allowed(role, tool_name):
            return f"Permission denied: role '{role}' cannot use tool '{tool_name}'"
        return self.tools[tool_name].execute(arguments)

registry = PermissionedToolRegistry(all_tools)
tools = registry.get_tools_for_role("analyst")  # only read tools
Where you'll use itPermission layers are mandatory for multi-tenant agent platforms. They prevent privilege escalation where a user tricks the model into calling restricted tools.
Under the hoodPermissions are checked at tool inclusion time (before the API call) AND at execution time (before running the tool). Dual checking prevents both prompt injection and runtime bypass.

def truncate_tool_result(result: str, max_chars: int = 4000) -> str:

27Retries with Backoff and Circuit Breaker per Tool

What & why. Individual tools may fail due to network issues, rate limits, or service outages. A circuit breaker tracks failure rates per tool and stops calling a failing tool after consecutive failures. Combined with exponential backoff, this prevents cascading failures.

class CircuitBreaker:
    def __init__(self, failure_threshold: int = 3, reset_timeout: int = 60):
        self.failures = 0
        self.threshold = failure_threshold
        self.reset_timeout = reset_timeout
        self.last_failure_time = 0
        self.state = "closed"  # closed = normal, open = failing

    def record_success(self):
        self.failures = 0
        self.state = "closed"

    def record_failure(self):
        self.failures += 1
        if self.failures >= self.threshold:
            self.state = "open"
            self.last_failure_time = time.time()

    def is_open(self) -> bool:
        if self.state == "open":
            if time.time() - self.last_failure_time > self.reset_timeout:
                self.state = "half-open"
                return False
            return True
        return False

breakers = {name: CircuitBreaker() for name in TOOL_REGISTRY}

def resilient_dispatch(tool_name: str, arguments: str) -> str:
    breaker = breakers[tool_name]
    if breaker.is_open():
        return f"Error: tool '{tool_name}' is temporarily unavailable (circuit open)"
    try:
        result = dispatch_tool(tool_name, arguments)
        breaker.record_success()
        return result
    except Exception as e:
        breaker.record_failure()
        return f"Error: {e}"
Where you'll use itCircuit breakers prevent an agent from repeatedly calling a failing tool, which wastes time and may trigger rate limits. They are standard in microservice architectures.
Under the hoodThe half-open state allows a single test request after the timeout. If it succeeds, the circuit closes; if it fails, the circuit reopens. This auto-recovery pattern avoids manual intervention.

28Observability: Span per Tool Invocation

What & why. Each tool invocation should be traced as a span in an observability system (LangSmith, Langfuse, OpenTelemetry). The span captures the tool name, arguments, result, latency, and any errors. This enables performance analysis and debugging of tool-calling behavior.

import time
from contextlib import contextmanager

class ToolTracer:
    def __init__(self):
        self.spans: list[dict] = []

    @contextmanager
    def trace(self, tool_name: str, arguments: str):
        span = {
            "tool": tool_name,
            "arguments": arguments[:200],
            "start_time": time.time(),
            "status": "ok",
        }
        try:
            yield span
        except Exception as e:
            span["status"] = "error"
            span["error"] = str(e)
            raise
        finally:
            span["end_time"] = time.time()
            span["duration_ms"] = (span["end_time"] - span["start_time"]) * 1000
            self.spans.append(span)

tracer = ToolTracer()

    result = dispatch_tool("get_weather", '{"city": "Tokyo"}')
    span["result_size"] = len(result)
# Span recorded: {"tool": "get_weather", "duration_ms": 142.3, "status": "ok"}
Where you'll use itPer-tool tracing reveals which tools are slow, which fail often, and which are called most frequently. This data drives tool optimization and infrastructure decisions.
Under the hoodOpenTelemetry provides the standard for distributed tracing. Each tool span gets a trace ID that links it to the parent agent loop span, enabling full request tracing.

29Schema Versioning for Backward Compatibility

What & why. When tool schemas change (new parameters, renamed fields), existing models may generate arguments matching the old schema. Schema versioning ensures backward compatibility by supporting old and new formats during transition periods.

class VersionedTool:
    def __init__(self, name: str, versions: dict[str, dict]):
        self.name = name
        self.versions = versions  # {"v1": schema_v1, "v2": schema_v2}

    def get_schema(self, version: str = "latest") -> dict:
        if version == "latest":
            version = max(self.versions.keys())
        return self.versions[version]

    def execute(self, arguments: str, schema_version: str = "latest") -> str:
        args = json.loads(arguments)
        if schema_version == "v1":
            args = self._migrate_v1_to_v2(args)
        return self._execute_impl(args)

    def _migrate_v1_to_v2(self, args: dict) -> dict:
        if "location" in args and "city" not in args:
            args["city"] = args.pop("location")
        return args

Where you'll use itSchema versioning prevents breaking changes when evolving tool interfaces. It is essential for multi-agent systems where different agents may use different schema versions.

34Sandbox Isolation: Processes and VMs

What & why. Tools that execute code or access the filesystem must run in isolated sandboxes. Process isolation (subprocess with restricted permissions), container isolation (Docker), or VM isolation prevent tools from affecting the host system or other tools.

import subprocess, resource

def sandboxed_code_execution(code: str, timeout: int = 10) -> str:
    """Execute Python code in a sandboxed subprocess."""
    try:
        result = subprocess.run(
            ["python", "-c", code],
            capture_output=True, text=True,
            timeout=timeout,
            # Restrict filesystem and network access
            env={"PATH": "/usr/bin", "HOME": "/tmp", "PYTHONPATH": ""},
        )
        if result.returncode != 0:
            return f"Error: {result.stderr[:500]}"
        return result.stdout[:5000]
    except subprocess.TimeoutExpired:
        return "Error: code execution timed out"

class DockerSandbox:

        self.image = image

             "--cpus=0.5", self.image, "python", "-c", code],
            capture_output=True, text=True, timeout=timeout
        )
        return result.stdout[:5000] if result.returncode == 0 else f"Error: {result.stderr[:500]}"

35Capability Tokens: Scoped Credentials

What & why. Instead of giving tools broad API keys, capability tokens grant time-limited, scope-limited access. A tool that reads user data gets a token scoped to that user's data for one hour. This limits damage from token compromise and enforces least-privilege access.

import jwt, time

class CapabilityToken:
    def __init__(self, secret: str):
        self.secret = secret

    def issue(self, tool_name: str, scopes: list[str], user_id: str,
              ttl_seconds: int = 3600) -> str:
        payload = {
            "tool": tool_name,
            "scopes": scopes,
            "user_id": user_id,
            "iat": int(time.time()),
            "exp": int(time.time()) + ttl_seconds,
        }
        return jwt.encode(payload, self.secret, algorithm="HS256")

    def verify(self, token: str, required_scope: str) -> dict:
        try:
            payload = jwt.decode(token, self.secret, algorithms=["HS256"])
            if required_scope not in payload["scopes"]:
                raise ValueError(f"Missing scope: {required_scope}")
            return payload
        except jwt.ExpiredSignatureError:
            raise ValueError("Token expired")

cap = CapabilityToken("secret-key")
token = cap.issue("database_query", ["read:analytics", "read:crm"], user_id="alice")
# Tool uses token to access only analytics and CRM data for alice
Where you'll use itCapability tokens enforce least-privilege in multi-tool systems. Each tool gets only the access it needs, and tokens expire automatically.
Under the hoodCapability tokens are similar to AWS STS temporary credentials. They provide fine-grained, time-limited access without sharing long-lived API keys.

36Audit Evidence Trails for Compliance

What & why. Compliance frameworks (SOC 2, ISO 27001, PDPA) require evidence that tools are used appropriately. Audit trails record every tool invocation with who, what, when, and outcome. These trails are the primary evidence during compliance audits.

import hashlib, json, time

class ComplianceAuditor:
    def __init__(self, log_path: str):
        self.log_path = log_path
        self.chain_hash = "genesis"

    def record_invocation(self, tool_name: str, caller: str, arguments: str,
                          result: str, status: str):
        entry = {
            "timestamp": time.time(),
            "tool": tool_name,
            "caller": caller,
            "arguments_hash": hashlib.sha256(arguments.encode()).hexdigest(),
            "result_status": status,
            "prev_hash": self.chain_hash,
        }
        entry_str = json.dumps(entry, sort_keys=True)
        entry["entry_hash"] = hashlib.sha256(entry_str.encode()).hexdigest()
        self.chain_hash = entry["entry_hash"]
        with open(self.log_path, "a") as f:
            f.write(json.dumps(entry) + "\n")

    def verify_chain(self) -> bool:
        prev_hash = "genesis"
        with open(self.log_path) as f:
            for line in f:
                entry = json.loads(line)
                if entry["prev_hash"] != prev_hash:
                    return False
                prev_hash = entry["entry_hash"]
        return True

38Computer-Use Abstraction: Reliability Ladder

What & why. Computer-use tools control a GUI: clicking, typing, scrolling. The reliability ladder ranks interaction methods from most to least reliable: API > CLI > accessibility tree > pixel coordinates. Always prefer higher-reliability methods.

# Reliability ladder for computer-use tools
RELIABILITY_LADDER = {
    "api": {"reliability": 1.0, "speed": "fast", "example": "REST API call"},
    "cli": {"reliability": 0.95, "speed": "fast", "example": "subprocess.run(['git', 'status'])"},
    "accessibility": {"reliability": 0.85, "speed": "medium", "example": "find element by role/name"},
    "pixel_coordinates": {"reliability": 0.6, "speed": "slow", "example": "click(x=450, y=320)"},
}

def select_interaction_method(target: str, available: list[str]) -> str:
    """Select the most reliable available method."""
    for method in ["api", "cli", "accessibility", "pixel_coordinates"]:
        if method in available:
            return method
    return "pixel_coordinates"  # fallback

# Tool that tries higher reliability first
def smart_click(element_description: str) -> str:
    methods = ["api", "cli", "accessibility", "pixel_coordinates"]
    for method in methods:
        try:
            return attempt_click(element_description, method)
        except Exception:
            continue
    return "All click methods failed"

An administrative operations console that allows AI-assisted infrastructure management with mandatory human approval for destructive operations. The system implements role-based tool access, audit logging, and circuit breakers for external service calls.

  2. Implement read-only tools (list servers, check status, view logs) with no approval required
  3. Build destructive tools (restart server, deploy code, delete resource) with approval gates

  5. Implement an audit chain that logs every tool invocation with hash verification
  6. Build a notification system for approval requests (Slack webhook integration)
  7. Add result truncation for large outputs (log files, deployment status)
  8. Create a compliance report generator from audit logs
class AdminOpsConsole:
    def __init__(self):
        self.registry = PermissionedToolRegistry()
        self.approval_gate = ApprovalGate()
        self.auditor = ComplianceAuditor("admin_audit.jsonl")
        self.circuit_breakers = {}

    def execute(self, role: str, tool_name: str, arguments: str, user_id: str) -> str:
        if not self.registry.is_allowed(role, tool_name):
            return f"Permission denied for role '{role}'"
        if self.approval_gate.needs_approval(tool_name):
            if not self.approval_gate.request_approval(tool_name, arguments, user_id):
                return "Action denied by administrator"
        breaker = self.circuit_breakers.get(tool_name, CircuitBreaker())
        if breaker.is_open():
            return f"Service '{tool_name}' temporarily unavailable"
        try:
            result = self.registry.execute_with_permission(role, tool_name, arguments)
            breaker.record_success()
            self.auditor.record_invocation(tool_name, user_id, arguments, "success", "ok")
            return truncate_tool_result(result)
        except Exception as e:
            breaker.record_failure()
            self.auditor.record_invocation(tool_name, user_id, arguments, "error", str(e))
            return f"Error: {e}"

Tool-Quality Eval Harness: Scoring Choice Accuracy

An evaluation harness that measures how accurately a model selects and populates tools across a benchmark suite of test cases. The harness runs each test case through the agent loop, compares tool calls to expected outputs, and produces accuracy reports by tool, category, and difficulty.

Architecture steps.

  1. Build a test suite of 50+ cases with expected tool names, arguments, and success criteria
  2. Implement a mock tool server that returns deterministic responses for test cases
  3. Create an evaluator that compares actual tool calls against expected calls
  4. Measure three dimensions: tool selection accuracy, argument correctness, final answer quality
  5. Add difficulty categories (easy: single tool, medium: chained tools, hard: dynamic selection)
  6. Generate per-tool accuracy metrics to identify weak spots in tool descriptions
  7. Build a regression suite that re-runs after schema or prompt changes
  8. Produce markdown reports with accuracy tables and failure analysis
class ToolEvalHarness:
    def __init__(self, test_cases: list[dict], mock_tools: dict):
        self.cases = test_cases
        self.mock = mock_tools
        self.results = []

    def run_case(self, case: dict) -> dict:
        messages = [{"role": "user", "content": case["query"]}]
        tools = case.get("available_tools", list(self.mock.keys()))
        resp = client.chat.completions.create(
            model="gpt-4o", messages=messages,
            tools=[self.mock[t]["schema"] for t in tools]
        )
        actual_calls = resp.choices[0].message.tool_calls or []
        expected = case["expected_tool_calls"]
        return {
            "tool_selection": self._score_selection(actual_calls, expected),
            "argument_correctness": self._score_arguments(actual_calls, expected),
            "difficulty": case.get("difficulty", "medium"),
        }

    def evaluate(self) -> dict:
        self.results = [self.run_case(c) for c in self.cases]
        return {
            "total": len(self.results),
            "selection_accuracy": sum(r["tool_selection"] for r in self.results) / len(self.results),
            "argument_accuracy": sum(r["argument_correctness"] for r in self.results) / len(self.results),
            "by_difficulty": self._group_by("difficulty"),
        }
