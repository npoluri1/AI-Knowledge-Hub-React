Part I · FoundationsTier 1 — Core loop mechanics, pseudocode, termination, state, costs

1The While-Loop Essence of Agency

What & why. Agency is not a single LLM call but a cycle: observe, think, act, observe again. A while-loop is the simplest construct that captures this cycle. Each iteration lets the model consume all prior observations and decide whether to act again or stop. Without the loop, the model can only respond once; with it, the model can pursue goals that require multiple steps.

# The simplest agent loop
messages = [{"role": "user", "content": prompt}]
while True:
    response = client.chat.completions.create(
        model="gpt-4o", messages=messages
    )
    answer = response.choices[0].message
    messages.append(answer)
    if answer.content:
        print(answer.content)
        break
Where you'll use itEvery chatbot, coding assistant, and autonomous agent framework reduces to this pattern at its core. Understanding the while-loop demystifies all agent frameworks.
Under the hoodThe loop manages a growing list of messages that serves as the agent's working memory. The LLM receives the full list each iteration, so context window size directly limits how many iterations are practical.

2Pseudocode of a Generic Agent Loop

What & why. Before writing real code, a clear pseudocode blueprint prevents design errors. The generic loop has four phases: build prompt from state, call LLM, parse the response for actions, execute actions and append observations. This separation of concerns makes each phase independently testable and replaceable.

# Pseudocode blueprint
state = initial_state(user_query)
for i in range(MAX_ITERATIONS):
    prompt = build_prompt(state)
    raw = llm_call(prompt)
    action = parse_action(raw)
    if action.type == "final_answer":
        return action.content
    observation = execute(action)
    state.append_observation(observation)
raise MaxIterationsExceeded
Where you'll use itFramework authors use this exact blueprint. LangGraph nodes, CrewAI agents, and AutoGen loops all implement these four phases, making this pseudocode the universal reference design.
Under the hoodThe parse_action phase is where tool-call detection happens. For OpenAI-style APIs the response carries a finish_reason and optional tool_calls; for Anthropic it carries stop_reason and content blocks of type tool_use.

3LLM Call → Parse Action → Execute → Append Observation

What & why. These four steps are the irreducible core of any agent loop. The LLM call sends messages and receives a response. Parsing extracts whether the model wants to use a tool or is done. Execution runs the tool and captures its output. Appending adds the tool result as a new message so the model sees it next iteration.

import openai, json

client = openai.OpenAI()
messages = [{"role": "user", "content": query}]
tools = [{"type": "function", "function": get_weather_def}]

for _ in range(10):
    resp = client.chat.completions.create(
        model="gpt-4o", messages=messages, tools=tools
    )
    msg = resp.choices[0].message
    messages.append(msg)
    if resp.choices[0].finish_reason == "stop":
        return msg.content
    if msg.tool_calls:
        for tc in msg.tool_calls:
            result = run_tool(tc.function.name, tc.function.arguments)
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
Where you'll use itThis four-step pattern appears in every production agent: customer-support bots that lookup accounts, coding agents that edit files, and data-pipeline agents that query databases.
Under the hoodThe append step is critical: if the tool result is not added as a message, the model has no way to see what happened and will either repeat the action or hallucinate an outcome.

4Max Iterations Guard

What & why. Without a hard limit, a confused agent can loop indefinitely, burning tokens and money. A max-iterations guard is a mandatory safety rail. It converts a potentially infinite loop into a bounded one and should raise a clear exception when the limit is reached.

MAX_ITER = 15
budget_spent = 0.0

for iteration in range(MAX_ITER):
    resp = client.chat.completions.create(model="gpt-4o", messages=messages)
    budget_spent += estimate_cost(resp.usage)
    messages.append(resp.choices[0].message)
    if resp.choices[0].finish_reason == "stop":
        break
    if resp.choices[0].finish_reason == "tool_calls":
        for tc in resp.choices[0].message.tool_calls:
            result = execute_tool(tc)
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
else:
    raise RuntimeError(f"Agent exceeded {MAX_ITER} iterations, spent ${budget_spent:.4f}")
Where you'll use itProduction agents always set iteration limits. OpenAI Assistants API defaults to 10 tool rounds. Anthropic recommends setting explicit maximums for any agentic workflow.
Under the hoodThe for/else construct in Python fires the else block only if the loop completes without a break, making it a clean pattern for detecting exhausted iteration budgets.

5Termination Detection and final_answer Convention

What & why. A well-designed loop needs a clear stopping signal. The common convention is a final_answer function the model can call to signal task completion. When the parser sees this function call, the loop returns its content instead of executing it as a tool.

final_answer_tool = {
    "type": "function",
    "function": {
        "name": "final_answer",
        "description": "Call this when you have the final answer. Do not use any other tool after.",
        "parameters": {"type": "object", "properties": {
            "answer": {"type": "string", "description": "The final response"}
        }, "required": ["answer"]}
    }
}

def parse_response(msg):
    if msg.tool_calls:
        for tc in msg.tool_calls:
            if tc.function.name == "final_answer":
                args = json.loads(tc.function.arguments)
                return {"done": True, "answer": args["answer"]}
            else:
                return {"done": False, "tool": tc}
    return {"done": True, "answer": msg.content}
Where you'll use itThe final_answer pattern is used by frameworks like SmolAgents and LangGraph. It gives the model explicit control over when to stop, which is more reliable than heuristic termination.
Under the hoodWithout explicit termination the model may keep calling tools after it already has the answer. The final_answer convention prevents unnecessary iterations and costs.

6Loop State: The State List

What & why. The messages list is the loop's state. It grows each iteration with the model's response and any tool results. This append-only design makes state inspection trivial: you can print, log, or serialize the list at any point to understand exactly what the model has seen.

from dataclasses import dataclass, field

@dataclass
class LoopState:
    messages: list = field(default_factory=list)
    iterations: int = 0
    total_tokens: int = 0
    tool_results: list = field(default_factory=list)

    def append_assistant(self, msg):
        self.messages.append(msg)
        self.iterations += 1

    def append_tool_result(self, tool_call_id: str, content: str):
        self.messages.append({"role": "tool", "tool_call_id": tool_call_id, "content": content})
        self.tool_results.append({"id": tool_call_id, "output": content})

    def snapshot(self) -> dict:
        return {"iterations": self.iterations, "tokens": self.total_tokens, "turns": len(self.messages)}
Where you'll use itA structured state object makes debugging agent failures far easier than a raw list. It also enables checkpointing, replay, and analytics on loop behavior.
Under the hoodLangGraph formalizes this as a TypedDict or Pydantic model that is passed between nodes. Each node reads from and writes to the state, making the loop a graph traversal.

7Printing vs Streaming Iterations

What & why. In a basic loop you print the model's response after each iteration. For better UX you can stream tokens as they arrive. Streaming within a loop requires collecting the full response for tool-call parsing while simultaneously yielding partial text to the UI.

for iteration in range(MAX_ITER):
    stream = client.chat.completions.create(
        model="gpt-4o", messages=messages, stream=True
    )
    full_content = ""
    tool_calls_acc = {}
    for chunk in stream:
        delta = chunk.choices[0].delta
        if delta.content:
            full_content += delta.content
            print(delta.content, end="", flush=True)
        if delta.tool_calls:
            for tc in delta.tool_calls:
                idx = tc.index
                if idx not in tool_calls_acc:
                    tool_calls_acc[idx] = {"id": tc.id, "name": "", "args": ""}
                tool_calls_acc[idx]["name"] += tc.function.name or ""
                tool_calls_acc[idx]["args"] += tc.function.arguments or ""
    print()
    if tool_calls_acc:
        handle_tool_calls(tool_calls_acc, messages)
Where you'll use itStreaming gives users immediate feedback during long iterations. ChatGPT, Claude, and every major chat UI stream within their agent loops.
Under the hoodTool-call deltas arrive across multiple chunks. The accumulator pattern merges partial function names and argument strings into complete objects before execution.

8Toy Echo-Tool Loop Demo

What & why. A minimal demo with an echo tool proves the loop mechanics without external dependencies. The echo tool simply returns its input, letting you verify that the full cycle works: LLM call, tool-call parsing, execution, observation append, and re-invocation.

import openai, json

client = openai.OpenAI()
echo_tool = {"type": "function", "function": {
    "name": "echo", "description": "Echoes input back",
    "parameters": {"type": "object", "properties": {
        "text": {"type": "string"}}, "required": ["text"]}
}}

def run_echo(text: str) -> str: return f"Echo: {text}"

messages = [{"role": "system", "content": "Use echo to repeat the user message, then give final answer."},
            {"role": "user", "content": "Hello world"}]

for i in range(5):
    resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=[echo_tool])
    msg = resp.choices[0].message
    messages.append(msg)
    if resp.choices[0].finish_reason == "stop":
        print(f"Done in {i+1} iterations: {msg.content}")

    for tc in msg.tool_calls:
        result = run_echo(json.loads(tc.function.arguments)["text"])
        messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
Where you'll use itEcho-tool demos are standard for testing agent loop scaffolding before integrating real tools. They verify message formatting, tool-call routing, and observation handling.
Under the hoodThe echo tool is the "hello world" of agent loops. It isolates loop mechanics from tool complexity, making it ideal for unit tests and CI pipelines.

9Iteration Costs Accumulate

What & why. Each loop iteration makes a full LLM API call with the entire message history. Costs scale quadratically with iteration count because each new message is sent in every subsequent call. Without cost tracking, a simple 10-iteration loop can cost significantly more than a single call.

import tiktoken

encoder = tiktoken.encoding_for_model("gpt-4o")

def estimate_cost(messages: list, model: str = "gpt-4o") -> float:
    total_tokens = sum(len(encoder.encode(m.get("content", "") or "")) for m in messages)
    if "gpt-4o" in model:
        return total_tokens * 2.5 / 1_000_000
    elif "gpt-4o-mini" in model:
        return total_tokens * 0.15 / 1_000_000
    return total_tokens * 1.0 / 1_000_000

cumulative = 0.0
for iteration in range(MAX_ITER):
    cost = estimate_cost(messages)
    cumulative += cost
    print(f"Iter {iteration}: +${cost:.6f} cumulative=${cumulative:.6f}")
    resp = client.chat.completions.create(model="gpt-4o", messages=messages)
    # ... process response ...
    if cumulative > BUDGET_LIMIT:
        raise RuntimeError(f"Budget exceeded: ${cumulative:.4f}")
Where you'll use itCost tracking prevents bill shock in production. Multi-agent systems running hundreds of loops per hour need per-loop cost accounting to stay within budgets.
Under the hoodThe quadratic cost growth comes from sending the full message history each iteration. Ten iterations with 5 messages each means 150 messages sent total (5+10+15+...+50).

10Common Beginner Bug: Forgetting to Append

What & why. The most common agent-loop bug is failing to append the tool result to messages. Without it the model never sees the observation and will either repeat the same tool call or hallucinate an answer. This bug produces loops that run to the iteration limit without making progress.

# BUGGY: tool result not appended
for i in range(MAX_ITER):
    resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
    msg = resp.choices[0].message
    messages.append(msg)  # append assistant message
    if resp.choices[0].finish_reason == "stop":
        break
    for tc in msg.tool_calls:
        result = execute_tool(tc)
        # MISSING: messages.append({"role": "tool", ...})
        # Model never sees result, loops forever

# FIXED: tool result appended correctly
        messages.append({
            "role": "tool",
            "tool_call_id": tc.id,
            "content": str(result)
        })
Where you'll use itThis bug accounts for a large fraction of agent loop bugs in early development. Linters and type checkers cannot catch it because the append is syntactically valid but semantically wrong.
Under the hoodThe OpenAI API requires alternating assistant/tool messages. Skipping a tool append breaks this alternation, causing API errors or silent misbehavior where the model ignores the tool result.

11Sleep and Rate Limiting Between Calls

What & why. API providers enforce rate limits measured in requests per minute and tokens per minute. A tight loop with no delays can hit these limits and receive 429 errors. Inserting sleep or using provider-recommended backoff prevents rate-limit failures in iterative loops.

import time

def call_with_retry(messages, model="gpt-4o", max_retries=3):
    for attempt in range(max_retries):
        try:
            return client.chat.completions.create(model=model, messages=messages)
        except openai.RateLimitError as e:
            wait = 2 ** attempt
            print(f"Rate limited, waiting {wait}s (attempt {attempt+1})")
            time.sleep(wait)
    raise RuntimeError("Rate limit exceeded after retries")

for i in range(MAX_ITER):
    resp = call_with_retry(messages)
    # ... process ...
    time.sleep(0.5)  # gentle pacing between iterations
Where you'll use itRate limiting is essential for loops running against tier-1 providers. OpenAI's free tier allows 500 RPM; a loop without pacing can exhaust this in seconds.
Under the hoodExponential backoff with jitter is the standard pattern. The retry-after header from the API tells you exactly how long to wait, but falling back to exponential backoff covers cases where it is missing.

12Manual Stepping: Debugger-Style Loops

What & why. During development you often want to step through an agent loop one iteration at a time, inspecting state before each LLM call. A generator-based or breakpoint-based loop lets you pause at each step, examine messages, and optionally override the model's decision.

def agent_loop_generator(messages, tools):
    """Yields (iteration, messages_copy) before each LLM call."""
    for i in range(MAX_ITER):
        yield i, [m.copy() for m in messages]  # snapshot for inspection
        resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
        msg = resp.choices[0].message
        messages.append(msg)
        if resp.choices[0].finish_reason == "stop":
            return msg.content
        for tc in msg.tool_calls:
            result = execute_tool(tc)
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})

# Debugger usage
loop = agent_loop_generator(messages, tools)
for iteration, snapshot in loop:
    print(f"=== Iteration {iteration} ===")
    for m in snapshot:
        print(f"  {m.get('role')}: {str(m.get('content', ''))[:120]}")
    input("Press Enter to continue...")
Where you'll use itGenerator-based stepping is invaluable for debugging agent behavior. It lets you identify exactly where the model makes wrong decisions without restarting the entire loop.
Under the hoodLangGraph implements a similar concept with breakpoints that pause graph execution. The generator pattern achieves the same result with plain Python, making it portable across frameworks.

13OpenAI Tool-Call Round-Trip Loop with finish_reason

What & why. The OpenAI API signals tool-use intent via finish_reason="tool_calls" and a non-null message.tool_calls array. A robust loop reads this signal to decide whether to execute tools or return the final answer. Each tool call carries a unique id that must be echoed back in the tool-result message.

def openai_agent_loop(query: str, tools: list, model="gpt-4o") -> str:
    messages = [{"role": "user", "content": query}]
    for _ in range(15):
        resp = client.chat.completions.create(model=model, messages=messages, tools=tools)
        choice = resp.choices[0]
        msg = choice.message
        messages.append(msg)
        if choice.finish_reason == "stop":
            return msg.content
        if choice.finish_reason == "tool_calls":
            for tc in msg.tool_calls:
                result = execute_tool(tc.function.name, tc.function.arguments)
                messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
    return "Reached iteration limit without final answer."
Where you'll use itThis is the standard OpenAI agent loop pattern used in production by ChatGPT plugins, OpenAI Assistants, and most third-party OpenAI-compatible agent frameworks.
Under the hoodThe finish_reason field is the API's mechanism for telling the client what happened. "stop" means natural completion; "tool_calls" means the model wants to call tools; "length" means token limit hit.

14Anthropic stop_reason tool_use Loop

What & why. Anthropic's Messages API structures tool use differently. Tool calls arrive as content blocks with type="tool_use", and the stop_reason is "tool_use" when tools should be executed. The tool result must be sent as a content block of type="tool_result" within a user message, not as a separate message role.

import anthropic

aclient = anthropic.Anthropic()

def anthropic_agent_loop(query: str, tools: list, model="claude-sonnet-4-20250514") -> str:
    messages = [{"role": "user", "content": query}]
    for _ in range(15):
        resp = aclient.messages.create(model=model, max_tokens=4096, messages=messages, tools=tools)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason == "end_turn":
            text_blocks = [b.text for b in resp.content if b.type == "text"]
            return "\n".join(text_blocks)
        if resp.stop_reason == "tool_use":
            tool_results = []
            for block in resp.content:
                if block.type == "tool_use":
                    result = execute_tool(block.name, block.input)
                    tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": str(result)})
            messages.append({"role": "user", "content": tool_results})
    return "Reached iteration limit."
Where you'll use itAnthropic's tool_use format is the basis for Claude's computer use and tool-calling capabilities. Understanding the content-block structure is essential for Claude-based agents.
Under the hoodUnlike OpenAI's separate message role for tool results, Anthropic bundles them as content blocks within a user message. This design keeps the conversation flat rather than introducing a new role type.

15Parallel Tool Calls: Handling Batch Results

What & why. Models may request multiple tool calls in a single response. These arrive as an array of tool_calls (OpenAI) or multiple tool_use blocks (Anthropic). Executing them sequentially wastes time; parallel execution with gather or ThreadPoolExecutor handles them concurrently and appends all results.

import asyncio
from concurrent.futures import ThreadPoolExecutor

def execute_parallel_tools(tool_calls, messages, max_workers=4):
    with ThreadPoolExecutor(max_workers=max_workers) as executor:
        futures = {}
        for tc in tool_calls:
            future = executor.submit(execute_tool, tc.function.name, tc.function.arguments)
            futures[tc.id] = future
        for tc_id, future in futures.items():
            result = future.result()
            messages.append({"role": "tool", "tool_call_id": tc_id, "content": str(result)})

async def execute_parallel_tools_async(tool_calls, messages):
    tasks = [asyncio.to_thread(execute_tool, tc.function.name, tc.function.arguments) for tc in tool_calls]
    results = await asyncio.gather(*tasks)
    for tc, result in zip(tool_calls, results):
        messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
Where you'll use itParallel tool execution is critical for agents that query multiple data sources simultaneously. Research agents, data-analysis pipelines, and multi-API orchestrations all benefit.
Under the hoodOpenAI sets parallel_tool_calls=true by default. The model learns to batch independent calls, reducing round-trips from N to 1 when multiple tools are needed simultaneously.

16Async Loop with asyncio.gather Observations

What & why. An async agent loop allows other tasks to run while waiting for LLM responses. Using asyncio.gather for the LLM call and tool execution enables high-concurrency agents that can serve multiple users or manage multiple sub-tasks without blocking.

import asyncio, openai

async_client = openai.AsyncOpenAI()

async def async_agent_loop(query: str, tools: list) -> str:
    messages = [{"role": "user", "content": query}]
    for _ in range(15):
        resp = await async_client.chat.completions.create(
            model="gpt-4o", messages=messages, tools=tools
        )
        msg = resp.choices[0].message
        messages.append(msg)
        if resp.choices[0].finish_reason == "stop":
            return msg.content
        if resp.choices[0].finish_reason == "tool_calls":
            tasks = [asyncio.to_thread(execute_tool, tc.function.name, tc.function.arguments)
                     for tc in msg.tool_calls]
            results = await asyncio.gather(*tasks)
            for tc, result in zip(msg.tool_calls, results):
                messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
    return "Limit reached"

# Run multiple agents concurrently
results = await asyncio.gather(
    async_agent_loop("Query A", tools),
    async_agent_loop("Query B", tools),
)
Where you'll use itAsync loops power concurrent agent servers. FastAPI endpoints returning StreamingResponse while running agent loops, and multi-agent systems coordinating via asyncio queues, both use this pattern.
Under the hoodThe openai library's async client uses aiohttp under the hood, enabling true non-blocking I/O. Tool execution is wrapped in asyncio.to_thread because most tools involve blocking I/O operations.

17Exponential Backoff Around Provider Errors

What & why. Provider APIs can fail transiently due to overload, network issues, or rate limits. Exponential backoff with jitter retries failed requests, waiting progressively longer between attempts. This pattern transforms flaky loops into resilient ones that survive transient failures.

import random, time

def resilient_call(messages, model="gpt-4o", max_retries=5):
    for attempt in range(max_retries):
        try:
            return client.chat.completions.create(model=model, messages=messages)
        except openai.APIStatusError as e:
            if e.status_code in (429, 500, 502, 503, 504):
                base_wait = min(2 ** attempt, 60)
                jitter = random.uniform(0, base_wait * 0.5)
                wait = base_wait + jitter
                retry_after = getattr(e.response.headers, "get", lambda k, d: d)("retry-after", None)
                if retry_after:
                    wait = max(wait, float(retry_after))
                print(f"Retry {attempt+1}/{max_retries} after {wait:.1f}s (HTTP {e.status_code})")
                time.sleep(wait)
            else:
                raise
    raise RuntimeError(f"All {max_retries} retries exhausted")
Where you'll use itProduction agent loops without backoff are fragile. OpenAI recommends retry-after-based backoff; Anthropic recommends exponential backoff with jitter as best practice.
Under the hoodJitter prevents thundering-herd problems where many clients retry at the same intervals. The decorrelated jitter formula is: wait = min(cap, random(base, prev_wait * 3)).

18Token Budget Meter Per Iteration

What & why. Beyond a total budget cap, you may want per-iteration token tracking to detect when a single iteration is consuming excessive tokens. This meter tracks input/output tokens separately and can trigger early termination or model downgrade if an iteration exceeds its allocation.

@dataclass
class TokenBudget:
    total_limit: int = 100_000
    per_iter_limit: int = 10_000
    spent: int = 0

    def check(self, usage) -> bool:
        self.spent += usage.total_tokens
        if usage.total_tokens > self.per_iter_limit:
            print(f"Warning: iteration used {usage.total_tokens} tokens (limit {self.per_iter_limit})")
        return self.spent <= self.total_limit

budget = TokenBudget()
for i in range(MAX_ITER):
    resp = client.chat.completions.create(model="gpt-4o", messages=messages)
    if not budget.check(resp.usage):
        print(f"Budget exhausted: {budget.spent}/{budget.total_limit} tokens used")
        break
    # ... process ...
Where you'll use itToken budgeting prevents runaway costs in production. Per-iteration limits catch pathological cases where the model generates extremely long responses or enters a degenerate loop pattern.
Under the hoodOpenAI returns usage.prompt_tokens and usage.completion_tokens per response. Tracking these separately lets you identify whether high costs come from large inputs (growing message history) or verbose outputs.

19Infinite Loop Detector: Repeated-Action Hash

What & why. Even with iteration limits, a confused agent may repeat the same action in every iteration, wasting all its budget on useless work. A repeated-action hash detects when the model produces the same tool call multiple times and stops the loop early.

import hashlib

def action_hash(msg) -> str:
    if not msg.tool_calls:
        return hashlib.md5((msg.content or "").encode()).hexdigest()
    calls = sorted([(tc.function.name, tc.function.arguments) for tc in msg.tool_calls])
    return hashlib.md5(str(calls).encode()).hexdigest()

seen_hashes = []
repetition_count = 0

for i in range(MAX_ITER):
    resp = client.chat.completions.create(model="gpt-4o", messages=messages)
    msg = resp.choices[0].message
    h = action_hash(msg)
    if h in seen_hashes:
        repetition_count += 1
        if repetition_count >= 3:
            print(f"Loop detected: same action repeated {repetition_count} times")
            break
    else:
        repetition_count = 0
    seen_hashes.append(h)
    messages.append(msg)
Where you'll use itRepetition detection catches loops where the model repeatedly calls the same failing tool or returns identical answers. It is a cheap safety net that prevents most infinite-loop pathologies.
Under the hoodA sliding window of recent hashes (rather than unbounded history) is more practical: if the same action appears 3 times in the last 5 iterations, the loop is likely stuck.

20Graceful Degradation: Fallback Answers

What & why. When a loop hits its iteration limit or encounters an unrecoverable error, it should produce a best-effort answer rather than raising an exception. Graceful degradation returns the best available response from the model's last attempt, even if the task was not fully completed.

def agent_loop_with_fallback(query: str, tools: list) -> str:

34Watchdog Timers: External Loop Killer

What & why. A watchdog timer is an external process that kills the agent loop if it runs too long. Unlike an internal iteration limit, a watchdog works even if the loop logic itself is broken (e.g., an infinite loop caused by a bug in iteration handling).

import threading, signal, sys

class Watchdog:
    def __init__(self, timeout_sec: int):
        self.timeout = timeout_sec
        self.timer = None

    def start(self, callback=None):
        def _kill():
            print(f"Watchdog triggered after {self.timeout}s, terminating loop")
            if callback: callback()
            sys.exit(1)
        self.timer = threading.Timer(self.timeout, _kill)
        self.timer.daemon = True
        self.timer.start()

    def reset(self):
        if self.timer: self.timer.cancel()
        self.start()

    def stop(self):
        if self.timer: self.timer.cancel()

watchdog.start()

    resp = client.chat.completions.create(model="gpt-4o", messages=messages)
    watchdog.reset()  # reset timer on each iteration
    # ... process ...
watchdog.stop()
Where you'll use itWatchdogs are safety nets for production agents. They catch bugs that internal guards miss, such as infinite loops caused by incorrect tool-call parsing.
Under the hoodThe watchdog runs on a separate thread, making it independent of the main loop's state. Even if the main thread is blocked by a hanging API call, the watchdog can terminate the process.

        for i in range(5):  # max iterations per step
            resp = client.chat.completions.create(model="gpt-4o", messages=messages, tools=tools)
            spent += resp.usage.total_tokens
            if spent >= total_budget:
                return f"Budget exhausted at step {step.name}: {spent}/{total_budget} tokens"
            msg = resp.choices[0].message
            messages.append(msg)
            if resp.choices[0].finish_reason == "stop":
                return msg.content
            for tc in (msg.tool_calls or []):
                result = execute_tool(tc)
                messages.append({"role": "tool", "tool_call_id": tc.id, "content": str(result)})
Where you'll use itBudget-aware planning is critical for API-cost-sensitive deployments. It ensures every task gets a fair share of the total budget.
Under the hoodThe plan step itself consumes tokens. A practical planner accounts for the planning overhead and reserves tokens for the final answer when allocating per-step budgets.

40Distributed Loops: Leader Election Sketch

What & why. In multi-instance deployments, multiple agents may pick up the same task from a shared queue. Leader election ensures only one agent processes each task. This prevents duplicate execution, which is especially dangerous for tools with side effects.

import redis

r = redis.Redis()

def try_acquire_task(task_id: str, agent_id: str, ttl: int = 300) -> bool:
    """Attempt to claim a task using Redis SETNX for leader election."""
    lock_key = f"agent_lock:{task_id}"
    acquired = r.set(lock_key, agent_id, nx=True, ex=ttl)
    return bool(acquired)

def release_task(task_id: str, agent_id: str):
    lock_key = f"agent_lock:{task_id}"
    current = r.get(lock_key)
    if current and current.decode() == agent_id:
        r.delete(lock_key)

def distributed_loop(task_id: str, query: str, tools: list):
    agent_id = f"agent-{os.getpid()}"
    if not try_acquire_task(task_id, agent_id):
        print(f"Another agent is handling {task_id}")
        return
    try:
        result = agent_loop(query, tools)
        save_result(task_id, result)
    finally:
        release_task(task_id, agent_id)
Where you'll use itDistributed agent systems (Kubernetes pods, serverless functions) need leader election for task deduplication. Redis SETNX with TTL is the simplest production-proven pattern.
Under the hoodThe TTL ensures that if an agent crashes without releasing the lock, the task becomes available again after the TTL expires. This provides crash safety without complex coordination.

41Exactly-Once Side Effects: Idempotency Keys

What & why. Agent loops may retry after failures, causing tools with side effects to execute multiple times. Idempotency keys ensure that repeated calls to a tool with the same key produce the same result as a single call. This is essential for payment, email, and database-update tools.

import uuid

def idempotent_tool_call(tool_name: str, args: dict, idempotency_key: str = None):
    """Execute a tool with an idempotency key to prevent duplicate side effects."""
    key = idempotency_key or str(uuid.uuid4())
    cache_key = f"idempotent:{tool_name}:{key}"
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)
    result = execute_tool(tool_name, args)
    r.setex(cache_key, 86400, json.dumps(result))  # cache for 24h
    return result

# In agent loop
for tc in msg.tool_calls:
    key = hashlib.md5(json.dumps({"name": tc.function.name, "args": tc.function.arguments}).encode()).hexdigest()
    result = idempotent_tool_call(tc.function.name, json.loads(tc.function.arguments), key)
Where you'll use itIdempotency keys are mandatory for payment processing (Stripe, PayPal), email sending (SendGrid), and database writes in retry-prone agent loops.
Under the hoodThe idempotency key must be deterministic based on the tool name and arguments. If the key is random, every retry generates a new key and defeats the purpose.

42Crash-Consistent Journaling: WAL Pattern for Agents

What & why. A write-ahead log (WAL) records each planned action before execution. If the agent crashes mid-action, the WAL enables recovery by replaying actions or rolling back incomplete ones. This pattern provides durability guarantees similar to databases.

import sqlite3, json, time

class AgentWAL:
    def __init__(self, db_path: str):
        self.conn = sqlite3.connect(db_path)
        self.conn.execute("""CREATE TABLE IF NOT EXISTS wal (
            id INTEGER PRIMARY KEY, timestamp REAL, action TEXT, status TEXT, result TEXT)""")

    def log_action(self, action: dict) -> int:
        cursor = self.conn.execute(
            "INSERT INTO wal (timestamp, action, status) VALUES (?, ?, ?)",
            (time.time(), json.dumps(action), "pending"))
        self.conn.commit()
        return cursor.lastrowid

    def complete(self, wal_id: int, result: str):
        self.conn.execute("UPDATE wal SET status='done', result=? WHERE id=?", (result, wal_id))
        self.conn.commit()

    def recover(self) -> list:
        pending = self.conn.execute("SELECT id, action FROM wal WHERE status='pending'").fetchall()
        return [{"id": row[0], "action": json.loads(row[1])} for row in pending]

# Usage in loop
wal = AgentWAL("agent.wal")
for i in range(MAX_ITER):
    for tc in (msg.tool_calls or []):
        action = {"tool": tc.function.name, "args": tc.function.arguments}
        wal_id = wal.log_action(action)
        try:
            result = execute_tool(tc)
            wal.complete(wal_id, result)
        except Exception as e:
            print(f"Action failed, WAL entry {wal_id} will be retried on recovery")
Where you'll use itLong-running batch agents benefit from WAL-based recovery. Instead of restarting from scratch after a crash, the agent resumes from the last incomplete action.
Under the hoodSQLite is a practical WAL backend for single-instance agents. For distributed agents, Kafka or PostgreSQL provide the same durability with horizontal scalability.

44Chaos Testing Loops: Injected Failures

What & why. Chaos testing intentionally injects failures (API timeouts, tool errors, malformed responses) into agent loops to verify that error handling works correctly. This practice, borrowed from distributed systems engineering, ensures loops are robust before deployment.

import random

class ChaosInjector:
    def __init__(self, failure_rate: float = 0.1):
        self.failure_rate = failure_rate

    def wrap_llm_call(self, real_call):
        def wrapped(*args, **kwargs):
            if random.random() < self.failure_rate:
                raise openai.APIStatusError("Chaos: simulated failure", response=None, code=None)
            return real_call(*args, **kwargs)
        return wrapped

    def wrap_tool(self, real_tool):
        def wrapped(name, args):
            if random.random() < self.failure_rate:
                return "Chaos: tool failed with timeout"
            return real_tool(name, args)
        return wrapped

# Run chaos tests
