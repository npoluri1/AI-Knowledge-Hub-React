1Why Govern AI: Risks, Harms, and Accountability

What & why. AI systems can cause harm through bias amplification, hallucinated facts, data leakage, privacy violations, and unsafe autonomous actions. Without governance, these risks materialize as reputational damage, regulatory fines, and user harm. Accountability frameworks assign clear ownership for AI outcomes — someone must be responsible when an AI system makes a consequential decision.

2Risk Tiering: Unacceptable, High, Limited, Minimal

What & why. Risk tiering classifies AI systems by their potential impact — unacceptable risks are banned, high risks require rigorous controls, limited risks need transparency obligations, and minimal risks face no specific requirements. This classification determines the governance effort and controls required for each system.

public enum RiskTier {
    UNACCEPTABLE(
        "Banned — social scoring, manipulation, exploitation",
        "No deployment permitted"
    ),
    HIGH(
        "Hiring, credit scoring, law enforcement, education",
        "Full DPIA, human oversight, testing, documentation"
    ),
    LIMITED(
        "Chatbots, emotion recognition, deepfakes",
        "Transparency disclosure, opt-out mechanisms"
    ),
    MINIMAL(
        "Spam filters, recommendation engines, games",
        "Basic documentation, no specific controls"
    );

    private final String examples;
    private final String requirements;

    RiskTier(String examples, String requirements) {
        this.examples = examples;
        this.requirements = requirements;
    }

    public static RiskTier classify(String systemType) {
        return switch (systemType) {
            case "hiring", "credit", "law_enforcement" -> RiskTier.HIGH;
            case "chatbot", "recommendation" -> RiskTier.LIMITED;
            default -> RiskTier.MINIMAL;
        };
    }
}
Where you'll use itRisk tiering is a legal requirement under the EU AI Act and a best practice everywhere. It prevents over-governing low-risk systems and under-governing high-risk ones.
Under the hoodThe EU AI Act defines four risk tiers with specific obligations for each. Unacceptable risks (social scoring, real-time biometrics) are prohibited. High-risk systems face the most stringent requirements.

4Acceptable-Use Policy Skeleton

What & why. An acceptable-use policy defines what employees can and cannot do with AI systems. It covers permitted use cases, prohibited applications, data handling rules, and consequences for violations. A clear policy prevents misuse before it happens and provides a basis for disciplinary action when violations occur.

# AI Acceptable-Use Policy — Skeleton
#
# 1. Purpose
#    Define acceptable use of AI tools (LLMs, copilots, custom models)
#    within [Organization].
#
# 2. Scope
#    All employees, contractors, and third parties accessing company AI
#    systems or using AI tools on company data.
#
# 3. Permitted Uses
#    - Drafting emails, documentation, code (with review)
#    - Summarizing internal documents
#    - Brainstorming and ideation
#    - Data analysis with approved tools
#
# 4. Prohibited Uses
#    - Entering confidential/PII data into external AI tools
#      without DPA approval
#    - Making automated decisions affecting individuals without
#      human review (credit, hiring, benefits)
#    - Generating content that violates IP, privacy, or
#      anti-discrimination laws
#    - Using AI to circumvent security controls
#
# 5. Data Classification Rules
#    PUBLIC: Safe to use in any AI tool
#    INTERNAL: Only approved AI tools with data processing agreement
#    CONFIDENTIAL: Only on-premise or approved private AI only
#    RESTRICTED: No AI tools permitted
#
# 6. Review Cycle
#    This policy is reviewed quarterly and updated as regulations change.
Where you'll use itAcceptable-use policies are the first line of defense against AI misuse. They set expectations and provide a basis for enforcement when violations occur.
Under the hoodEffective policies are short, specific, and enforceable. Include real examples, clear prohibitions, and consequences. Review quarterly as AI capabilities and regulations evolve rapidly.

5Data Classification for Prompts: Public, Internal, Confidential, Restricted

What & why. Not all data can be sent to external LLM providers. Data classification labels (Public, Internal, Confidential, Restricted) determine which AI tools can process which data. This prevents accidental data exfiltration through prompts and ensures compliance with data processing agreements.

public enum DataClassification {
    PUBLIC("Safe for any AI tool, including public APIs"),
    INTERNAL("Approved AI tools with DPA; no PII"),
    CONFIDENTIAL("On-premise AI only; approved by data owner"),
    RESTRICTED("No AI processing permitted");

    private final String description;

    DataClassification(String description) {
        this.description = description;
    }

    public boolean canUseExternalAi() {
        return this == PUBLIC;
    }

    public boolean canUseApprovedAi() {
        return this == PUBLIC || this == INTERNAL;
    }

    // Prompt classification before sending to LLM
    public static DataClassification classifyPrompt(String prompt) {
        if (containsNric(prompt) || containsCreditCard(prompt)) {
            return DataClassification.RESTRICTED;
        }
        if (containsCustomerData(prompt) || containsInternalMetrics(prompt)) {
            return DataClassification.CONFIDENTIAL;
        }
        if (containsEmployeeData(prompt) || containsStrategy(prompt)) {
            return DataClassification.INTERNAL;
        }
        return DataClassification.PUBLIC;
    }

    private static boolean containsNric(String text) {
        return text.matches(".*\\b[A-Z]\\d{7}[A-Z]\\b.*");
    }

    private static boolean containsCreditCard(String text) {
        return text.matches(".*\\b\\d{4}[\\s-]?\\d{4}[\\s-]?\\d{4}[\\s-]?\\d{4}\\b.*");
    }
}
Where you'll use itPrompt classification prevents data leakage. An employee pasting a customer NRIC into ChatGPT violates PDPA. Automated classification catches this before the prompt is sent.
Under the hoodClassification can be automated using regex patterns for structured data (NRIC, credit cards) and NLP classifiers for unstructured sensitive content. Manual review handles edge cases.

6Human Oversight: Meaning and Levels

What & why. Human oversight means humans can understand, monitor, and override AI decisions. The EU AI Act defines levels: "human oversight" (human reviews before action), "human-in-the-loop" (human must approve each action), and "human-on-the-loop" (human monitors and can intervene). Higher-risk systems require stronger oversight.

// Implementation pattern for human-in-the-loop
public class HumanApprovalGate {
    public DecisionResult process(AiDecision decision) {
        // Present decision to human reviewer
        ReviewRequest review = reviewService.createReview(decision);

        // Wait for human decision (timeout: 24h)
        HumanDecision hd = reviewService.awaitDecision(
            review.getId(), Duration.ofHours(24));

        if (hd == null) {
            return DecisionResult.deferred("Awaiting human review");
        }

        if (hd.isApproved()) {
            return DecisionResult.approved(decision, hd.reviewer());
        } else {
            return DecisionResult.rejected(decision, hd.reason());
        }
    }
}
Where you'll use itHuman oversight is required for all high-risk AI systems under the EU AI Act. The level of oversight must be proportional to the risk tier and impact of the decision.
Under the hoodEffective human oversight requires clear decision interfaces, training for reviewers, and escalation paths when reviewers are unavailable. The oversight mechanism should not be a bottleneck that degrades user experience.

7Transparency: User Disclosure for Chatbots

What & why. Users must know when they are interacting with an AI system. The EU AI Act requires that AI-generated content is labeled, deepfakes are disclosed, and chatbots identify themselves. Transparency builds trust and enables informed consent — users adjust their behavior differently when they know they are talking to an AI.

@RestController
@RequestMapping("/api/chat")
public class TransparentChatController {

    // </div>
}
Where you'll use itTransparency disclosures are legally required in the EU and increasingly expected globally. They prevent deception and set appropriate expectations for AI-generated content.
Under the hoodTransparency obligations apply differently by risk tier: chatbots must disclose their nature, deepfakes must be labeled, and emotion recognition systems must inform users. Non-compliance can result in fines up to 1.5% of global turnover under the EU AI Act.

8Vendor Questionnaires and Due Diligence Basics

What & why. Using third-party AI providers (OpenAI, Azure, Bedrock) means trusting them with your data. Vendor due diligence evaluates their security, privacy, compliance, and operational practices before onboarding. Standardized questionnaires (SIG, CAIQ) ensure consistent evaluation across vendors.

// Vendor Due Diligence Checklist

Where you'll use itVendor due diligence is required before sharing any data with AI providers. Gaps identified here become contractual requirements or decision criteria for vendor selection.
Under the hoodKey AI vendor concerns: whether prompts/outputs are used for model training, data residency options, encryption standards, and incident notification timelines. Most providers now offer enterprise agreements addressing these.

9Incident Definition and Reporting Lines

What & why. An AI incident is any event where an AI system causes or could cause harm — biased output, hallucinated medical advice, data leakage, or unauthorized action. Clear incident definitions and reporting lines ensure rapid response. Without them, incidents go unreported, response is delayed, and regulatory notification deadlines are missed.

public enum IncidentSeverity {
    LOW("Bias detected in non-critical output; no user impact",
        "Internal report, fix within 7 days"),
    MEDIUM("Hallucinated information used in decision; potential impact",
        "Escalate to AI lead, fix within 48 hours, assess user impact"),
    HIGH("Data breach via AI; PII exposed; significant user harm",
        "Immediate escalation to CISO + DPO, regulatory notification"),
    CRITICAL("Safety-critical AI failure; physical harm risk",
        "System shutdown, crisis team activation, regulatory notification")
}

public record IncidentReport(
    String id,
    Instant timestamp,
    IncidentSeverity severity,
    String aiSystemId,
    String description,
    List<String> affectedUsers,
    String rootCause,
    String mitigation,
    boolean regulatoryNotificationRequired,
    Instant deadline
) {
    public static IncidentReport create(
            String systemId, IncidentSeverity severity, String desc) {
        Duration deadline = switch (severity) {
            case CRITICAL, HIGH -> Duration.ofHours(72);
            case MEDIUM -> Duration.ofDays(7);
            case LOW -> Duration.ofDays(30);
        };
        return new IncidentReport(
            UUID.randomUUID().toString(), Instant.now(),
            severity, systemId, desc, List.of(),
            "Under investigation", "Pending",
            severity.ordinal() >= IncidentSeverity.HIGH.ordinal(),
            Instant.now().plus(deadline));
    }
}
Where you'll use itIncident response for AI must be as rigorous as for cybersecurity. The EU AI Act requires notification of serious incidents within 72 hours. Delayed response amplifies harm.
Under the hoodAI incidents differ from software bugs: the "bug" is often in the model's behavior, not code. Root cause analysis requires examining prompts, training data, fine-tuning decisions, and guardrail configuration.

What & why. The NIST AI Risk Management Framework provides a voluntary but influential framework organized into four functions: Govern (establish culture), Map (identify risks), Measure (assess risks), Manage (respond to risks). It is the US standard reference for AI risk management and aligns with ISO 42001.

27Fairness Testing: Metrics and Disparate Impact Code Sketch

What & why. Fairness testing measures whether AI outputs disproportionately harm specific demographic groups. Disparate impact analysis compares outcomes across groups — a ratio below 0.8 (80% rule) indicates potential discrimination. Fairness metrics must be tracked and reported for high-risk AI systems.

// Fairness metrics calculation
public record FairnessReport(
    String metricName,
    Map<String, Double> groupScores,
    double disparateImpactRatio,
    boolean passesThreshold
) {
    // 80% rule: ratio of favorable outcomes
    // between most and least favored group
    public static FairnessReport disparateImpact(
            Map<String, Double> approvalRates) {
        double maxRate = approvalRates.values().stream()
            .mapToDouble(d -> d).max().orElse(1.0);
        double minRate = approvalRates.values().stream()
            .mapToDouble(d -> d).min().orElse(0.0);

        double ratio = minRate / maxRate;
        return new FairnessReport(
            "Disparate Impact",
            approvalRates,
            ratio,
            ratio >= 0.8  // 80% threshold
        );
    }
}

29Privacy Engineering: PETs, Differential Privacy, and Synthetic Data

What & why. Privacy-Enhancing Technologies (PETs) enable AI development while minimizing privacy risks. Differential privacy adds calibrated noise to prevent individual identification. // Differential privacy: add noise to LLM outputs
public class DifferentialPrivacyFilter {
    private final double epsilon;  // Privacy budget
    private final Random random;

    public DifferentialPrivacyFilter(double epsilon) {
        this.epsilon = epsilon;
        this.random = new SecureRandom();
    }

    // Laplace mechanism for numerical outputs
    public double privatize(double trueValue, double sensitivity) {
        double scale = sensitivity / epsilon;
        double noise = laplaceSample(scale);
        return trueValue + noise;
    }

    // For categorical outputs (e.g., classification)
    public String privatizeCategorical(
            Map<String, Double> probabilities) {
        double scale = 1.0 / epsilon;
        Map<String, Double> noisyProbs = probabilities.entrySet()
            .stream()
            .collect(Collectors.toMap(
                Map.Entry::getKey,
                e -> Math.max(0, e.getValue() + laplaceSample(scale))
            ));
        // Select based on noisy probabilities
        return weightedRandomSelect(noisyProbs);
    }

    private double laplaceSample(double scale) {
        double u = random.nextDouble() - 0.5;
        return -scale * Math.signum(u) * Math.log(1 - 2 * Math.abs(u));
    }
}

Under the hoodEpsilon (privacy budget) controls the privacy-utility trade-off: lower epsilon = stronger privacy but noisier outputs. Typical values are 0.1-1.0 for strong privacy, 1.0-10.0 for moderate.
