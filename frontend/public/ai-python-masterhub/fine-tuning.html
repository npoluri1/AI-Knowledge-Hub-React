How to Use This Chapter

Fine-tuning adapts a pretrained language model to your domain, style, or task by continuing gradient descent on curated data. This chapter progresses from understanding when fine-tuning is warranted, through supervised fine-tuning mechanics, into alignment techniques like DPO and RLHF, and concludes with production deployment concerns.

Part I · FoundationsTier 1 — when and how to fine-tune

1Prompting vs RAG vs Fine-Tune Decision Table

What & why. Not every problem needs fine-tuning. Prompt engineering costs nothing at inference time, RAG grounds outputs in retrieved documents, and fine-tuning permanently alters model behavior. Choosing wrong wastes compute and adds maintenance burden.

# Decision matrix
# | Need               | Prompt | RAG  | Fine-tune |
# |---------------------|--------|------|-----------|
# | Domain vocabulary   |   x    |  x   |    x      |
# | Live external facts |   x    |  x   |    -      |
# | Consistent style    |   -    |  -   |    x      |
# | Structured output   |   x    |  -   |    x      |
# | Zero-shot fast prot |   x    |  -   |    -      |
# | Latency at scale    |   -    |  x   |    x      |
Where you'll use itArchitecture reviews where teams debate adding a fine-tune when RAG alone would suffice, saving weeks of data curation.
Under the hoodFine-tuning shifts the model's internal probability distributions for tokens; prompting and RAG only manipulate the input context without weight changes.

2What Fine-Tuning Changes in Weights

What & why. Supervised fine-tuning runs additional gradient descent steps on your data, nudging every parameter (full FT) or a subset (PEFT/LoRA) toward your target distribution. The model retains broad knowledge from pretraining while specializing on your task's loss landscape.

for batch in dataloader:
    loss = model(batch).loss      # cross-entropy on your data
    loss.backward()
    optimizer.step()              # every weight gets a delta
    optimizer.zero_grad()

# Full FT: all parameters updated
# LoRA/PEFT: only adapter parameters updated
# The frozen base weights retain pretrained knowledge
Where you'll use itWhen you need the model to consistently produce a format, vocabulary, or reasoning pattern that prompting alone cannot reliably elicit.
Under the hoodBackpropagation through all layers means even early embeddings shift slightly; this is why fine-tuning on small, noisy data can degrade general capabilities.

3Chat JSONL Dataset Format

What & why. Most fine-tuning APIs expect JSONL where each line is a JSON object containing a messages array. The standard roles are system, user, and assistant. Consistent formatting prevents silent failures during tokenization.

{"messages": [
  {"role": "system", "content": "You are a helpful support agent."},
  {"role": "user", "content": "How do I reset my password?"},
  {"role": "assistant", "content": "Go to Settings, click Reset Password, and follow the email link."}
]}
{"messages": [
  {"role": "system", "content": "You are a helpful support agent."},
  {"role": "user", "content": "Can I change my email?"},
  {"role": "assistant", "content": "Yes, navigate to Account Settings and update your email address."}
]}
Where you'll use itOpenAI, Anthropic, and most HuggingFace SFTTrainer configs expect exactly this schema for conversational fine-tuning.
Under the hoodThe tokenizer concatenates messages with special tokens like <|im_start> and <|im_end> so the model learns turn boundaries as part of the sequence.

4Instruction / Input / Output Anatomy

What & why. Beyond chat format, many datasets use a three-field structure: instruction (the task), optional input (context), and output (desired response). This decomposition makes it clear what the model must produce given a task and context.

{"instruction": "Summarize the following article",
 "input": "AI safety researchers gathered in San Francisco...",
 "output": "AI safety researchers held a conference in SF to discuss alignment."}

# Equivalent chat format
{"messages": [
  {"role": "user", "content": "Summarize the following article:\nAI safety researchers gathered..."},
  {"role": "assistant", "content": "AI safety researchers held a conference in SF to discuss alignment."}
]}
Where you'll use itData pipelines that convert internal documentation into training examples by templating instruction/input/output triples.
Under the hoodDuring training the model only computes loss on the output (assistant) tokens; instruction tokens are provided as context but not supervised.

5OpenAI Fine-Tune API Walkthrough

What & why. OpenAI's API lets you fine-tune GPT-4o-mini and other models by uploading a JSONL file, triggering a training job, and referencing the resulting model ID. The process takes minutes to hours depending on dataset size.

import openai

client = openai.OpenAI()

# Step 1: upload training data
file = client.files.create(file=open("train.jsonl", "rb"), purpose="fine-tune")

# Step 2: create fine-tune job
job = client.fine_tuning.jobs.create(
    training_file=file.id,
    model="gpt-4o-mini-2024-07-18",
    hyperparameters={"n_epochs": 3}
)

# Step 3: poll until complete
job = client.fine_tuning.jobs.retrieve(job.id)
print(job.status, job.fine_tuned_model)
Where you'll use itRapid prototyping of domain-specific assistants where you need consistent formatting without managing GPU infrastructure.
Under the hoodOpenAI runs distributed SFT behind the scenes and provides the fine-tuned model as a new model ID you reference in subsequent API calls.

6Data Cleaning & Deduplication

What & why. Garbage in, garbage out. Duplicate examples cause the model to overweight certain patterns. Inconsistent formatting, profanity, or broken markup all degrade fine-tune quality. Cleaning is typically the highest-ROI step.

import hashlib, json

seen_hashes = set()
clean = []
for line in open("raw.jsonl"):
    row = json.loads(line)
    content = json.dumps(row["messages"], sort_keys=True)
    h = hashlib.sha256(content.encode()).hexdigest()
    if h not in seen_hashes and len(content) > 20:
        seen_hashes.add(h)
        clean.append(row)

print(f"{len(clean)} unique examples from {sum(1 for _ in open('raw.jsonl'))} total")
Where you'll use itEvery production fine-tune starts here; teams often find 10-30% duplicates in their first dataset export from support tickets or logs.
Under the hoodNear-duplicate detection (e.g., MinHash or cosine similarity on embeddings) catches paraphrased duplicates that exact hashing misses.

7Train / Validation Split & Loss Watching

What & why. Splitting data 90/10 or 95/5 lets you monitor validation loss during training. If training loss drops while validation loss rises, you are overfitting. A held-out set is non-negotiable for quality assurance.

from datasets import load_dataset

ds = load_dataset("json", data_files="train.jsonl", split="train")
split = ds.train_test_split(test_size=0.1, seed=42)
split["train"].to_json("sft_train.jsonl")
split["test"].to_json("sft_val.jsonl")

# In HF Trainer:
# training_args = TrainingArguments(
#     eval_strategy="steps", eval_steps=50,
#     load_best_model_at_end=True, metric_for_best_model="eval_loss"
# )
Where you'll use itEvery supervised fine-tune uses this pattern; the validation curve is the primary signal for early stopping decisions.
Under the hoodEvaluation loss is computed on the validation set without gradient updates; it measures how well the model generalizes beyond the training examples.

8Epochs, Learning Rate & Basics

What & why. Epochs define how many passes over the data; learning rate controls step size. Too many epochs or too high a learning rate causes catastrophic forgetting. Typical fine-tuning uses 1-5 epochs with learning rates between 1e-5 and 5e-5.

from transformers import TrainingArguments

args = TrainingArguments(
    output_dir="./checkpoints",
    num_train_epochs=3,
    learning_rate=2e-5,
    lr_scheduler_type="cosine",
    warmup_ratio=0.1,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,  # effective batch = 16
    fp16=True,
)
Where you'll use itFine-tuning any HuggingFace model; these hyperparameters are the first knobs to tune when results are unsatisfactory.
Under the hoodWarmup prevents large gradient shocks early in training when the loss landscape is still being explored; cosine decay smoothly reduces the rate.

9Catastrophic Forgetting Intro

What & why. Fine-tuning on narrow data can erase general capabilities the model learned during pretraining. The model becomes excellent at your task but incoherent on everything else. This is the primary risk of aggressive fine-tuning.

# Symptoms of catastrophic forgetting:
# 1. Fine-tune eval loss drops, but general chat quality collapses
# 2. Model stops following basic instructions outside your domain
# 3. Perplexity on a general benchmark (e.g., HellaSwag) spikes

# Mitigation strategies:
# - Use LoRA instead of full FT (fewer parameters changed)
# - Keep epochs low (1-3)
# - Mix in general-purpose data (replay buffer)
# - Use smaller learning rates
Where you'll use itWhen teams report that their fine-tuned model "forgot" how to follow basic prompts or answer general questions.
Under the hoodNeural networks exhibit sequential learning bias; new gradient updates overwrite weight regions used for prior capabilities, especially in later layers.

10When NOT to Fine-Tune

What & why. Fine-tuning is expensive, requires data, and adds deployment complexity. If your problem is solved by better prompting, few-shot examples, or RAG retrieval, skip fine-tuning. Small datasets (under 500 examples) rarely justify it.

# Decision checklist -- do NOT fine-tune if:
# - You have fewer than 500 high-quality examples
# - The task changes frequently (new products, policies weekly)
# - A general model already handles it with good prompting
# - You need to cite sources (RAG is better for grounding)
# - The main gain is tone/format (system prompt + examples suffice)
# - You cannot commit to ongoing maintenance and retraining

# Do fine-tune when:
# - You need consistent output format at scale
# - Domain vocabulary is critical (legal, medical, financial)
# - Latency requires smaller fine-tuned model over large prompted one
# - You have 1000+ labeled examples and a stable task definition
Where you'll use itProject kickoffs where the team assumes fine-tuning is needed; this checklist saves weeks of unnecessary work.
Under the hoodThe break-even point depends on task complexity: simple formatting tasks yield to prompting, while deep domain reasoning requires weight adaptation.

11Small-Model-First Strategy

What & why. Start with the smallest model that could plausibly solve your task (e.g., 1.5B or 3B parameters). Fine-tune it, evaluate, and only scale up if quality is insufficient. Smaller models are cheaper to train, faster to iterate, and easier to deploy.

from transformers import AutoModelForCausalLM

# Start small, scale only if needed
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-1.5B-Instruct")

# Scale strategy: 1.5B -> 3B -> 7B -> 13B
# Each step: fine-tune, eval on benchmark, measure cost/quality
Where you'll use itCost-conscious teams who discover that a fine-tuned 3B model outperforms a prompted 70B model on their specific structured task.
Under the hoodSmaller models have less capacity but also less noise; fine-tuning them on a focused task can yield sharper specialization per parameter.

12Evaluating Fine-Tune vs Base

What & why. A fine-tune is only useful if it improves on your target task without degrading general capabilities. You need both task-specific metrics and general benchmarks to make this judgment.

import evaluate

accuracy_metric = evaluate.load("accuracy")

for model_name in ["base-model", "your-finetuned-model"]:
    preds = run_inference(model_name, eval_data)
    acc = accuracy_metric.compute(
        references=eval_data["labels"], predictions=preds
    )
    print(f"{model_name}: accuracy={acc['accuracy']:.3f}")

# Also check: MMLU, HellaSwag, HumanEval before and after
# Task-specific gains may mask general regressions
Where you'll use itBefore promoting any fine-tuned model to production; the eval report is the gate between experiment and deployment.
Under the hoodTask-specific gains may mask regressions on general benchmarks; always check both dimensions to ensure the model remains broadly useful.

Part II · IntermediateTier 2 — hands-on SFT with HuggingFace

13HuggingFace Trainer Basics

What & why. The Trainer class from transformers handles the training loop, logging, checkpointing, and evaluation for you. Pair it with TrainingArguments for configuration and a data collator for batch preparation.

from transformers import (
    AutoModelForCausalLM, AutoTokenizer,
    TrainingArguments, Trainer, DataCollatorForLanguageModeling
)

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-3B-Instruct")
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-3B-Instruct")

training_args = TrainingArguments(
    output_dir="./output", num_train_epochs=3,
    learning_rate=2e-5, per_device_train_batch_size=4,
    logging_steps=10, save_strategy="epoch",
    evaluation_strategy="epoch"
)

trainer = Trainer(
    model=model, args=training_args,
    train_dataset=train_ds, eval_dataset=val_ds,
    data_collator=DataCollatorForLanguageModeling(tokenizer, mlm=False)
)
trainer.train()
Where you'll use itAny HuggingFace fine-tuning project; Trainer is the standard entry point for supervised training without writing a custom loop.
Under the hoodTrainer wraps a standard PyTorch training loop with distributed training support (DDP/FSDP), mixed precision, gradient accumulation, and checkpoint resumption.

14HF Datasets: Map & Tokenize

What & why. The datasets library provides efficient, memory-mapped data processing. Map functions apply tokenization across your dataset in parallel. Arrow-backed storage means no JSON parsing overhead during training.

from datasets import load_dataset
from transformers import AutoTokenizer

ds = load_dataset("json", data_files="train.jsonl", split="train")
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-3B-Instruct")
tokenizer.pad_token = tokenizer.eos_token

def tokenize(example):
    text = tokenizer.apply_chat_template(
        example["messages"], tokenize=False
    )
    return tokenizer(text, truncation=True, max_length=2048)

tokenized = ds.map(tokenize, batched=True, remove_columns=ds.column_names)
Where you'll use itEvery HuggingFace training pipeline; apply_chat_template ensures consistent formatting with the model's expected prompt structure.
Under the hoodMap uses multiprocessing by default (num_proc=auto), processing millions of examples in seconds via Apache Arrow's columnar format.

15Packing vs Padding

What & why. Padding wastes compute by filling short sequences with tokens. Packing concatenates multiple examples into a single sequence, eliminating waste but requiring attention mask adjustments to prevent cross-example attention.

# Without packing: every batch padded to max_length
# Wasted compute: short examples padded with 80%+ pad tokens

# With packing: multiple examples per sequence
# SFTTrainer has built-in packing=True flag
from trl import SFTConfig

config = SFTConfig(
    packing=True,
    max_seq_length=2048,
    # Handles block-diagonal attention masking automatically
)

# Monitor: tokens_per_second should increase 2-5x
# Verify: loss should be comparable to unpadded training
Where you'll use itWhen training on variable-length data (chat conversations, documents); packing can 2-5x throughput compared to naive padding.
Under the hoodTrue packing requires block-diagonal attention masks so tokens from different examples do not attend to each other; HuggingFace handles this automatically.

16LoRA Preview via PEFT

What & why. Even before diving deep into LoRA (covered in the next chapter), PEFT lets you add trainable low-rank adapters to frozen model weights. This reduces GPU memory by 60-80% while achieving comparable quality to full fine-tuning.

from peft import LoraConfig, get_peft_model, TaskType

lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16, lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05
)

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-3B-Instruct")
peft_model = get_peft_model(model, lora_config)
peft_model.print_trainable_parameters()
# trainable params: 3,407,872 || all params: 3,000,000,000 || 0.11%
Where you'll use itFine-tuning on consumer GPUs where full FT is impossible; a single 24GB GPU can fine-tune a 7B model with LoRA.
Under the hoodPEFT inserts adapter matrices alongside frozen weights; only these small matrices receive gradients, drastically cutting memory for optimizer states.

17TRL SFTTrainer

What & why. TRL (Transformer Reinforcement Learning) provides SFTTrainer, which extends HF Trainer with conversation formatting, label masking, and packing support out of the box. It is the recommended tool for supervised fine-tuning of chat models.

from trl import SFTTrainer, SFTConfig

sft_config = SFTConfig(
    output_dir="./sft_output",
    per_device_train_batch_size=4,
    learning_rate=2e-5,
    num_train_epochs=3,
    max_seq_length=2048,
    packing=True,
)

def formatting_func(examples):
    return [tokenizer.apply_chat_template(msgs, tokenize=False)
            for msgs in examples["messages"]]

trainer = SFTTrainer(
    model=model, args=sft_config,
    train_dataset=ds, eval_dataset=val_ds,
    formatting_func=formatting_func
)
trainer.train()
Where you'll use itModern fine-tuning projects; SFTTrainer handles chat formatting, packing, and label masking automatically.
Under the hoodSFTTrainer overrides the default loss computation to mask non-assistant tokens, so the model only learns to generate responses.

18Completion-Only Loss Masking

What & why. In chat fine-tuning, you only want the model to learn predicting the assistant's response, not regurgitating the user's prompt. Loss masking sets labels to -100 for all non-assistant tokens, excluding them from the gradient.

# Manual masking approach
def mask_prompt_tokens(examples):
    labels = examples["input_ids"].copy()
    in_assistant = False
    for i, token_id in enumerate(labels):
        if token_id == assistant_token_id_start:
            in_assistant = True
        elif token_id == assistant_token_id_end:
            in_assistant = False
        if not in_assistant:
            labels[i] = -100  # ignore in loss
    return {"labels": labels}

# SFTTrainer does this automatically for chat-formatted data
# PyTorch CrossEntropyLoss ignores targets == -100
Where you'll use itEvery chat fine-tune; without masking, the model wastes capacity learning to reproduce prompts rather than generate responses.
Under the hoodPyTorch's CrossEntropyLoss ignores targets equal to -100, so masked positions contribute zero gradient to the model.

19Checkpointing & Resume

What & why. Fine-tuning jobs can take hours or days. Checkpointing saves model state periodically so you can resume from the last save if the job crashes, or pick the best checkpoint based on validation loss.

training_args = TrainingArguments(
    output_dir="./checkpoints",
    save_strategy="steps",
    save_steps=200,
    save_total_limit=3,
    load_best_model_at_end=True,
    metric_for_best_model="eval_loss",
)

# Resume a crashed training run
trainer.train(resume_from_checkpoint="./checkpoints/checkpoint-1000")

# Or auto-resume from latest
trainer.train(resume_from_checkpoint=True)
Where you'll use itLong-running fine-tunes on cloud instances where spot interrupts or OOM errors are common.
Under the hoodCheckpoints save model weights, optimizer state, scheduler state, and RNG state so training resumes identically, not just approximately.

20Overfitting Curve Signatures

What & why. Recognizing overfitting early saves wasted compute. The telltale sign is diverging train and validation loss curves: train loss keeps falling while validation loss plateaus or rises.

# Overfitting signatures to monitor:
# 1. val_loss stops decreasing while train_loss keeps dropping
# 2. Model starts memorizing exact training examples verbatim
# 3. Generation on held-out prompts becomes repetitive
# 4. Task accuracy on eval set plateaus while train accuracy = 100%

# Prevention toolkit:
# - Early stopping (patience=3 on eval_loss)
# - Dropout / LoRA dropout
# - Data augmentation
# - Fewer epochs (1-3 typically)
# - Mix in regularization data
Where you'll use itReviewing training logs; the moment val_loss curves upward, you should stop training or increase regularization.
Under the hoodOverfitting happens when the model memorizes training-specific patterns rather than learning generalizable features; small datasets amplify this risk.

21Synthetic Data Generation

What & why. When you lack enough real training data, you can use a stronger model to generate synthetic examples. This bootstraps your dataset, but quality filtering is critical to avoid amplifying the teacher's biases.

import openai

# Critical: filter synthetic data
# - Remove near-duplicates
# - Human-review a sample
# - Check for hallucinated facts
# - Mix real and synthetic (e.g., 70/30)
Where you'll use itBootstrapping fine-tuning datasets when real labeled examples are scarce or expensive to annotate.
Under the hoodSynthetic data inherits the teacher model's knowledge and biases; mixing real and synthetic examples often yields the best results.

22Distillation: Teacher-Student Framework

What & why. Knowledge distillation trains a smaller student model to mimic a larger teacher's output distributions. The student learns not just the correct answer but the teacher's confidence and reasoning patterns encoded in soft label probabilities.

import torch, torch.nn.functional as F

def distillation_loss(student_logits, teacher_logits, labels,
                      temperature=2.0, alpha=0.5):
    soft_loss = F.kl_div(
        F.log_softmax(student_logits / temperature, dim=-1),
        F.softmax(teacher_logits / temperature, dim=-1),
        reduction="batchmean"
    ) * (temperature ** 2)

    hard_loss = F.cross_entropy(
        student_logits.view(-1, student_logits.size(-1)),
        labels.view(-1)
    )
    return alpha * soft_loss + (1 - alpha) * hard_loss
Where you'll use itDeploying smaller models that match the quality of larger ones; distilled 7B models often match prompted 70B models on specific tasks.
Under the hoodSoft labels encode inter-class relationships the teacher has learned; the temperature parameter controls how much of this dark knowledge transfers to the student.

Part III · AdvancedTier 3 — alignment and preference optimization

24Preference Pairs: Chosen vs Rejected

What & why. Alignment training uses pairs of responses where one is preferred (chosen) and one is dispreferred (rejected). The model learns to score chosen responses higher than rejected ones, shaping behavior toward human preferences.

{
  "prompt": "Explain quantum computing",
  "chosen": "Quantum computing uses qubits that can exist in superposition...",
  "rejected": "Quantum computing is like regular computing but faster..."
}
{
  "prompt": "Write a poem about rain",
  "chosen": "Soft drops compose a symphony on the windowpane...",
  "rejected": "Rain falls down from the sky it is wet and cold..."
}
Where you'll use itPost-SFT alignment where you want the model to prefer helpful, harmless, and honest responses over lazy or incorrect ones.
Under the hoodThe quality gap between chosen and rejected drives learning signal; too-small gaps yield weak training; too-large gaps make the model overconfident.

25Reward Model Concept

What & why. RLHF starts by training a reward model on preference pairs to assign scalar scores to responses. This learned reward function then guides the language model's policy optimization via reinforcement learning.

from transformers import AutoModelForSequenceClassification

rm = AutoModelForSequenceClassification.from_pretrained(
    "Qwen/Qwen2.5-3B-Instruct", num_labels=1
)

for batch in preference_loader:
    chosen_scores = rm(batch["chosen_input_ids"]).logits
    rejected_scores = rm(batch["rejected_input_ids"]).logits
    loss = -F.logsigmoid(chosen_scores - rejected_scores).mean()
    loss.backward()
Where you'll use itRLHF pipelines where you need a learned scoring function to guide policy optimization without human-in-the-loop scoring.
Under the hoodThe reward model uses a Bradley-Terry preference model: P(chosen > rejected) = sigmoid(r_chosen - r_rejected).

26RLHF PPO Loop Components

What & why. PPO (Proximal Policy Optimization) is the RL algorithm used in RLHF. The language model is the policy, the reward model provides the signal, and a KL penalty prevents the model from diverging too far from the SFT baseline.

# PPO components in RLHF:
# 1. Policy model (the LLM being optimized)
# 2. Reward model (scores responses)
# 3. Reference model (frozen SFT copy, computes KL penalty)
# 4. Value model (estimates expected future rewards)

# Simplified PPO step
old_logprobs = ref_model(generated_tokens).logprobs
new_logprobs = policy_model(generated_tokens).logprobs
rewards = reward_model(generated_tokens) - kl_coef * (new_logprobs - old_logprobs)

ratio = torch.exp(new_logprobs - old_logprobs)
clipped = torch.clamp(ratio, 1-eps, 1+eps) * advantages
loss = -torch.min(ratio * advantages, clipped).mean()
Where you'll use itFull RLHF pipelines at scale (ChatGPT, Claude); PPO is complex but offers the most control over alignment.
Under the hoodThe KL penalty term prevents reward hacking, where the model finds degenerate outputs that score high with the reward model but are nonsensical to humans.

27DPO Objective & TRL DPOTrainer

What & why. Direct Preference Optimization bypasses the reward model entirely by deriving a closed-form objective from the RLHF framework. It trains the policy directly on preference pairs using a simple binary cross-entropy loss.

from trl import DPOTrainer, DPOConfig

dpo_config = DPOConfig(
    output_dir="./dpo_output",
    per_device_train_batch_size=2,
    learning_rate=5e-7,
    beta=0.1,                    # KL penalty strength
    num_train_epochs=1,
    gradient_accumulation_steps=8
)

trainer = DPOTrainer(
    model=model,
    ref_model=ref_model,         # frozen SFT copy
    args=dpo_config,
    train_dataset=preference_ds,
    tokenizer=tokenizer
)
trainer.train()
Where you'll use itWhen you want alignment without the complexity of RL; DPO is the most popular alternative to PPO in 2024-2025.
Under the hoodDPO reparameterizes the RLHF objective so the optimal policy has a closed-form solution relative to the reward function, eliminating the need for a separate reward model.

28ORPO: Single-Stage Alignment

What & why. Odds Ratio Preference Optimization combines SFT and alignment into a single training stage. It adds a preference loss term to the standard SFT loss, eliminating the need for a separate alignment phase.

from trl import ORPOConfig, ORPOTrainer

orpo_config = ORPOConfig(
    output_dir="./orpo_output",
    learning_rate=5e-6,
    beta=0.1,
    per_device_train_batch_size=4,
    num_train_epochs=1
)

trainer = ORPOTrainer(
    model=model, args=orpo_config,
    train_dataset=preference_ds,  # needs chosen + rejected
    tokenizer=tokenizer
)
trainer.train()
Where you'll use itWhen you want to skip the two-stage SFT-then-DPO pipeline; ORPO trains a base model directly to preference-aligned output in one pass.
Under the hoodORPO uses the odds ratio between chosen and rejected responses as the preference signal, added directly to the cross-entropy SFT loss.

29KTO: Binary Feedback Optimization

What & why. KTO (Kahneman-Tversky Optimization) works with binary good/bad signals rather than preference pairs. This is easier to collect at scale since annotators only need to rate individual responses, not compare pairs.

# KTO dataset format
{"prompt": "What is 2+2?", "completion": "4", "label": true}
{"prompt": "What is 2+2?", "completion": "5", "label": false}

from trl import KTOConfig, KTOTrainer

kto_config = KTOConfig(
    output_dir="./kto_output",
    learning_rate=5e-6, beta=0.1
)

trainer = KTOTrainer(
    model=model, ref_model=ref_model,
    args=kto_config,
    train_dataset=kto_ds,
    tokenizer=tokenizer
)
Where you'll use itWhen you have thumbs-up/thumbs-down data from users rather than ranked preference pairs; scales better for production feedback loops.
Under the hoodKTO adapts prospect theory: losses (bad responses) are weighted more heavily than gains (good responses), matching human psychology.

30Alignment Eval: Win-Rates & LLM Judge

What & why. Evaluating aligned models requires comparing outputs to a reference. Win-rate evaluation (head-to-head comparison) and LLM-as-judge (using GPT-4 to score) are the standard approaches for measuring alignment quality.

def llm_judge(prompt, response_a, response_b):
    resp = client.chat.completions.create(
        model="gpt-4o",
        messages=[{
            "role": "user",
            "content": f"Compare these two responses to: {prompt}\n\n"
                       f"A: {response_a}\n\nB: {response_b}\n\n"
                       "Which is better? Respond with JSON: "
                       '{"winner": "A"|"B"|"tie", "reasoning": "..."}'
        }],
        response_format={"type": "json_object"}
    )
    return json.loads(resp.choices[0].message.content)

Under the hoodLLM judges correlate ~80% with human preferences; position bias is mitigated by swapping A/B ordering and averaging.

32Multi-Task Mix Ratios

What & why. When fine-tuning on multiple tasks simultaneously, the ratio of examples per task significantly affects performance. Equal mixing rarely works; task-specific ratios must balance each task's difficulty and data availability.

task_weights = {
    "summarization": 0.30,
    "classification": 0.25,
    "extraction": 0.20,
    "generation": 0.15,
    "safety": 0.10
}

# Proportional sampling
from torch.utils.data import WeightedRandomSampler
weights = [task_weights[ex["task"]] for ex in dataset]
sampler = WeightedRandomSampler(weights, num_samples=len(dataset))

# Alternative: temperature-based mixing
# n_i / sum(n_j^(1-T)) where T controls rebalancing
Where you'll use itMulti-task fine-tunes where you need the model to handle several capabilities without separate models for each.
Under the hoodTemperature-based mixing upweights rare tasks and downweights frequent ones, preventing majority-task dominance in gradient updates.

33Continual Learning & Replay

What & why. When you need to update a fine-tuned model with new data over time, continual learning techniques prevent catastrophic forgetting of previously learned capabilities. Replay buffers mix old data with new during training.

replay_buffer = load_previous_data("old_training.jsonl")
new_data = load_new_data("new_training.jsonl")

# Mix: 20% old data, 80% new data
import random
mixed = (
    random.sample(replay_buffer, k=int(0.2 * len(new_data)))
    + list(new_data)
)
random.shuffle(mixed)

# Or use elastic weight consolidation (EWC)
# Penalizes changes to important weights from previous tasks
# fisher = compute_fisher(old_model, replay_buffer)
# ewc_loss = lambda_ * (fisher * (theta - theta_old)^2).sum()
Where you'll use itModels that need periodic updates with new products, policies, or knowledge without retraining from scratch.
Under the hoodReplay buffers are simple but effective; EWC and similar methods add regularization terms that protect important weights from previous training phases.

34Merge and Unload Adapters

What & why. After training, LoRA adapters can be merged into the base model weights to produce a single model with no adapter overhead at inference. This eliminates the latency and complexity of loading separate adapter files.

from peft import PeftModel

base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-3B-Instruct")
model = PeftModel.from_pretrained(base_model, "./lora_checkpoint")

# Merge adapter weights into base
merged_model = model.merge_and_unload()

# Save as standalone model (no adapter files needed)
merged_model.save_pretrained("./merged_model")
tokenizer.save_pretrained("./merged_model")
Where you'll use itProduction deployment where you want a single model artifact without PEFT overhead; reduces inference latency by removing adapter forward passes.
Under the hoodMerging computes W_merged = W_base + alpha/r * B @ A for each adapted layer, producing identical output to adapter-based inference.

What & why. GGUF is the format used by llama.cpp for efficient CPU/GPU inference. Exporting your fine-tuned model to GGUF lets you run it locally, test quantized versions, and deploy without Python dependency.

36Full-FT vs PEFT Compute Math

What & why. Understanding the compute cost difference between full fine-tuning and PEFT is essential for budgeting. Full FT requires optimizer states for every parameter (4x model size in fp32), while LoRA reduces this by orders of magnitude.

# Compute comparison for a 7B parameter model:
# Full FT (AdamW, fp32 states):
#   Weights:    7B * 4 bytes = 28 GB
#   Gradients:  7B * 4 bytes = 28 GB
#   Optimizer:  7B * 8 bytes = 56 GB  (m + v)
#   Total:      ~112 GB

# LoRA (rank=16, 4 target modules):
#   Frozen weights: 7B * 2 bytes (fp16) = 14 GB
#   LoRA params:    ~20M * 4 bytes = 80 MB
#   Optimizer:      ~20M * 8 bytes = 160 MB
#   Total:          ~14.3 GB

# Ratio: full FT uses ~8x more memory
Where you'll use itGPU budgeting and infrastructure planning; this math determines how many GPUs you need and what instance type to provision.
Under the hoodThe dominant cost is optimizer states; AdamW stores first and second moments (2x model size), which PEFT avoids by freezing most parameters.

37FSDP, DeepSpeed ZeRO Overview

What & why. Distributed training frameworks split model state across GPUs. DeepSpeed ZeRO partitions optimizer states (Stage 1), gradients (Stage 2), and parameters (Stage 3) to reduce per-GPU memory. FSDP is PyTorch's native equivalent.

# DeepSpeed ZeRO Stage 2 config
{
    "zero_optimization": {
        "stage": 2,
        "offload_optimizer": {"device": "cpu"},
        "overlap_comm": true
    },
    "fp16": {"enabled": true},
    "train_batch_size": 32,
    "train_micro_batch_size_per_gpu": 4,
    "gradient_accumulation_steps": 2
}

# FSDP equivalent
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP
model = FSDP(model, sharding_strategy=ShardingStrategy.FULL_SHARD)
Where you'll use itTraining models larger than single-GPU capacity; ZeRO-2 with CPU offloading lets a 7B model train on 2x 24GB GPUs.
Under the hoodZeRO Stage 3 partitions parameters so each GPU stores only 1/N of the model; all-gather operations reconstruct the full parameters during forward/backward passes.
