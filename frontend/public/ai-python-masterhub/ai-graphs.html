1DAG Definition and Topological Order

What & why. A Directed Acyclic Graph (DAG) is a graph with directed edges and no cycles. Topological ordering arranges nodes so every edge goes from earlier to later. DAGs are the foundation of workflow engines, build systems, and data pipelines because they guarantee a valid execution order without deadlocks.

from collections import defaultdict, deque

def topological_sort(graph: dict[str, list[str]]) -> list[str]:
    in_degree = defaultdict(int)
    for node in graph:
        in_degree.setdefault(node, 0)
        for neighbor in graph[node]:
            in_degree[neighbor] += 1
    queue = deque([n for n in in_degree if in_degree[n] == 0])
    order = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for neighbor in graph[node]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)
    return order

dag = {
    "extract": ["clean", "validate"],
    "clean": ["transform"], "validate": ["transform"],
    "transform": ["aggregate", "index"],
    "aggregate": ["export"], "index": ["export"], "export": [],
}
print(topological_sort(dag))
Where you'll use itTopological sort is the core algorithm for task schedulers (Airflow, Prefect), build systems (Make, Bazel), and data pipeline orchestrators.
Under the hoodKahn's algorithm (BFS-based) detects cycles: if sorted output has fewer nodes than input, a cycle exists. DFS-based sort uses post-order traversal and detects cycles via back edges.

3State Machines: States, Transitions, Guards

What & why. A state machine defines a system as a set of states with guarded transitions. The system is always in exactly one state. Transitions fire when a condition (guard) is met. State machines model lifecycles (order: pending to paid to shipped), agent modes (idle to planning to executing), and protocol handlers.

from enum import Enum

class OrderState(Enum):
    PENDING = "pending"
    PAID = "paid"
    SHIPPED = "shipped"
    DELIVERED = "delivered"
    CANCELLED = "cancelled"

transitions = {
    (OrderState.PENDING, "payment_received"): OrderState.PAID,
    (OrderState.PENDING, "cancelled"): OrderState.CANCELLED,
    (OrderState.PAID, "shipped"): OrderState.SHIPPED,
    (OrderState.SHIPPED, "delivered"): OrderState.DELIVERED,
}

class OrderMachine:
    def __init__(self):
        self.state = OrderState.PENDING
    def transition(self, event: str):
        key = (self.state, event)
        if key in transitions:
            self.state = transitions[key]
            print(f"  {event}: {self.state.value}")
        else:
            print(f"  {event}: invalid from {self.state.value}")

machine = OrderMachine()

machine.transition("shipped")
machine.transition("delivered")
machine.transition("cancelled")
Where you'll use itState machines are used for order processing, user account lifecycles, agent mode switching, API protocol handlers, and any system where valid operations depend on current state.
Under the hoodState machines are isomorphic to directed graphs where nodes are states and edges are transitions. Harel statecharts extend this with hierarchy (nested states), parallelism, and history.

4Cycles and Termination Conditions

What & why. Cycles in graphs enable loops: retry on failure, iterative refinement, agent decision loops. Without termination conditions, cycles cause infinite execution. Every cyclic graph must define a stopping criterion: max iterations, convergence threshold, explicit exit signal, or timeout.

from typing import TypedDict

class LoopState(TypedDict):
    value: float
    iteration: int
    converged: bool

def iterate(state: LoopState) -> dict:
    new_value = state["value"] * 0.5 + 0.25
    diff = abs(new_value - state["value"])
    return {"value": new_value, "iteration": state["iteration"] + 1, "converged": diff < 0.001}

def should_continue(state: LoopState) -> bool:
    return not state["converged"] and state["iteration"] < 100

state = {"value": 0.0, "iteration": 0, "converged": False}
while should_continue(state):
    state = iterate(state)
print(f"Converged to {state['value']:.4f} in {state['iteration']} iterations")
Where you'll use itEvery agent loop, retry mechanism, and iterative refinement pattern requires termination conditions. Without them, LLM costs grow unbounded.
Under the hoodTermination conditions are checked between cycle iterations. In LangGraph, this is the routing function after each node. In plain Python, it is the while-loop condition.

6BFS and DFS Traversal Recap

What & why. Breadth-First Search visits nodes level by level using a queue. Depth-First Search explores as deep as possible before backtracking using a stack. BFS finds shortest paths in unweighted graphs. DFS is used for cycle detection, topological sort, and exploring all paths.

from collections import deque

def bfs(graph, start):
    visited, queue = set(), deque([start])
    visited.add(start)
    order = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append(neighbor)
    return order

def dfs(graph, start):
    visited, stack, order = set(), [start], []
    while stack:
        node = stack.pop()
        if node not in visited:
            visited.add(node)
            order.append(node)
            stack.extend(reversed(graph[node]))
    return order

graph = {"root": ["a", "b"], "a": ["c", "d"], "b": ["e"], "c": [], "d": [], "e": []}
print("BFS:", bfs(graph, "root"))
print("DFS:", dfs(graph, "root"))
Where you'll use itBFS is used for level-order processing and shortest-path queries. DFS is used for cycle detection, dependency resolution, and exploring all possible paths.
Under the hoodBoth run in O(V+E) time and O(V) space. BFS uses a queue; DFS uses a stack (or recursion). For large graphs, iterative DFS avoids Python's recursion limit.

7Workflow vs Agent Spectrum

What & why. Workflows are deterministic graphs where the path is predetermined or conditionally selected. Agents are dynamic graphs where the LLM decides the next node at runtime. Most real systems fall on a spectrum: simple routing is workflow-like, while multi-step reasoning with tool use is agent-like.

# Semi-dynamic: LLM classifies but routes to fixed nodes

# Full agent: LLM decides next action from unbounded options
# agent: think -> (any_tool | respond | ask_human)

# |---Workflow---|---Hybrid---|---Agent---|

Where you'll use itUse workflows for predictable paths (data pipelines, approval chains). Use agents for open-ended tasks (research, coding). Use hybrid for most production systems.
Under the hoodThe distinction maps to graph expressiveness: workflows are DAGs or finite state machines (decidable). Agents are Turing-complete (potentially undecidable). Workflows have bounded execution; agents need recursion limits.

8Event-Driven Pipelines

What & why. Event-driven pipelines decouple graph nodes via message queues or event buses. Instead of direct edges, nodes publish events and subscribe to topics. This enables loose coupling, independent scaling, replay, and late-binding of processing logic.

from collections import defaultdict
from typing import Callable, Any

class EventBus:
    def __init__(self):
        self.handlers = defaultdict(list)
        self.events = []
    def subscribe(self, topic, handler):
        self.handlers[topic].append(handler)
    def publish(self, topic, data):
        self.events.append((topic, data))
        for handler in self.handlers.get(topic, []):
            handler(data)
    def replay(self):
        for topic, data in self.events:
            for handler in self.handlers.get(topic, []):
                handler(data)

bus = EventBus()
bus.subscribe("data.extracted", lambda d: print(f"Clean: {d}"))
bus.subscribe("data.cleaned", lambda d: print(f"Transform: {d}"))
bus.subscribe("data.transformed", lambda d: print(f"Store: {d}"))
bus.publish("data.extracted", "raw_record_1")
bus.publish("data.cleaned", "clean_record_1")
bus.publish("data.transformed", "final_record_1")
Where you'll use itEvent-driven pipelines are used for real-time data processing (Kafka + Flink), microservice orchestration, and decoupled AI inference pipelines.
Under the hoodEvent buses replace direct edges with pub/sub messaging. This adds latency but gains decoupling, replayability, and independent scaling.

11Building a DAG Executor in Pure Python

What & why. A DAG executor takes a graph definition and executes nodes in topological order, running independent nodes in parallel. Building one from scratch reveals how workflow engines work: dependency resolution, parallel scheduling, error propagation, and result collection.

import asyncio
from collections import defaultdict
from typing import Callable

class DAGExecutor:
    def __init__(self):
        self.nodes = {}
        self.edges = defaultdict(list)
        self.in_degree = defaultdict(int)
    def add_node(self, name, func):
        self.nodes[name] = func
        self.in_degree.setdefault(name, 0)
    def add_edge(self, source, target):
        self.edges[source].append(target)
        self.in_degree[target] += 1
    async def execute(self, initial_state):
        state = dict(initial_state)
        queue = [n for n in self.nodes if self.in_degree[n] == 0]
        while queue:
            tasks = []
            for node_name in queue:
                result = self.nodes[node_name](state)
                state.update(result)
            next_queue = []
            for node_name in queue:
                for target in self.edges[node_name]:
                    self.in_degree[target] -= 1
                    if self.in_degree[target] == 0:
                        next_queue.append(target)
            queue = next_queue
        return state

dag = DAGExecutor()
dag.add_node("fetch", lambda s: {"data": "fetched"})
dag.add_node("process", lambda s: {"data": f"processed({s['data']})"})
dag.add_edge("fetch", "process")
result = asyncio.run(dag.execute({}))
print(result["data"])
Where you'll use itUnderstanding DAG executors is essential for custom workflow engines, debugging Airflow/Prefect DAGs, and building lightweight orchestrators.
Under the hoodThe executor maintains a ready queue (nodes with in_degree=0). After each batch, it decrements in_degree for downstream nodes. This is Kahn's algorithm adapted for parallel execution.

12Cycle Detection Algorithm

What & why. Cycle detection prevents infinite loops in graph-based systems. DFS-based detection uses three colors: white (unvisited), gray (in-progress), black (completed). Encountering a gray node means a cycle exists. This is critical for validating workflows before execution.

class CycleDetector:
    WHITE, GRAY, BLACK = 0, 1, 2
    def __init__(self, graph):
        self.graph = graph
        self.color = {node: self.WHITE for node in graph}
        self.cycle_path = []
    def has_cycle(self):
        for node in self.graph:
            if self.color[node] == self.WHITE:
                if self._dfs(node):
                    return True
        return False
    def _dfs(self, node):
        self.color[node] = self.GRAY
        self.cycle_path.append(node)
        for neighbor in self.graph.get(node, []):
            if self.color[neighbor] == self.GRAY:
                cycle_start = self.cycle_path.index(neighbor)
                print(f"Cycle: {' -> '.join(self.cycle_path[cycle_start:])} -> {neighbor}")
                return True
            if self.color[neighbor] == self.WHITE:
                if self._dfs(neighbor):
                    return True
        self.color[node] = self.BLACK
        self.cycle_path.pop()
        return False

dag = {"A": ["B", "C"], "B": ["D"], "C": ["D"], "D": []}
cyclic = {"A": ["B"], "B": ["C"], "C": ["A"]}
print("DAG:", CycleDetector(dag).has_cycle())
print("Cyclic:", CycleDetector(cyclic).has_cycle())
Where you'll use itCycle detection is used in build systems, workflow validators, spreadsheet engines, and graph database constraint checking.
Under the hoodDFS cycle detection runs in O(V+E) time. A back edge (to a gray node) indicates a cycle. Tarjan's algorithm finds all strongly connected components in a single DFS pass.

13Retry and Backoff Edges

What & why. Modeling retries as explicit graph edges makes failure handling visible and configurable. A retry edge goes from the failed node back to itself with a backoff delay. This transforms implicit error handling into explicit graph topology.

import time, random

class RetryState:
    def __init__(self):
        self.data = ""
        self.attempts = 0
        self.max_retries = 3
        self.backoff_base = 0.1

def attempt_process(state):
    state.attempts += 1
    if random.random() < 0.7 and state.attempts < state.max_retries:
        state.last_error = f"Error on attempt {state.attempts}"
        return state
    state.data = f"Processed on attempt {state.attempts}"
    return state

state = RetryState()
for _ in range(5):
    state = attempt_process(state)
    if not hasattr(state, "last_error") or state.attempts >= state.max_retries:
        break
    delay = state.backoff_base * (2 ** (state.attempts - 1))
    print(f"  Retry {state.attempts} after {delay:.1f}s backoff")
    time.sleep(min(delay, 0.1))
print(f"Result: {state.data} after {state.attempts} attempts")
Where you'll use itExplicit retry edges are used in data pipelines, API integrations, and LLM inference retry logic.
Under the hoodExponential backoff doubles the delay after each failure: base, 2*base, 4*base. Adding jitter prevents thundering herd when many clients retry simultaneously.

14Fan-Out and Join Barriers

What & why. Fan-out splits work across parallel nodes; join barriers synchronize them before proceeding. A join barrier blocks the downstream node until all upstream nodes complete. Without explicit barriers, partial results could be processed prematurely.

import asyncio
from typing import TypedDict, Annotated
import operator

class FanState(TypedDict):
    input: str
    results: Annotated[list[str], operator.add]
    merged: str

async def fetch_api_a(state):
    await asyncio.sleep(0.1)
    return {"results": [f"API_A({state['input']})"]}

async def fetch_api_b(state):
    await asyncio.sleep(0.05)
    return {"results": [f"API_B({state['input']})"]}

async def fetch_api_c(state):
    await asyncio.sleep(0.15)
    return {"results": [f"API_C({state['input']})"]}

def merge(state):
    return {"merged": " | ".join(state["results"])}

async def run_pipeline():
    state = {"input": "query", "results": [], "merged": ""}
    results = await asyncio.gather(fetch_api_a(state), fetch_api_b(state), fetch_api_c(state))
    for r in results:
        state["results"].extend(r["results"])
    state = merge(state)
    print(f"Merged: {state['merged']}")
    return state

asyncio.run(run_pipeline())
Where you'll use itFan-out/join is used for parallel API calls, multi-source data aggregation, and consensus-based decision making.
Under the hoodThe join barrier blocks until all incoming edges complete. In asyncio, gather() implements this. In LangGraph, the join node waits for all predecessors.

15Statechart Hierarchy, Guards, Actions

What & why. Harel statecharts extend finite state machines with hierarchy (states contain sub-states), concurrency (orthogonal regions), and history (remember last sub-state). Guards are boolean conditions on transitions. Actions are side effects triggered by transitions.

from enum import Enum, auto

class AgentMode(Enum):
    IDLE = auto()
    PLANNING = auto()
    EXECUTING = auto()
    TOOL_USE = auto()
    REVIEWING = auto()

class AgentStatechart:
    def __init__(self):
        self.mode = AgentMode.IDLE
        self.actions_log = []
    def on_enter(self, mode):
        self.actions_log.append(f"entered {mode.name}")
    def on_exit(self, mode):
        self.actions_log.append(f"exited {mode.name}")
    def transition(self, event, guard=True):
        if not guard:
            print(f"  Guard rejected: {event}")
            return
        old = self.mode
        self.on_exit(old)
        transitions = {
            (AgentMode.IDLE, "task_received"): AgentMode.PLANNING,
            (AgentMode.PLANNING, "plan_ready"): AgentMode.EXECUTING,
            (AgentMode.EXECUTING, "tool_needed"): AgentMode.TOOL_USE,
            (AgentMode.TOOL_USE, "result_received"): AgentMode.EXECUTING,
            (AgentMode.EXECUTING, "complete"): AgentMode.REVIEWING,
            (AgentMode.REVIEWING, "approved"): AgentMode.IDLE,
        }
        self.mode = transitions.get((old, event), old)
        self.on_enter(self.mode)
        print(f"  {old.name} -> {self.mode.name} on {event}")

agent = AgentStatechart()
agent.transition("task_received")
agent.transition("plan_ready")
agent.transition("tool_needed", guard=True)
agent.transition("tool_needed", guard=False)
print("Actions:", agent.actions_log)
Where you'll use itStatecharts model agent lifecycles, UI wizard flows, protocol handlers, and any system with complex state-dependent behavior.
Under the hoodHierarchical statecharts reduce the number of transitions by O(n) compared to flat FSMs. Orthogonal regions enable concurrent sub-state machines.

16Dynamic Graph Construction at Runtime

What & why. Some applications build graphs dynamically based on input: a user's query determines tools to include, a data schema determines the processing pipeline, or a config file defines the workflow. Dynamic construction enables flexible, data-driven architectures.

from typing import Callable

class DynamicGraph:
    def __init__(self):
        self.nodes = {}
        self.edges = {}
    def add_node(self, name, func):
        self.nodes[name] = func
        self.edges.setdefault(name, [])
    def add_edge(self, src, dst):
        self.edges.setdefault(src, []).append(dst)
    def build_from_config(self, config):
        for node_cfg in config["nodes"]:
            name = node_cfg["name"]
            self.add_node(name, lambda s, n=name: {n: f"processed by {n}"})
        for edge_cfg in config["edges"]:
            self.add_edge(edge_cfg["from"], edge_cfg["to"])
    def execute(self, start, state):
        visited = set()
        queue = [start]
        while queue:
            node = queue.pop(0)
            if node in visited or node not in self.nodes:
                continue
            result = self.nodes[node](state)
            state.update(result)
            visited.add(node)
            queue.extend(self.edges.get(node, []))
        return state

config = {"nodes": [{"name": "fetch"}, {"name": "transform"}, {"name": "store"}],
          "edges": [{"from": "fetch", "to": "transform"}, {"from": "transform", "to": "store"}]}
graph = DynamicGraph()
graph.build_from_config(config)
result = graph.execute("fetch", {"input": "data"})
print(result)
Where you'll use itDynamic graphs are used for user-configurable workflows, data-driven pipeline generation, and plugin architectures.
Under the hoodDynamic construction involves: parsing a config/DSL, registering node functions, wiring edges, validating topology, and compiling to an executable.

17Graph Validation and Lint Rules

What & why. Graph validation catches errors before execution: unreachable nodes, missing edges, type mismatches, cycles in DAGs, and incomplete routing. Lint rules enforce conventions: naming patterns, required nodes, and edge constraints.

class GraphValidator:
    def __init__(self, nodes, edges, start, end):
        self.nodes, self.edges, self.start, self.end = nodes, edges, start, end
        self.errors = []
    def validate(self):
        self._check_start_end()
        self._check_unreachable()
        self._check_dangling()
        self._check_cycles()
        return self.errors
    def _check_start_end(self):
        if self.start not in self.nodes:
            self.errors.append(f"Start node not in graph")
        if self.end not in self.nodes:
            self.errors.append(f"End node not in graph")
    def _check_unreachable(self):
        reachable, queue = set(), [self.start]
        while queue:
            node = queue.pop(0)
            if node in reachable: continue
            reachable.add(node)
            queue.extend(self.edges.get(node, []))
        unreachable = self.nodes - reachable
        if unreachable: self.errors.append(f"Unreachable: {unreachable}")
    def _check_dangling(self):
        for src, targets in self.edges.items():
            for target in targets:
                if target not in self.nodes:
                    self.errors.append(f"Dangling edge: {src} -> {target}")
    def _check_cycles(self):
        visited, path = set(), set()
        def dfs(node):
            if node in path: self.errors.append(f"Cycle at {node}"); return
            if node in visited: return
            visited.add(node); path.add(node)
            for neighbor in self.edges.get(node, []): dfs(neighbor)
            path.remove(node)
        for node in self.nodes: dfs(node)

23Petri Net Token Semantics

What & why. Petri nets model concurrent systems with places (state), transitions (actions), and tokens (current distribution). A transition fires when all input places have tokens, consuming inputs and producing outputs. Petri nets formally verify concurrency, deadlock, and liveness.

from dataclasses import dataclass

@dataclass
class PetriNet:
    places: set
    transitions: set
    input_arcs: dict
    output_arcs: dict
    marking: dict
    def enabled(self):
        enabled = set()
        for t in self.transitions:
            inputs = self.input_arcs.get(t, set())
            if all(self.marking.get(p, 0) > 0 for p in inputs):
                enabled.add(t)
        return enabled
    def fire(self, transition):
        if transition not in self.enabled():
            return False
        for p in self.input_arcs.get(transition, set()):
            self.marking[p] -= 1
        for p in self.output_arcs.get(transition, set()):
            self.marking[p] = self.marking.get(p, 0) + 1
        return True

    places={"idle", "fetched", "processed", "stored"},

    input_arcs={"fetch": {"idle"}, "process": {"fetched"}, "store": {"processed"}},
    output_arcs={"fetch": {"fetched"}, "process": {"processed"}, "store": {"stored"}},
    marking={"idle": 1, "fetched": 0, "processed": 0, "stored": 0},
)
while pn.enabled():
    for t in pn.enabled():
        pn.fire(t)
        print(f"  Fired {t}: {pn.marking}")

24LATS: Language-Agent Tree Search

What & why. LATS combines LLM reasoning with Monte Carlo Tree Search. The agent explores a tree of possible actions, evaluates each path, and backpropagates rewards. This produces higher-quality results than single-path ReAct by exploring alternatives.

import math
from dataclasses import dataclass, field

@dataclass
class LATNode:
    state: str
    action: str = ""
    reward: float = 0.0
    visits: int = 0
    children: list = field(default_factory=list)
    parent: "LATNode" = None
    def ucb1(self, exploration=1.41):
        if self.visits == 0: return float("inf")
        return self.reward / self.visits + exploration * math.sqrt(math.log(self.parent.visits) / self.visits)

def select(node):
    while node.children:
        node = max(node.children, key=lambda c: c.ucb1())
    return node

def expand(node, actions):
    for action in actions:
        child = LATNode(state=f"{node.state}->{action}", action=action, parent=node)
        node.children.append(child)
    return node.children[0] if node.children else node

def backpropagate(node, reward):
    while node:
        node.visits += 1
        node.reward += reward
        node = node.parent

root = LATNode(state="start")
expand(root, ["action_a", "action_b", "action_c"])
for child in root.children:
    reward = 1.0 if child.action == "action_b" else 0.3
    backpropagate(child, reward)
best = max(root.children, key=lambda c: c.reward / c.visits if c.visits else 0)
print(f"Best action: {best.action} (reward: {best.reward/best.visits:.2f})")
Where you'll use itLATS is used for complex reasoning: code generation with debugging, multi-step planning, and creative problem solving.
Under the hoodLATS adapts MCTS to LLM agents: selection uses UCB1, expansion generates LLM actions, simulation evaluates with the LLM, backpropagation updates counts.

25Plan Validation via Graph Checks

What & why. Before executing an AI-generated plan, validate it as a graph: check reachability, acyclicity, resource constraints, and precondition satisfaction. Graph-based validation catches invalid plans before wasting LLM tokens.

class PlanValidator:
    def __init__(self, steps, available_resources):
        self.steps = {s["name"]: s for s in steps}
        self.available = set(available_resources)
    def validate(self):
        errors = []
        errors.extend(self._check_acyclic())
        errors.extend(self._check_resources())
        return errors
    def _check_acyclic(self):
        visited, path = set(), set()
        def dfs(name):
            if name in path: return [f"Cycle: {name}"]
            if name in visited: return []
            visited.add(name); path.add(name)
            errs = []
            for dep in self.steps[name]["depends_on"]:
                errs.extend(dfs(dep))
            path.remove(name)
            return errs
        errs = []
        for name in self.steps: errs.extend(dfs(name))
        return errs
    def _check_resources(self):
        produced = set(self.available)
        errors = []
        for name, step in self.steps.items():
            for req in step["requires"]:
                if req not in produced:
                    errors.append(f"Missing '{req}' for '{name}'")
            produced.update(step["produces"])
        return errors

26Distributed Sagas and Compensation Paths

What & why. Sagas model distributed transactions as steps with compensating actions for rollback. If step 3 fails, steps 2 and 1 must be compensated. Essential for AI systems performing multi-step real-world actions.

from typing import Callable

@dataclass

    compensation: Callable
    executed: bool = False

class Saga:
    def __init__(self, steps):
        self.steps = steps
        self.executed_steps = []
    def execute(self, context):
        for step in self.steps:
            try:
                context = step.action(context)
                step.executed = True
                self.executed_steps.append(step)
                print(f"  Executed: {step.name}")

                print(f"  Failed: {step.name} - {e}")

                raise
        return context

        for step in reversed(self.executed_steps):
            context = step.compensation(context)
            print(f"  Compensated: {step.name}")

30Embedding Nodes for Semantic Traversal

What & why. Node embeddings map graph nodes to vector space where proximity reflects semantic similarity. This enables hybrid traversal: follow structural edges and semantic nearest-neighbors, discovering implicit connections between distant but similar nodes.

import numpy as np

class SemanticGraph:
    def __init__(self):
        self.nodes, self.edges, self.embeddings = {}, {}, {}
    def add_node(self, name, props, embedding):
        self.nodes[name] = props
        self.embeddings[name] = embedding
    def add_edge(self, src, dst):
        self.edges.setdefault(src, []).append(dst)
    def structural_neighbors(self, node):
        return self.edges.get(node, [])
    def semantic_neighbors(self, node, k=3):
        if node not in self.embeddings: return []
        emb = self.embeddings[node]
        scores = {}
        for other, other_emb in self.embeddings.items():
            if other != node:
                sim = np.dot(emb, other_emb) / (np.linalg.norm(emb) * np.linalg.norm(other_emb))
                scores[other] = sim
        return sorted(scores, key=scores.get, reverse=True)[:k]

33Formal Verification of Agent Workflows

What & why. Formal verification proves that a workflow satisfies properties: safety (nothing bad happens), liveness (something good eventually happens), and boundedness (termination within N steps). Model checking exhaustively explores all reachable states.

class WorkflowVerifier:
    def __init__(self, states, transitions, initial, accepting):
        self.states = states
        self.transitions = transitions
        self.initial = initial
        self.accepting = accepting
    def check_safety(self, unsafe_states):
        reachable = self._reachable()
        violations = reachable & unsafe_states
        if violations: print(f"Safety violation: {violations}")
        return not violations
    def check_liveness(self):
        return bool(self._reachable() & self.accepting)
    def _reachable(self):
        visited, queue = set(), [self.initial]
        while queue:
            state = queue.pop(0)
            if state in visited: continue
            visited.add(state)
            for _, s in self.transitions.get(state, []):
                queue.append(s)
        return visited

     "executing": [("complete", "done"), ("fail", "error")], "error": [("retry", "planning")]},
    "idle", {"done"})
print("Safety:", verifier.check_safety({"error"}))
print("Liveness:", verifier.check_liveness())

What & why. CRDTs enable concurrent state updates without coordination. Each replica applies updates independently and merges automatically. For AI agents, CRDT-inspired strategies allow concurrent shared state updates without conflicts.

from collections import Counter

class GCounter:
    def __init__(self, replica_id):
        self.replica_id = replica_id
        self.counts = Counter()
    def increment(self, amount=1):
        self.counts[self.replica_id] += amount
    def value(self):
        return sum(self.counts.values())
    def merge(self, other):
        for replica, count in other.counts.items():
            self.counts[replica] = max(self.counts[replica], count)

agent_a = GCounter("agent_a")
agent_b = GCounter("agent_b")
agent_a.increment(3)
agent_b.increment(2)
agent_a.merge(agent_b)
print(f"Counter: {agent_a.value()}")  # 5
Where you'll use itCRDTs are used in collaborative editing, distributed counters, multi-agent shared state, and any system with concurrent updates.
Under the hoodCRDTs guarantee eventual consistency: all replicas converge after all updates are delivered. Common CRDTs: G-Counter, PN-Counter, G-Set, LWW-Register, OR-Set.

35Graph Database Internals: Labeled Property Stores and Indexes

What & why. Graph databases store labeled property graphs with internal indexes for fast lookups by label, property, and relationship. Understanding internals helps optimize queries, choose storage engines, and troubleshoot performance.

from collections import defaultdict

class GraphDBInternals:
    def __init__(self):
        self.node_store = {}
        self.edge_store = defaultdict(list)
        self.label_index = defaultdict(set)
        self.property_index = defaultdict(set)
    def create_node(self, node_id, label, props):
        self.node_store[node_id] = {"label": label, "properties": props}
        self.label_index[label].add(node_id)
        for k, v in props.items():
            self.property_index[(k, v)].add(node_id)
    def create_edge(self, source, target, rel_type, props=None):
        self.edge_store[source].append((rel_type, target, props or {}))
    def find_by_label(self, label):
        return list(self.label_index.get(label, set()))
    def find_by_property(self, key, value):
        return list(self.property_index.get((key, value), set()))
    def neighbors(self, node_id, rel_type=None):
        edges = self.edge_store.get(node_id, [])
        if rel_type: return [t for r, t, _ in edges if r == rel_type]
        return [t for _, t, _ in edges]

db.create_edge("n1", "n2", "WORKS_AT", {"since": 2020})

36Event Sourcing and Graph Projections

What & why. Event sourcing stores all state changes as an immutable event log. Graph projections derive graph views from events. This enables time-travel, audit trails, and multiple projections from the same events.

from dataclasses import dataclass

@dataclass
class Event:
    type: str
    entity_id: str
    data: dict
    timestamp: float

class EventStore:
    def __init__(self):
        self.events = []
    def append(self, event):
        self.events.append(event)
    def project_graph(self, up_to=None):
        nodes, edges = {}, []
        for event in self.events:
            if up_to and event.timestamp > up_to: break
            if event.type == "node_created":
                nodes[event.entity_id] = event.data
            elif event.type == "node_deleted":
                nodes.pop(event.entity_id, None)
            elif event.type == "edge_created":
                edges.append(event.data)
        return {"nodes": nodes, "edges": edges}

print("Graph at t=3:", store.project_graph(up_to=3.0))

37Large-Graph Sharding Strategies

What & why. Graph sharding distributes large graphs across machines. Unlike table sharding, graph sharding must minimize cross-shard edges. Common strategies: vertex-cut (split edges), edge-cut (split vertices), and hybrid. The goal is locality for related nodes.

from collections import defaultdict

class GraphSharder:
    def __init__(self, num_shards):
        self.num_shards = num_shards
        self.shards = defaultdict(lambda: {"nodes": {}, "edges": []})
    def hash_shard(self, node_id):
        return hash(node_id) % self.num_shards
    def assign_node(self, node_id, properties):
        self.shards[self.hash_shard(node_id)]["nodes"][node_id] = properties
    def assign_edge(self, src, dst, rel_type):
        src_shard = self.hash_shard(src)
        self.shards[src_shard]["edges"].append({"from": src, "to": dst, "cross": self.hash_shard(dst) != src_shard})
    def stats(self):
        for sid, shard in sorted(self.shards.items()):
            cross = sum(1 for e in shard["edges"] if e["cross"])
            print(f"  Shard {sid}: {len(shard['nodes'])} nodes, {len(shard['edges'])} edges ({cross} cross)")

sharder = GraphSharder(3)
for nid in ["user_1", "user_2", "user_3", "org_1"]:
    sharder.assign_node(nid, {"name": nid})
for src, dst in [("user_1", "org_1"), ("user_2", "org_1"), ("user_3", "org_1")]:
    sharder.assign_edge(src, dst, "WORKS_AT")
sharder.stats()

40Safety Interlocks and Kill-Switch Nodes

What & why. Safety interlocks are graph nodes that monitor state and halt execution when dangerous conditions are detected. Kill-switch nodes abort any downstream execution immediately. Critical for AI agents interacting with real-world systems.

class KillSwitch:
    def __init__(self):
        self.killed = False
        self.reason = ""
    def trigger(self, reason):
        self.killed = True
        self.reason = reason
        print(f"  KILL SWITCH: {reason}")
    def check(self):
        return not self.killed

def safety_check(state, ks):
    if state["budget"] <= 0:
        ks.trigger("Budget exhausted")
        return {**state, "flag": "BUDGET_EXCEEDED"}
    return state

def safe_action(state, ks):
    if not ks.check(): return state
    return {"budget": state["budget"] - 0.10, "actions": state["actions"] + 1}

ks = KillSwitch()
state = {"budget": 0.50, "actions": 0}
for i in range(10):
    state = safety_check(state, ks)
    if not ks.check():
        print(f"  Stopped: {ks.reason}")
        break
    state = safe_action(state, ks)
    print(f"  Action {state['actions']} (budget: ${state['budget']:.2f})")
Where you'll use itSafety interlocks are mandatory for production AI agents: budget guards, rate limiters, safety classifiers, and human override mechanisms.
Under the hoodKill-switch nodes check global safety state before allowing actions. They can be synchronous (check before execution) or asynchronous (abort via cancellation tokens).
