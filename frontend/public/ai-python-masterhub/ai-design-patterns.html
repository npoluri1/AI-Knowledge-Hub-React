Part I · FoundationsTier 1 — Core pattern vocabulary and single-call basics

1What a Pattern Is: Problem-Force-Solution

What & why. A design pattern is a named, reusable solution to a recurring problem under specific forces. Unlike ad-hoc code, a pattern has a name that communicates intent, a context where it applies, forces that make the problem non-trivial, and a solution structure that resolves those forces. In AI systems, patterns emerge from repeated failures: hallucinations drive the Validator pattern, latency drives the Cache-Aside pattern, and autonomy risks drive the Human-in-the-Loop gate.

# Pattern anatomy: every pattern has these components
pattern = {
    "name": "Retry-With-Feedback",
    "problem": "LLM calls intermittently fail or return low-quality output",
    "forces": ["provider unreliability", "quality variance", "cost sensitivity"],
    "solution": "On failure, feed error details back to the LLM and retry",
    "tradeoffs": ["increased latency", "higher cost", "improved reliability"],
    "context": "production pipelines where reliability matters more than speed",
}

# Using a pattern means applying the structure, not copying code
# The same pattern appears in different implementations:
# - RetryWithFeedback class
# - retry decorator with error context
# - LangGraph loop node with feedback edge
Where you'll use itEvery AI architecture discussion uses pattern names as shorthand. Saying "we need a Validator wrapping the output" communicates the structure, tradeoffs, and implementation approach in three words.
Under the hoodThe pattern concept comes from Christopher Alexander's architecture work, adopted by the Gang-of-Four for software. In AI, patterns are newer but equally important: they encode hard-won lessons about LLM behavior, failure modes, and composition strategies.

2Pattern Catalog Map Overview

What & why. The AI design pattern catalog is organized by complexity: single-call patterns (baseline), composition patterns (multiple calls), control-flow patterns (branching and looping), and systemic patterns (cross-cutting concerns). Understanding the map helps you select the right pattern without implementing everything first. Start simple and add patterns as problems emerge.

3Chain / Pipeline: Sequential Steps

What & why. The Chain pattern connects LLM calls and tools in a linear sequence where each step's output feeds the next step's input. Pipelines are the most common composition pattern: extract then transform then load, or research then draft then review. Each step is independent and testable, and the chain fails fast when any step fails.

from typing import Callable

def chain(*steps: Callable) -> Callable:
    """Compose steps into a sequential pipeline."""
    def execute(input_data):
        result = input_data
        for step in steps:
            result = step(result)
        return result
    return execute

def extract(raw_text: str) -> dict:
    return {"entities": raw_text.split(","), "length": len(raw_text)}

def transform(data: dict) -> dict:
    return {"entities": [e.strip().lower() for e in data["entities"]],
            "count": len(data["entities"])}

def validate(data: dict) -> dict:
    assert data["count"] > 0, "No entities found"
    return data

pipeline = chain(extract, transform, validate)
result = pipeline("Alice, Bob, Charlie")
print(result)  # {"entities": ["alice", "bob", "charlie"], "count": 3}
Where you'll use itChains appear everywhere: RAG pipelines (retrieve then augment then generate), content pipelines (research then draft then edit), and data pipelines (extract then clean then load). Start with a chain before adding branching.
Under the hoodEach step in the chain is a function with a defined input/output contract. The chain orchestrator handles sequencing, error propagation, and optional logging between steps. Frameworks like LangChain and LangGraph provide chain abstractions with additional features like memory and streaming.

4Router / Classifier: Dispatch to Handlers

What & why. The Router pattern classifies incoming requests and dispatches them to specialized handlers. Instead of one LLM call trying to handle everything, a lightweight classifier routes each request to the most appropriate handler: a billing question goes to the billing handler, a technical question goes to the technical handler. This improves accuracy by giving each handler a focused scope.

from enum import Enum
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

class Category(Enum):
    BILLING = "billing"
    TECHNICAL = "technical"
    GENERAL = "general"

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def classify(query: str) -> Category:
    resp = llm.invoke([HumanMessage(content=(
        f"Classify into exactly one: billing, technical, general.\n"
        f"Query: {query}\nCategory:"
    ))])
    return Category(resp.content.strip().lower())

handlers = {
    Category.BILLING: lambda q: f"Billing answer for: {q}",
    Category.TECHNICAL: lambda q: f"Technical answer for: {q}",
    Category.GENERAL: lambda q: f"General answer for: {q}",
}

def route(query: str) -> str:
    category = classify(query)
    return handlers[category](query)

print(route("How do I reset my password?"))  # General handler
Where you'll use itRouters power customer support triage, intent classification in chatbots, and model routing (simple queries to cheap models, complex ones to expensive models). The pattern reduces cost by avoiding expensive models for simple tasks.
Under the hoodThe classifier can be a fine-tuned small model, a few-shot LLM call, or an embedding-based similarity search. The tradeoff is classifier accuracy versus latency: an LLM classifier adds one call but is more flexible than a rule-based system.

5Single LLM Call: Baseline Always Start Here

What & why. Before implementing any complex pattern, start with a single LLM call. The single-call baseline establishes the minimum viable solution: send a prompt, get a response, check if it is good enough. Most tasks need only this. Adding patterns is justified only when the single call fails to meet quality, reliability, or cost requirements. Measure first, then decide.

from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

llm = ChatOpenAI(model="gpt-4o", temperature=0)

def baseline_call(query: str) -> dict:
    """Single LLM call as baseline measurement."""
    response = llm.invoke([HumanMessage(content=query)])
    return {
        "answer": response.content,
        "tokens_used": response.usage_metadata.get("total_tokens", 0),
        "model": "gpt-4o",
        "latency_ms": 0,  # measured externally
    }

# Always run this first to establish quality baseline
result = baseline_call("Summarize the benefits of microservices")
print(f"Answer: {result['answer'][:100]}...")
print(f"Tokens: {result['tokens_used']}")

# Measure: quality (human eval), cost (tokens), latency (time)
# Only add patterns if this baseline is insufficient
Where you'll use itEvery AI project should start with a single-call baseline. It establishes the quality floor and cost ceiling. If a single call with a good prompt achieves 95% accuracy, the remaining 5% may not justify the complexity of multi-call patterns.
Under the hoodThe baseline is also your debugging reference. When a complex pattern fails, you compare against the single call to determine if the pattern introduced the failure or if the underlying task is just hard.

6Prompt Template as a Pattern

What & why. A Prompt Template is a reusable, parameterized prompt structure that standardizes how you interact with LLMs. Unlike ad-hoc string concatenation, templates separate the prompt structure from the variable data. They enable A/B testing of prompt phrasing, version control of prompts, and consistent behavior across your application. Every pattern that involves an LLM call benefits from templated prompts.

from langchain_core.prompts import ChatPromptTemplate

# Structured template with variables
template = ChatPromptTemplate.from_messages([
    ("system", (
        "You are a {domain} expert. Answer concisely. "
        "If unsure, say 'I don't know'. "
        "Tone: {tone}. Max length: {max_words} words."
    )),
    ("human", "{question}"),
])

# Instantiate with variables
prompt = template.invoke({
    "domain": "Python",
    "tone": "professional",
    "max_words": 100,
    "question": "What are Python decorators?",
})

# Version control: track template versions
TEMPLATES = {
    "v1": template,
    "v2": ChatPromptTemplate.from_messages([
        ("system", "You are a {domain} expert. Be concise and accurate."),
        ("human", "{question}"),
    ]),
}
Where you'll use itTemplates are the foundation of prompt engineering at scale. They enable systematic testing (swap variables to test edge cases), team collaboration (shared templates), and rollback (revert to a previous template version).
Under the hoodLangChain's ChatPromptTemplate supports variable interpolation, few-shot examples as message placeholders, and conditional prompt sections. The template compiles to a function that maps variables to a list of messages.

7Validator: Wrapper Around Outputs

What & why. The Validator pattern wraps LLM outputs with a schema check, catching malformed or out-of-range responses before they propagate downstream. LLMs frequently produce text that looks plausible but violates structural requirements: missing fields, wrong types, or values outside acceptable ranges. A validator catches these early and either fixes them or triggers a retry.

from pydantic import BaseModel, Field, field_validator
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

class SentimentResult(BaseModel):
    label: str = Field(description="positive, negative, or neutral")
    confidence: float = Field(ge=0.0, le=1.0)

    @field_validator("label")
    @classmethod
    def must_be_valid(cls, v):
        if v not in ("positive", "negative", "neutral"):
            raise ValueError(f"Invalid label: {v}")
        return v

llm = ChatOpenAI(model="gpt-4o", temperature=0)

def validate_sentiment(text: str) -> SentimentResult:
    raw = llm.invoke([HumanMessage(content=(
        f"Classify sentiment as JSON: {{label, confidence}}\nText: {text}"
    ))])
    result = SentimentResult.model_validate_json(raw.content)
    return result

try:
    result = validate_sentiment("This is great!")
    print(f"{result.label}: {result.confidence}")
except Exception as e:
    print(f"Validation failed: {e}")
Where you'll use itValidators are essential for any LLM output that feeds into downstream code. Use them for structured data extraction, classification, parameter generation, and any case where downstream code assumes specific types or ranges.
Under the hoodPydantic v2 uses Rust-based validation for speed. Combined with structured output (response_format), you can enforce schemas at the API level, reducing validation failures. When validation fails, the error message can feed back to the LLM for correction.

8Retry-With-Feedback Loop

What & why. When an LLM call fails or produces invalid output, the Retry-With-Feedback pattern feeds the error details back to the LLM and asks it to try again. Unlike blind retries that repeat the same call, feedback-informed retries give the LLM specific information about what went wrong, enabling self-correction. This dramatically improves success rates for structured output tasks.

from pydantic import BaseModel, ValidationError
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

class CalendarEvent(BaseModel):
    title: str
    date: str  # YYYY-MM-DD
    attendees: int

llm = ChatOpenAI(model="gpt-4o", temperature=0)

def retry_with_feedback(query: str, max_retries: int = 3) -> CalendarEvent:
    errors = []
    for attempt in range(max_retries):
        context = query
        if errors:
            context += f"\n\nPrevious errors (fix these):\n" + "\n".join(errors)
        raw = llm.invoke([HumanMessage(content=context)])
        try:
            return CalendarEvent.model_validate_json(raw.content)
        except ValidationError as e:
            errors.append(f"Attempt {attempt+1}: {e}")
    raise RuntimeError(f"Failed after {max_retries} attempts: {errors}")

result = retry_with_feedback(
    "Extract: Team standup on 2025-03-15, 5 people attending. "
    "Return JSON with title, date, attendees fields."
)
print(result)
Where you'll use itRetry-with-feedback is critical for structured extraction tasks where the LLM sometimes produces valid-but-wrong JSON, missing fields, or malformed dates. It improves first-pass yield from ~70% to ~95% for complex schemas.
Under the hoodThe feedback loop works because LLMs can learn from in-context error messages. Each retry includes the previous errors, creating a few-shot learning effect. The key is providing specific, actionable error messages rather than generic "try again" instructions.

9Cache-Aside for LLM Responses

What & why. The Cache-Aside pattern stores LLM responses so identical or similar queries can be served from cache instead of making expensive API calls. The application first checks the cache; on a miss, it calls the LLM and stores the result. This reduces cost, latency, and API rate-limit pressure. Semantic caching extends this to similar queries using embedding similarity.

import hashlib, json, time

class LLMCache:
    def __init__(self, ttl_seconds: int = 3600):
        self.store: dict[str, dict] = {}
        self.ttl = ttl_seconds

    def _key(self, model: str, prompt: str) -> str:
        raw = f"{model}:{prompt}"
        return hashlib.sha256(raw.encode()).hexdigest()

    def get(self, model: str, prompt: str) -> str | None:
        key = self._key(model, prompt)
        entry = self.store.get(key)
        if entry and time.time() - entry["ts"] < self.ttl:
            return entry["response"]
        return None

    def set(self, model: str, prompt: str, response: str):
        key = self._key(model, prompt)
        self.store[key] = {"response": response, "ts": time.time()}

cache = LLMCache(ttl_seconds=1800)

def cached_llm_call(model: str, prompt: str) -> str:
    hit = cache.get(model, prompt)
    if hit:
        return hit  # cache hit, no API call
    response = call_llm_api(model, prompt)  # your API call
    cache.set(model, prompt, response)
    return response
Where you'll use itCaching is essential for any production LLM system. FAQ-style queries, classification tasks, and template-based generation benefit enormously. Semantic caching (using embeddings to match similar queries) extends the hit rate beyond exact matches.
Under the hoodCache keys are typically SHA-256 hashes of the model name plus full prompt. TTL (time-to-live) ensures stale responses are refreshed. For semantic caching, compute an embedding of the prompt and use vector similarity (cosine) to find near-duplicate cached queries.

10Fan-Out / Gather: Parallel Calls

What & why. The Fan-Out pattern dispatches multiple independent LLM calls in parallel, then Gather collects their results. When a task has independent subtasks, running them concurrently reduces total latency from the sum of individual calls to the duration of the slowest call. This is especially valuable when calling multiple different models or processing multiple documents simultaneously.

import asyncio
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o", temperature=0)

async def summarize_chunk(chunk: str) -> str:
    from langchain_core.messages import HumanMessage
    resp = await llm.ainvoke([HumanMessage(content=f"Summarize: {chunk}")])
    return resp.content

async def fan_out_gather(chunks: list[str]) -> list[str]:
    tasks = [summarize_chunk(chunk) for chunk in chunks]
    results = await asyncio.gather(*tasks, return_exceptions=True)
    summaries = []
    for r in results:
        if isinstance(r, Exception):
            summaries.append(f"Error: {r}")
        else:
            summaries.append(r)
    return summaries

chunks = [
    "Python 3.12 introduces type parameter syntax.",
    "FastAPI supports WebSocket connections natively.",
    "React 19 adds server components by default.",
]
summaries = asyncio.run(fan_out_gather(chunks))
Where you'll use itFan-out is used in multi-document RAG (summarize each document in parallel), multi-model evaluation (query multiple models simultaneously), and content generation (generate multiple drafts at once for selection).
Under the hoodasyncio.gather runs coroutines concurrently on the event loop. For CPU-bound work, use ProcessPoolExecutor. The tradeoff: parallel calls increase peak token usage and may hit rate limits, so implement semaphore-based concurrency limiting for production.

11Aggregator: Merge Results

What & why. The Aggregator pattern combines multiple LLM outputs into a single coherent result. After Fan-Out produces partial results, the Aggregator merges them using strategies like concatenation, voting, LLM-based synthesis, or weighted averaging. The choice of aggregation strategy depends on the task: voting for classification, LLM synthesis for summarization, and averaging for numerical estimates.

from collections import Counter

def aggregate_classifications(labels: list[str]) -> dict:
    """Majority vote aggregation for classification."""
    counts = Counter(labels)
    winner = counts.most_common(1)[0]
    return {
        "label": winner[0],
        "confidence": winner[1] / len(labels),
        "vote_distribution": dict(counts),
    }

def aggregate_numerical(values: list[float], weights: list[float] = None) -> dict:
    """Weighted average aggregation for numerical outputs."""
    if weights is None:
        weights = [1.0] * len(values)
    total_weight = sum(weights)
    weighted_avg = sum(v * w for v, w in zip(values, weights)) / total_weight
    variance = sum((v - weighted_avg) ** 2 for v in values) / len(values)
    return {"value": weighted_avg, "variance": variance, "n": len(values)}

# Example: 3 models classify the same text
labels = ["positive", "positive", "neutral"]
result = aggregate_classifications(labels)
print(f"Consensus: {result['label']} ({result['confidence']:.0%})")
Where you'll use itAggregation is used in ensemble methods (combine multiple model outputs), multi-perspective analysis (merge different viewpoints), and consensus systems (vote on the best answer from multiple LLM calls).
Under the hoodThe aggregation pattern mirrors ensemble learning in ML. For classification, majority vote works well. For generation, a separate LLM call can synthesize the best elements from multiple drafts. For numerical outputs, weighted averaging with outlier rejection provides robust estimates.

12Human-in-the-Loop Gate

What & why. The Human-in-the-Loop (HITL) pattern inserts a human approval or review step at critical points in an AI pipeline. The system generates output, presents it to a human for approval or correction, and only proceeds after human sign-off. HITL is essential for high-stakes decisions: financial transactions, medical recommendations, legal document generation, and any action that cannot be easily undone.

from dataclasses import dataclass
from enum import Enum

class ApprovalStatus(Enum):
    PENDING = "pending"
    APPROVED = "approved"
    REJECTED = "rejected"

@dataclass
class HITLGate:
    description: str
    status: ApprovalStatus = ApprovalStatus.PENDING
    reviewer_notes: str = ""

    def present(self, ai_output: str) -> dict:
        return {
            "gate": self.description,
            "ai_output": ai_output,
            "status": self.status.value,
            "action_required": "Approve or reject this output",
        }

    def approve(self, notes: str = ""):
        self.status = ApprovalStatus.APPROVED
        self.reviewer_notes = notes

    def reject(self, reason: str):
        self.status = ApprovalStatus.REJECTED
        self.reviewer_notes = reason

gate = HITLGate(description="Approve generated invoice email")
result = gate.present("Dear customer, your invoice #1234 is due March 15.")
gate.approve(notes="Looks good, send it")
print(f"Status: {gate.status.value}")  # approved
Where you'll use itHITL gates are used in content moderation queues, automated trading systems, medical image analysis, financial compliance, and any system where AI output feeds into real-world actions. Most regulated industries require HITL for critical decisions.
Under the hoodHITL introduces latency (seconds to hours depending on the gate). Design for async: queue the output, notify the human, and resume on approval. Track approval rates to identify which AI outputs consistently need human correction and improve those prompts.

13Orchestrator-Workers: Decomposition

What & why. The Orchestrator-Workers pattern decomposes a complex task into subtasks, assigns each to a specialized worker, and synthesizes the results. The orchestrator understands the full problem, breaks it into independent subtasks, and coordinates the workers. Each worker has a focused scope and toolset, improving accuracy over a single monolithic prompt trying to do everything.

from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

llm = ChatOpenAI(model="gpt-4o", temperature=0)

def orchestrator(task: str) -> dict:
    plan = llm.invoke([HumanMessage(content=(
        f"Break this into 3 subtasks, one per line:\n{task}"
    ))])
    subtasks = [s.strip() for s in plan.content.split("\n") if s.strip()]

    results = {}
    for i, subtask in enumerate(subtasks):
        worker_prompt = f"Complete this subtask concisely: {subtask}"
        resp = llm.invoke([HumanMessage(content=worker_prompt)])
        results[f"subtask_{i}"] = {"task": subtask, "result": resp.content}

    synthesis = llm.invoke([HumanMessage(content=(
        f"Synthesize these results into one coherent answer:\n{results}"
    ))])
    return {"subtasks": results, "synthesis": synthesis.content}

answer = orchestrator("Compare Python, Go, and Rust for web server performance")
print(answer["synthesis"][:200])
Where you'll use itOrchestrator-workers power complex research tasks, multi-source analysis, content production pipelines, and any task where one prompt is insufficient. The pattern scales by adding specialized workers for new domains.
Under the hoodThe orchestrator is itself an LLM call, so it can hallucinate subtasks. Constrain the decomposition with examples and templates. Workers can run in parallel (asyncio.gather) or sequentially depending on dependencies between subtasks.

14Evaluator-Optimizer: Generate-Critique-Refine

What & why. The Evaluator-Optimizer pattern creates a quality loop: one LLM generates output, another evaluates it against criteria, and feedback drives refinement. Unlike simple retry, this pattern uses an independent evaluator to assess quality against explicit rubrics. The generator and evaluator can be different models: a cheaper model for generation, a more capable model for evaluation.

from langchain_openai import ChatOpenAI

generator = ChatOpenAI(model="gpt-4o-mini", temperature=0.7)
evaluator = ChatOpenAI(model="gpt-4o", temperature=0)

def generate_and_refine(topic: str, max_rounds: int = 3) -> str:
    draft = generator.invoke(f"Write a short paragraph about {topic}").content

    for round_num in range(max_rounds):
        critique = evaluator.invoke(
            f"Evaluate this paragraph on clarity and accuracy. "
            f"List specific improvements:\n\n{draft}"
        ).content

        if "no improvements" in critique.lower():
            break

        draft = generator.invoke(
            f"Refine this paragraph based on feedback:\n\n"
            f"Current: {draft}\nFeedback: {critique}"
        ).content

    return draft

final = generate_and_refine("quantum computing applications")
print(final)
Where you'll use itThis pattern is used in code review pipelines (generate code, evaluate against standards, refine), content quality loops (draft, edit, polish), and any task where iterative improvement produces meaningfully better output than a single pass.
Under the hoodThe key insight is separating generation from evaluation. A single LLM doing both tends to be sycophantic (rating its own output highly). Separate evaluator prompts with explicit rubrics produce more honest assessments. Set max_rounds to prevent infinite refinement loops.

15Generator-Critic: Adversarial Pair

What & why. The Generator-Critic pattern pairs two LLMs in an adversarial relationship: the Generator produces output and the Critic actively searches for flaws. Unlike Evaluator-Optimizer which refines, the Critic's job is to find problems, not suggest fixes. This adversarial dynamic surfaces edge cases and weaknesses that a cooperative evaluator might miss.

from langchain_openai import ChatOpenAI

generator = ChatOpenAI(model="gpt-4o", temperature=0.7)
critic = ChatOpenAI(model="gpt-4o", temperature=0)

def adversarial_generate(topic: str, rounds: int = 2) -> str:
    draft = generator.invoke(f"Write a security analysis of {topic}").content

    for _ in range(rounds):
        attack = critic.invoke(
            f"Find the 3 weakest claims in this analysis. "
            f"For each, explain the flaw concisely:\n\n{draft}"
        ).content

        draft = generator.invoke(
            f"Defend against these critiques and strengthen the analysis:\n\n"
            f"Analysis: {draft}\nCriticisms: {attack}"
        ).content

    return draft

result = adversarial_generate("REST API authentication strategies")
print(result[:300])
Where you'll use itThe Generator-Critic pattern is used in red-team exercises (attack the system to find vulnerabilities), argument strengthening (find logical flaws), and robustness testing (surface failure modes before production).
Under the hoodThe adversarial dynamic exploits the LLM's ability to reason about weaknesses. The Critic has no stake in the output quality, so it finds genuine flaws. This mirrors peer review in academic publishing and code review in software engineering.

16Triage: Escalation Severity Flows

What & why. The Triage pattern classifies incoming requests by severity and routes them to appropriate handlers with different response SLAs. Low-severity issues get automated responses, medium issues queue for human review, and high-severity issues trigger immediate alerts. This prevents critical issues from being buried in a queue of routine requests.

from enum import Enum
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

class Severity(Enum):
    LOW = "low"        # automated response
    MEDIUM = "medium"  # queue for review
    HIGH = "high"      # immediate alert

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def triage(ticket: str) -> dict:
    resp = llm.invoke([HumanMessage(content=(
        f"Classify severity (low/medium/high) with one-line reason:\n{ticket}"
    ))])
    level = Severity(resp.content.split()[0].strip().lower())

    actions = {
        Severity.LOW: "auto_reply",
        Severity.MEDIUM: "add_to_queue",
        Severity.HIGH: "page_oncall",
    }
    return {"severity": level.value, "action": actions[level],
            "reasoning": resp.content}

print(triage("Production database is unreachable since 3am"))
# high severity, page_oncall
Where you'll use itTriage is essential for support ticketing systems, incident management, content moderation queues, and any system handling variable-priority requests. It ensures critical issues get human attention immediately.
Under the hoodThe triage classifier should be fast and cheap (gpt-4o-mini or a fine-tuned small model). The severity thresholds should be tunable without code changes. Track triage accuracy over time to calibrate the classifier against human judgment.

17Saga: Compensation Multi-Step Transactions

What & why. The Saga pattern manages multi-step transactions where each step has a compensating action (undo). If any step fails, the saga executes compensating actions for all completed steps in reverse order. This provides eventual consistency without distributed locks. In AI pipelines, sagas handle steps like API calls, database writes, and email sends that must be rolled back on failure.

from dataclasses import dataclass, field

@dataclass
class SagaStep:
    name: str
    action: callable
    compensate: callable

@dataclass
class Saga:
    steps: list[SagaStep] = field(default_factory=list)
    completed: list[str] = field(default_factory=list)

    def execute(self, context: dict) -> dict:
        for step in self.steps:
            try:
                context = step.action(context)
                self.completed.append(step.name)
            except Exception as e:
                print(f"Step {step.name} failed: {e}")
                self._compensate(context)
                return {"status": "rolled_back", "failed_at": step.name}
        return {"status": "completed", "context": context}

    def _compensate(self, context: dict):
        for name in reversed(self.completed):
            step = next(s for s in self.steps if s.name == name)
            print(f"Compensating: {name}")
            step.compensate(context)
Where you'll use itSagas are essential for AI workflows that interact with external systems: billing (charge then notify, compensate if notification fails), provisioning (create resource then configure, deprovision on failure), and multi-API orchestration.
Under the hoodEach step's compensate function must be idempotent (safe to run multiple times). The saga can be choreography-based (each step triggers the next) or orchestration-based (a coordinator manages the sequence). The orchestration approach is easier to reason about and debug.

18Circuit Breaker: Provider Failures

What & why. The Circuit Breaker pattern prevents cascading failures by detecting when an LLM provider is failing and temporarily stopping requests to it. The breaker has three states: closed (normal), open (failing, reject requests), and half-open (testing recovery). This protects your system from provider outages and prevents wasting tokens on calls that will fail.

import time

class CircuitBreaker:
    def __init__(self, failure_threshold: int = 5, reset_timeout: int = 60):
        self.failures = 0
        self.threshold = failure_threshold
        self.reset_timeout = reset_timeout
        self.state = "closed"
        self.opened_at = 0.0

    def call(self, func, *args, **kwargs):
        if self.state == "open":
            if time.time() - self.opened_at > self.reset_timeout:
                self.state = "half-open"
            else:
                raise RuntimeError("Circuit breaker is OPEN")

        try:
            result = func(*args, **kwargs)
            if self.state == "half-open":
                self.state = "closed"
                self.failures = 0
            return result
        except Exception as e:
            self.failures += 1
            if self.failures >= self.threshold:
                self.state = "open"
                self.opened_at = time.time()
            raise

breaker = CircuitBreaker(failure_threshold=3, reset_timeout=30)
# Use: result = breaker.call(llm.invoke, prompt)
Where you'll use itCircuit breakers are critical for multi-provider architectures: if your primary LLM provider fails, the breaker opens and you fall back to a secondary provider. This is essential for production reliability.
Under the hoodThe breaker tracks consecutive failures (not total failures). After the reset_timeout, it enters half-open and allows one test request. If that succeeds, it closes; if it fails, it re-opens. This prevents hammering a recovering provider.

19Bulkhead: Resource Isolation Pools

What & why. The Bulkhead pattern isolates resources into separate pools so that a failure or overload in one pool does not exhaust resources for others. In AI systems, this means separate rate-limit pools, token budgets, and connection pools for different features or customers. A high-volume feature cannot starve a critical feature of API calls.

import asyncio

class Bulkhead:
    def __init__(self, name: str, max_concurrent: int, max_queue: int = 10):
        self.name = name
        self.semaphore = asyncio.Semaphore(max_concurrent)
        self.queue_limit = max_queue
        self.active = 0

    async def execute(self, func, *args, **kwargs):
        if self.active >= self.queue_limit + self.semaphore._value:
            raise RuntimeError(f"Bulkhead {self.name} queue full")
        async with self.semaphore:
            self.active += 1
            try:
                return await func(*args, **kwargs)
            finally:
                self.active -= 1

# Separate pools for different features
billing_bulkhead = Bulkhead("billing", max_concurrent=5)
chat_bulkhead = Bulkhead("chat", max_concurrent=20)
embed_bulkhead = Bulkhead("embeddings", max_concurrent=50)
Where you'll use itBulkheads prevent noisy-neighbor problems in multi-tenant systems and protect critical features from being overwhelmed by high-volume non-critical features. Essential for shared LLM infrastructure.
Under the hoodBorrowed from ship design (watertight compartments), the pattern uses semaphores to limit concurrent access. When a bulkhead is full, requests are queued or rejected rather than consuming shared resources. This isolates failure domains.

20Sidecar: Guardrail Service Adjacent

What & why. The Sidecar pattern deploys a guardrail service alongside the main LLM service, intercepting inputs and outputs without modifying the core service. The sidecar handles PII detection, content filtering, output validation, and audit logging. This separates safety concerns from business logic, enabling independent evolution of the guardrail and the main service.

import re, time

class SidecarGuard:
    def __init__(self, block_pii: bool = True, max_tokens: int = 1000):
        self.block_pii = block_pii
        self.max_tokens = max_tokens
        self.blocked: list[dict] = []

    def pre_call(self, prompt: str) -> str:
        if self.block_pii and has_pii(prompt):
            self.blocked.append({"reason": "PII detected", "ts": time.time()})
            return redact_pii(prompt)
        return prompt

    def post_call(self, response: str) -> str:
        if self.block_pii and has_pii(response):
            return redact_pii(response)
        if len(response.split()) > self.max_tokens:
            return response[:self.max_tokens] + " [truncated]"
        return response

    def audit_log(self, prompt: str, response: str):
        log_entry = {"prompt_hash": hash(prompt), "response_len": len(response)}
        print(f"[audit] {log_entry}")

def has_pii(text: str) -> bool:
    return bool(re.search(r"\b\d{3}-\d{2}-\d{4}\b|[\w.]+@[\w.]+\b", text))

def redact_pii(text: str) -> str:
    text = re.sub(r"[\w.]+@[\w.]+", "[REDACTED_EMAIL]", text)
    return re.sub(r"\b\d{3}-\d{2}-\d{4}\b", "[REDACTED_SSN]", text)
Where you'll use itSidecars are used in microservice architectures where guardrails must apply to multiple LLM services without duplicating logic. They also enable A/B testing guardrail policies independently of the main service.
Under the hoodThe sidecar pattern mirrors the Kubernetes sidecar concept: a lightweight process running alongside the main service. In-process, it is a wrapper class. In distributed systems, it is a separate service that the main service calls before and after LLM interactions.

21Event-Sourced: Run History Append-Only

What & why. Event Sourcing stores every LLM interaction as an immutable event in an append-only log. Instead of storing only the latest state, you store the complete history of prompts, responses, tool calls, and user feedback. This enables full replay, debugging, analytics, and audit compliance. You can reconstruct the state at any point in time by replaying events.

import json, time, uuid
from pathlib import Path

class EventStore:
    def __init__(self, path: str = "events.jsonl"):
        self.path = Path(path)

    def append(self, event_type: str, data: dict):
        event = {
            "id": str(uuid.uuid4()),
            "type": event_type,
            "timestamp": time.time(),
            "data": data,
        }
        with open(self.path, "a") as f:
            f.write(json.dumps(event) + "\n")
        return event["id"]

    def replay(self, run_id: str = None) -> list[dict]:
        events = []
        with open(self.path) as f:
            for line in f:
                event = json.loads(line)
                if run_id is None or event["data"].get("run_id") == run_id:
                    events.append(event)
        return events

store = EventStore()

store.append("llm_response", {"tokens": 150, "latency_ms": 800})
Where you'll use itEvent sourcing is essential for regulated industries (finance, healthcare) where you must prove what the AI did and why. It also enables analytics (which prompts produce the best results) and debugging (replay a failing request step by step).
Under the hoodAppend-only logs are simple, fast, and naturally concurrent (no write conflicts). Tradeoffs: storage grows unboundedly (implement compaction), and replaying large histories is slow (implement snapshots for state reconstruction).

22Blackboard: Shared Solution Space

What & why. The Blackboard pattern provides a shared data structure that multiple agents or components read from and write to. Unlike point-to-point communication, the blackboard decouples producers from consumers. Any agent can contribute information, and any agent can read what others have contributed. This enables emergent collaboration without explicit coordination.

from threading import Lock

class Blackboard:

    def read_all(self) -> dict:
        return dict(self._data)

    def keys(self) -> list[str]:
        return list(self._data.keys())

23Mentor-Verifier: Teach-Check Loop

What & why. The Mentor-Verifier pattern pairs a teaching agent (Mentor) with a checking agent (Verifier). The Mentor explains concepts and guides reasoning, while the Verifier independently checks the Mentor's claims for accuracy. This creates a self-correcting loop where errors in teaching are caught by verification, and verification failures prompt re-examination.

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o", temperature=0)

def mentor_verifier_loop(topic: str, rounds: int = 2) -> str:
    explanation = llm.invoke(
        f"Teach me about {topic} step by step."
    ).content

    for round_num in range(rounds):
        verification = llm.invoke(
            f"Verify each claim in this explanation for accuracy. "
            f"List any errors:\n\n{explanation}"
        ).content

        if "no errors" in verification.lower():
            return explanation

        explanation = llm.invoke(
            f"Fix the errors in this explanation:\n\n"
            f"Original: {explanation}\nErrors: {verification}"
        ).content

    return explanation

result = mentor_verifier_loop("CAP theorem in distributed systems")
print(result[:500])
Where you'll use itMentor-Verifier is used in educational AI systems (tutor that verifies its own explanations), knowledge base construction (write then verify facts), and code documentation (generate docs then verify accuracy against source).
Under the hoodThe pattern exploits the fact that LLMs are better at verification than generation. Checking a claim against known facts is easier than generating accurate claims from scratch. The Mentor-Verifier loop progressively improves accuracy through iteration.

What & why. The Adapter pattern provides a uniform interface across different LLM providers. 26Composition: Combining Patterns Safely

What & why. Patterns rarely work in isolation; real systems compose multiple patterns. The challenge is ensuring composed patterns do not conflict: a Retry around a Validator can create infinite loops, and a Circuit Breaker around a Cache can prevent cache population. Safe composition requires understanding pattern interactions and designing explicit boundaries between them.

from pydantic import BaseModel

class Output(BaseModel):
    answer: str
    confidence: float

def safe_composed_call(prompt: str, max_retries: int = 3) -> Output:
    errors = []
    for attempt in range(max_retries):
        try:
            raw = llm_call(prompt)  # the LLM call
            return Output.model_validate_json(raw)  # Validator
        except ValidationError as e:
            errors.append(str(e))
            if attempt < max_retries - 1:
                prompt += f"\nFix these errors: {errors[-1]}"
    raise RuntimeError(f"Failed after {max_retries} retries")

# 1. Retry wraps Validator (not the other way around)
# 2. Circuit Breaker wraps Retry (not individual calls)
# 3. Cache wraps everything (check cache first)
# 4. HITL wraps the final output (approve before serving)

What & why. The God Prompt anti-pattern tries to accomplish everything in a single massive prompt: classification, extraction, generation, validation, and formatting. While it seems efficient, it fails because the LLM's attention is divided across too many objectives, quality degrades for each additional task, and errors compound. Break the God Prompt into focused steps with clear responsibilities.

28Anti-Pattern: Silent Retries Masking Bugs

What & why. Silent retries hide failures by automatically retrying without logging or surfacing the original error. This makes debugging nearly impossible: the system appears to work but has hidden quality issues. Silent retries also waste tokens and can amplify bugs by retrying with the same broken prompt. Always log retries with full context.

# BAD: Silent retry
def bad_call(prompt):
    for _ in range(3):
        try:
            return llm_call(prompt)
        except:
            pass  # silent failure, no logging
    return None  # caller has no idea retries happened

# GOOD: Transparent retry with logging
import logging

logger = logging.getLogger("llm_retries")

def good_call(prompt, max_retries=3):
    for attempt in range(max_retries):
        try:
            result = llm_call(prompt)
            if attempt > 0:
                logger.warning(f"Retry succeeded on attempt {attempt+1}")
            return result
        except Exception as e:
            logger.error(f"Attempt {attempt+1}/{max_retries} failed: {e}")
            if attempt == max_retries - 1:
                raise
            prompt += f"\n[Retry context] Previous error: {e}"
    raise RuntimeError("Exhausted retries")
Where you'll use itSilent retries are a common junior mistake. Always implement retry logging with attempt numbers, error messages, and timing. This data feeds into reliability dashboards and helps identify systematic issues.
Under the hoodRetry logging creates an audit trail that reveals patterns: if retries consistently fail for certain prompt types, there is a systematic issue. Without logging, you only see the final (possibly degraded) output.

What & why. Unbounded autonomy gives an AI agent the ability to take actions without limits: unlimited tool calls, no cost caps, no human oversight, and no maximum iteration count. 30Idempotency Keys in AI Workflows

What & why. Idempotency keys ensure that repeating an operation produces the same result as running it once. In AI workflows, retries, network errors, and distributed systems can cause duplicate execution. Idempotency keys prevent duplicate billing, duplicate email sends, and duplicate database writes. Every external-facing operation should accept an idempotency key.

import uuid, hashlib, json

class IdempotencyStore:
    def __init__(self):
        self.results: dict[str, dict] = {}

    def compute_key(self, operation: str, params: dict) -> str:
        raw = json.dumps({"op": operation, "params": params}, sort_keys=True)
        return hashlib.sha256(raw.encode()).hexdigest()[:16]

    def execute(self, key: str, operation_fn):
        if key in self.results:
            return self.results[key]  # return cached result
        result = operation_fn()
        self.results[key] = result
        return result

store = IdempotencyStore()

def charge_customer(customer_id: str, amount: float) -> dict:
    key = store.compute_key("charge", {"customer": customer_id, "amount": amount})
    return store.execute(key, lambda: {"charged": amount, "status": "ok"})

# First call executes, second call returns cached result
print(charge_customer("C001", 49.99))
print(charge_customer("C001", 49.99))  # same key, same result
Where you'll use itIdempotency is essential for billing APIs, email sending, database writes, and any operation with side effects. Every payment gateway, email service, and messaging system requires idempotency keys for reliability.
Under the hoodIdempotency keys are typically UUIDs generated by the client and sent with the request. The server stores the result keyed by the idempotency key. On duplicate requests, it returns the stored result without re-executing. TTL the keys after 24-48 hours.

31Versioned Pattern Implementations

What & why. Versioning pattern implementations enables safe evolution: you can run v1 and v2 side by side, gradually migrate traffic, and roll back on failure. This applies to prompts, models, pipeline structures, and even the patterns themselves. Version everything, test new versions against benchmarks, and migrate traffic with canary deployments.

from dataclasses import dataclass
from typing import Any
import random

@dataclass
class PatternVersion:
    name: str
    version: str
    implementation: Any
    traffic_pct: float = 1.0

class VersionedPattern:
    def __init__(self, pattern_name: str):
        self.pattern_name = pattern_name
        self.versions: dict[str, PatternVersion] = {}

    def register(self, version: str, impl: Any, traffic_pct: float = 1.0):
        self.versions[version] = PatternVersion(
            name=self.pattern_name, version=version,
            implementation=impl, traffic_pct=traffic_pct,
        )

    def route(self, input_data) -> Any:
        r = random.random()
        cumulative = 0.0
        for ver in self.versions.values():
            cumulative += ver.traffic_pct
            if r <= cumulative:
                return ver.implementation(input_data)
        latest = list(self.versions.values())[-1]
        return latest.implementation(input_data)

pipeline = VersionedPattern("summarize")
pipeline.register("v1", lambda x: f"Summary v1: {x[:50]}", 0.8)
pipeline.register("v2", lambda x: f"Summary v2: {x[:100]}", 0.2)

Where you'll use itVersioning is critical for prompt evolution, model upgrades, and pipeline changes. Run old and new versions simultaneously, compare output quality, and shift traffic gradually. This prevents breaking changes from affecting all users at once.
Under the hoodVersioned patterns mirror canary deployments in infrastructure. The traffic percentage controls the rollout: start at 1%, monitor quality metrics, increase to 10%, 50%, then 100%. Roll back instantly if quality degrades.

35Latency Budgets per Pattern

What & why. Latency budgets define the maximum acceptable time for each pattern in a pipeline. If your overall SLA is 2 seconds and you use a Chain with three steps, each step has roughly 600ms of budget. Exceeding the budget degrades user experience. Design patterns with latency awareness: use smaller models for routing, cache aggressively, and parallelize where possible.

import time

class LatencyBudget:
    def __init__(self, total_ms: int):
        self.total_ms = total_ms
        self.steps: list[dict] = []

    def step(self, name: str):
        return _StepContext(self, name)

    def report(self):
        used = sum(s["elapsed_ms"] for s in self.steps)
        remaining = self.total_ms - used
        for s in self.steps:
            pct = s["elapsed_ms"] / self.total_ms * 100
            print(f"  {s['name']}: {s['elapsed_ms']:.0f}ms ({pct:.0f}%)")
        print(f"  Total: {used:.0f}ms / {self.total_ms}ms")
        return remaining > 0

class _StepContext:
    def __init__(self, budget, name):
        self.budget = budget
        self.name = name
    def __enter__(self):
        self.start = time.time()
        return self
    def __exit__(self, *args):
        elapsed = (time.time() - self.start) * 1000
        self.budget.steps.append({"name": self.name, "elapsed_ms": elapsed})

budget = LatencyBudget(total_ms=2000)
with budget.step("classify"):
    time.sleep(0.1)
with budget.step("generate"):
    time.sleep(0.5)
budget.report()
Where you'll use itLatency budgets are essential for user-facing applications. Set budgets per pattern and enforce them: if classification exceeds 200ms, use a smaller model. If generation exceeds 1s, stream the response.
Under the hoodLatency budgets should account for network latency, LLM inference time, and post-processing. Measure P50, P95, and P99 latencies, not just averages. P99 latency often reveals timeout issues hidden by averages.

37Formal Pattern Language: Forces, Tradeoffs, Notation

What & why. A formal pattern language provides notation for expressing pattern relationships: which patterns compose safely, which conflict, and what tradeoffs each imposes. 39Consistency Models: Eventual vs Strict in Pipelines

What & why. AI pipelines face consistency choices: strict consistency (all steps complete before the result is served) versus eventual consistency (results are served progressively as steps complete). Strict consistency is simpler but slower; eventual consistency improves latency but adds complexity. The choice depends on whether downstream consumers can tolerate partial results.

import asyncio

class StrictPipeline:
    async def run(self, steps, input_data):
        result = input_data
        for step in steps:
            result = await step(result)
        return result  # only returns when ALL steps are done

class EventualPipeline:
    def __init__(self, steps):
        self.steps = steps
        self.results: dict = {}

    async def run(self, input_data):
        async def run_step(step, data, key):
            self.results[key] = {"status": "running"}
            result = await step(data)
            self.results[key] = {"status": "done", "result": result}

        tasks = [run_step(s, input_data, f"step_{i}")
                 for i, s in enumerate(self.steps)]
        asyncio.gather(*tasks)
        return self.results
Where you'll use itStrict consistency suits user-facing responses (show nothing until complete). Eventual consistency suits streaming dashboards, progressive rendering, and multi-stage workflows where partial results are useful.
Under the hoodConsistency models in AI pipelines mirror distributed systems tradeoffs. Eventual consistency requires handling partial states in the UI or downstream consumers. Strict consistency requires timeout handling for slow steps.

from datetime import datetime, timedelta

class PatternDeprecation:

44Performance Engineering: Memoization Boundaries

What & why. Memoization stores function results for identical inputs. In AI pipelines, memoization boundaries define which stages can be memoized and which cannot. Pure functions (deterministic transforms, validators) can always be memoized. LLM calls can be memoized only if the prompt is identical (exact match) or semantically similar (embedding cache). Understanding memoization boundaries prevents caching non-deterministic outputs.

import functools, json, hashlib

def memoize_exact(func):
    """Memoize with exact input match."""
    cache = {}
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        key = hashlib.sha256(
            json.dumps({"args": args, "kwargs": kwargs}, sort_keys=True,
                       default=str).encode()
        ).hexdigest()
        if key not in cache:
            cache[key] = func(*args, **kwargs)
        return cache[key]
    return wrapper

# Safe to memoize: deterministic function
@memoize_exact
def normalize_text(text: str) -> str:
    return text.strip().lower()

# Safe to memoize: LLM call (with same prompt)
@memoize_exact
def classify_exact(text: str) -> str:
    return llm_invoke(f"Classify: {text}")  # deterministic if temp=0

# NOT safe to memoize: temperature > 0
# def classify_fuzzy(text):  # different outputs each time
#     return llm_invoke(f"Classify: {text}", temperature=0.7)
Where you'll use itMemoization is a performance optimization that reduces API calls and latency. Identify memoization boundaries in your pipeline: deterministic steps (always cache), zero-temperature LLM calls (cache with key = prompt hash), and non-deterministic calls (do not cache).
Under the hoodMemoization boundaries are determined by function purity. Pure functions (same input, same output) can be memoized. Impure functions (LLM calls with temperature > 0, time-dependent calls) cannot. Document memoization decisions to prevent accidental caching of non-deterministic outputs.

Support Desk Triage: Router + HITL

Build a support desk system that classifies incoming tickets by severity and intent, routes them to specialized handlers, and escalates complex issues to human agents with full context.

Architecture steps.

  1. Create a Pydantic model for SupportTicket with fields: id, subject, body, category, severity, customer_id
  2. Build a Router classifier using gpt-4o-mini that categorizes tickets into billing, technical, and general intents
  3. Implement a SeverityAssessor that scores urgency from 1-5 based on ticket content and customer tier
  4. Create specialized handlers for each category with focused prompts and tool access
  5. Build a Cache-Aside layer that stores responses for duplicate or near-duplicate tickets
  6. Implement an HITL gate that presents tickets with severity >= 4 to human agents with full context
  7. Add a CircuitBreaker around the primary LLM provider with fallback to a secondary model
  8. Log all routing decisions, handler outputs, and human interventions to an event store
from pydantic import BaseModel
from enum import Enum

class Category(Enum):
    BILLING = "billing"
    TECHNICAL = "technical"
    GENERAL = "general"

class SupportTicket(BaseModel):
    id: str
    subject: str
    body: str
    category: Category | None = None
    severity: int | None = None
    routed_to: str | None = None

def triage_ticket(ticket: SupportTicket, llm) -> SupportTicket:
    classification = llm.invoke(
        f"Classify intent and severity (1-5):\nSubject: {ticket.subject}\nBody: {ticket.body}"
    )
    parts = classification.content.split("|")
    ticket.category = Category(parts[0].strip().lower())
    ticket.severity = int(parts[1].strip())

    if ticket.severity >= 4:
        ticket.routed_to = "human_agent"
    else:
        ticket.routed_to = f"auto_{ticket.category.value}"
    return ticket

from pydantic import BaseModel
from langchain_openai import ChatOpenAI

class ContentRequest(BaseModel):
    topic: str
    audience: str
    word_count: int = 500
    quality_threshold: float = 4.0

class EvalResult(BaseModel):
    clarity: int
    accuracy: int
    engagement: int

    @property
    def average(self) -> float:
        return (self.clarity + self.accuracy + self.engagement) / 3

def produce_content(request: ContentRequest) -> dict:
    llm = ChatOpenAI(model="gpt-4o", temperature=0)
    draft = llm.invoke(
        f"Write {request.word_count} words about {request.topic} "
        f"for {request.audience}"
    ).content
    for round_num in range(3):
        evaluation = evaluate_draft(draft, llm)
        if evaluation.average >= request.quality_threshold:
            return {"draft": draft, "score": evaluation.average, "rounds": round_num + 1}
        draft = refine_draft(draft, evaluation, llm)
    return {"draft": draft, "score": evaluation.average, "rounds": 3}

Architecture steps.

  1. Create a BillingContext Pydantic model with customer_id, amount, items, invoice_id, and notification_sent fields
  2. Implement Step 1: ChargeCustomer with compensating RefundCustomer action
  3. Implement Step 2: GenerateInvoice with compensating VoidInvoice action
  4. Implement Step 3: SendNotification with compensating void notification (log that original was retracted)
  5. Implement Step 4: LogTransaction with compensating delete entry action
  6. Build the Saga orchestrator that executes steps sequentially and compensates on failure
  7. Add a CircuitBreaker around the payment provider with timeout of 5 seconds
  8. Implement idempotency keys for each step to prevent duplicate charges or notifications
from pydantic import BaseModel
import uuid, time

class BillingContext(BaseModel):
    customer_id: str
    amount: float
    items: list[dict]
    invoice_id: str | None = None
    notification_sent: bool = False
    transaction_logged: bool = False

class SagaStep:
    def __init__(self, name, action, compensate):
        self.name = name
        self.action = action
        self.compensate = compensate

def charge_customer(ctx: BillingContext) -> BillingContext:
    print(f"Charging {ctx.customer_id}: ${ctx.amount}")
    return ctx

def refund_customer(ctx: BillingContext) -> BillingContext:
    print(f"Refunding {ctx.customer_id}: ${ctx.amount}")
    return ctx

def generate_invoice(ctx: BillingContext) -> BillingContext:
    ctx.invoice_id = str(uuid.uuid4())[:8]
    print(f"Invoice created: {ctx.invoice_id}")
    return ctx

def void_invoice(ctx: BillingContext) -> BillingContext:
    print(f"Voiding invoice: {ctx.invoice_id}")
    ctx.invoice_id = None
    return ctx

steps = [
    SagaStep("charge", charge_customer, refund_customer),
    SagaStep("invoice", generate_invoice, void_invoice),
]
