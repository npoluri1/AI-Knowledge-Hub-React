Part I · FoundationsTier 1 — why LoRA and QLoRA

1Why Full Fine-Tuning Is Expensive

What & why. Full fine-tuning updates every parameter, requiring optimizer states that consume 8-16 bytes per parameter. A 7B model needs ~112GB just for AdamW states in fp32, exceeding even high-end consumer GPUs.

# Memory breakdown for full FT (7B model, AdamW, fp32)
# Model weights:   7B * 4 bytes =  28 GB
# Gradients:       7B * 4 bytes =  28 GB
# AdamW m state:   7B * 4 bytes =  28 GB
# AdamW v state:   7B * 4 bytes =  28 GB
# Total:                        ~112 GB

# With bf16 mixed precision: ~84 GB
# Still requires multi-GPU or cloud A100/H100
Where you'll use itWhen evaluating infrastructure costs for a fine-tuning project; this math determines whether you need cloud GPUs or can use local hardware.
Under the hoodThe optimizer states (AdamW's first and second moment estimates) dominate memory; they are the target LoRA eliminates by freezing most parameters.

2Low-Rank A*B Decomposition

What & why. LoRA assumes weight updates have low intrinsic rank. Instead of updating a full d x d weight matrix, it learns two small matrices A (d x r) and B (r x d) where r is much smaller than d, capturing the essential adaptation with far fewer parameters.

import torch

class LoRALinear(torch.nn.Module):
    def __init__(self, in_f, out_f, r=16, alpha=32):
        super().__init__()
        self.weight = torch.nn.Parameter(
            torch.randn(out_f, in_f), requires_grad=False  # frozen
        )
        self.A = torch.nn.Parameter(torch.randn(in_f, r) * 0.01)
        self.B = torch.nn.Parameter(torch.zeros(r, out_f))
        self.scaling = alpha / r

    def forward(self, x):
        return x @ self.weight.T + (x @ self.A @ self.B.T) * self.scaling

# Full update: d^2 params; LoRA: 2*d*r params
# d=4096, r=16: 16M vs 131K (128x fewer)
Where you'll use itUnderstanding why LoRA works: the adapter learns a low-rank approximation of the full weight update, sufficient for most task adaptations.
Under the hoodResearch shows that pretrained model weight updates during fine-tuning have low intrinsic dimensionality; LoRA exploits this structural property.

3Target Weight Matrices

What & why. LoRA is applied to specific weight matrices in the model. The attention projection layers (query, key, value, output) are the primary targets, with MLP layers as optional secondary targets for higher-capacity adaptation.

# LLaMA / Mistral / Qwen target patterns:
# Minimal:  ["q_proj", "v_proj"]
# Standard: ["q_proj", "k_proj", "v_proj", "o_proj"]
# Full:     ["q_proj", "k_proj", "v_proj", "o_proj",
#            "gate_proj", "up_proj", "down_proj"]

# GPT-2 / GPT-NeoX:
#   ["c_attn"] or ["c_attn", "c_proj"]

# Impact on trainable params (7B model, r=16):
# q,v only:      ~1.7M (0.05%)
# all attention:  ~3.4M (0.11%)
# full:           ~13.6M (0.45%)
Where you'll use itConfiguring LoRA for any architecture; the right target modules determine what the adapter can modify.
Under the hoodAttention layers control what information flows through the model; adapting them gives LoRA direct control over the model's reasoning pathways.

4Rank r Meaning and Defaults

What & why. Rank r determines the adapter's capacity. Higher rank = more parameters = more adaptation ability, but also more memory and risk of overfitting. r=8 to r=32 covers most use cases.

from peft import LoraConfig

# Rank selection guide
# r=8:   Simple tasks (classification, basic formatting)
# r=16:  General purpose (chat, summarization) -- RECOMMENDED
# r=32:  Complex domain adaptation (legal, medical)
# r=64:  Maximum adaptation (style transfer, complex reasoning)

config = LoraConfig(r=16, lora_alpha=32,
                    target_modules=["q_proj", "v_proj"],
                    lora_dropout=0.05)

# Trainable param count scales linearly with r
# r=16: ~3.4M; r=32: ~6.8M (2x more)
Where you'll use itEvery LoRA configuration; r=16 is the community consensus default, starting point before ablation.
Under the hoodThe rank controls the dimensionality of the subspace the adapter operates in; task complexity determines how much capacity is needed.

5Alpha Scaling Explained

What & why. Alpha is a scaling factor that controls the magnitude of the LoRA adapter's output relative to the frozen base weights. The effective scaling is alpha/r, so doubling alpha doubles the adapter's influence.

# Effective scaling = alpha / r
# alpha=32, r=16 -> scaling = 2.0 (adapter output doubled)
# alpha=16, r=16 -> scaling = 1.0 (adapter output unchanged)
# alpha=64, r=16 -> scaling = 4.0 (adapter output quadrupled)

# Convention: alpha = 2 * r (scaling factor of 2)
# Actual adapter output:
# output = base_output + (alpha / r) * (dropout(x) @ A @ B)
Where you'll use itFine-tuning where the model seems under-adapted (increase alpha) or over-adapted (decrease alpha) relative to the base model's capabilities.
Under the hoodAlpha acts as a learning rate multiplier for the adapter; higher alpha amplifies the adapter's signal, which can improve convergence speed but risks instability.

6PEFT LoraConfig Minimal Example

What & why. PEFT (Parameter-Efficient Fine-Tuning) is the HuggingFace library that manages LoRA adapters. A minimal LoraConfig and get_peft_model call is all you need to convert any model for LoRA training.

from peft import LoraConfig, get_peft_model, TaskType
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-3B-Instruct",
    torch_dtype="auto", device_map="auto"
)

lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16, lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05, bias="none"
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# trainable params: 3,407,872 || all: 3,000,000,000 || 0.11%
Where you'll use itThe starting point for any LoRA fine-tune; this 10-line setup converts any HuggingFace model to LoRA-trainable.
Under the hoodget_peft_model wraps the model's target modules with LoRA adapter layers while freezing all other parameters via requires_grad=False.

7QLoRA: NF4, Double Quant, Paged Optimizers

What & why. QLoRA quantizes the frozen base model to 4-bit NF4 (Normal Float 4), applies double quantization to compression constants, and uses paged optimizers to handle memory spikes. This enables fine-tuning 7B-13B models on a single 24GB GPU.

import torch
from transformers import BitsAndBytesConfig, AutoModelForCausalLM

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16
)

model = AutoModelForCausalLM.from_pretrained(
    "mistralai/Mistral-7B-Instruct-v0.3",
    quantization_config=bnb_config,
    device_map="auto"
)

# 7B model in ~4GB VRAM (base) + ~1GB LoRA overhead
# Total: ~5GB VRAM vs ~84GB for full FT in bf16
Where you'll use itFine-tuning 7B-13B models on consumer GPUs (RTX 3090, RTX 4090) where full precision is impossible.
Under the hoodNF4 uses information-theoretically optimal quantization for normally-distributed weights, achieving better quality than standard INT4.

Under the hoodBitsAndBytes dequantizes NF4 weights to bf16 in the forward pass kernel, so computation happens in higher precision while storage is 4-bit.

9Consumer GPU Feasibility: 7B / 13B

What & why. QLoRA makes it possible to fine-tune models on consumer hardware. The key constraint is VRAM: a 24GB GPU handles 7B with QLoRA easily and 13B with careful configuration.

# Consumer GPU VRAM budgets:
# RTX 3060 12GB:  QLoRA 3B, maybe 7B at r=8, batch_size=1
# RTX 3090 24GB:  QLoRA 7B comfortably, 13B tight
# RTX 4090 24GB:  QLoRA 7B easy, 13B with grad accumulation
# A6000 48GB:     QLoRA 13B easy, 30B possible
# A100 80GB:      Full FT 7B, QLoRA 30B+, LoRA 65B

# QLoRA 7B (r=16) memory estimate:
# Quantized base:  ~4 GB
# LoRA params:     ~20 MB
# Optimizer state: ~40 MB
# Gradients:       ~20 MB
# Activations:     ~2-8 GB (depends on seq_length)
# Total:           ~7-13 GB
Where you'll use itHardware procurement decisions; knowing your GPU's capacity determines which models you can fine-tune locally.
Under the hoodThe activation memory is the hidden variable; it scales with batch size, sequence length, and model depth, often dominating the memory budget.

11Rank vs Quality Tradeoffs

What & why. Higher rank increases capacity but also VRAM usage and overfitting risk. The relationship is not linear: doubling rank from 16 to 32 rarely doubles quality. Profiling across ranks reveals the sweet spot.

for r in [4, 8, 16, 32, 64]:
    config = LoraConfig(r=r, lora_alpha=2*r,
                        target_modules=["q_proj","v_proj","k_proj","o_proj"])
    model = get_peft_model(base_model, config)
    trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)

# Typical findings:
# r=4:  good for simple tasks, underfits complex ones

Where you'll use itHyperparameter search; the rank-quality curve helps justify the chosen rank in model documentation.
Under the hoodThe intrinsic dimensionality of task-specific updates is typically 10-50 for most fine-tuning tasks, explaining why r=16-32 suffices.

12LoRA Learning Rates

What & why. LoRA adapters require higher learning rates than full fine-tuning because the gradients are scaled down by the small adapter matrices. Typical LoRA LR is 1e-4 to 3e-4, compared to 1e-5 to 5e-5 for full FT.

from transformers import TrainingArguments

args = TrainingArguments(
    output_dir="./lora_output",
    learning_rate=2e-4,           # 10x higher than full FT
    lr_scheduler_type="cosine",
    warmup_ratio=0.1,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,
    num_train_epochs=3, bf16=True
)

# Why higher LR works:
# LoRA gradients are small (few params, small matrices)
# Higher LR compensates for reduced gradient magnitude
# The alpha/r scaling already dampens adapter output
Where you'll use itEvery LoRA training run; getting the learning rate right is the single most impactful hyperparameter choice.
Under the hoodThe effective learning rate for the model's output is LR * alpha/r; this compound scaling explains why LoRA can use higher raw learning rates safely.

13rsLoRA and DoRA Variants

What & why. rsLoRA (rank-stabilized LoRA) adjusts the scaling factor to alpha/sqrt(r) instead of alpha/r, providing more stable training at higher ranks. DoRA (Weight-Decomposed Low-Rank Adaptation) decomposes weights into magnitude and direction for better adaptation.

# rsLoRA: scaling = alpha / sqrt(r)
# At r=16, alpha=32: scaling = 32/sqrt(16) = 8.0 (vs 2.0 standard)
# More stable at high ranks, prevents over-damping

from peft import LoraConfig
config = LoraConfig(
    r=32, lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    use_rslora=True           # if supported in PEFT version
)

# DoRA: decompose weight W = m * (W + BA) / ||W + BA||
config_dora = LoraConfig(
    r=16, lora_alpha=32,
    use_dora=True             # weight-decomposed LoRA
)
Where you'll use itWhen standard LoRA underperforms at high ranks; rsLoRA and DoRA can unlock better quality from the same parameter budget.
Under the hoodrsLoRA prevents the "rank collapse" phenomenon where high-rank adapters underperform low-rank ones due to over-damping from alpha/r scaling.

15Load Adapter at Inference

What & why. Loading a LoRA adapter onto a base model is the standard inference pattern. The base model loads once; adapters are loaded on top, with the forward pass adding the adapter output to the frozen base output.

from peft import PeftModel
from transformers import AutoModelForCausalLM, AutoTokenizer

base = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-3B-Instruct",
    torch_dtype="auto", device_map="auto"
)

model = PeftModel.from_pretrained(base, "./my-lora-adapter")
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-3B-Instruct")

inputs = tokenizer("Explain LoRA in simple terms:", return_tensors="pt")
output = model.generate(**inputs, max_new_tokens=200)
print(tokenizer.decode(output[0], skip_special_tokens=True))
Where you'll use itServing fine-tuned models; the adapter loads in seconds while the base model is cached in VRAM.
Under the hoodPeftModel wraps the base model and intercepts the forward pass for target modules, adding the LoRA output (A @ B) to the base output.

16Multi-Adapter: Set Adapter Swap

What & why. Multiple adapters can be loaded simultaneously and swapped at inference time without reloading the base model. This enables serving multiple fine-tuned personas or tasks from a single GPU.

from peft import PeftModel

model = PeftModel.from_pretrained(base_model, "./adapter-task-a",
                                   adapter_name="task_a")
model.load_adapter("./adapter-task-b", adapter_name="task_b")
model.load_adapter("./adapter-task-c", adapter_name="task_c")

print(model.peft_config.keys())  # dict_keys(['task_a', 'task_b', 'task_c'])

# Swap at inference time (no reload needed)
model.set_adapter("task_b")
output_b = model.generate(**inputs, max_new_tokens=200)

model.set_adapter("task_c")
output_c = model.generate(**inputs, max_new_tokens=200)
Where you'll use itMulti-tenant serving where each customer or persona gets a dedicated adapter; base model loaded once, adapters swapped per-request.
Under the hoodAdapter weights are small enough (10-50MB) to fit in CPU RAM; swapping involves a memory copy to GPU, taking milliseconds.

17Merge into Base Weights

What & why. For production deployment, merging the adapter into the base model eliminates PEFT overhead and produces a standard model file. This simplifies serving infrastructure and reduces inference latency.

from peft import PeftModel

model = PeftModel.from_pretrained(base_model, "./my-lora-adapter")
merged = model.merge_and_unload()

# Save as standalone model
merged.save_pretrained("./merged_model")
tokenizer.save_pretrained("./merged_model")

# Verify: merged model produces same output as adapter model
import torch
with torch.no_grad():
    out_adapter = model.generate(**inputs, max_new_tokens=50)
    out_merged = merged.generate(**inputs, max_new_tokens=50)
    assert torch.equal(out_adapter, out_merged)

# Convert merged model to GGUF for llama.cpp deployment
# python convert_hf_to_gguf.py ./merged_model --outfile model.gguf
Where you'll use itProduction deployment where you want a single model file; merges adapter overhead into base weights permanently.
Under the hoodMerging is a simple matrix addition: W_merged = W_base + (alpha/r) * B @ A for each adapted layer, producing bit-identical inference.

Part III · AdvancedTier 3 — internals, math, and distributed training

19dW = B*A Scaling Derivation

What & why. The LoRA forward pass computes h = Wx + (alpha/r) * BAx. Understanding this derivation shows why LoRA is mathematically equivalent to a low-rank weight update and why the scaling factor matters.

# Standard forward: h = W * x
# LoRA forward:    h = W * x + (alpha/r) * B @ A @ x
# Effective weight update: dW = (alpha/r) * B @ A
# This is a rank-r approximation of the full weight update dW_full
#
# Why low-rank works:
# Fine-tuning updates have been shown to lie in a
# low-dimensional subspace (intrinsic dimensionality ~10-100)
# A rank-r decomposition captures this subspace efficiently
Where you'll use itUnderstanding why LoRA works theoretically; essential for making informed decisions about rank and alpha.
Under the hoodThe Aghajanyan et al. (2020) paper showed pretrained models have low intrinsic dimensionality, providing the theoretical foundation for LoRA.

20Init A Gaussian, B Zeros: Why

What & why. LoRA initializes A with random Gaussian values and B with zeros so the initial adapter output is exactly zero. This means training starts from the base model's behavior and only diverges as gradients update the adapter.

# Initialization: A ~ N(0, sigma^2), B = 0
# At step 0: B @ A = 0 @ A = 0
# So: h = W @ x + alpha/r * 0 = W @ x (identical to base model)

import torch
A = torch.randn(4096, 16) * 0.01  # small random init
B = torch.zeros(16, 4096)          # zero init
print((B @ A).abs().max())  # tensor(0.)

# Benefits:
# 1. Safe starting point: no random perturbation of base model
# 2. Gradual adaptation: model starts from known-good behavior
# 3. Stability: prevents initial gradient explosions
Where you'll use itUnderstanding adapter initialization; this choice is critical for training stability and convergence.
Under the hoodThe zero initialization of B creates a "residual connection" pattern where the adapter adds to (rather than replaces) the base model's output.

21Gradient Flow Through Frozen Base

What & why. In LoRA, gradients flow through the frozen base model to reach the adapter parameters but never update the base weights. This means activations are computed normally but only the adapter receives learning signal.

# Gradient flow diagram:
# Input x -> [Frozen W] -> h_base    (no grad)
# Input x -> [A (trainable)] -> [B (trainable)] -> h_adapt (grad here)
# Output = h_base + (alpha/r) * h_adapt

# The frozen base still participates in forward computation
# Gradients flow through: loss -> h_adapt -> B -> A
# But NOT through: h_base -> W (requires_grad=False)

# Implication: base model activations consume memory for
# gradient computation even though they aren't updated
# This is why activations (not weights) often dominate VRAM
Where you'll use itUnderstanding why LoRA still requires significant VRAM despite freezing most weights; activation memory is the bottleneck.
Under the hoodFrozen weights still need forward activations stored for backpropagation through the adapter; gradient checkpointing reduces this at the cost of recomputation.

22NF4 Quantile Quantization Detail

What & why. NF4 (NormalFloat4) is an information-theoretically optimal 4-bit quantization scheme for normally-distributed weights. It uses 16 quantization levels spaced according to the normal distribution's quantiles.

# NF4 quantization levels (precomputed for standard normal):
# [-1.0, -0.6962, -0.5251, -0.3949, -0.2844,
#  -0.1848, -0.0911, 0.0, 0.0796, 0.1609,
#  0.2461, 0.3379, 0.4407, 0.5626, 0.7230, 1.0]

# Why NF4 beats INT4:
# INT4: uniform quantization levels (equal spacing)
# NF4: quantization levels follow the weight distribution
# Result: ~0.5 bits less quantization error than INT4

# Process:
# 1. Absmax normalize weights to [-1, 1]
# 2. Map each weight to nearest NF4 level
# 3. Store 4-bit indices
# 4. Dequantize: index -> level * absmax_for_block
Where you'll use itUnderstanding why QLoRA produces better quality than naive INT4 quantization; NF4 is a key innovation.
Under the hoodNF4 assumes weights are approximately normally distributed (true for pretrained models) and optimizes quantization levels accordingly.

23BF16 Compute, 4-bit Storage

What & why. QLoRA stores weights in 4-bit for memory efficiency but dequantizes to bf16 for computation. This separation means the model uses minimal storage while maintaining numerical precision during forward/backward passes.

# QLoRA memory model:
# Storage: 4-bit NF4 (4 bits per param)
# Compute: bf16 (16 bits per param, temporary)
# Optimizer states: fp32 (only for LoRA params)

# 7B model breakdown:
# Storage: 7B * 0.516 bytes = 3.6 GB (NF4 + double quant)
# Compute: ~1-2 layers * 2 bytes = 1-2 GB (bf16, layer-by-layer)
# Total: ~8.5 GB peak (with gradient checkpointing)

# This is why QLoRA fits in 24GB:
# 3.6 GB storage + 2 GB compute + 1 GB LoRA + 2 GB activations
Where you'll use itUnderstanding QLoRA's memory model; the storage/compute separation is the key insight enabling consumer-GPU fine-tuning.
Under the hoodDequantization happens in the CUDA kernel just before matrix multiplication; the overhead is minimal (~5% compute time).

24Paged Optimizers and Unified Memory

What & why. Paged optimizers use CUDA unified memory to handle VRAM spikes during gradient checkpointing and long sequences. When GPU memory is full, optimizer states spill to CPU RAM and are paged back as needed.

# Paged optimizer concept:
# Normal optimizer: states locked in VRAM
# Paged optimizer: states in unified memory (CPU+GPU shared)
# When VRAM pressure high: states page to CPU
# When GPU needs states: pages transfer back

# Enable in QLoRA config
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16
)

# Use with 8-bit paged AdamW
# Optimizer states automatically use paged memory when VRAM is constrained
Where you'll use itTraining on long sequences where activation memory spikes can cause OOM; paged optimizers prevent crashes at the cost of CPU-GPU transfers.
Under the hoodCUDA unified memory (cudaMallocManaged) provides a virtual memory layer that transparently moves pages between CPU and GPU on demand.

25Blockwise K-bit Quantization

What & why. Blockwise quantization divides weight tensors into small blocks (typically 64 elements) and quantizes each block independently with its own scaling factor. This reduces quantization error compared to per-tensor quantization.

# Blockwise quantization:
# Weight tensor: [4096, 4096] = 16M elements
# Block size: 64
# Number of blocks: 16M / 64 = 262,144 blocks
# Each block: 64 elements -> 64 4-bit indices + 1 fp32 scale
# Overhead: ~0.5% extra memory

# Benefit: local precision
# Per-tensor: one scale for 16M elements (coarse)
# Per-block: one scale for 64 elements (fine-grained)
# Result: ~1-2 dB lower quantization error

# BitsAndBytes applies this automatically in 4-bit mode
# Block size is fixed at 64
Where you'll use itUnderstanding why QLoRA's quantization quality is high; blockwise quantization is a key component of NF4's effectiveness.
Under the hoodThe block size of 64 balances quantization precision against scale factor overhead; smaller blocks improve quality but increase storage.

26Double Quantization Savings Math

What & why. Double quantization quantizes the quantization constants themselves, further reducing memory. The per-block fp32 scales are quantized to 8-bit, saving ~0.37 bits per parameter.

# Single quantization:
# 4-bit weights: 0.5 bytes/param
# fp32 scales (1 per 64 elements): 4/64 = 0.0625 bytes/param
# Total: 0.5625 bytes/param

# Double quantization:
# 4-bit weights: 0.5 bytes/param
# 8-bit quantized scales: 0.015625 bytes/param
# Total: ~0.516 bytes/param

# Savings: 0.046 bytes/param
# 7B params: 7B * 0.046 = 322 MB saved
# 70B params: 70B * 0.046 = 3.2 GB saved

# bnb_4bit_use_double_quant=True enables this
# Marginal for 7B, significant for 70B+
Where you'll use itLarge model fine-tuning where every megabyte counts; double quantization is always worth enabling.
Under the hoodDouble quantization exploits the fact that block scales are also approximately normally distributed, so they too benefit from quantization.

27Theory: SVF and Beyond

What & why. Singular Value Fine-tuning (SVF) and related methods generalize LoRA by learning in the singular value decomposition space of weight matrices. These approaches can achieve better quality at the same parameter count.

# PEFT generalization landscape:
# LoRA:   W' = W + BA (low-rank additive)
# DoRA:   W' = m * (W + BA) / ||W + BA|| (magnitude-direction)
# rsLoRA: scaling = alpha/sqrt(r) (rank-stabilized)
# SVF:    decompose W = U S V^T, learn delta on S (diagonal)
# AdaLoRA: adaptive rank allocation per layer

# SVF concept:
# SVD: W = U * diag(s) * V^T
# Instead of adding BA, modify the singular values s
# Fewer parameters than LoRA (d params vs 2*d*r)
Where you'll use itResearch and cutting-edge applications where standard LoRA doesn't achieve sufficient quality per parameter.
Under the hoodAll PEFT methods approximate weight updates in different subspaces; LoRA uses random projections, SVF uses the SVD basis, and DoRA decomposes magnitude from direction.

29Adapter Averaging and Federated Sketch

What & why. Multiple LoRA adapters can be averaged to combine their capabilities without explicit multi-task training. This enables federated learning patterns where adapters from different participants are merged.

import torch

def average_adapters(adapter_paths, weights=None):
    if weights is None:
        weights = [1.0 / len(adapter_paths)] * len(adapter_paths)

    state_dicts = [torch.load(p)["state_dict"] for p in adapter_paths]
    merged = {}
    for key in state_dicts[0]:
        merged[key] = sum(w * sd[key] for w, sd in zip(weights, state_dicts))
    return merged

# Task arithmetic: adapter_a + adapter_b - adapter_base
# Can combine: "French" + "Code" = French code assistant

# Federated sketch:
# 1. Each participant trains a local adapter
# 2. Adapters sent to central server
# 3. Server averages adapters (no raw data shared)
# 4. Merged adapter distributed back
Where you'll use itCombining multiple specialized adapters or privacy-preserving training where data cannot leave individual devices.
Under the hoodAdapter averaging works because LoRA updates live in similar subspaces; averaging produces a meaningful combined update without interference.

Where you'll use itSecurity review before deploying third-party adapters; supply-chain attacks through model weights are an emerging threat.
Under the hoodAdversarial adapters can encode trigger-response pairs in the weight matrices; detection requires behavioral testing, not just weight inspection.

31S-LoRA: Multi-Tenant Serving

What & why. S-LoRA enables serving thousands of LoRA adapters from a single base model on one GPU by batching adapter computations and using unified paging for adapter weights.

# S-LoRA concept:
# 1. Base model loaded once in GPU memory
# 2. Thousands of adapters stored in CPU RAM / disk
# 3. Per-request adapter paged to GPU on demand
# 4. Batch requests with different adapters simultaneously

class SLoRAServer:
    def __init__(self, base_model, adapter_pool):
        self.base = base_model
        self.adapters = adapter_pool  # {name: adapter_path}

    def serve_batch(self, requests):
        groups = group_by_adapter(requests)
        outputs = {}
        for adapter_name, batch in groups.items():
            self.load_adapter(adapter_name)  # cached or paged
            outputs[adapter_name] = self.base(batch)
        return outputs

# Key: CUDA unified memory pages adapters in/out as needed
# Latency: ~10ms for adapter swap (CPU -> GPU transfer)
Where you'll use itMulti-tenant LLM serving where each customer has a custom adapter; serves thousands of adapters from a single GPU.
Under the hoodS-LoRA uses custom CUDA kernels for batched adapter computation and unified memory for transparent CPU-GPU adapter paging.

32Quality-per-VRAM Benchmarking

What & why. Comparing configurations by quality-per-VRAM reveals the most efficient setup. A configuration that achieves 95% of the quality at 30% of the VRAM is often the right production choice.

import time, torch

def benchmark_config(model_fn, eval_fn, config_name):
    torch.cuda.reset_peak_memory_stats()
    model = model_fn()
    start = time.time()
    quality = eval_fn(model)
    elapsed = time.time() - start
    peak_vram = torch.cuda.max_memory_allocated() / 1e9

    return {
        "config": config_name,
        "quality": quality,
        "vram_gb": peak_vram,
        "quality_per_vram": quality / peak_vram,
        "time_s": elapsed
    }

# Compare:
# | Config      | Quality | VRAM  | Q/V   |
# |-------------|---------|-------|-------|
# | Full FT     | 0.94    | 84 GB | 0.011 |
# | LoRA r=16   | 0.92    | 14 GB | 0.066 |
# | QLoRA r=16  | 0.91    | 8 GB  | 0.114 |
Where you'll use itArchitecture selection; this data drives the decision between full FT and various PEFT configurations.
Under the hoodQuality-per-VRAM is the true cost metric; it normalizes quality gains against infrastructure cost.

33Production Rollout Playbook

What & why. Moving a LoRA adapter from experiment to production requires model validation, A/B testing, monitoring, and rollback capability. This playbook defines the gates between stages.

# Production rollout stages:
# 1. Lab validation
#    - Eval on held-out test set (accuracy, latency)
#    - Safety eval (refusal rate, harmful content)

# 2. Shadow deployment

# 3. Canary release (5% traffic)

# - Safety refusal rate drops below threshold

Under the hoodCanary deployments detect quality regressions before full exposure; adapter models are ideal for canary because swapping is instant.
