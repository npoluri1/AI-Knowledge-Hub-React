1Single-Agent Limits: Context, Focus, and Reliability

What & why. A single agent handling everything suffers from context overload (too many tools and instructions), role confusion (being both researcher and writer), and reliability degradation (more steps = more failure points). Multi-agent systems address these by distributing work across specialized agents, each with a narrow scope and focused context.

# Single agent: overloaded with responsibilities
single_agent_prompt = """
You are a researcher, writer, editor, fact-checker, and SEO specialist.
Analyze the topic, find sources, write the article, edit it,
check facts, optimize for SEO, and format the final output.
You have 15 tools available.
"""

# Multi-agent: specialized roles
researcher_prompt = """
You are a research specialist. Find and summarize authoritative sources.
You have 3 tools: web_search, academic_search, internal_docs.
Output: structured research brief with citations.
"""

writer_prompt = """
You are a technical writer. Transform research briefs into clear articles.
You have 1 tool: format_article.
Input: research brief. Output: polished article draft.
"""

editor_prompt = """
You are an editor. Review articles for clarity, accuracy, and flow.
You have 1 tool: suggest_edits.
Input: article draft. Output: edited version with change notes.
"""
Where you'll use itMulti-agent decomposition works best when tasks have natural boundaries (research then write then edit) or when different specializations are needed (data analysis, visualization, narrative).
Under the hoodEach agent runs its own LLM call with a focused prompt and limited tools. This reduces context size per call, improves tool selection accuracy, and enables independent failure handling.

2Roles and Specialization: Researcher, Writer, Critic

What & why. Role specialization assigns each agent a distinct persona with specific capabilities, constraints, and quality standards. A researcher gathers facts, a writer composes prose, and a critic evaluates quality. Each agent's prompt is optimized for its role, with domain-specific instructions and evaluation criteria.

Where you'll use itRole specialization improves quality because each agent's entire context is dedicated to one task. A researcher's context is full of sources, not writing guidelines. A writer's context is full of prose, not search results.
Under the hoodEach role's system prompt is carefully crafted with domain-specific instructions, constraints, and evaluation criteria. Temperature is tuned per role: low for research (factual), medium for writing (creative), medium-low for critique (precise).

3Supervisor Pattern: Central Router for Task Distribution

What & why. The supervisor pattern places a central agent that receives all tasks, analyzes them, and routes to the appropriate specialist agent. The supervisor decides which agent handles each subtask, monitors progress, and assembles the final result. It's the simplest multi-agent topology.

from langgraph.graph import StateGraph, MessagesState
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o")

def supervisor(state: MessagesState):
    """Central router that decides which agent handles the task."""
    response = llm.invoke([
        {"role": "system", "content": """You are a supervisor. Route tasks:
        - For research questions: say "route to researcher"
        - For writing tasks: say "route to writer"
        - For review/feedback: say "route to critic"
        - For complete: say "done" """},
        *state["messages"]
    ])
    return {"messages": [response]}

def researcher(state: MessagesState):
    """Handles research tasks."""
    response = llm.invoke([
        {"role": "system", "content": "You are a research specialist. "
         "Find and summarize authoritative information."},
        *state["messages"]
    ])
    return {"messages": [response]}

def writer(state: MessagesState):
    """Handles writing tasks."""
    response = llm.invoke([
        {"role": "system", "content": "You are a writer. "
         "Transform inputs into clear, engaging prose."},
        *state["messages"]
    ])
    return {"messages": [response]}

# Build the graph
graph = StateGraph(MessagesState)
graph.add_node("supervisor", supervisor)
graph.add_node("researcher", researcher)
graph.add_node("writer", writer)
graph.set_entry_point("supervisor")
Where you'll use itThe supervisor pattern is the starting point for multi-agent systems. It's simple to implement and debug. The supervisor makes all routing decisions, making the system's behavior predictable.
Under the hoodThe supervisor is itself an LLM call. It parses the task and returns a routing decision. More sophisticated supervisors maintain a task queue and can split complex tasks into subtasks.

4Sequential Pipeline: Handoffs Between Agents

What & why. A sequential pipeline passes output from one agent directly to the next. Agent A produces a result, which becomes the input for Agent B, whose output feeds Agent C. This is the simplest coordination pattern: no shared state, no routing decisions, just linear flow.

class SequentialPipeline:
    def __init__(self, agents: list):
        self.agents = agents

    async def run(self, initial_input: str) -> str:
        """Run agents in sequence, passing output to next."""
        current_input = initial_input
        for agent in self.agents:
            current_input = await agent.process(current_input)
            print(f"[{agent.name}] -> {current_input[:100]}...")
        return current_input

# Pipeline: research -> write -> edit -> format
pipeline = SequentialPipeline([
    Agent(name="Researcher", prompt="Gather facts on: {input}"),
    Agent(name="Writer", prompt="Write article from: {input}"),
    Agent(name="Editor", prompt="Edit for quality: {input}"),
    Agent(name="Formatter", prompt="Format as blog post: {input}")
])

result = await pipeline.run("The impact of AI on healthcare")

# Flow: "The impact of AI on healthcare"
#   -> Researcher: research brief with sources
#   -> Writer: article draft
#   -> Editor: polished article with corrections
#   -> Formatter: HTML blog post
Where you'll use itPipelines are ideal for content production (research-write-edit-publish), data processing (extract-transform-load), and any workflow with clear sequential stages.
Under the hoodPipelines are deterministic: the same input always follows the same path. This makes them easy to debug and test. Each agent sees only the output of the previous agent, not the full history.

6Shared Task List: The Blackboard Pattern

What & why. The blackboard pattern uses a shared data structure (the blackboard) that all agents can read from and write to. Agents post tasks, results, and status updates to the blackboard. Other agents monitor it and pick up tasks they can handle. This decouples agents from each other.

import asyncio
from dataclasses import dataclass, field

@dataclass
class Blackboard:
    tasks: list[dict] = field(default_factory=list)
    results: list[dict] = field(default_factory=list)
    lock: asyncio.Lock = field(default_factory=asyncio.Lock)

    async def post_task(self, task: dict):
        async with self.lock:
            self.tasks.append(task)

    async def post_result(self, result: dict):
        async with self.lock:
            self.results.append(result)

    async def get_pending_tasks(self) -> list[dict]:
        async with self.lock:
            return [t for t in self.tasks if t["status"] == "pending"]

    async def claim_task(self, task_id: str, agent_name: str) -> bool:
        async with self.lock:
            for task in self.tasks:
                if task["id"] == task_id and task["status"] == "pending":
                    task["status"] = "claimed"
                    task["claimed_by"] = agent_name
                    return True
            return False

# Agent loop
async def agent_worker(agent, blackboard):
    while True:
        tasks = await blackboard.get_pending_tasks()
        for task in tasks:
            if agent.can_handle(task["type"]):
                if await blackboard.claim_task(task["id"], agent.name):
                    result = await agent.process(task["content"])
                    await blackboard.post_result({
                        "task_id": task["id"],
                        "agent": agent.name,
                        "result": result
                    })
        await asyncio.sleep(1)  # poll interval
Where you'll use itThe blackboard pattern is ideal for dynamic task allocation where tasks have different requirements and agents have different capabilities. It naturally load-balances across agents.
Under the hoodThe blackboard is a shared state with locking for concurrency. Agents poll for tasks, claim them atomically, and post results. The pattern decouples task creation from task execution.

7Message Envelope: from, to, content

What & why. The message envelope is the standard communication format between agents. It contains who sent it (from), who receives it (to), the content, metadata (timestamp, correlation ID, priority), and optionally structured data. Standardizing the envelope ensures all agents can interoperate regardless of implementation.

from dataclasses import dataclass, field
from datetime import datetime
import uuid

@dataclass
class MessageEnvelope:
    id: str = field(default_factory=lambda: str(uuid.uuid4()))
    from_agent: str = ""
    to_agent: str = ""
    content: str = ""
    message_type: str = "task"  # task, result, feedback, system
    correlation_id: str = ""  # groups related messages
    priority: int = 0  # higher = more urgent
    timestamp: datetime = field(default_factory=datetime.now)
    metadata: dict = field(default_factory=dict)

    def create_reply(self, content: str) -> "MessageEnvelope":
        """Create a reply message maintaining correlation."""
        return MessageEnvelope(
            from_agent=self.to_agent,
            to_agent=self.from_agent,
            content=content,
            message_type="result",
            correlation_id=self.correlation_id,
            metadata={"reply_to": self.id}
        )

# Usage
task = MessageEnvelope(
    from_agent="supervisor",
    to_agent="researcher",
    content="Research the impact of MCP on enterprise tooling",
    message_type="task",
    priority=1
)

result = task.create_reply(
    content="MCP reduces integration complexity from MxN to M+N..."
)
# result.correlation_id == task.correlation_id
# result.from_agent == "researcher"
# result.to_agent == "supervisor"
Where you'll use itStandard message envelopes enable tracing, debugging, and logging in multi-agent systems. The correlation ID groups all messages related to one task across multiple agents.
Under the hoodThe envelope pattern is similar to enterprise messaging (JMS, AMQP). It provides a uniform interface for agent communication regardless of the underlying transport.

8Topology: Star vs. Chain vs. Mesh

What & why. Agent topology defines how agents are connected. Star topology has one coordinator connected to all workers. Chain topology passes work linearly. Mesh topology connects all agents to all others. Each topology has trade-offs in complexity, fault tolerance, and communication overhead.

# Topology definitions and trade-offs

topologies = {

    },
    "chain": {
        "description": "Linear pipeline A -> B -> C -> D",
        "communication": "Each agent talks only to next/prev",
        "pros": ["Simple flow", "Clear responsibility", "Easy to reason about"],
        "cons": ["Single point of failure per link", "No parallelism"],
        "best_for": "Sequential processing, content pipelines"
    },
    "mesh": {
        "description": "All agents connected to all others",
        "communication": "Any agent can message any other",
        "pros": ["Maximum flexibility", "No SPOF", "Parallel collaboration"],
        "cons": ["Complex routing", "Message explosion", "Hard to debug"],
        "best_for": "Debate, brainstorming, collaborative problem-solving"
    },
    "hierarchical": {
        "description": "Tree structure: manager -> team leads -> workers",

Where you'll use itStart with star topology for simplicity. Move to chain for sequential workflows. Use mesh sparingly (communication overhead grows quadratically). Hierarchical for large-scale systems.
Under the hoodMost production systems combine topologies: a hierarchical structure where each team uses a star or chain internally. The choice affects message routing, fault tolerance, and debugging complexity.

9Demo: Two-Agent Translator and Reviewer Loop

What & why. A minimal multi-agent system with two agents: a translator that converts text between languages, and a reviewer that checks translation quality. They loop until the reviewer approves the translation. This demonstrates the core patterns: role specialization, message passing, termination conditions, and quality feedback.

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o")

def translator(text: str, feedback: str = "") -> str:
    """Translate English to French, incorporating reviewer feedback."""
    prompt = f"""You are an expert French translator.
Translate the following English text to French.
{f"Incorporate this feedback: {feedback}" if feedback else ""}

English: {text}
French translation:"""
    return llm.invoke(prompt).content

def reviewer(english: str, french: str) -> tuple[bool, str]:
    """Review translation quality. Returns (approved, feedback)."""
    prompt = f"""You are a French translation quality reviewer.
Evaluate this translation:

English: {english}
French: {french}

Is the translation accurate, natural, and culturally appropriate?
Reply with APPROVED if good, or REVISION_NEEDED with specific feedback."""
    response = llm.invoke(prompt).content
    approved = "APPROVED" in response.upper()
    return approved, response

# Translation loop
def translate_with_review(text: str, max_iterations: int = 3) -> str:
    """Translate with iterative review."""
    feedback = ""
    for i in range(max_iterations):
        french = translator(text, feedback)
        approved, feedback = reviewer(text, french)
        print(f"Iteration {i+1}: {'APPROVED' if approved else 'NEEDS REVISION'}")
        if approved:
            return french
    print("Max iterations reached, returning best attempt")
    return french

result = translate_with_review("The quick brown fox jumps over the lazy dog.")
Where you'll use itThe translator-reviewer loop is a template for any quality improvement workflow: generate, evaluate, refine. It works for code review, content editing, and design iteration.
Under the hoodThe loop demonstrates key multi-agent concepts: specialized agents, structured feedback, termination conditions, and bounded iteration. The max_iterations prevents infinite loops.

10Cost Multiplication Awareness

What & why. Multi-agent systems multiply costs. A pipeline of 3 agents means 3x the LLM calls. A debate between 5 agents means 5x per round. Before adding agents, calculate the cost multiplier and determine if the quality improvement justifies the expense. Profile real costs before committing to an architecture.

# Cost multiplier analysis
def estimate_multiagent_cost(
    task_count: int,
    agents_per_task: float,
    rounds_per_task: float,
    avg_tokens_per_call: int,
    cost_per_1k_tokens: float
) -> dict:
    """Estimate total cost of a multi-agent system."""
    total_calls = task_count * agents_per_task * rounds_per_task
    total_tokens = total_calls * avg_tokens_per_call
    total_cost = (total_tokens / 1000) * cost_per_1k_tokens

    single_agent_calls = task_count
    single_agent_tokens = single_agent_calls * avg_tokens_per_call * 3  # 3x for retries
    single_agent_cost = (single_agent_tokens / 1000) * cost_per_1k_tokens

    return {
        "multi_agent": {
            "total_calls": total_calls,
            "total_tokens": total_tokens,
            "total_cost": total_cost
        },
        "single_agent": {
            "total_calls": single_agent_calls,
            "total_tokens": single_agent_tokens,
            "total_cost": single_agent_cost
        },
        "cost_multiplier": total_cost / single_agent_cost if single_agent_cost > 0 else float("inf")
    }

# Example: 100 tasks, 3 agents, 2 rounds
# Multi-agent: 600 calls, ~$12.00
# Single-agent: 300 calls, ~$6.00
# Cost multiplier: 2.0x
# Question: Is 2x cost worth the quality improvement?
Where you'll use itCost multiplication is the most overlooked multi-agent trade-off. Always calculate cost multiplier before committing to an architecture. Start with fewer agents and add only when quality justifies cost.
Under the hoodThe cost multiplier depends on agents per task and rounds of interaction. A 2-agent pipeline is 2x cost. A 5-agent debate with 3 rounds is 15x cost. Profile actual token usage to get accurate estimates.

11Termination: Votes and Done Flags

What & why. Multi-agent systems need clear termination conditions. Without them, agents can loop indefinitely. Common patterns: done flags (agent signals completion), majority vote (most agents agree to stop), max iterations (hard limit), and quality thresholds (stop when quality score exceeds threshold).

class MultiAgentOrchestrator:
    def __init__(self, agents: list, max_rounds: int = 5):
        self.agents = agents
        self.max_rounds = max_rounds

    async def run(self, task: str) -> dict:
        context = {"task": task, "round": 0, "done_votes": 0}

        for round_num in range(self.max_rounds):
            context["round"] = round_num
            votes = []

            for agent in self.agents:
                result = await agent.process(task, context)
                votes.append(result.get("vote_done", False))
                context["results"] = context.get("results", [])
                context["results"].append(result)

            # Check termination conditions
            if all(votes):
                return {"status": "consensus", "result": context["results"]}

            done_count = sum(votes)
            if done_count > len(self.agents) / 2:
                return {"status": "majority", "result": context["results"]}

        return {"status": "max_rounds", "result": context["results"]}

# Termination conditions:
# 1. All agents vote done (unanimous)
# 2. Majority vote done
# 3. Max rounds reached (hard limit)
# 4. Quality score above threshold
# 5. No improvement between rounds
Where you'll use itTermination conditions prevent runaway costs and infinite loops. Always set a max_rounds as a safety net, even with other termination conditions.
Under the hoodThe orchestrator collects termination votes from each agent. Agents vote "done" when they believe the task is complete or no further improvement is possible. The orchestrator decides based on the voting strategy.

12Common Pitfalls: Role Bleed and Coordination Failures

What & why. Role bleed occurs when an agent takes on responsibilities outside its assigned role (e.g., the researcher starts writing prose). Coordination failures include duplicate work (two agents doing the same task), missed handoffs (output not passed to next agent), and circular dependencies (agents waiting for each other).

13Handoff Protocol: Structured Transfer Payload

What & why. A structured handoff protocol ensures that when work passes between agents, all necessary context travels with it. The handoff payload includes the original task, accumulated work, decisions made, constraints, and what the next agent should focus on. This prevents context loss at handoff boundaries.

from dataclasses import dataclass, field

@dataclass
class HandoffPayload:
    task_id: str
    original_task: str
    current_output: str
    completed_steps: list[str]
    pending_steps: list[str]
    decisions: list[dict]
    constraints: list[str]
    context: dict = field(default_factory=dict)

    def for_next_agent(self, agent_role: str) -> str:
        """Format handoff for the next agent."""
        return f"""HANDOFF from {self.completed_steps[-1] if self.completed_steps else 'start'}

Original task: {self.original_task}

Current work:
{self.current_output}

What you should focus on as {agent_role}:
{chr(10).join(f'- {step}' for step in self.pending_steps[:1])}

Constraints:
{chr(10).join(f'- {c}' for c in self.constraints)}

Decisions made:
{chr(10).join(f'- {d["decision"]}: {d["rationale"]}' for d in self.decisions)}
"""

# Pipeline with structured handoffs
payload = HandoffPayload(
    task_id="task-001",
    original_task="Write a technical blog post about MCP",
    current_output="",
    completed_steps=[],
    pending_steps=["Research MCP protocol", "Write draft", "Edit and review"],
    decisions=[],
    constraints=["Max 2000 words", "Include code examples", "Target: developers"]

Where you'll use itStructured handoffs prevent the most common multi-agent failure: the next agent doesn't have enough context. The payload is self-contained; the next agent doesn't need to query previous agents.
Under the hoodThe handoff payload is a structured contract between agents. It includes what was done, what's pending, and what constraints apply. This makes handoffs explicit and debuggable.

14Hierarchical Manager-Workers: Delegation Trees

What & why. Hierarchical systems mirror human organizations: a manager agent decomposes tasks and delegates to worker agents. Workers report results back to the manager, who aggregates and decides next steps. This scales better than flat topologies because the manager handles coordination, not the workers.

class ManagerAgent:
    def __init__(self, workers: dict):
        self.workers = workers  # role -> agent
        self.llm = ChatOpenAI(model="gpt-4o")

    async def decompose(self, task: str) -> list[dict]:
        """Break task into subtasks with role assignments."""
        response = await self.llm.ainvoke([{
            "role": "system",
            "content": f"""Decpose this task into subtasks.
Available workers: {list(self.workers.keys())}
Return JSON array of: {{"role": "...", "subtask": "...", "depends_on": [...]}}"""
        }, {"role": "user", "content": task}])
        return parse_json(response.content)

    async def coordinate(self, task: str) -> str:
        """Decompose, delegate, aggregate."""
        subtasks = await self.decompose(task)
        results = {}

        # Execute independent tasks in parallel
        independent = [s for s in subtasks if not s.get("depends_on")]
        parallel_results = await asyncio.gather(*[
            self.workers[s["role"]].process(s["subtask"])
            for s in independent
        ])
        for s, r in zip(independent, parallel_results):
            results[s["role"]] = r

        # Execute dependent tasks sequentially
        dependent = [s for s in subtasks if s.get("depends_on")]
        for s in dependent:
            context = {dep: results[dep] for dep in s["depends_on"]}
            results[s["role"]] = await self.workers[s["role"]].process(
                s["subtask"], context=context
            )

        # Aggregate results
        return await self.aggregate(results)

    async def aggregate(self, results: dict) -> str:
        """Combine worker results into final output."""
        response = await self.llm.ainvoke([{
            "role": "system",

15Debate Pattern: Pro/Con Rounds Then Judge

What & why. The debate pattern has agents argue opposing positions for several rounds, then a judge agent evaluates the arguments and produces a final decision. This forces consideration of multiple perspectives and often produces more nuanced, well-reasoned conclusions than a single-pass approach.

async def debate_rounds(
    topic: str,
    pro_agent, con_agent, judge_agent,
    num_rounds: int = 3
) -> str:
    """Run a structured debate and get a judged conclusion."""
    pro_arguments = []
    con_arguments = []

    for round_num in range(num_rounds):
        # Pro agent argues
        pro_context = f"""Topic: {topic}
Round {round_num + 1} of {num_rounds}.
Previous con arguments: {con_arguments}
Make your strongest argument FOR this topic."""
        pro = await pro_agent.process(pro_context)
        pro_arguments.append(pro)

        # Con agent rebuts
        con_context = f"""Topic: {topic}
Round {round_num + 1} of {num_rounds}.
Previous pro arguments: {pro_arguments}
Make your strongest argument AGAINST this topic."""
        con = await con_agent.process(con_context)
        con_arguments.append(con)

    # Judge evaluates
    judgment_context = f"""Topic: {topic}

PRO arguments (all rounds):
{chr(10).join(f'Round {i+1}: {a}' for i, a in enumerate(pro_arguments))}

CON arguments (all rounds):
{chr(10).join(f'Round {i+1}: {a}' for i, a in enumerate(con_arguments))}

Evaluate both sides. Consider:
1. Which arguments are strongest?
2. What evidence supports each side?
3. What are the risks of each position?

Provide a balanced, reasoned conclusion."""
    return await judge_agent.process(judgment_context)
Where you'll use itDebate is valuable for high-stakes decisions where groupthink is a risk. It forces consideration of counterarguments and produces more robust conclusions than simple voting.
Under the hoodEach round builds on previous arguments, allowing agents to address specific points. The judge has access to all rounds, providing comprehensive context for the final decision.

16Voting Ensemble: Majority and Self-Consistency Across Personas

What & why. Voting ensembles run the same task through multiple agents (or the same agent with different personas/temperatures) and take the majority answer. Self-consistency checks that the same reasoning path is followed multiple times. This improves reliability for factual questions and reduces hallucination.

async def voting_ensemble(
    task: str,
    agents: list,
    vote_threshold: float = 0.6
) -> dict:
    """Run task through multiple agents, take majority vote."""
    responses = []
    for agent in agents:
        response = await agent.process(task)
        responses.append(response)

    # Extract final answers
    answers = [extract_answer(r) for r in responses]

    # Count votes per answer
    vote_counts = {}
    for answer in answers:
        normalized = normalize_answer(answer)
        vote_counts[normalized] = vote_counts.get(normalized, 0) + 1

    # Find majority
    total = len(answers)
    for answer, count in vote_counts.items():
        if count / total >= vote_threshold:
            return {
                "answer": answer,
                "confidence": count / total,
                "votes": vote_counts,
                "individual_responses": responses
            }

    # No majority: return most common with low confidence
    best = max(vote_counts, key=vote_counts.get)
    return {
        "answer": best,
        "confidence": vote_counts[best] / total,
        "votes": vote_counts,
        "warning": "No clear majority"
    }

17Market/Negotiation: Bidding for Tasks

What & why. Market-based coordination has agents bid on tasks based on their capabilities, cost, and availability. The supervisor accepts the best bid. This is more efficient than fixed assignment because agents self-select tasks they're best at, and the system adapts to agent availability.

@dataclass
class TaskBid:
    agent_name: str
    task_id: str
    estimated_cost: float
    estimated_quality: float  # 0-1, agent's self-assessed quality
    confidence: float  # 0-1, how confident in estimate
    completion_time: int  # estimated seconds

class MarketOrchestrator:
    def __init__(self, agents: list):
        self.agents = agents

    async def auction(self, task: str, task_type: str) -> str:
        """Collect bids and select best agent."""
        bids = []
        for agent in self.agents:
            if agent.can_handle(task_type):
                bid = await agent.bid_on_task(task)
                bids.append(bid)

        if not bids:
            return "No agent available for this task"

        # Score bids: quality * confidence / cost
        scored = [
            (bid, bid.estimated_quality * bid.confidence / max(bid.estimated_cost, 0.001))
            for bid in bids
        ]
        scored.sort(key=lambda x: x[1], reverse=True)

        # Winner executes
        winner = scored[0][0]
        result = await self.get_agent(winner.agent_name).process(task)
        return result

    def get_agent(self, name: str):
        return next(a for a in self.agents if a.name == name)
Where you'll use itMarket-based coordination works when agents have different cost-quality profiles. It naturally allocates tasks to the most cost-effective agent.
Under the hoodAgents bid with their estimated cost, quality, and confidence. The scoring function balances quality against cost. This creates competition that drives efficiency.

19Shared Memory vs. Message Passing

What & why. Multi-agent systems coordinate through either shared memory (all agents read/write a common store) or message passing (agents communicate directly). Shared memory is simpler but creates coupling. Message passing is more flexible but adds communication overhead. The choice depends on coordination complexity.

# Shared memory approach
class SharedMemory:
    def __init__(self):
        self.store = {}
        self.lock = asyncio.Lock()

    async def read(self, key: str):
        async with self.lock:
            return self.store.get(key)

    async def write(self, key: str, value):
        async with self.lock:
            self.store[key] = value

    async def list_keys(self, prefix: str = ""):
        async with self.lock:
            return [k for k in self.store if k.startswith(prefix)]

# Message passing approach
class MessageBus:
    def __init__(self):
        self.queues = {}  # agent_name -> asyncio.Queue

    async def send(self, to_agent: str, message: MessageEnvelope):
        if to_agent not in self.queues:
            self.queues[to_agent] = asyncio.Queue()
        await self.queues[to_agent].put(message)

    async def receive(self, agent_name: str) -> MessageEnvelope:
        if agent_name not in self.queues:
            self.queues[agent_name] = asyncio.Queue()
        return await self.queues[agent_name].get()

# Trade-offs:
# Shared memory:
# + Simple, fast reads
# + Natural for shared state
# - Coupling (agents depend on shared schema)
# - Concurrency issues (locks, race conditions)

# Message passing:
# + Decoupled (agents don't share state)
# + Scalable (messages can be queued, replayed)
# - Higher latency (serialization, routing)
# - More complex (message format, error handling)
Where you'll use itUse shared memory for small, tightly-coupled agent teams. Use message passing for large systems, cross-process agents, or when agents need to be independently deployable.
Under the hoodMost production systems use both: shared memory for fast local coordination, message passing for cross-service communication. The choice is per-interaction, not per-system.

20Async Fan-Out and Gather: Specialists in Parallel

What & why. Fan-out sends the same task to multiple specialist agents simultaneously. Gather collects all results. This is faster than sequential execution and leverages each agent's specialization. The results can be merged, voted on, or selected based on quality metrics.

import asyncio

async def fan_out_gather(
    task: str,
    specialists: list[dict]
) -> dict:
    """Send task to multiple specialists in parallel, collect results."""
    async def call_specialist(spec):
        agent = spec["agent"]
        result = await agent.process(task)
        return {
            "specialist": spec["name"],
            "result": result,
            "quality_hint": spec.get("quality_hint", 0.5)
        }

    # Fan-out: send to all specialists simultaneously
    tasks = [call_specialist(spec) for spec in specialists]
    results = await asyncio.gather(*tasks, return_exceptions=True)

    # Gather: collect successful results
    successful = [r for r in results if not isinstance(r, Exception)]
    failed = [r for r in results if isinstance(r, Exception)]

    return {
        "task": task,
        "results": successful,
        "failed_count": len(failed),
        "success_count": len(successful)
    }

21Failure Isolation: Try Per Agent, Fallback to Solo

What & why. In multi-agent systems, one agent's failure shouldn't cascade. Failure isolation catches per-agent errors and falls back to a simpler execution path (single agent). This ensures the system degrades gracefully rather than failing completely.

class ResilientOrchestrator:
    def __init__(self, agents: dict, fallback_agent=None):
        self.agents = agents
        self.fallback = fallback_agent

    async def execute(self, task: str) -> str:
        """Try multi-agent execution, fallback to single agent."""
        try:
            return await self._multi_agent_execute(task)
        except Exception as e:
            print(f"Multi-agent execution failed: {e}")
            if self.fallback:
                print("Falling back to single agent")
                return await self.fallback.process(task)
            raise

    async def _multi_agent_execute(self, task: str) -> str:
        """Execute with failure isolation per agent."""
        results = {}
        for name, agent in self.agents.items():
            try:
                results[name] = await agent.process(task)
            except Exception as e:
                print(f"Agent {name} failed: {e}")
                results[name] = f"Agent {name} failed: {e}"
                continue  # Skip failed agent, continue with others

        # Aggregate available results
        successful = {k: v for k, v in results.items()
                      if not v.startswith("Agent") or "failed" not in v}
        return await self._aggregate(successful)

What & why. Multi-hop conversations involve messages passing through multiple agents. Tracing records the full path: which agent processed which message, what decisions were made, and how the final result was assembled. This is essential for debugging and understanding system behavior.

27Negotiation Protocols: Contract-Net Pattern

What & why. The Contract-Net Protocol (CNP) is a distributed task allocation mechanism. A manager broadcasts a task announcement, agents submit bids, and the manager awards the contract to the best bidder. This decentralizes task assignment and lets agents self-select based on capability and cost.

class ContractNetManager:

        self.contracts = {}

What & why. When agents disagree on output, strategy, or priorities, conflict resolution mechanisms determine the outcome. Strategies include majority vote, weighted vote (by expertise), escalation to a senior agent, and domain-based arbitration (most relevant expert decides).

class ConflictResolver:
    def __init__(self, agents: dict):
        self.agents = agents
        self.expertise_scores = {}  # agent -> domain -> expertise

    def resolve(self, conflict: dict) -> str:
        """Resolve a conflict between agents."""
        strategy = conflict.get("resolution_strategy", "weighted_vote")

        if strategy == "majority_vote":
            return self._majority_vote(conflict["disagreements"])

        elif strategy == "weighted_vote":
            return self._weighted_vote(conflict["disagreements"], conflict["domain"])

        elif strategy == "domain_arbitration":
            return self._domain_arbitration(conflict["disagreements"], conflict["domain"])

        elif strategy == "escalate":
            return self._escalate_to_senior(conflict)

    def _weighted_vote(self, disagreements: list, domain: str) -> str:
        """Weight votes by domain expertise."""
        votes = {}
        for d in disagreements:
            agent = d["agent"]
            weight = self.expertise_scores.get(agent, {}).get(domain, 0.5)
            answer = d["position"]
            votes[answer] = votes.get(answer, 0) + weight

        return max(votes, key=votes.get)

    def _domain_arbitration(self, disagreements: list, domain: str) -> str:
        """Most relevant expert decides."""
        experts = sorted(
            disagreements,
            key=lambda d: self.expertise_scores.get(d["agent"], {}).get(domain, 0),
            reverse=True
        )
        return experts[0]["position"]
Where you'll use itConflict resolution prevents deadlocks in multi-agent systems. The strategy should be chosen based on the conflict type: factual disagreements use domain arbitration, preference disagreements use voting.
Under the hoodExpertise scores are maintained based on historical performance. Agents with higher accuracy in a domain get more weight in that domain's decisions.

30Trust Scores Between Agents: Updating Over Time

What & why. Trust scores quantify how reliable an agent's output is. They update based on historical performance: successful tasks increase trust, failures decrease it. Trust scores influence task assignment, voting weight, and conflict resolution. They adapt to changing agent capabilities.

class TrustManager:
    def __init__(self, decay_rate: float = 0.95):
        self.scores = {}  # agent -> domain -> trust_score
        self.decay_rate = decay_rate
        self.history = []

    def get_trust(self, agent: str, domain: str) -> float:
        """Get current trust score for agent in domain."""
        return self.scores.get(agent, {}).get(domain, 0.5)

    def update_trust(self, agent: str, domain: str,
                     success: bool, confidence: float):
        """Update trust based on task outcome."""
        current = self.get_trust(agent, domain)

        if success:
            # Increase trust, weighted by confidence
            new_score = current + (1 - current) * confidence * 0.1
        else:
            # Decrease trust, weighted by failure severity
            new_score = current * (1 - confidence * 0.2)

        self.scores.setdefault(agent, {})[domain] = max(0.1, min(0.99, new_score))

        # Apply decay to all scores (trust degrades over time)
        self._apply_decay()

    def _apply_decay(self):
        """Gradually reduce all trust scores toward baseline."""
        for agent in self.scores:
            for domain in self.scores[agent]:
                current = self.scores[agent][domain]
                self.scores[agent][domain] = (
                    current * self.decay_rate + 0.5 * (1 - self.decay_rate)
                )
Where you'll use itTrust scores prevent consistently poor-performing agents from dominating. They also recover naturally (decay toward baseline) if an agent improves over time.
Under the hoodTrust scores use exponential moving averages with decay. This means recent performance matters more than historical performance. The decay rate controls how quickly trust resets toward baseline.

36Formal Models: BDI (Beliefs-Desires-Intentions) Mapping

What & why. BDI is a model of practical reasoning borrowed from philosophy and AI. Agents maintain beliefs (what they know), desires (what they want), and intentions (what they're committed to doing). Mapping LLM agents to BDI provides a formal framework for agent decision-making and inter-agent communication.

@dataclass
class BDIAgent:
    beliefs: dict      # What the agent knows about the world
    desires: list      # Goals the agent wants to achieve
    intentions: list   # Commitments the agent has made

    def reason(self, observation: dict) -> str:
        """BDI reasoning cycle."""
        # 1. Update beliefs from observation
        self.beliefs.update(observation)

        # 2. Filter desires by current beliefs
        achievable = [d for d in self.desires if self._can_achieve(d)]

        # 3. Select intentions based on beliefs and desires
        if not self.intentions:
            self.intentions = self._deliberate(achievable)

        # 4. Execute current intentions
        if self.intentions:
            action = self._plan_action(self.intentions[0])
            if self._achieved(self.intentions[0]):
                self.intentions.pop(0)
            return action

        return "idle"

    def _can_achieve(self, desire):
        """Check if current beliefs support achieving this desire."""
        return all(
            self.beliefs.get(req, False) for req in desire.get("requires", [])
        )

    def _deliberate(self, achievable):
        """Select which desires to commit to."""
        return sorted(achievable, key=lambda d: d.get("priority", 0), reverse=True)[:3]

# Mapping to LLM agents:
# beliefs = context window (what the agent knows)
# desires = system prompt goals (what the agent should do)
# intentions = current task list (what the agent is committed to)
Where you'll use itBDI provides a formal framework for reasoning about agent behavior. It helps identify why agents make certain decisions and how to change their behavior by modifying beliefs, desires, or intentions.
Under the hoodBDI reasoning cycles: perceive -> update beliefs -> deliberate -> select intentions -> act. LLM agents implement this implicitly through prompt engineering and context management.

38Byzantine Tolerance: Malicious Agent Defense

What & why. Byzantine fault tolerance (BFT) ensures a system functions correctly even when some agents are faulty or malicious. In multi-agent systems, this means detecting and isolating agents that produce incorrect, contradictory, or adversarial outputs. BFT requires 3f+1 agents to tolerate f faulty agents.

class ByzantineDetector:
    def __init__(self, min_agreement: float = 0.6):
        self.min_agreement = min_agreement

    def detect_byzantine(self, agent_outputs: dict) -> list[str]:
        """Identify agents with outputs far from consensus."""
        outputs = list(agent_outputs.values())
        if len(outputs) < 3:
            return []  # Need at least 3 for detection

        # Find consensus using embedding similarity
        embeddings = [get_embedding(o) for o in outputs]
        consensus = np.mean(embeddings, axis=0)

        byzantine_agents = []
        for agent, embedding in zip(agent_outputs.keys(), embeddings):
            similarity = cosine_similarity(embedding, consensus)
            if similarity < self.min_agreement:
                byzantine_agents.append(agent)

        return byzantine_agents

    def tolerate_byzantine(self, agent_outputs: dict, threshold: int) -> dict:
        """Return outputs excluding Byzantine agents."""
        byzantine = self.detect_byzantine(agent_outputs)
        clean = {k: v for k, v in agent_outputs.items() if k not in byzantine}

        if len(clean) < threshold:
            raise InsufficientHealthyAgents(
                f"Only {len(clean)} healthy agents, need {threshold}"
            )

        return clean

# Example: To tolerate 2 malicious agents, need at least 7 agents

What & why. Swarm intelligence uses decentralized, self-organized behavior inspired by ant colonies and bird flocks.         return sorted(
            self.pheromones.items(),
            key=lambda x: x[1],
            reverse=True
        )

40Distributed Consensus: Raft Analogy for Decisions

What & why. Consensus algorithms ensure all agents agree on a shared state or decision. Raft is a practical consensus algorithm: one leader proposes decisions, followers vote, and majority approval commits the decision. In multi-agent systems, Raft-like consensus ensures all agents agree on task assignments, priorities, and shared facts.

class RaftConsensus:
    def __init__(self, agents: list):
        self.agents = agents
        self.leader = None
        self.current_term = 0
        self.votes_received = {}

    def elect_leader(self) -> str:
        """Simple leader election."""
        self.current_term += 1
        # In practice: random timeout, request_vote RPCs
        # For simplicity: round-robin leader
        leader_idx = self.current_term % len(self.agents)
        self.leader = self.agents[leader_idx]
        return self.leader

    async def propose(self, proposal: dict) -> dict:
        """Leader proposes, followers vote."""
        if not self.leader:
            self.elect_leader()

        votes = {"yes": 0, "no": 0}
        for agent in self.agents:
            if agent == self.leader:
                votes["yes"] += 1  # Leader votes yes
                continue

            # Follower evaluates proposal
            vote = await agent.vote_on(proposal)
            votes[vote] = votes.get(vote, 0) + 1

        majority_needed = len(self.agents) // 2 + 1
        committed = votes["yes"] >= majority_needed

        return {
            "proposal": proposal,
            "committed": committed,
            "votes": votes,
            "leader": self.leader,
            "term": self.current_term
        }

            "max_cost_per_hour": rules.get("cost_limit", 5.0)
        }

    def check_action(self, agent_name: str, action: dict) -> bool:
        """Validate agent action against containment rules."""
        if self.kill_switch_active:
            return False

        rules = self.containment_rules.get(agent_name, {})
        if action.get("tokens", 0) > rules.get("max_tokens_per_call", 4000):
            return False
        if action.get("tool") not in rules.get("allowed_tools", []):
            return False
        return True

    def monitor_anomalies(self):
        """Detect and respond to anomalous agent behavior."""
        for agent in self.agents:
            metrics = agent.get_metrics()
            if metrics["calls_per_minute"] > 100:
                self.activate_kill_switch(f"Agent {agent.name} exceeded call limit")
            if metrics["error_rate"] > 0.5:
                self.activate_kill_switch(f"Agent {agent.name} error rate too high")
Where you'll use itSafety mechanisms are mandatory for production multi-agent systems. Kill-switches prevent runaway costs and cascading failures. Containment limits prevent agents from exceeding their authorized scope.
Under the hoodContainment rules are enforced at the agent wrapper level. Every action passes through the safety check before execution. Anomaly monitoring runs on a separate thread and can trigger kill-switches.

43Economics: ROI Per Added Agent Curve

What & why. Each additional agent has a marginal benefit (improved quality, coverage, or speed) and marginal cost (LLM tokens, coordination overhead, latency). The ROI curve shows the point where adding more agents costs more than the value they provide. This is the fundamental economic constraint on multi-agent systems.

# ROI analysis per agent count
def analyze_roi(task_count: int, base_cost_per_task: float):
    """Analyze ROI as agents are added."""
    results = []
    for n_agents in range(1, 11):
        # Quality improvement (diminishing returns)
        quality = 1 - (0.5 ** n_agents)  # approaches 1.0

        # Cost multiplier (super-linear)
        if n_agents <= 3:
            cost_mult = n_agents
        else:
            cost_mult = 3 + (n_agents - 3) ** 1.5

        total_cost = task_count * base_cost_per_task * cost_mult
        quality_value = task_count * quality * 100  # $100 per quality unit

        roi = (quality_value - total_cost) / total_cost * 100

        results.append({
            "agents": n_agents,
            "quality": quality,
            "cost_multiplier": cost_mult,
            "total_cost": total_cost,
            "quality_value": quality_value,
            "roi_pct": roi
        })

    return results

# Typical ROI curve:
# 1 agent:  ROI = 100% (baseline)
# 2 agents: ROI = 150% (good improvement)
# 3 agents: ROI = 120% (still positive)
# 4 agents: ROI = 80%  (declining)
# 5 agents: ROI = 40%  (marginal)
# 6+ agents: ROI negative (cost exceeds benefit)

# Sweet spot: 2-4 agents for most tasks
Where you'll use itROI analysis prevents over-investment in multi-agent systems. The optimal agent count is where marginal benefit equals marginal cost, typically 2-4 agents.
Under the hoodThe ROI curve depends on task complexity and agent specialization quality. Well-specialized agents have steeper quality improvements; poorly-specialized agents add cost without quality gains.

Content Factory: Researcher-Writer-Editor with Approvals

A content production pipeline with three specialized agents: a researcher gathers sources and facts, a writer composes the article, and an editor reviews for quality. Includes approval gates where a human must approve the research brief before writing begins and the draft before publication.

Architecture steps.

  2. Build a sequential pipeline: researcher -> approval gate -> writer -> editor -> approval gate -> publish
  3. Implement structured handoff payloads with research briefs, decisions, and constraints
  4. Add approval gates: human reviews research brief and final draft before proceeding
  5. Set budget caps per role: researcher $5, writer $10, editor $3
  6. Implement quality verification gate after editor review

  8. Build retry loop: if editor rejects, writer revises up to 2 times
from langgraph.graph import StateGraph, MessagesState

class ContentState(MessagesState):
    research_brief: str = ""
    article_draft: str = ""
    edited_version: str = ""
    approved: bool = False
    iteration: int = 0

def researcher(state: ContentState):
    """Gather research brief on the topic."""
    topic = state["messages"][-1].content
    brief = await research_agent.process(f"Research: {topic}")
    return {"research_brief": brief, "messages": [
        {"role": "assistant", "content": f"Research complete. Brief:\n{brief}"}
    ]}

def writer(state: ContentState):
    """Write article from research brief."""
    draft = await writer_agent.process(
        f"Write article from this research:\n\n{state['research_brief']}"
    )
    return {"article_draft": draft, "iteration": state.get("iteration", 0) + 1}

def editor(state: ContentState):
    """Review and edit the article."""
    edited = await editor_agent.process(
        f"Edit this article:\n\n{state['article_draft']}"
    )
    return {"edited_version": edited}

def quality_check(state: ContentState):
    """Check if quality meets threshold."""
    score = await quality_agent.process(state["edited_version"])
    approved = float(score) >= 0.8
    return {"approved": approved}

graph.add_node("writer", writer)

Incident Response Triage Swarm Over Alerts

An incident response system where multiple specialized agents triage incoming alerts simultaneously. A triage agent classifies severity, a diagnostics agent identifies root cause, a runbook agent suggests remediation, and a communication agent drafts status updates. They operate as a swarm with a blackboard for shared state.

Architecture steps.

  1. Build alert ingestion pipeline: receive alerts from monitoring systems (Prometheus, Datadog)
  2. Implement triage agent: classify severity (P1-P4), identify affected services, deduplicate
  3. Add diagnostics agent: correlate alert with recent deployments, logs, metrics
  4. Build runbook agent: match alert pattern to known runbooks, suggest remediation steps
  5. Create communication agent: draft status updates for different audiences (engineering, leadership, customers)
  6. Implement blackboard pattern: shared state for alert context, agent findings, and decisions
  7. Add escalation rules: P1 alerts automatically page on-call, P2 create tickets
  8. Build verification loop: after remediation, diagnostics agent confirms resolution
class IncidentSwarm:
    def __init__(self):
        self.blackboard = Blackboard()
        self.agents = {
            "triage": TriageAgent(),
            "diagnostics": DiagnosticsAgent(),
            "runbook": RunbookAgent(),
            "comms": CommunicationAgent()
        }

    async def handle_alert(self, alert: dict) -> dict:
        """Process alert through agent swarm."""
        # Post alert to blackboard
        await self.blackboard.post_task({
            "id": alert["id"],
            "type": "alert",
            "content": alert,
            "status": "pending"
        })

        # Triage agent classifies
        triage_result = await self.agents["triage"].process(alert)
        await self.blackboard.post_result({
            "agent": "triage",
            "severity": triage_result["severity"],
            "affected_services": triage_result["services"]
        })

        # Diagnostics agent correlates
        context = await self.blackboard.get_context(alert["id"])
        diag_result = await self.agents["diagnostics"].process(context)

        # Runbook agent suggests remediation
        runbook = await self.agents["runbook"].process({
            "alert": alert,
            "diagnosis": diag_result
        })

        # Communication agent drafts updates
        if triage_result["severity"] in ["P1", "P2"]:
            status_update = await self.agents["comms"].process({
                "alert": alert,
                "diagnosis": diag_result,
                "remediation": runbook
            })

        return {
            "severity": triage_result["severity"],
            "diagnosis": diag_result,
            "remediation": runbook,
            "status_update": status_update
        }
