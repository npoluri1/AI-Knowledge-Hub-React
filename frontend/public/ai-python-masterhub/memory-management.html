1Why Context Windows Force Memory Design

What & why. Every LLM has a maximum context window (GPT-4o: 128K tokens, Claude: 200K). Once conversation history exceeds this limit, older messages must be dropped, summarized, or moved to external storage. Without a memory strategy, agents lose earlier context and produce inconsistent responses.

import tiktoken

encoder = tiktoken.encoding_for_model("gpt-4o")
MAX_CONTEXT = 128_000

def context_usage(messages: list) -> dict:
    total = sum(len(encoder.encode(m.get("content", "") or "")) for m in messages)
    return {"tokens_used": total, "remaining": MAX_CONTEXT - total,
            "utilization": f"{total/MAX_CONTEXT*100:.1f}%"}

print(context_usage(long_conversation))
Where you'll use itEvery production chatbot must handle context-window limits. Applications that ignore this produce hallucinated or contradictory responses when the window overflows.
Under the hoodContext window limits affect attention quality, not just token counts. Models perform worse on information buried in the middle of long contexts (the "lost in the middle" phenomenon).

2Conversation Buffer: Simplest Memory

What & why. A conversation buffer stores all messages in a list and sends the entire list to the model each turn. It is the simplest memory strategy and works well for short conversations. When the buffer exceeds the context window, older messages are trimmed.

class ConversationBuffer:
    def __init__(self, max_tokens: int = 100_000):
        self.messages: list[dict] = []
        self.max_tokens = max_tokens
        self.encoder = tiktoken.encoding_for_model("gpt-4o")

    def add(self, role: str, content: str):
        self.messages.append({"role": role, "content": content})
        self._trim()

    def _trim(self):
        while self._token_count() > self.max_tokens and len(self.messages) > 2:
            self.messages.pop(0)

    def _token_count(self) -> int:
        return sum(len(self.encoder.encode(m["content"] or "")) for m in self.messages)

    def get_messages(self) -> list[dict]:
        return list(self.messages)

buf = ConversationBuffer(max_tokens=80_000)
buf.add("user", "Hello")
buf.add("assistant", "Hi there!")
buf.add("user", "What did I just say?")
Where you'll use itBuffer memory is the default for simple chatbots and prototypes. It preserves exact message fidelity but discards the oldest messages when space runs out.
Under the hoodThe pop(0) operation on a Python list is O(n), but conversation buffers are small enough that this is negligible. For very long conversations, collections.deque with maxlen provides O(1) trimming.

3Sliding Window: Last-K Turns

What & why. A sliding window keeps only the most recent K turns (each turn = user + assistant messages). This guarantees bounded memory usage while preserving recent context. It is the most common memory strategy in production chat systems.

class SlidingWindowMemory:
    def __init__(self, window_size: int = 20):
        self.window_size = window_size
        self.history: list[dict] = []

    def add(self, message: dict):
        self.history.append(message)
        if len(self.history) > self.window_size * 2:
            self.history = self.history[-(self.window_size * 2):]

    def get_messages(self, system_prompt: str = None) -> list[dict]:
        msgs = []
        if system_prompt:
            msgs.append({"role": "system", "content": system_prompt})
        msgs.extend(self.history)
        return msgs

memory = SlidingWindowMemory(window_size=10)
for turn in conversation:
    memory.add({"role": "user", "content": turn["user"]})
    memory.add({"role": "assistant", "content": turn["assistant"]})

response = client.chat.completions.create(
    model="gpt-4o", messages=memory.get_messages("You are a helpful assistant.")
)
Where you'll use itCustomer support chatbots, voice assistants, and live-chat agents all use sliding windows. The window size balances context richness against token cost.
Under the hoodThe window size should be tuned per application. Too small (5 turns) loses important context; too large (100 turns) wastes tokens on low-relevance early messages.

4Token Counting and Trimming

What & why. Counting messages by turn is imprecise because messages vary in length. Token-based trimming measures actual content size and removes messages until the total fits within the budget. This prevents unexpected overflows when a user sends a very long message.

import tiktoken

class TokenAwareMemory:
    def __init__(self, max_tokens: int = 100_000):
        self.max_tokens = max_tokens
        self.encoder = tiktoken.encoding_for_model("gpt-4o")
        self.messages: list[dict] = []

    def add(self, role: str, content: str):
        self.messages.append({"role": role, "content": content})
        self._enforce_limit()

    def _enforce_limit(self):
        while self._total_tokens() > self.max_tokens and len(self.messages) > 2:
            self.messages.pop(0)

    def _total_tokens(self) -> int:
        return sum(len(self.encoder.encode(m.get("content", "") or "")) for m in self.messages)

mem = TokenAwareMemory(max_tokens=50_000)
mem.add("system", "You are a helpful assistant.")
mem.add("user", "x" * 10_000)  # long message
print(f"Tokens: {mem._total_tokens()}, Messages: {len(mem.messages)}")
Where you'll use itToken-aware trimming is essential when users can send arbitrarily long messages. It prevents a single large message from pushing earlier context out of the window.
Under the hoodtiktoken is the fastest Python tokenizer for OpenAI models. For Anthropic models, the anthropic library provides count_tokens(). Google models use the same tiktoken-compatible counting.

5Summary-of-So-Far Compression

What & why. Instead of dropping old messages, a summary compression strategy uses the LLM to summarize earlier conversation turns into a compact paragraph. This preserves the semantic content of the full history while using far fewer tokens. The summary is prepended to the message list each turn.

class SummaryMemory:
    def __init__(self, summarize_threshold: int = 30):
        self.messages: list[dict] = []
        self.summary: str = ""
        self.summarize_threshold = summarize_threshold

    def add(self, role: str, content: str):
        self.messages.append({"role": role, "content": content})
        if len(self.messages) >= self.summarize_threshold:
            self._compress()

    def _compress(self):
        half = len(self.messages) // 2
        to_summarize = self.messages[:half]
        resp = client.chat.completions.create(model="gpt-4o-mini", messages=[
            {"role": "system", "content": "Summarize this conversation concisely."},
            *to_summarize
        ])
        new_summary = resp.choices[0].message.content
        self.summary = f"{self.summary}\n{new_summary}".strip() if self.summary else new_summary
        self.messages = self.messages[half:]

    def get_messages(self, system_prompt: str = None) -> list[dict]:
        msgs = []
        if system_prompt:
            msgs.append({"role": "system", "content": system_prompt})
        if self.summary:
            msgs.append({"role": "system", "content": f"Conversation summary so far:\n{self.summary}"})
        msgs.extend(self.messages)
        return msgs
Where you'll use itLong-running chatbots, therapy bots, and educational tutors use summary memory to maintain coherence across hours of conversation without losing important context.
Under the hoodSummarization uses a cheaper, faster model (gpt-4o-mini) to reduce costs. The summary is not a lossless representation; nuance and specific details are inevitably lost.

6System and Persona Persistence Across Sessions

What & why. The system prompt establishes the agent's persona, rules, and capabilities. It must persist across sessions (conversation restarts) to maintain consistent behavior. Storing the system prompt separately from conversation history ensures it is always present regardless of memory trimming.

class PersistentPersona:
    def __init__(self, persona: str, user_id: str):
        self.persona = persona
        self.user_id = user_id
        self.conversation = SlidingWindowMemory(window_size=20)

    def get_messages(self) -> list[dict]:
        return [
            {"role": "system", "content": self.persona},
            *self.conversation.get_messages()
        ]

    def save_persona(self, path: str):
        with open(f"{path}/{self.user_id}_persona.json", "w") as f:
            json.dump({"persona": self.persona}, f)

assistant = PersistentPersona(
    persona="You are a senior Python tutor. Be concise and use code examples.",
    user_id="user_123"
)
Where you'll use itPersonalized assistants, branded chatbots, and role-playing applications all require persona persistence. The system prompt is never trimmed by sliding-window logic.
Under the hoodThe system prompt is always sent as the first message. It consumes tokens every turn but is essential for consistent behavior. Some frameworks cache it to avoid re-sending unchanged content.

7Key-Value Facts About User Profile

What & why. Beyond conversation history, agents benefit from structured key-value facts about the user (name, preferences, dietary restrictions, timezone). These facts are extracted during conversation and stored in a dictionary, then injected into the system prompt each turn.

class UserFactStore:
    def __init__(self):
        self.facts: dict[str, str] = {}

    def update(self, key: str, value: str):
        self.facts[key] = value

    def extract_facts(self, messages: list[dict]):
        resp = client.chat.completions.create(model="gpt-4o-mini", messages=[
            {"role": "system", "content": "Extract user facts as JSON key-value pairs. "
             "Return {} if no new facts found."},
            *messages[-4:]
        ])
        import json
        try:
            new_facts = json.loads(resp.choices[0].message.content)
            self.facts.update(new_facts)
        except json.JSONDecodeError:
            pass

    def to_prompt_section(self) -> str:
        if not self.facts:
            return ""
        lines = [f"- {k}: {v}" for k, v in self.facts.items()]
        return "Known facts about the user:\n" + "\n".join(lines)

store = UserFactStore()
store.update("name", "Alice")
store.update("timezone", "UTC+8")
store.update("language", "Python")
Where you'll use itPersonalized assistants, CRM-integrated bots, and educational platforms use fact stores to remember user preferences without relying on conversation context.
Under the hoodFact extraction can be done with a small model or with regex patterns for simple cases. Over-extraction wastes storage; under-extraction misses important preferences.

8Storing Memory as Dicts in JSON

What & why. JSON is the universal format for serializing agent memory. Each memory entry is a dict with metadata (timestamp, source, importance) and content. JSON storage enables persistence, portability, and inspection across sessions and systems.

import json, time

def create_memory(role: str, content: str, metadata: dict = None) -> dict:
    return {
        "role": role,
        "content": content,
        "timestamp": time.time(),
        "importance": metadata.get("importance", 0.5) if metadata else 0.5,
        "source": metadata.get("source", "conversation") if metadata else "conversation",
    }

def save_memories(memories: list[dict], path: str):
    with open(path, "w") as f:
        json.dump(memories, f, indent=2)

def load_memories(path: str) -> list[dict]:
    with open(path) as f:
        return json.load(f)

memories = [
    create_memory("user", "I prefer dark mode", {"importance": 0.8, "source": "preference"}),
    create_memory("assistant", "I noted your preference for dark mode", {"importance": 0.6}),
]
save_memories(memories, "user_123_memory.json")
Where you'll use itJSON-backed memory is the foundation for all persistent memory systems. It works with file systems, databases, and key-value stores alike.
Under the hoodAdding metadata (timestamps, importance, source) enables filtering and prioritization during retrieval. Without metadata, all memories are treated equally regardless of relevance.

9Retrieval by Recency

What & why. Recency-based retrieval ranks memories by how recently they were created. Recent memories are more likely to be relevant to the current conversation. This is the simplest retrieval strategy and requires no embeddings or vector databases.

def retrieve_by_recency(memories: list[dict], top_k: int = 5) -> list[dict]:
    """Return the most recent memories, sorted by timestamp descending."""
    sorted_mem = sorted(memories, key=lambda m: m["timestamp"], reverse=True)
    return sorted_mem[:top_k]

def build_prompt_with_recency(query: str, memories: list[dict]) -> list[dict]:
    relevant = retrieve_by_recency(memories, top_k=5)
    context = "\n".join(f"- {m['content']}" for m in relevant)
    return [
        {"role": "system", "content": f"Relevant memories:\n{context}\n\nAnswer the user's question."},
        {"role": "user", "content": query}
    ]
Where you'll use itRecency retrieval works well for ongoing conversations where the most recent context is most important. It is the default strategy for simple memory systems.
Under the hoodRecency retrieval ignores older memories entirely. For tasks that require historical context (e.g., "what did we discuss last month?"), recency alone is insufficient.

10Demo Chatbot with Rolling Window

What & why. A complete chatbot using sliding-window memory demonstrates the full pattern: receive user input, append to window, call LLM with window contents, append assistant response, and repeat. This is the minimal viable agent memory implementation.

import openai, tiktoken

client = openai.OpenAI()
encoder = tiktoken.encoding_for_model("gpt-4o")

class RollingChatbot:
    def __init__(self, system_prompt: str, window_tokens: int = 40_000):
        self.system = {"role": "system", "content": system_prompt}
        self.history: list[dict] = []
        self.window_tokens = window_tokens

    def chat(self, user_msg: str) -> str:
        self.history.append({"role": "user", "content": user_msg})
        self._trim()
        messages = [self.system] + self.history
        resp = client.chat.completions.create(model="gpt-4o", messages=messages)
        reply = resp.choices[0].message.content
        self.history.append({"role": "assistant", "content": reply})
        return reply

    def _trim(self):
        while self._token_count() > self.window_tokens and len(self.history) > 2:
            self.history.pop(0)

    def _token_count(self) -> int:
        return sum(len(encoder.encode(m.get("content", "") or "")) for m in self.history)

bot = RollingChatbot("You are a helpful Python tutor.")
print(bot.chat("What is a decorator?"))
print(bot.chat("Show me an example"))
Where you'll use itThis pattern is the starting point for every production chatbot. It provides reliable, bounded-memory behavior that scales to any conversation length.
Under the hoodThe window_tokens parameter should be set to about 70% of the model's context window, leaving room for the system prompt, user query, and assistant response.

11Memory vs RAG: Distinction

What & why. Memory stores the agent's own conversation history and learned facts. RAG (Retrieval-Augmented Generation) retrieves external documents. Memory answers "what have we discussed?"; RAG answers "what does the documentation say?" They are complementary: memory provides personalization, RAG provides knowledge.

class MemoryPlusRAG:
    def __init__(self, memory: SlidingWindowMemory, retriever):
        self.memory = memory
        self.retriever = retriever

    def respond(self, query: str) -> list[dict]:
        # Memory: conversation context
        mem_messages = self.memory.get_messages()
        # RAG: external knowledge
        docs = self.retriever.search(query, top_k=3)
        doc_context = "\n".join(d["content"] for d in docs)
        return [
            {"role": "system", "content": f"Use these documents:\n{doc_context}"},
            *mem_messages,
            {"role": "user", "content": query}
        ]
Where you'll use itCustomer support bots combine memory (knowing the user's history) with RAG (accessing product documentation). Neither alone provides the full picture.
Under the hoodMemory is stateful and grows over time; RAG is stateless and retrieves fresh content each turn. Mixing them requires careful token budget allocation between memory context and retrieved documents.

12PII Caution: Early Habits

What & why. Storing conversation history means storing personal data (names, addresses, health information). Early in development, habits around PII handling determine long-term compliance. Never store raw PII without encryption, never log it to stdout, and always implement deletion capabilities from day one.

import re, hashlib

def mask_pii(text: str) -> str:
    """Mask common PII patterns before storage."""
    text = re.sub(r'\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b', '[CARD_REDACTED]', text)
    text = re.sub(r'\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b', '[EMAIL_REDACTED]', text)
    text = re.sub(r'\b\d{3}[-.]?\d{3}[-.]?\d{4}\b', '[PHONE_REDACTED]', text)
    return text

def safe_memory_store(text: str) -> dict:
    return {
        "content": mask_pii(text),
        "content_hash": hashlib.sha256(text.encode()).hexdigest(),
        "pii_masked": True,
    }

safe = safe_memory_store("Contact me at alice@example.com or 555-123-4567")
print(safe["content"])  # "Contact me at [EMAIL_REDACTED] or [PHONE_REDACTED]"
Where you'll use itGDPR, PDPA, and HIPAA all require PII handling from the first line of code. Retrofitting PII protection into existing systems is orders of magnitude harder than building it in from the start.
Under the hoodRegex-based PII detection is imperfect but catches most common patterns. Production systems should use dedicated PII detection services (AWS Comprehend, Azure Text Analytics) for higher accuracy.

13Vector Memory: Embed, Store, Recall Top-K into Prompt

What & why. Vector memory embeds each memory entry into a dense vector and stores it in a vector database. At query time, the current conversation is embedded and the most similar memories are retrieved. This surfaces relevant memories regardless of when they occurred, unlike recency-only retrieval.

import numpy as np
from openai import OpenAI

client = OpenAI()
memory_vectors: list[tuple[dict, list[float]]] = []

def embed_and_store(memory: dict):
    resp = client.embeddings.create(model="text-embedding-3-small", input=memory["content"])
    vec = resp.data[0].embedding
    memory_vectors.append((memory, vec))

def recall_top_k(query: str, k: int = 5) -> list[dict]:
    resp = client.embeddings.create(model="text-embedding-3-small", input=query)
    q_vec = np.array(resp.data[0].embedding)
    scored = [(mem, np.dot(q_vec, np.array(v))) for mem, v in memory_vectors]
    scored.sort(key=lambda x: x[1], reverse=True)
    return [mem for mem, score in scored[:k]]
Where you'll use itVector memory is the standard for agents that need to recall specific facts from long histories. It is used in customer-support bots, research assistants, and personal AI companions.
Under the hoodEmbedding-based recall uses cosine similarity (or dot product for normalized vectors) to find semantically similar memories. It can surface memories that are topically related but temporally distant.

14Episodic vs Semantic vs Procedural Taxonomy

What & why. Memory science distinguishes three types: episodic (specific events: "yesterday you asked about decorators"), semantic (general knowledge: "Python uses dynamic typing"), and procedural (how-to: "the user prefers async style"). Each type requires different storage, retrieval, and update strategies.

@dataclass
class MemoryEntry:
    content: str
    memory_type: str  # "episodic" | "semantic" | "procedural"
    timestamp: float
    metadata: dict = field(default_factory=dict)

class TypedMemoryStore:
    def __init__(self):
        self.episodic: list[MemoryEntry] = []
        self.semantic: list[MemoryEntry] = []
        self.procedural: list[MemoryEntry] = []

    def store(self, entry: MemoryEntry):
        getattr(self, entry.memory_type).append(entry)

    def retrieve_all(self, top_k: int = 10) -> list[MemoryEntry]:
        combined = self.episodic[-3:] + self.semantic[-3:] + self.procedural[-3:]
        return combined[:top_k]

store = TypedMemoryStore()
store.store(MemoryEntry("User asked about decorators on Monday", "episodic", time.time()))
store.store(MemoryEntry("Python uses dynamic typing", "semantic", time.time()))
store.store(MemoryEntry("User prefers async code style", "procedural", time.time()))
Where you'll use itTyped memory stores enable retrieval strategies tailored to each type. Episodic memories are retrieved by recency; semantic by relevance; procedural by task context.
Under the hoodThis taxonomy mirrors the cognitive science distinction between declarative memory (episodic + semantic) and procedural memory. Agents that separate these types make more natural-seeming decisions.

15Entity Memory: Extraction Patterns

What & why. Entity memory tracks named entities (people, places, products) mentioned in conversation. Each entity gets a profile dict with extracted attributes. Entity memory enables the agent to answer questions like "what is Alice's email?" without scanning the entire conversation.

class EntityMemory:
    def __init__(self):
        self.entities: dict[str, dict] = {}

    def extract_and_store(self, messages: list[dict]):
        resp = client.chat.completions.create(model="gpt-4o-mini", messages=[
            {"role": "system", "content": "Extract entities as JSON: "
             '{"entities": [{"name": "...", "type": "...", "attributes": {...}}]}'},
            messages[-1]
        ])
        import json
        try:
            data = json.loads(resp.choices[0].message.content)
            for ent in data.get("entities", []):
                name = ent["name"]
                if name not in self.entities:
                    self.entities[name] = {"type": ent["type"], "attributes": {}}
                self.entities[name]["attributes"].update(ent.get("attributes", {}))
        except json.JSONDecodeError:
            pass

    def get_entity(self, name: str) -> dict | None:
        return self.entities.get(name)

    def to_prompt_section(self) -> str:
        lines = []
        for name, data in self.entities.items():
            attrs = ", ".join(f"{k}={v}" for k, v in data["attributes"].items())
            lines.append(f"- {name} ({data['type']}): {attrs}")
        return "Known entities:\n" + "\n".join(lines)
Where you'll use itCRM bots, relationship managers, and research assistants benefit from entity memory. It provides structured access to key nouns and their attributes.
Under the hoodEntity extraction can be done with a small LLM call or with NER (Named Entity Recognition) models. LLM-based extraction captures custom entity types beyond the standard person/org/location.

What & why. LangChain's ConversationSummaryMemory maintains a running summary that is updated each turn. New messages are merged into the existing summary, keeping it current without re-summarizing the entire history. This provides O(1) summary growth per turn.

Where you'll use itConversationSummaryMemory is the standard LangChain memory class for long conversations. It preserves the gist of the conversation while keeping token usage bounded.
Under the hoodEach save_context call sends the existing summary plus the new exchange to the LLM, asking it to produce an updated summary. This incremental approach is faster than re-summarizing the full history.

17Hybrid Recency + Relevance Scoring

What & why. Combining recency and relevance scores produces better retrieval than either alone. A memory that is both recent AND relevant to the current query scores highest. The hybrid score is typically a weighted combination: score = alpha * recency + (1 - alpha) * relevance.

import time, numpy as np

def hybrid_score(memory: dict, query_vec: np.ndarray, mem_vec: np.ndarray,
                 alpha: float = 0.3) -> float:
    """Score combining recency and semantic relevance."""
    recency = 1.0 / (1.0 + (time.time() - memory["timestamp"]) / 86400)  # decay over days
    relevance = float(np.dot(query_vec, mem_vec))
    return alpha * recency + (1 - alpha) * relevance

def hybrid_retrieve(query: str, memories: list[dict], vectors: list[np.ndarray],
                     k: int = 5, alpha: float = 0.3) -> list[dict]:
    resp = client.embeddings.create(model="text-embedding-3-small", input=query)
    q_vec = np.array(resp.data[0].embedding)
    scored = [(mem, hybrid_score(mem, q_vec, mem_vec, alpha))
              for mem, mem_vec in zip(memories, vectors)]
    scored.sort(key=lambda x: x[1], reverse=True)
    return [m for m, s in scored[:k]]
Where you'll use itHybrid scoring is the standard for production memory retrieval. It ensures recent conversations have appropriate weight while still surfacing older relevant memories.
Under the hoodThe alpha parameter controls the recency-relevance tradeoff. Alpha=1.0 is pure recency; alpha=0.0 is pure relevance. Typical values range from 0.2 to 0.4.

18Write Policies: What Deserves Saving

What & why. Not every message deserves to be stored in long-term memory. Write policies determine which memories are worth saving based on importance, novelty, and actionability. Saving everything wastes storage and retrieval quality; saving too little loses important context.

class WritePolicy:
    def should_save(self, message: dict, existing_memories: list[dict]) -> bool:
        content = message.get("content", "")
        # Always save explicit preferences and facts
        if any(kw in content.lower() for kw in ["i prefer", "i like", "my name is", "i work at"]):
            return True
        # Save if message is long (likely contains detailed information)
        if len(content) > 200:
            return True
        # Save if message is a question (likely important to user)
        if "?" in content:
            return True
        # Skip short acknowledgments and chitchat
        if len(content) < 50 and not any(kw in content.lower() for kw in ["help", "error", "problem"]):
            return False
        return True

policy = WritePolicy()
for msg in new_messages:
    if policy.should_save(msg, existing_memories):
        embed_and_store(create_memory(msg["role"], msg["content"]))
Where you'll use itWrite policies prevent memory bloat. They are critical for agents running 24/7 where millions of messages would otherwise accumulate without discrimination.
Under the hoodLLM-based write policies can evaluate novelty and importance more accurately than keyword rules. A small model call can score whether a memory is "worth remembering" on a 1-10 scale.

19Memory Deduplication: Near-Identical Entries

What & why. Users often repeat themselves across sessions. Without deduplication, the same fact gets stored multiple times, wasting retrieval budget on redundant memories. Near-duplicate detection compares embedding similarity and merges entries with high overlap.

def deduplicate_memories(memories: list[dict], vectors: list[np.ndarray],
                         threshold: float = 0.95) -> list[dict]:
    """Remove near-duplicate memories based on embedding similarity."""
    keep = []
    keep_vectors = []
    for mem, vec in zip(memories, vectors):
        if not keep:
            keep.append(mem)
            keep_vectors.append(vec)
            continue
        similarities = [float(np.dot(vec, kv)) for kv in keep_vectors]
        max_sim = max(similarities)
        if max_sim < threshold:
            keep.append(mem)
            keep_vectors.append(vec)
        else:
            # Merge: keep the newer one, update timestamp
            idx = similarities.index(max_sim)
            keep[idx]["timestamp"] = max(keep[idx]["timestamp"], mem["timestamp"])
            keep[idx]["content"] = mem["content"]  # prefer newer content
    return keep

unique_memories = deduplicate_memories(all_memories, all_vectors, threshold=0.95)
Where you'll use itDeduplication is essential for long-running agents. Without it, retrieval quality degrades as duplicate memories dominate the top-K results.
Under the hoodThe 0.95 threshold is tuned per embedding model. text-embedding-3-small produces vectors where 0.95 cosine similarity indicates near-identical semantic content.

20TTL Expiry and Forgetting Curves

What & why. Not all memories should persist forever. TTL (time-to-live) expiry automatically removes old, low-importance memories. This mimics human forgetting and prevents the memory store from growing unboundedly. Important memories get longer TTLs; transient facts expire quickly.

import time

class TTLMemoryStore:
    def __init__(self):
        self.memories: list[dict] = []

    def store(self, content: str, importance: float = 0.5):
        ttl_days = int(importance * 30) + 1  # 1-31 days based on importance
        self.memories.append({
            "content": content,
            "timestamp": time.time(),
            "expires_at": time.time() + (ttl_days * 86400),
            "importance": importance,
        })

    def retrieve_active(self) -> list[dict]:
        now = time.time()
        self.memories = [m for m in self.memories if m["expires_at"] > now]
        return self.memories

    def force_expiry(self, older_than_days: int):
        cutoff = time.time() - (older_than_days * 86400)
        self.memories = [m for m in self.memories if m["timestamp"] > cutoff]

store = TTLMemoryStore()
store.store("User prefers dark mode", importance=0.9)  # expires in ~28 days
store.store("User said hello", importance=0.1)  # expires in ~4 days
Where you'll use itTTL expiry is essential for compliance with data retention policies. GDPR requires data minimization; TTL-based expiry automates this requirement.
Under the hoodForgetting curves from cognitive science show that memory retention decays exponentially. The importance-based TTL approximates this: high-importance memories persist, low-importance ones fade.

    def __init__(self, user_id: str, max_messages: int = 100, ttl: int = 86400):

25Conflict Resolution: Contradictory Facts

What & why. When a user says "I love coffee" then later "I quit coffee," the memory store has contradictory facts. Conflict resolution strategies include newest-wins (prefer the latest statement), evidence-weighted (prefer the most supported), and explicit-override (user statements override system inferences).

class ConflictResolver:
    def __init__(self, strategy: str = "newest_wins"):
        self.strategy = strategy

    def resolve(self, memories: list[dict]) -> dict:
        if self.strategy == "newest_wins":
            return max(memories, key=lambda m: m["timestamp"])
        elif self.strategy == "evidence_weighted":
            return max(memories, key=lambda m: m.get("confidence", 0.5))
        elif self.strategy == "explicit_override":
            explicit = [m for m in memories if m.get("source") == "user_stated"]
            return explicit[-1] if explicit else memories[-1]

    def detect_conflicts(self, memories: list[dict]) -> list[tuple]:
        conflicts = []
        for i, m1 in enumerate(memories):
            for m2 in memories[i+1:]:
                if self._are_contradictory(m1, m2):
                    conflicts.append((m1, m2))
        return conflicts

    def _are_contradictory(self, m1: dict, m2: dict) -> bool:
        resp = client.chat.completions.create(model="gpt-4o-mini", messages=[
            {"role": "system", "content": "Are these two statements contradictory? Answer yes/no."},
            {"role": "user", "content": f"Statement 1: {m1['content']}\nStatement 2: {m2['content']}"}
        ])
        return "yes" in resp.choices[0].message.content.lower()
Where you'll use itConflict resolution is critical for agents that remember preferences over months. Users change their minds; the memory system must handle this gracefully.
Under the hoodThe newest-wins strategy is simplest but may revert intentional long-term preferences. Evidence-weighted requires tracking how many times a fact was stated, which is more robust but more complex.

26User-Model Drift: Tracking Preferences Over Months

What & why. User preferences evolve over time. A memory system must track how preferences change and avoid treating outdated preferences as current. Drift detection monitors when a user's stated preferences diverge from their recent behavior.

class DriftTracker:
    def __init__(self, memory_store):
        self.store = memory_store

    def detect_drift(self, user_id: str, preference_key: str) -> dict:
        history = self.store.get_by_key(user_id, preference_key)
        if len(history) < 2:
            return {"drift": False}
        recent = [h for h in history if h["timestamp"] > time.time() - 30*86400]
        old = [h for h in history if h["timestamp"] <= time.time() - 30*86400]
        if not recent or not old:
            return {"drift": False}
        recent_vals = [h["value"] for h in recent]
        old_vals = [h["value"] for h in old]
        if set(recent_vals) != set(old_vals):
            return {"drift": True, "old": old_vals[-1], "new": recent_vals[-1],
                    "confidence": len(recent) / (len(recent) + len(old))}
        return {"drift": False}

30Hierarchical Memory: L1 Hot, L2 Vector, L3 Archive

What & why. Hierarchical memory mirrors CPU cache design: L1 (hot context in the prompt) is fast but small, L2 (vector store) is larger but slower to query, L3 (cold archive) is vast but rarely accessed. Memories migrate between levels based on access frequency and recency.

class HierarchicalMemory:
    def __init__(self):
        self.l1_hot: list[dict] = []       # in-prompt, ~10 items
        self.l2_vector: list[dict] = []    # vector store, ~10K items
        self.l3_archive: list[dict] = []   # cold storage, unlimited

    def promote(self, memory: dict):
        """Move memory to a hotter tier."""
        if memory not in self.l1_hot:
            self.l1_hot.insert(0, memory)
            if len(self.l1_hot) > 10:
                demoted = self.l1_hot.pop()
                self.l2_vector.append(demoted)

    def demote(self, memory: dict):
        """Move memory to a colder tier."""
        if memory in self.l1_hot:
            self.l1_hot.remove(memory)
            self.l2_vector.append(memory)
        elif memory in self.l2_vector:
            self.l2_vector.remove(memory)
            self.l3_archive.append(memory)

    def access(self, memory: dict):
        """Record access and promote if frequently used."""
        memory["access_count"] = memory.get("access_count", 0) + 1
        if memory["access_count"] >= 3 and memory in self.l2_vector:
            self.promote(memory)
Where you'll use itHierarchical memory optimizes the tradeoff between retrieval speed and storage capacity. Hot memories are always in context; warm memories are one query away; cold memories require deeper search.
Under the hoodThis mirrors the L1/L2/L3 cache hierarchy in CPUs. The key insight is that most accesses hit a small number of frequently used memories, so the hot tier provides outsized value.

34Forgetting as Feature: Information-Theoretic View

What & why. From an information-theoretic perspective, forgetting is not a bug but a feature. It removes redundant, outdated, and low-value information, keeping the memory store efficient and retrieval focused. Optimal forgetting maximizes the information density of retained memories.

import math

def information_value(memory: dict, all_memories: list[dict]) -> float:
    """Estimate the unique information a memory provides."""
    unique_words = set(memory["content"].lower().split())
    all_words = set()
    for m in all_memories:
        if m["id"] != memory["id"]:
            all_words.update(m["content"].lower().split())
    novel_words = unique_words - all_words
    if not unique_words:
        return 0.0
    return len(novel_words) / len(unique_words)

class OptimalForgetter:
    def __init__(self, target_density: float = 0.3):
        self.target_density = target_density

    def decide_forget(self, memories: list[dict]) -> list[dict]:
        scored = [(m, information_value(m, memories)) for m in memories]
        scored.sort(key=lambda x: x[1])
        cutoff = int(len(scored) * (1 - self.target_density))
        return [m for m, s in scored[cutoff:]]
Where you'll use itOptimal forgetting keeps memory stores efficient. It is especially important for agents with limited storage or retrieval budgets where every slot must carry maximum information.
Under the hoodThis mirrors the Von Restorff effect in psychology: distinctive memories are remembered better. Forgetting common, redundant information preserves the most distinctive and useful memories.

36Right-to-Be-Forgotten: Engineering Deletion Cascades

What & why. GDPR and PDPA grant users the right to have their personal data deleted. For memory systems, this means implementing cascading deletes across all storage layers: conversation history, vector embeddings, summaries, entity profiles, and backup copies.

class DeletionManager:
    def __init__(self, stores: list):
        self.stores = stores  # all storage backends

    def delete_user(self, user_id: str) -> dict:
        """Cascading delete across all storage layers."""
        report = {"user_id": user_id, "deleted": {}}
        for store in self.stores:
            try:
                count = store.delete_by_user(user_id)
                report["deleted"][store.__class__.__name__] = count
            except Exception as e:
                report["deleted"][store.__class__.__name__] = f"ERROR: {e}"
        # Verify deletion
        report["verified"] = self._verify_deletion(user_id)
        # Log for compliance audit
        self._log_deletion(report)
        return report

    def _verify_deletion(self, user_id: str) -> bool:
        for store in self.stores:
            if store.has_user(user_id):
                return False
        return True

37Federated Personal Memory: On-Device Sketch

What & why. Federated personal memory keeps sensitive data on the user's device and only sends anonymized updates to the server. This architecture provides personalization without centralizing PII, aligning with privacy-by-design principles and reducing data breach risk.

class FederatedMemory:
    """On-device memory with privacy-preserving server sync."""
    def __init__(self, device_id: str):
        self.device_id = device_id
        self.local_memories: list[dict] = []

    def store_local(self, memory: dict):
        """Store sensitive data only on device."""
        memory["device_id"] = self.device_id
        self.local_memories.append(memory)

    def sync_anonymized(self) -> dict:
        """Send only anonymized patterns to server."""
        patterns = self._extract_patterns(self.local_memories)
        anonymized = {
            "device_hash": hashlib.sha256(self.device_id.encode()).hexdigest()[:8],
            "pattern_count": len(patterns),
            "categories": list(set(p["category"] for p in patterns)),
            "embedding_centroids": [p["centroid"] for p in patterns[:5]],
        }
        return anonymized  # no PII leaves the device

    def _extract_patterns(self, memories: list[dict]) -> list[dict]:
        return [{"category": m.get("category", "general"), "centroid": m.get("embedding", [])}
                for m in memories[-20:]]

38Consistency Under Concurrent Writers

What & why. When multiple agents or processes write to the same user's memory concurrently, race conditions can cause lost updates or inconsistent state. Consistency mechanisms (optimistic locking, CRDTs, or serialization) ensure memory remains coherent under concurrent access.

import redis

class ConcurrentMemory:
    def __init__(self, redis_client):
        self.r = redis_client

    def store_with_lock(self, user_id: str, memory: dict, max_retries: int = 3):
        lock_key = f"memory_lock:{user_id}"
        for attempt in range(max_retries):
            if self.r.set(lock_key, "1", nx=True, ex=5):
                try:
                    key = f"memory:{user_id}"
                    existing = json.loads(self.r.get(key) or "[]")
                    existing.append(memory)
                    self.r.set(key, json.dumps(existing))
                    return True
                finally:
                    self.r.delete(lock_key)
            time.sleep(0.1 * (2 ** attempt))
        raise RuntimeError(f"Failed to acquire lock after {max_retries} attempts")

    def append_if_absent(self, user_id: str, memory: dict):
        """Append only if no duplicate exists (idempotent write)."""
        key = f"memory:{user_id}"
        memory_hash = hashlib.md5(memory["content"].encode()).hexdigest()
        existing = json.loads(self.r.get(key) or "[]")
        existing_hashes = {hashlib.md5(m["content"].encode()).hexdigest() for m in existing}
        if memory_hash not in existing_hashes:
            existing.append(memory)
            self.r.set(key, json.dumps(existing))
Where you'll use itConcurrent writes occur in multi-agent systems and collaborative assistants. Without locking, two agents writing simultaneously can overwrite each other's updates.
Under the hoodRedis SETNX with TTL provides a simple distributed lock. For higher performance, CRDTs (conflict-free replicated data types) allow concurrent writes without coordination.

39Schema Evolution: Memory Format Migrations

What & why. As the memory system evolves, the format of stored memories may change (new fields, renamed keys, different embedding dimensions). Schema versioning and migration scripts ensure old memories remain accessible after format changes.

MEMORY_SCHEMAS = {
    "v1": {"fields": ["content", "timestamp"]},
    "v2": {"fields": ["content", "timestamp", "importance", "source"]},
    "v3": {"fields": ["content", "timestamp", "importance", "source", "embedding_version"]},
}

def migrate_memory(memory: dict, from_version: str, to_version: str) -> dict:
    """Migrate a memory entry from one schema version to another."""
    migrated = dict(memory)
    if from_version == "v1" and to_version in ("v2", "v3"):
        migrated.setdefault("importance", 0.5)
        migrated.setdefault("source", "unknown")
    if from_version in ("v1", "v2") and to_version == "v3":
        migrated.setdefault("embedding_version", "text-embedding-3-small")
    migrated["_schema_version"] = to_version
    return migrated

def migrate_all(store, from_ver: str, to_ver: str):
    for i, memory in enumerate(store.memories):
        store.memories[i] = migrate_memory(memory, from_ver, to_ver)
    store.metadata["schema_version"] = to_ver
Where you'll use itSchema evolution is essential for long-lived memory stores. Without it, upgrading the memory format requires rebuilding from scratch, losing all historical context.
Under the hoodThe _schema_version field enables lazy migration: memories are migrated on read if their version is behind the current schema. This avoids costly full-database migrations.

40Cost Economics: Storage vs Embeddings vs Recompute

What & why. Memory systems have three cost components: storage (bytes on disk), embeddings (API calls to embed each memory), and recompute (re-embedding when the model changes). Understanding these costs enables informed architectural decisions about what to store and how to retrieve it.

def memory_cost_analysis(memories: list[dict]) -> dict:

        "recompute_cost_usd": f"${recompute_cost:.4f}",
        "monthly_storage_usd": f"${storage_bytes / 1_000_000 * 0.023:.4f}",  # S3 pricing
