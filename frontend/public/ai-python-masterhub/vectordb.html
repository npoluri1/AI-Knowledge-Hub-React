Part I · FoundationsTier 1 — core concepts and basic operations

1Why Exact Nearest Neighbor Fails at Scale

What & why. Brute-force exact NN search compares a query against every vector in the dataset. At 1 million vectors of dimension 768, each query requires 768M multiplications. At 100M vectors, queries take seconds to minutes, which is unacceptable for real-time applications.

# Brute-force complexity:
# n vectors, d dimensions
# Per query: O(n * d) multiplications + O(n) comparisons
#
# Example: 1M vectors, dim=768
# Multiplications: 1M * 768 = 768M per query
# At ~1 GFLOP/s (single thread): ~0.77 seconds per query
#
# Example: 100M vectors, dim=768
# Multiplications: 100M * 768 = 76.8B per query
# At ~1 GFLOP/s: ~77 seconds per query
#
# Vector databases solve this with ANN indexes that achieve
# sub-linear query time (typically O(log n) or O(n^0.5))
Where you'll use itJustification for choosing a vector database over naive numpy search when dataset size exceeds ~100K vectors.
Under the hoodANN algorithms trade exactness for speed, typically achieving 95-99% recall with 100-1000x speedup over brute force.

2Vector Database Value Proposition

What & why. Vector databases combine ANN indexing with operational features: persistence, metadata filtering, horizontal scaling, backups, and ACID-like guarantees. They are the infrastructure layer between your embedding model and your application.

# Vector DB vs numpy/FAISS:
# | Feature            | numpy/FAISS | Vector DB     |
# |--------------------|-------------|---------------|
# | Persistence        | Manual      | Built-in      |
# | Metadata filtering | No          | Yes           |
# | Horizontal scaling | No          | Yes (shards)  |
# | Backup/restore     | Manual      | Snapshots     |
# | Multi-tenancy      | No          | Yes           |
# | Real-time insert   | Reindex     | Automatic     |
# | CRUD operations    | No          | Full CRUD     |
# | Access control     | No          | Yes           |
#
# Use vector DB when: dataset > 100K vectors, need filtering,
# need persistence, need multi-user access, need backups
Where you'll use itArchitecture decisions where teams debate between FAISS and a vector database; this table clarifies when each is appropriate.
Under the hoodVector databases are specialized OLAP systems optimized for high-dimensional similarity search with operational guarantees.

3Collections, Points, and Payloads

What & why. The core abstractions across vector databases: a collection is a group of vectors (like a table), a point is a single vector with metadata, and a payload is the metadata dictionary attached to each point.

# Conceptual model (Qdrant-style terminology):
# Collection = table of vectors
# Point = row = {id, vector, payload}
# Payload = metadata = {"title": "...", "category": "...", "date": "..."}

# Example: a document collection
collection = {
    "name": "documents",
    "vectors": {
        "size": 768,          # embedding dimension
        "distance": "Cosine"  # similarity metric
    }
}

point = {
    "id": 1,
    "vector": [0.12, -0.45, 0.78, ...],  # 768 floats
    "payload": {
        "title": "Introduction to RAG",
        "category": "tutorial",
        "author": "Jane Doe",
        "date": "2024-06-15"
    }
}

# Different engines use different terminology:
# Pinecone: index, vector, metadata
# Chroma: collection, embedding, metadata
# Weaviate: class, object, properties
# pgvector: table, row, JSONB columns
Where you'll use itSchema design for any vector database; understanding these three abstractions maps directly to all engines.
Under the hoodPayloads are stored separately from vectors to keep the ANN index compact; metadata filtering happens in a post-filter or pre-filter step.

4Chroma Quickstart: Add and Query

What & why. Chroma is a lightweight, embedded vector database ideal for prototyping. It runs in-process with zero configuration, making it the fastest path from notebook to working vector search.

import chromadb

# Create an in-memory client
client = chromadb.Client()

# Create a collection (auto-generates embeddings if needed)
collection = client.create_collection(
    name="documents",
    metadata={"hnsw:space": "cosine"}
)

# Add documents
collection.add(
    documents=["RAG combines retrieval with generation",
               "LoRA reduces trainable parameters via low-rank adapters",
               "Vector databases enable fast similarity search"],
    metadatas=[
        {"topic": "rag"}, {"topic": "fine-tuning"}, {"topic": "vector-db"}
    ],
    ids=["doc1", "doc2", "doc3"]
)

# Query
results = collection.query(
    query_texts=["How does parameter-efficient tuning work?"],
    n_results=2
)
print(results["documents"])
# [['LoRA reduces trainable parameters...', 'RAG combines...']]
Where you'll use itPrototyping RAG pipelines, building proofs of concept, and small-scale applications with <100K documents.
Under the hoodChroma uses HNSW index internally and handles embedding generation via a default sentence-transformers model if no embeddings are provided.

5Distance Metrics Configuration

What & why. The distance metric determines how similarity is computed. Cosine similarity measures angular distance (best for text), Euclidean measures spatial distance (best for images), and dot product measures alignment (best for normalized vectors).

# Distance metrics:
# Cosine: sim = 1 - (A . B) / (||A|| * ||B||)
#   Range: [-1, 1], best for: text embeddings (normalized)
#   1 = identical, 0 = orthogonal, -1 = opposite

# Euclidean (L2): dist = ||A - B||^2
#   Range: [0, inf), best for: image embeddings
#   0 = identical, larger = more different

# Dot Product: sim = A . B
#   Range: (-inf, inf), best for: normalized vectors
#   Higher = more similar (if vectors are normalized)

# Configuration by engine:
# Chroma:    metadata={"hnsw:space": "cosine"}
# Qdrant:    distance=Distance.COSINE
# Pinecone:  metric="cosine"
# pgvector:  operator: vector_cosine_ops (or vector_l2_ops)

# Rule of thumb: use cosine for text, L2 for images
# Most embedding models are trained with cosine similarity
Where you'll use itChoosing the right metric for your embedding model; mismatched metrics degrade search quality significantly.
Under the hoodThe metric choice affects index optimization: cosine allows pre-normalization (reducing comparison cost), while L2 requires full vector comparison.

6Metadata Where Filters

What & why. Metadata filtering restricts search to vectors matching certain conditions before or after ANN search. Pre-filtering eliminates non-matching vectors from the index; post-filtering applies conditions after retrieval.

# Chroma metadata filtering
results = collection.query(
    query_texts=["RAG pipeline"],
    n_results=5,
    where={"topic": "rag"}  # exact match
)

# Compound filters
results = collection.query(
    query_texts=["optimization"],
    n_results=5,
    where={
        "$and": [
            {"topic": {"$in": ["fine-tuning", "optimization"]}},
            {"date": {"$gte": "2024-01-01"}},
            {"author": "Jane Doe"}
        ]
    }
)

# Qdrant filtering
from qdrant_client.models import Filter, FieldCondition, MatchValue
results = client.search(
    collection_name="documents",
    query_vector=query_embedding,
    query_filter=Filter(must=[
        FieldCondition(key="topic", match=MatchValue(value="rag"))
    ]),
    limit=5
)
Where you'll use itMulti-tenant search, date-range queries, category filtering, and any application where metadata narrows the search scope.
Under the hoodPre-filtering (remove vectors before ANN) is faster but reduces recall; post-filtering preserves recall but may return fewer results than requested.

7Upsert and Delete Lifecycle

What & why. Vector databases support upsert (insert or update) and delete operations, enabling real-time data management. Understanding the lifecycle prevents stale data issues and index bloat.

# Chroma upsert and delete
# Upsert: insert if new, update if exists
collection.upsert(
    ids=["doc1", "doc4"],
    documents=["Updated content for doc1", "New document"],
    metadatas=[{"topic": "updated"}, {"topic": "new"}]
)

# Delete by ID
collection.delete(ids=["doc2"])

# Delete by filter
collection.delete(where={"topic": "old-topic"})

# Qdrant upsert/delete
from qdrant_client.models import PointStruct
client.upsert(
    collection_name="documents",
    points=[
        PointStruct(id=1, vector=emb1, payload={"title": "Updated"}),
        PointStruct(id=5, vector=emb5, payload={"title": "New"})
    ]
)
client.delete(
    collection_name="documents",
    points_selector=[1, 2, 3]  # or Filter condition
)
Where you'll use itAny production system where documents are added, updated, or removed over time; upsert prevents duplicates on re-indexing.
Under the hoodDeletes typically mark vectors as tombstones; the ANN index is not immediately rebuilt, so deleted vectors may still appear in search until compacted.

8pgvector Extension Basics

What & why. pgvector adds vector search to PostgreSQL, enabling you to use a familiar database for both relational data and vector search. It avoids a separate vector DB for small-to-medium workloads.

-- Enable pgvector extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Create table with vector column
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    embedding vector(768) NOT NULL,
    metadata JSONB DEFAULT '{}'::jsonb,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Insert with pre-computed embedding
INSERT INTO documents (content, embedding, metadata)
VALUES ('RAG combines retrieval with generation',
        '[0.12, -0.45, 0.78, ...]'::vector,
        '{"topic": "rag"}'::jsonb);

-- Create HNSW index for fast search
CREATE INDEX ON documents
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 200);

-- Query with cosine similarity
SELECT content, metadata,
       1 - (embedding <=> '[0.12, -0.45, ...]'::vector) AS similarity
FROM documents
ORDER BY embedding <=> '[0.12, -0.45, ...]'::vector
LIMIT 5;
Where you'll use itTeams already running PostgreSQL who want vector search without adding infrastructure; ideal for <10M vectors.
Under the hoodpgvector supports IVFFlat and HNSW indexes; HNSW is recommended for most use cases due to better recall-latency tradeoffs.

10FAISS Flat Index and Top-k Thresholds

What & why. FAISS (Facebook AI Similarity Search) is a library, not a database. It provides high-performance ANN search in memory without persistence or metadata filtering. Flat indexes provide exact search; useful for baselines and small datasets.

import faiss
import numpy as np

# Create flat (exact) index
dimension = 768
index = faiss.IndexFlatIP(dimension)  # inner product (use with normalized vectors)

# Add vectors (must be float32)
vectors = np.random.randn(100000, dimension).astype("float32")
faiss.normalize_L2(vectors)  # normalize for cosine similarity
index.add(vectors)

# Search
query = np.random.randn(1, dimension).astype("float32")
faiss.normalize_L2(query)
distances, indices = index.search(query, k=10)

# top_k threshold: return results only above similarity threshold
# FAISS returns top-k by default; post-filter for threshold
for dist, idx in zip(distances[0], indices[0]):
    if dist > 0.7:  # similarity threshold
        print(f"Vector {idx}: similarity={dist:.4f}")
Where you'll use itBenchmarking ANN algorithms, prototyping search without database overhead, and as a component in custom vector search pipelines.
Under the hoodFAISS flat index uses brute-force search; it is the gold standard for recall (100%) but has O(n*d) query complexity.

11HNSW Graph Intuition: M, efConstruction, efSearch

What & why. HNSW (Hierarchical Navigable Small World) builds a multi-layer graph where vectors are nodes connected to nearby neighbors. Search starts at the top (sparse) layer and descends to the bottom (dense) layer for precise results.

# HNSW parameters:
# M: max connections per node (higher = better recall, more memory)
# efConstruction: build-time beam width (higher = better graph quality)
# efSearch: query-time beam width (higher = better recall, slower)

# Typical values:
# | Quality   | M    | efConstruction | efSearch |
# |-----------|------|----------------|----------|
# | Fast      | 8    | 100            | 32       |
# | Balanced  | 16   | 200            | 64       |
# | Accurate  | 32   | 400            | 128      |

# Qdrant config
from qdrant_client.models import VectorParams, Distance
client.create_collection(
    collection_name="docs",
    vectors_config=VectorParams(size=768, distance=Distance.COSINE),
    hnsw_config={"m": 16, "ef_construct": 200, "full_scan_threshold": 10000}
)

# efSearch is set at query time
# Higher efSearch = higher recall but slower queries
Where you'll use itTuning HNSW indexes for your recall/latency requirements; these three parameters control the core tradeoff.
Under the hoodHNSW achieves O(log n) search complexity by navigating a skip-list-like hierarchy; each layer provides a coarser approximation of the vector space.

12IVF: Centroids and nprobe

What & why. IVF (Inverted File Index) partitions vectors into clusters (Voronoi cells) using k-means. Search only examines the nprobe nearest clusters, reducing the search space proportionally.

# IVF parameters:
# nlist: number of clusters (centroids)
# nprobe: clusters to search per query

# Rule of thumb: nlist = sqrt(n) to 4*sqrt(n)
# nprobe = 1 to nlist (higher = better recall, slower)

# For 1M vectors:
# nlist = 1024 (sqrt(1M) ≈ 1000)
# nprobe = 16 to 128

# FAISS IVF example
import faiss
dimension = 768
nlist = 1024
quantizer = faiss.IndexFlatIP(dimension)
index = faiss.IndexIVFFlat(quantizer, dimension, nlist,
                           faiss.METRIC_INNER_PRODUCT)
index.train(vectors)  # k-means training
index.add(vectors)
index.nprobe = 32  # search 32 clusters

# IVF + PQ (Product Quantization) for memory efficiency
# index = faiss.IndexIVFPQ(quantizer, dimension, nlist, 32, 8)
# 32 sub-quantizers, 8 bits each = 32 bytes per vector (vs 3072)
Where you'll use itLarge datasets where HNSW memory overhead is too high; IVF uses less memory but has lower recall at equal speed.
Under the hoodIVF is a coarse quantizer: it assigns vectors to clusters at index time, then search only compares against vectors in the nearest clusters.

13PQ: Product Quantization Compression

What & why. Product Quantization compresses high-dimensional vectors by splitting them into sub-vectors and quantizing each independently. A 768-dim float32 vector (3072 bytes) can be compressed to 32-64 bytes with minimal quality loss.

# PQ concept:
# 768-dim vector -> 32 sub-vectors of 24 dims each
# Each sub-vector quantized to 8-bit (256 centroids)
# Storage: 32 bytes per vector (vs 3072 bytes for float32)
# Compression ratio: ~96x

# PQ accuracy vs storage:
# | Sub-quantizers | Bits | Storage | Recall@10 |
# |----------------|------|---------|-----------|
# | 16             | 8    | 16 B    | ~0.92     |
# | 32             | 8    | 32 B    | ~0.96     |
# | 64             | 8    | 64 B    | ~0.98     |
# | 32             | 16   | 64 B    | ~0.99     |

# FAISS PQ index
index = faiss.IndexIVFPQ(quantizer, 768, nlist=1024,
                         m=32,     # sub-quantizers
                         nbits=8)  # bits per sub-quantizer

# Qdrant: quantization config
from qdrant_client.models import VectorParams, ScalarQuantization
vectors_config = VectorParams(
    size=768, distance=Distance.COSINE,
    quantization_config=ScalarQuantization(
        type="int8", scalar={"type": "int8"}
    )
)
Where you'll use itLarge-scale deployments (100M+ vectors) where memory cost is the primary constraint; PQ reduces storage by 10-100x.
Under the hoodPQ uses the triangle inequality to prune comparisons; only sub-quantizer centroid distances are computed, avoiding full vector comparison.

14Recall-Latency Benchmark Script

What & why. Measuring recall vs latency for different index configurations reveals the optimal operating point. A benchmark script systematically varies parameters and plots the Pareto frontier.

import time, faiss, numpy as np

def benchmark_recall_latency(index, queries, ground_truth, k=10):
    """Measure recall@k and average query latency."""
    start = time.time()
    distances, indices = index.search(queries, k)
    latency = (time.time() - start) / len(queries) * 1000  # ms

    # Recall@k: fraction of ground-truth neighbors found
    recall = 0
    for i in range(len(queries)):
        found = set(indices[i].tolist())
        expected = set(ground_truth[i].tolist())
        recall += len(found & expected) / k
    recall /= len(queries)

    return {"recall": recall, "latency_ms": latency}

# Ground truth from flat index
flat_index = faiss.IndexFlatIP(dimension)
flat_index.add(vectors)
_, ground_truth = flat_index.search(queries, k=10)

# Benchmark HNSW at different efSearch values
for ef in [16, 32, 64, 128, 256]:
    hnsw_index.hnsw.efSearch = ef
    result = benchmark_recall_latency(hnsw_index, queries, ground_truth)
    print(f"ef={ef}: recall={result['recall']:.3f}, "
          f"latency={result['latency_ms']:.2f}ms")
Where you'll use itSelecting index parameters for production; this benchmark provides the data to choose between speed and accuracy.
Under the hoodThe Pareto frontier shows the best recall achievable at each latency budget; the optimal point depends on application requirements.

15Namespaces and Multi-Tenancy

What & why. Namespaces partition a single vector database instance into isolated logical collections. Each tenant's data lives in a namespace, sharing the same index infrastructure but with query-time isolation.

Under the hoodNamespaces share the underlying ANN index, so memory overhead is minimal; isolation is enforced at query time, not storage time.

What & why. Payload indexes accelerate metadata filtering by creating secondary indexes on payload fields. Without indexing, filters require scanning all vectors; with indexing, the database can pre-filter efficiently.

)

client.create_payload_index(

)

client.create_payload_index(

# Index types: keyword (exact), integer, float, text (full-text)

17Consistency and Durability Guarantees

What & why. Vector databases vary in their consistency models. Some offer eventual consistency (inserts may not be immediately searchable), while others provide strong consistency. Durability guarantees determine data loss risk on failure.

# Consistency models across engines:
# | Engine      | Consistency          | Durability      |
# |-------------|----------------------|-----------------|
# | Pinecone    | Strong (synchronous) | Managed backups |
# | Qdrant      | Configurable         | WAL + snapshots |
# | Weaviate    | Eventual (default)   | LSM-tree        |
# | Chroma      | Strong (embedded)    | Optional persist|
# | pgvector    | Strong (ACID)        | PostgreSQL WAL  |
# | Milvus      | Strong (session)     | WAL + snapshots |

# Qdrant: WAL for durability
# Write-Ahead Log ensures data survives process crashes
# Configurable consistency level per request:
# results = client.search(
#     collection_name="docs",
#     query_vector=emb,
#     consistency_model="majority"  # read from majority of replicas
# )
Where you'll use itChoosing a vector database for production workloads where data loss or stale reads have business impact.
Under the hoodWAL (Write-Ahead Log) is the standard durability mechanism; writes are logged before being applied to the index, enabling recovery after crashes.

18Snapshots, Backup, and Export

What & why. Snappoints capture the state of a vector database at a point in time for backup and disaster recovery. Export functionality enables migration between engines or environments.

19Bulk Import Optimizations

What & why. Bulk importing millions of vectors requires batching, parallel processing, and index tuning. Naive single-vector insertion is 100-1000x slower than optimized bulk loading.

# Bulk import strategy:
# 1. Batch inserts (100-1000 vectors per API call)
# 2. Disable indexing during import, build index after
# 3. Use multiple parallel workers

import asyncio
from qdrant_client.models import PointStruct

async def bulk_insert(client, collection, vectors, batch_size=500):
    """Insert vectors in parallel batches."""
    tasks = []
    for i in range(0, len(vectors), batch_size):
        batch = vectors[i:i+batch_size]
        points = [
            PointStruct(id=v["id"], vector=v["embedding"],
                       payload=v["metadata"])
            for v in batch
        ]
        tasks.append(client.upsert(
            collection_name=collection,
            points=points
        ))
    await asyncio.gather(*tasks)

# For 1M vectors: ~5-15 minutes with optimized bulk import
# vs ~24-48 hours with single-vector insertion
Where you'll use itInitial data loading, re-indexing after schema changes, and data migration between environments.
Under the hoodBatch inserts amortize network overhead; disabling indexing during bulk load avoids rebuilding the index after each insert.

21Sharding and Replication Topology

What & why. Sharding distributes vectors across multiple nodes for horizontal scaling. Replication copies data across nodes for fault tolerance. Together they enable billion-vector deployments with high availability.

# Sharding strategies:
# Hash-based: vector_id % num_shards (uniform distribution)
# Range-based: shard by ID range or metadata
# Geographic: shard by region for latency

# Qdrant sharding config
from qdrant_client.models import (
    VectorParams, Distance, ShardStorageImplementation
)
client.create_collection(
    collection_name="products",
    vectors_config=VectorParams(size=768, distance=Distance.COSINE),
    shard_number=4,            # 4 shards
    replication_factor=2,      # 2 copies per shard
    on_disk_payload=True       # store payload on disk
)

# Replication topology:
# Shard 1: [Primary, Replica-A]

24RRF Hybrid Fusion Implementation

What & why.Reciprocal Rank Fusion (RRF) combines results from multiple search engines (vector + keyword) into a single ranking. It is the standard method for hybrid search.

def reciprocal_rank_fusion(result_lists, k=60):
    """
    Combine multiple ranked lists using RRF.
    RRF_score = sum(1 / (k + rank_i)) across all lists.
    k=60 is the standard constant from the original paper.
    """
    scores = {}
    for results in result_lists:
        for rank, doc_id in enumerate(results):
            if doc_id not in scores:
                scores[doc_id] = 0
            scores[doc_id] += 1 / (k + rank + 1)

    return sorted(scores.items(), key=lambda x: -x[1])

# Usage: combine vector search + BM25 keyword search
vector_results = ["doc3", "doc1", "doc5", "doc2"]  # ranked by cosine
keyword_results = ["doc1", "doc2", "doc4", "doc3"]  # ranked by BM25

fused = reciprocal_rank_fusion([vector_results, keyword_results])
# [('doc1', 0.0328), ('doc3', 0.0323), ('doc2', 0.0323), ...]

# Hybrid search: combine vector + keyword for better recall
# Vector captures semantic similarity; keyword captures exact matches
Where you'll use itHybrid search systems where neither vector nor keyword search alone achieves sufficient recall; RRF is the simplest fusion method.
Under the hoodRRF normalizes rankings across different scoring scales (cosine vs BM25) into a unified score; k=60 dampens the effect of top-ranked vs bottom-ranked differences.

31mmap and Memory Hierarchy Effects

What & why. Memory-mapped I/O (mmap) allows the OS to page vector index data between disk and RAM on demand. This enables indexes larger than physical RAM but introduces latency variability from page faults.

# Memory hierarchy for vector search:
# L1/L2 Cache: ~1-10 ns (hot vectors)
# RAM: ~100 ns (warm vectors)
# SSD (mmap): ~10-100 us (cold vectors)
# HDD (mmap): ~5-10 ms (frozen vectors)

    collection_name="large_index",

)

# Impact on query latency:
# All-RAM: p50=2ms, p99=5ms
# Partial mmap: p50=5ms, p99=50ms (page faults)
# Mostly mmap: p50=20ms, p99=200ms

# Tuning: mlock important vectors in RAM
# Use SSD for cold storage, RAM for hot indexes
Where you'll use itCost optimization for large datasets where keeping all vectors in RAM is expensive; mmap trades latency for memory.

32Graph Traversal Complexity

What & why. HNSW search traverses the graph from the entry point, visiting O(log n) nodes in expectation. Understanding the traversal complexity helps explain why HNSW is both fast and scalable.

# HNSW search complexity:
# - Each layer: visit up to efSearch nodes
# - Number of layers: O(log n)
# - Total comparisons: O(log n * efSearch * d)
# - For n=1M, efSearch=64, d=768:
#   log2(1M) ≈ 20 layers
#   20 * 64 * 768 ≈ 1M comparisons
#   vs brute force: 1M * 768 = 768M comparisons
#   Speedup: ~768x

# Empirical measurements:
# n=1M, d=768, HNSW M=16, ef=64:
# Query time: ~1-5ms (vs ~750ms brute force)
# Recall@10: ~97-99%
# Memory: ~1.5GB (vectors + graph edges)

# Graph construction complexity:
# O(n * log n * M * d) for inserting n vectors
# Build time for 1M vectors: ~5-30 minutes (depends on M, efConstruction)
Where you'll use itCapacity planning and performance prediction; knowing the complexity helps estimate query time for larger datasets.
Under the hoodHNSW's graph structure is a skip-list generalization to high dimensions; each layer provides a navigation shortcut to the dense bottom layer.

38ann-benchmarks Methodology Rigor

What & why. ann-benchmarks is the standard benchmark for comparing ANN algorithms. Understanding its methodology prevents drawing incorrect conclusions from poorly designed evaluations.

# ann-benchmarks methodology:
# 1. Dataset: standard datasets (SIFT1M, GIST1M, deep1B)
# 2. Build: train index on full dataset
# 3. Query: 10K queries, measure recall@10 and QPS
# 4. Plot: recall vs QPS curve (Pareto frontier)

# Common pitfalls:
# - Not reporting build time (some indexes take hours to build)
# - Ignoring memory usage (recall/QPS ignores cost)
# - Using default parameters (unfair comparison)
# - Small datasets (algorithms behave differently at scale)
# - Missing error bars (single run vs average)

# Fair comparison framework:
def fair_benchmark(indexes, queries, ground_truth, k=10):
    results = []
    for name, index in indexes.items():
        # Warmup
        index.search(queries[:100], k)
        # Benchmark
        start = time.time()
        for _ in range(3):  # 3 runs for averaging
            dists, idxs = index.search(queries, k)
        elapsed = (time.time() - start) / 3

        recall = compute_recall(idxs, ground_truth)
        qps = len(queries) / elapsed
        mem = get_memory_usage(index)

        results.append({
            "name": name, "recall": recall, "qps": qps,
            "memory_mb": mem, "build_time_s": index.build_time
        })
    return results

    pairs = [(query, r.payload["title"]) for r in fused]
    scores = reranker.predict(pairs)

pgvector RAG Backend with Tenant Isolation

Build a RAG backend using pgvector with row-level security for multi-tenant document retrieval, combining vector search with PostgreSQL's full-text search.

Architecture steps.

  1. Set up PostgreSQL with pgvector extension; create documents table with vector column and tenant_id
  2. Enable row-level security: CREATE POLICY for tenant_id = current_setting('app.tenant')
  3. Create HNSW index on embedding column; create GIN index for full-text search
  4. Implement hybrid query: vector cosine search UNION full-text search with ts_rank
  5. Build FastAPI endpoints: document upload (embed + insert), search (hybrid), admin (tenant management)
  6. Add connection pooling (asyncpg) and query caching (Redis) for performance
  7. Evaluate: compare pgvector-only vs hybrid vs hybrid+reranker on tenant-scoped queries
  8. Deploy with per-tenant query logging and usage metrics
-- Schema
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    content TEXT NOT NULL,
    embedding vector(384) NOT NULL,
    fts tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    metadata JSONB DEFAULT '{}'::jsonb,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Indexes
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON documents USING GIN (fts);

-- Row-level security
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON documents
    USING (tenant_id = current_setting('app.tenant'));

-- Hybrid search function
CREATE OR REPLACE FUNCTION hybrid_search(
    p_tenant TEXT, p_query TEXT, p_embedding vector(384),
    p_limit INT DEFAULT 10
) RETURNS TABLE(id INT, content TEXT, score FLOAT) AS $$
BEGIN
    SET LOCAL app.tenant = p_tenant;
    RETURN QUERY
    SELECT d.id, d.content,
           GREATEST(
               1 - (d.embedding <=> p_embedding),
               ts_rank_cd(d.fts, plainto_tsquery('english', p_query))
           ) AS score
    FROM documents d
    WHERE d.tenant_id = p_tenant
    ORDER BY score DESC
    LIMIT p_limit;
END;
$$ LANGUAGE plpgsql;
