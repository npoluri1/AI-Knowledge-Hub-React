Part I · FoundationsTier 1 — ConversableAgent, chat initiation, code execution, human input

1Conversation-as-Computation

What & why. AutoGen's core insight is that multi-turn conversations between agents are a form of computation. Instead of a single LLM call producing a final answer, agents exchange messages iteratively: one generates a draft, another critiques it, the first revises, and the cycle continues until a termination condition is met. This conversational approach produces higher-quality outputs for complex tasks because errors are caught and corrected through dialogue rather than requiring perfect single-shot generation.

# The conversation-as-computation model:
# Agent A generates -> Agent B critiques -> Agent A revises -> done
# Each message is a computation step; the conversation is the program

from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent(
    name="assistant",
    llm_config={"model": "gpt-4o"},
    system_message="You are a helpful assistant.",
)

user_proxy = UserProxyAgent(
    name="user_proxy",
    human_input_mode="NEVER",
    code_execution_config={"work_dir": "workspace"},
)

# This conversation is a computation:
# 1. UserProxy sends initial request
# 2. Assistant generates response
# 3. UserProxy executes any code in the response
# 4. Assistant processes execution results
# 5. Loop until termination message is detected
user_proxy.initiate_chat(
    assistant,
    message="Write Python code to calculate the first 10 Fibonacci numbers.",
    max_turns=3,
)
Where you'll use itConversation-as-computation is ideal for tasks requiring iteration: code generation with debugging, document drafting with review, data analysis with validation, and research with fact-checking. The multi-turn approach catches errors that single-shot generation misses.
Under the hoodAutoGen manages a message queue between agents. Each agent processes incoming messages and produces responses. The runtime checks termination conditions after each message. When a termination condition is met, the conversation stops and the final state is returned.

2ConversableAgent: Assistant and User Proxy Pair

What & why. ConversableAgent is the base class for all AutoGen agents. AssistantAgent is a conversable agent with LLM capabilities that generates responses. UserProxyAgent is a conversable agent that represents a human user and can execute code. The pair pattern (assistant + user_proxy) is AutoGen's fundamental building block: the assistant generates code and text, and the user proxy executes the code and returns results.

from autogen import AssistantAgent, UserProxyAgent

# AssistantAgent: LLM-powered agent that generates code and text
assistant = AssistantAgent(
    name="coder",
    llm_config={
        "model": "gpt-4o",
        "temperature": 0.1,
    },
    system_message=(
        "You are a Python expert. Write code to solve problems. "
        "Always include the full code in your response. "
        "When you receive execution results, fix any errors."
    ),
)

# UserProxyAgent: Executes code and returns results
user_proxy = UserProxyAgent(
    name="executor",
    human_input_mode="NEVER",
    max_consecutive_auto_reply=5,
    is_termination_msg=lambda x: x.get("content", "").rstrip().endswith("TERMINATE"),
    code_execution_config={
        "work_dir": "coding_output",
        "use_docker": False,
    },
)

# The assistant generates code, the proxy executes it
user_proxy.initiate_chat(
    assistant,
    message="Calculate the factorial of 20 using a recursive function.",
)
Where you'll use itThe assistant-proxy pair is the foundation for code generation, debugging, and analysis tasks. The assistant focuses on reasoning and code writing; the proxy handles execution and environment interaction. This separation of concerns makes the system reliable and testable.
Under the hoodAssistantAgent wraps a ChatModel and constructs prompts from the conversation history. UserProxyAgent includes a code executor that extracts code blocks from messages, runs them in a subprocess, and returns stdout/stderr as the next message.

3initiate_chat Basics

What & why. initiate_chat starts a conversation between two or more agents. The first agent (sender) sends a message to the second agent (recipient). The recipient processes the message and responds. If the response does not trigger a termination condition, the sender processes the response and may reply. This back-and-forth continues until a termination condition is met or max_turns is reached. The method returns a ChatResult object with the full conversation history.

from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent(
    name="planner",
    llm_config={"model": "gpt-4o"},
    system_message="You create plans. Be specific and actionable.",
)

user_proxy = UserProxyAgent(
    name="user",
    human_input_mode="TERMINATE",
    max_consecutive_auto_reply=3,
    is_termination_msg=lambda x: "TERMINATE" in x.get("content", ""),
)

result = user_proxy.initiate_chat(
    assistant,
    message="Create a 3-step plan to learn AutoGen.",
    max_turns=5,
)

# Inspect the conversation
print(f"Summary: {result.summary}")
print(f"Total messages: {len(result.chat_history)}")
print(f"Cost: {result.cost}")
Where you'll use itinitiate_chat is the entry point for all AutoGen conversations. Control the conversation length with max_turns, the termination with is_termination_msg, and the human interaction level with human_input_mode.
Under the hoodinitiate_chat creates a GroupChat with two participants (even for two-agent conversations). It sends the initial message, then alternates between agents until a termination condition is met. The ChatResult aggregates all messages, costs, and summary data.

What & why. The llm_config parameter on AssistantAgent configures which LLM to use and its parameters. It accepts a dictionary with model, api_key, temperature, and other ChatModel parameters. You can also pass a list of config dicts for model fallback: if the primary model fails, AutoGen tries the next one. Environment variables like OPENAI_API_KEY are read automatically if not specified.

Where you'll use itConfigure llm_config at the application level, not per-conversation. Use model fallbacks for production reliability. For local development, use Ollama to avoid API costs. Set temperature low (0-0.2) for code generation, higher (0.5-0.7) for creative tasks.
Under the hoodAutoGen passes llm_config to LangChain ChatModel under the hood. The config dict keys map directly to ChatOpenAI constructor parameters. Model fallback is implemented as a retry chain that tries each config in order.

5Code Execution: Local and Dangerous

What & why. AutoGen's UserProxyAgent can execute Python code blocks from assistant responses. This is powerful but inherently dangerous: the LLM can generate code that deletes files, makes network requests, or accesses sensitive data. Local execution (use_docker=False) runs code in the host environment. Docker execution (use_docker=True) sandboxes code in a container. Always use Docker in production and review code before execution in high-risk scenarios.

from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent(
    name="coder",
    llm_config={"model": "gpt-4o"},
    system_message="Write Python code to solve problems.",
)

# DANGEROUS: Local execution with no sandbox
unsafe_proxy = UserProxyAgent(
    name="unsafe",
    human_input_mode="NEVER",
    code_execution_config={
        "work_dir": "output",
        "use_docker": False,  # Runs on host machine
    },
)

# SAFER: Docker sandboxed execution
safe_proxy = UserProxyAgent(
    name="safe",
    human_input_mode="NEVER",
    code_execution_config={
        "work_dir": "output",
        "use_docker": True,  # Runs in Docker container
        "docker_image": "python:3.11-slim",
    },
)

# For production, always use Docker
safe_proxy.initiate_chat(
    assistant,
    message="Analyze this dataset and create a visualization.",
)
Where you'll use itCode execution is AutoGen's most powerful feature and its biggest risk. Use Docker sandboxing in production. For development, local execution is convenient but review generated code. Never run AutoGen code execution on systems with access to production databases or credentials.
Under the hoodWhen code execution is enabled, UserProxyAgent extracts Python code blocks (between ```python and ``` markers) from the assistant's response. It writes them to files in the work_dir, executes them via subprocess (or Docker API), and returns stdout/stderr as the next message.

6human_input_mode: ALWAYS, NEVER, TERMINATE

What & why. The human_input_mode parameter controls when the UserProxyAgent prompts for human input. "ALWAYS" asks for input before every reply. "TERMINATE" asks only when a termination message is detected, giving the human a chance to override. "NEVER" runs fully automated with no human input. The mode determines the balance between automation and human oversight.

from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent(
    name="assistant",
    llm_config={"model": "gpt-4o"},
    system_message="You are a helpful coding assistant.",
)

# Mode 1: ALWAYS - human approves every response
interactive_proxy = UserProxyAgent(
    name="interactive",
    human_input_mode="ALWAYS",  # Prompt human before every reply
)

# Mode 2: TERMINATE - human only intervenes at termination
semi_auto_proxy = UserProxyAgent(
    name="semi_auto",
    human_input_mode="TERMINATE",
    is_termination_msg=lambda x: "TERMINATE" in x.get("content", ""),
)

# Mode 3: NEVER - fully automated
fully_auto_proxy = UserProxyAgent(
    name="fully_auto",
    human_input_mode="NEVER",
    max_consecutive_auto_reply=10,
)

# Use TERMINATE for most production workflows
# It allows automation but gives humans a final say
Where you'll use itUse TERMINATE for most workflows: it automates the conversation but pauses at termination for human approval. Use NEVER for fully automated pipelines (with max_consecutive_auto_reply as safety). Use ALWAYS for interactive development and debugging.
Under the hoodWhen human_input_mode is "TERMINATE" or "ALWAYS", the UserProxyAgent calls input() to read from stdin. In production, replace this with a webhook or message queue integration. The human response is sent as the next message in the conversation.

7Auto-Reply Mechanism

What & why. AutoGen agents can automatically reply to messages without human intervention. The auto-reply mechanism is controlled by max_consecutive_auto_reply: after this many automatic replies, the agent stops and waits for human input (or terminates). This prevents infinite loops in fully automated mode. You can also register custom reply functions that trigger on specific message patterns.

from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent(
    name="assistant",
    llm_config={"model": "gpt-4o"},
    system_message="You are a helpful assistant.",
)

# Auto-reply limited to 5 consecutive responses
proxy = UserProxyAgent(
    name="user",
    human_input_mode="NEVER",
    max_consecutive_auto_reply=5,
    is_termination_msg=lambda x: x.get("content", "").rstrip().endswith("TERMINATE"),
)

# Register a custom reply function
def custom_reply(recipient, messages, sender, config):
    """Reply to messages containing 'help' with a specific response."""
    last_message = messages[-1].get("content", "")
    if "help" in last_message.lower():
        return True, "I can help you with coding, analysis, and research."
    return False, None  # Fall through to default behavior

assistant.register_reply(
    trigger="user",
    reply_func=custom_reply,
)

proxy.initiate_chat(
    assistant,
    message="I need help writing a Python script.",
)
Where you'll use itAuto-reply limits prevent cost runaway in fully automated mode. Custom reply functions enable message routing, filtering, and special handling without modifying agent internals. Use them to implement domain-specific behaviors.
Under the hoodAutoGen processes messages through a reply function chain. Each agent has a chain of registered reply functions. The first function that returns (True, response) handles the message. If no custom function handles it, the default LLM-based reply is used.

8Termination Messages and Conditions

What & why. Termination conditions determine when a conversation stops. The is_termination_msg parameter accepts a callable that checks each incoming message. When it returns True, the conversation ends. Common patterns: checking for "TERMINATE" in the message, checking message count, or checking for specific content patterns. Proper termination prevents infinite conversations and controls cost.

from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent(
    name="assistant",
    llm_config={"model": "gpt-4o"},
    system_message=(
        "You are a helpful assistant. "
        "When you are done, end your message with TERMINATE."
    ),
)

# Pattern 1: Check for TERMINATE keyword
proxy = UserProxyAgent(
    name="user",
    human_input_mode="NEVER",
    is_termination_msg=lambda x: x.get("content", "").rstrip().endswith("TERMINATE"),
)

# Pattern 2: Check message count
turn_count = {"n": 0}
def check_turns(msg):
    turn_count["n"] += 1
    return turn_count["n"] >= 10

proxy_turns = UserProxyAgent(
    name="user",
    human_input_mode="NEVER",
    is_termination_msg=check_turns,
)

# Pattern 3: Check for specific content
def check_completion(msg):
    content = msg.get("content", "")
    return "DONE" in content or "COMPLETE" in content

proxy_done = UserProxyAgent(
    name="user",
    human_input_mode="NEVER",
    is_termination_msg=check_completion,
)
Where you'll use itAlways set a termination condition. Without one, conversations can run indefinitely, consuming API tokens. The TERMINATE keyword pattern is the standard approach: instruct the LLM to end with TERMINATE and check for it in the termination function.
Under the hoodAfter each message is processed, AutoGen calls the is_termination_msg function with the message dict. If it returns True, the conversation stops and the ChatResult is returned. The termination check happens before the next agent processes the message.

9Two-Agent Code Generation Demo

What & why. The canonical AutoGen pattern is a code generation conversation: a UserProxyAgent requests code, an AssistantAgent writes it, the proxy executes it, and if there are errors the assistant fixes them. This iterative loop continues until the code runs successfully. The conversation history provides full traceability of the development process.

from autogen import AssistantAgent, UserProxyAgent

# Configure the coding assistant
coder = AssistantAgent(
    name="coder",
    llm_config={
        "model": "gpt-4o",
        "temperature": 0.1,
    },
    system_message=(
        "You are an expert Python developer. "
        "Write clean, well-documented code. "
        "When you receive execution results or errors, "
        "fix the code and try again."
    ),
)

# Configure the code executor
executor = UserProxyAgent(
    name="executor",
    human_input_mode="TERMINATE",
    max_consecutive_auto_reply=8,
    is_termination_msg=lambda x: x.get("content", "").rstrip().endswith("TERMINATE"),
    code_execution_config={
        "work_dir": "code_output",
        "use_docker": False,
    },
)

# Start the code generation conversation
result = executor.initiate_chat(
    coder,
    message=(
        "Write a Python script that:\n"
        "1. Creates a list of 100 random numbers\n"
        "2. Calculates mean, median, and std deviation\n"
        "3. Plots a histogram\n"
        "4. Saves the plot as stats.png"
    ),
)

# Review the conversation
print(f"Messages: {len(result.chat_history)}")
print(f"Cost: ${result.cost.get('usage_included_in_price', 0):.4f}")
Where you'll use itThis two-agent code generation pattern is the most common AutoGen use case. It works for data analysis, scripting, testing, and any task where code needs to be written, executed, and debugged iteratively.
Under the hoodThe conversation alternates: coder writes code, executor runs it, coder sees output/errors and revises. The max_consecutive_auto_reply limit on the executor prevents infinite loops. The TERMINATE keyword signals successful completion.

10system_message Shaping Persona

What & why. The system_message parameter on AssistantAgent defines the agent's persona, expertise, and behavioral instructions. It is the most powerful lever for controlling agent behavior. A well-crafted system_message constrains the LLM's output to the desired domain, format, and quality level. It persists across all messages in the conversation, providing consistent behavioral framing.

11max_consecutive_auto_reply Guard

What & why. The max_consecutive_auto_reply parameter limits how many times an agent can automatically reply before stopping. This is a critical safety guard: without it, two agents in NEVER mode can loop indefinitely, consuming API tokens. Set this parameter on every agent in fully automated mode. The count resets when a human provides input.

from autogen import AssistantAgent, UserProxyAgent

assistant = AssistantAgent(
    name="assistant",
    llm_config={"model": "gpt-4o"},
    system_message="You are a helpful assistant. End with TERMINATE when done.",
)

# Without max_consecutive_auto_reply, this could loop forever
unsafe_proxy = UserProxyAgent(
    name="unsafe",
    human_input_mode="NEVER",
    # No max_consecutive_auto_reply = unlimited replies!
)

# With max_consecutive_auto_reply, the conversation stops after 10 turns
safe_proxy = UserProxyAgent(
    name="safe",
    human_input_mode="NEVER",
    max_consecutive_auto_reply=10,  # Safety guard
    is_termination_msg=lambda x: x.get("content", "").rstrip().endswith("TERMINATE"),
)

# The count tracks consecutive auto-replies
# Human input resets the counter
result = safe_proxy.initiate_chat(
    assistant,
    message="Write a comprehensive analysis of Python web frameworks.",
    max_turns=10,
)
Where you'll use itAlways set max_consecutive_auto_reply on agents with human_input_mode="NEVER". A value of 5-10 is typical for most workflows. Increase only for tasks that genuinely require many iterations, like complex debugging sessions.
Under the hoodAutoGen counts consecutive auto-replies per agent. When the limit is reached, the agent stops replying and the conversation either terminates (if no other agent can continue) or waits for human input. The counter resets when human_input_mode prompts the user.

12When AutoGen Fits and When It Does Not

What & why. AutoGen excels at conversational code generation, debugging, and iterative refinement. It fits scenarios where agents need to exchange multiple messages to converge on a solution: code generation with execution feedback, document drafting with review cycles, and analysis with validation. It is less suitable for role-based team workflows (use CrewAI), graph-based orchestration (use LangGraph), or simple single-turn tasks.

# AutoGen fits when: iterative refinement through conversation
# AutoGen struggles when: fixed team roles and sequential tasks

Where you'll use itChoose AutoGen when you need conversational iteration with code execution. It is the best framework for code generation and debugging tasks. For role-based team workflows, consider CrewAI. For complex orchestration, consider LangGraph.
Under the hoodAutoGen's strength is its code execution integration: the user proxy runs code and returns results, enabling true iterative development. This tight feedback loop between generation and execution is unique to AutoGen among multi-agent frameworks.

Part II · IntermediateTier 2 — GroupChat, registered functions, nested chats, sandboxing

13GroupChat and GroupChatManager

What & why. GroupChat enables conversations with 3+ agents. A GroupChatManager orchestrates the conversation, deciding which agent speaks next based on speaker selection rules. All agents see all messages, enabling collaborative problem-solving. GroupChatManager wraps a GroupChat and provides the LLM-based speaker selection when automatic mode is used.

from autogen import AssistantAgent, UserProxyAgent, GroupChat, GroupChatManager

coder = AssistantAgent(
    name="coder",
    llm_config={"model": "gpt-4o"},
    system_message="You write Python code.",
)

reviewer = AssistantAgent(
    name="reviewer",
    llm_config={"model": "gpt-4o"},
    system_message="You review code for bugs and improvements.",
)

planner = AssistantAgent(
    name="planner",
    llm_config={"model": "gpt-4o"},
    system_message="You create implementation plans.",
)

user_proxy = UserProxyAgent(
    name="user",
    human_input_mode="NEVER",
    max_consecutive_auto_reply=1,
    code_execution_config={"work_dir": "output", "use_docker": False},
)

# Create group chat with all participants
group_chat = GroupChat(
    agents=[user_proxy, coder, reviewer, planner],
    messages=[],
    max_round=12,
    speaker_selection_method="auto",  # LLM decides who speaks
)

# Manager orchestrates the conversation
manager = GroupChatManager(
    groupchat=group_chat,
    llm_config={"model": "gpt-4o"},
)

# Start the group conversation
user_proxy.initiate_chat(
    manager,
    message="Build a REST API for a todo application.",
)
Where you'll use itGroupChat is ideal for collaborative tasks where multiple perspectives improve quality: code review with multiple reviewers, brainstorming with diverse expertise, and planning with cross-functional input.
Under the hoodGroupChatManager uses the LLM to select the next speaker based on the conversation history and each agent's role description. The selection prompt includes all agent names and system messages, allowing the LLM to choose the most appropriate next speaker.

14Speaker Selection Methods

What & why. GroupChat supports multiple speaker selection methods. "auto" uses the LLM to choose the next speaker dynamically. "round_robin" cycles through agents in order. "manual" requires the human to select the next speaker. Custom functions can implement domain-specific selection logic: route to the specialist based on message content, or enforce turn-taking patterns.

from autogen import AssistantAgent, GroupChat, GroupChatManager

coder = AssistantAgent(
    name="coder", llm_config={"model": "gpt-4o"},
    system_message="You write code.",
)
reviewer = AssistantAgent(
    name="reviewer", llm_config={"model": "gpt-4o"},
    system_message="You review code.",
)
tester = AssistantAgent(
    name="tester", llm_config={"model": "gpt-4o"},
    system_message="You write tests.",
)

# Round-robin: deterministic turn order
round_robin_chat = GroupChat(
    agents=[coder, reviewer, tester],
    messages=[],
    max_round=9,
    speaker_selection_method="round_robin",
)

# LLM-based: dynamic speaker selection
auto_chat = GroupChat(
    agents=[coder, reviewer, tester],
    messages=[],
    max_round=12,
    speaker_selection_method="auto",
)

# Custom function: route based on content
def select_speaker(recipient, messages, sender, config):
    last_msg = messages[-1].get("content", "").lower()
    if "test" in last_msg:
        return "tester"
    if "review" in last_msg or "bug" in last_msg:
        return "reviewer"
    return "coder"

custom_chat = GroupChat(
    agents=[coder, reviewer, tester],
    messages=[],
    max_round=9,
    speaker_selection_method=select_speaker,
)
Where you'll use it"auto" is the default and works well for most cases. "round_robin" is useful when you want deterministic turn-taking. Custom functions enable domain-specific routing based on message content or conversation state.
Under the hoodFor "auto" selection, GroupChatManager sends a prompt to the LLM listing all agents and asking which should speak next based on the conversation. The LLM returns the agent name, and GroupChatManager routes the next message to that agent.

15Registered Functions: register_for_llm and executor

What & why. AutoGen allows you to register custom functions that agents can call during conversations. register_for_llm adds the function to the agent's tool list (visible to the LLM), while the executor function handles the actual execution. This is AutoGen's equivalent of tool calling: the LLM decides when to call a function, and the executor runs it.

from autogen import AssistantAgent, UserProxyAgent

def calculate(expression: str) -> str:
    """Evaluate a mathematical expression safely."""
    allowed = set("0123456789+-*/.() ")
    if not all(c in allowed for c in expression):
        return "Error: invalid characters"
    try:
        return str(eval(expression))
    except Exception as e:
        return f"Error: {e}"

# Interop pattern: AutoGen agent as a LangGraph node
from autogen import AssistantAgent
from langgraph.graph import StateGraph, START, END
from typing import TypedDict

class PipelineState(TypedDict):
    query: str
    autogen_response: str
    final_output: str

# AutoGen agent
autogen_agent = AssistantAgent(
    name="researcher",
    llm_config={"model": "gpt-4o"},
    system_message="You research topics thoroughly.",
)

def run_autogen_agent(state: PipelineState) -> dict:
    """Wrap AutoGen execution in a LangGraph node."""
    from autogen import UserProxyAgent
    proxy = UserProxyAgent(
        name="proxy", human_input_mode="NEVER",
        max_consecutive_auto_reply=1,
    )
    result = proxy.initiate_chat(
        autogen_agent,
        message=state["query"],
        max_turns=2,
    )
    return {"autogen_response": result.summary}

def post_process(state: PipelineState) -> dict:
    return {"final_output": f"Processed: {state['autogen_response']}"}

# Build LangGraph with AutoGen node
graph = StateGraph(PipelineState)
graph.add_node("research", run_autogen_agent)
graph.add_node("process", post_process)
graph.add_edge(START, "research")
graph.add_edge("research", "process")
graph.add_edge("process", END)

32Formal Conversation Policies: Statecharts

What & why. AutoGen conversations can be modeled as statecharts: formal state machines that define valid message sequences. States represent conversation phases (drafting, reviewing, revising), and transitions define valid next states. This formalization prevents invalid conversation flows, enables verification, and makes complex multi-agent workflows predictable and debuggable.

# Statechart-inspired conversation policy
# Model conversation as explicit states and transitions

conversation_states = {
    "init": {"next": ["drafting"]},
    "drafting": {"next": ["reviewing", "complete"]},
    "reviewing": {"next": ["revising", "approved"]},
    "revising": {"next": ["reviewing"]},
    "approved": {"next": ["complete"]},
    "complete": {"next": []},
}

# Implement as a custom reply function
class StatefulConversation:
    def __init__(self):
        self.state = "init"
        self.transitions = conversation_states

    def check_transition(self, new_state):
        valid = self.transitions.get(self.state, {}).get("next", [])
        if new_state in valid:
            self.state = new_state
            return True
        return False

policy = StatefulConversation()

33Cost Governance: Transcripts Ledger

What & why. AutoGen tracks token usage and cost in ChatResult.cost. For production, build a cost governance system that logs all conversation costs, enforces budgets, and alerts on overspend. import json

class CostGovernor:
    def __init__(self, budget_per_conversation=0.50):
        self.budget = budget_per_conversation
        self.ledger = []
        self.total_spend = 0.0

    def check_budget(self, cost):
        self.total_spend += cost
        self.ledger.append({
            "timestamp": time.time(),
            "cost": cost,
            "running_total": self.total_spend,

        return {
            "total_cost": self.total_spend,
            "conversations": len(self.ledger),
            "avg_cost": self.total_spend / max(len(self.ledger), 1),
        }

34Enterprise Deploy: Containers and Queues

What & why. Production AutoGen deployments use containerized agents, message queues for job dispatch, and databases for state persistence. Each conversation runs in an isolated container with resource limits. A queue receives conversation requests and dispatches them to available containers. Conversation state is stored in a database for recovery and audit. This architecture scales horizontally and provides fault isolation.

# Enterprise deployment architecture (conceptual)
# Each component runs as a separate container/service

# 1. API Gateway receives conversation requests
# 2. Queue (Redis/RabbitMQ) buffers jobs
# 3. Worker containers pull jobs and run AutoGen conversations
# 4. Database stores conversation state and results
# 5. Monitoring tracks costs, latency, and errors

import json
import redis

r = redis.Redis(host="localhost", port=6379, db=0)

def enqueue_conversation(task, user_id):
    """Add a conversation request to the queue."""
    job = {
        "task": task,
        "user_id": user_id,
        "timestamp": time.time(),
        "status": "pending",
    }
    r.lpush("autogen_jobs", json.dumps(job))
    return job

def process_conversation(job):
    """Process a conversation from the queue."""
    from autogen import AssistantAgent, UserProxyAgent
    assistant = AssistantAgent(
        name="assistant",
        llm_config={"model": "gpt-4o"},
        system_message="You are a helpful assistant.",
    )
    proxy = UserProxyAgent(
        name="user",
        human_input_mode="NEVER",
        max_consecutive_auto_reply=5,
    )
    result = proxy.initiate_chat(assistant, message=job["task"])
    return {
        "result": result.summary,
        "cost": result.cost,
        "turns": len(result.chat_history),
    }

# Worker loop
while True:
    _, job_raw = r.brpop("autogen_jobs")
    job = json.loads(job_raw)
    try:
        output = process_conversation(job)
        r.hset(f"job:{job['user_id']}", mapping=output)
    except Exception as e:
        r.hset(f"job:{job['user_id']}", "error", str(e))
Where you'll use itEnterprise deployment requires containerization, queue-based job dispatch, and database persistence. This architecture enables horizontal scaling, fault isolation, and resource management. Use Docker Compose or Kubernetes for orchestration.
Under the hoodEach worker container creates its own AutoGen agent instances and runs conversations independently. The queue ensures jobs are distributed across available workers. Database persistence enables recovery from worker crashes without losing conversation state.
