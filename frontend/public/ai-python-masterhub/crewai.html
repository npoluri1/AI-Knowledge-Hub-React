Part I · FoundationsTier 1 — Agents, tasks, crews, and basic execution

1CrewAI Philosophy: Role-Based Teamwork

What & why. CrewAI treats AI agents as team members with specific roles rather than generic tool-calling loops. Each agent is defined by a role (what it does), a goal (what it optimizes for), and a backstory (the context that shapes its reasoning). This design produces more coherent and domain-appropriate outputs because the LLM receives a persona frame that constrains and focuses its generation. The philosophy mirrors human teams: assign the right specialist to each task rather than expecting one generalist to do everything.

# CrewAI models collaboration as specialized roles
# Role + Goal + Backstory = focused agent persona
# This is fundamentally different from a single prompt with all instructions

from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Senior Research Analyst",
    goal="Uncover the latest trends in AI agent frameworks",
    backstory="You are an experienced analyst who has tracked the AI landscape for over a decade.",
    verbose=True,
    allow_delegation=False,
)

planner = Agent(
    role="Content Strategist",
    goal="Structure raw research into a compelling narrative",
    backstory="You are a seasoned editor who turns dense analysis into readable articles.",
    verbose=True,
    allow_delegation=False,
)

print(f"Researcher: {researcher.role}")
print(f"Planner: {planner.role}")
Where you'll use itCrewAI fits any scenario where multiple specialized perspectives must collaborate: content pipelines (researcher + writer + editor), data workflows (extractor + transformer + validator), and customer support (triage agent + domain specialist + escalation handler).
Under the hoodEach Agent wraps a LangChain ChatModel and constructs a system prompt by combining role, goal, backstory, and tool descriptions. CrewAI uses its own orchestration layer on top of LangChain to manage multi-turn delegation between agents.

2Installation and LLM Configuration

What & why. CrewAI is installed via pip and requires a language model backend. The simplest setup uses an OpenAI API key, but CrewAI supports any LangChain-compatible ChatModel including local models via Ollama, Anthropic, and Azure OpenAI. Environment variables keep credentials out of source code. Install crewai with extras for tools: pip install crewai crewai-tools.

# Install CrewAI and its tools package
# pip install crewai crewai-tools

import os
from crewai import Agent, Task, Crew, Process

# Set API key via environment (never hardcode)
os.environ["OPENAI_API_KEY"] = "sk-..."

# CrewAI defaults to OpenAI gpt-4o
# Override with any ChatModel-compatible provider
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="gpt-4o",
    temperature=0.1,
)

# Pass custom LLM to any agent
agent = Agent(
    role="Analyst",
    goal="Produce accurate data analysis",
    backstory="You are a meticulous data analyst.",
    llm=llm,
    verbose=True,
)
Where you'll use itEvery CrewAI project starts here. Pin your LLM provider and model in configuration, not in agent definitions, so you can swap providers or adjust temperature without touching agent logic.
Under the hoodCrewAI delegates LLM calls to LangChain ChatModel instances. When you specify a model string like "gpt-4o", CrewAI auto-creates a ChatOpenAI instance. Custom LLMs bypass this auto-detection and give you full control over parameters.

3Agent Anatomy: Role, Goal, and Backstory

What & why. Every Agent requires three string fields. The role names the function (e.g., "Senior Data Engineer"). The goal defines the success criteria that the agent optimizes toward. The backstory provides domain context and behavioral instructions that persist across all of the agent's task executions. Together these three fields form a persona that shapes every LLM call the agent makes. You can also set optional fields like llm, tools, allow_delegation, and max_iter.

from crewai import Agent

# Minimal agent with required fields
writer = Agent(
    role="Technical Writer",
    goal="Write clear, concise documentation for developer APIs",
    backstory=(
        "You are a documentation specialist with 15 years of experience "
        "writing for companies like Stripe and Twilio. You value precision, "
        "real code examples, and avoiding unnecessary jargon."
    ),
    verbose=True,
    allow_delegation=False,
    max_iter=15,
)

# The backstory is injected into the system prompt
# The goal is used by the crew process to evaluate task completion
print(writer.role)
print(writer.goal)
Where you'll use itWell-crafted backstories dramatically improve output quality. A "data analyst" with a backstory about healthcare compliance produces very different results than one with a backstory about marketing analytics. Invest time in backstory design for critical roles.
Under the hoodAt kickoff, CrewAI concatenates role, goal, backstory, and tool descriptions into a system message. The agent's LLM receives this system message plus the task description and any inter-agent delegation messages throughout the crew run.

4Task Description and Expected Output

What & why. Tasks are the work units assigned to agents. Each task has a description (what to do), an expected_output (format and content expectations), and an agent (who executes it). The expected_output field acts as a quality contract: it tells the LLM exactly what structure to produce. Vague expected_output leads to inconsistent results; precise expected_output with format examples yields reliable outputs.

from crewai import Agent, Task

analyst = Agent(
    role="Market Analyst",
    goal="Analyze competitor positioning",
    backstory="You are an expert in SaaS market analysis.",
)

# Task with precise expected output specification
analysis_task = Task(
    description=(
        "Analyze the top 3 competitors in the AI agent framework space. "
        "For each competitor, cover: pricing model, key differentiators, "
        "target audience, and strengths/weaknesses."
    ),
    expected_output=(
        "A structured markdown table with columns: Competitor, Pricing, "
        "Differentiator, Target Audience, Strengths, Weaknesses. "
        "Followed by a 2-paragraph synthesis paragraph."
    ),
    agent=analyst,
)

# The agent receives both description and expected_output
# CrewAI uses expected_output to evaluate task completion
print(analysis_task.expected_output)
Where you'll use itExpected output specifications are the single most impactful quality lever in CrewAI. Writing them like acceptance criteria (specific format, required fields, length constraints) dramatically reduces the need for retry or manual post-processing.
Under the hoodWhen an agent completes its LLM generation, CrewAI compares the output against the expected_output string. In sequential mode, this comparison determines whether the task is marked as complete. The comparison is heuristic, not strict validation.

5Crew Assembly and Kickoff

What & why. A Crew groups agents, tasks, and a process into a single executable unit. After defining agents and tasks, you instantiate Crew with agents (list), tasks (list), process (sequential or hierarchical), and verbose (logging level). Calling kickoff() executes the crew, returning a CrewOutput object. kickoff() accepts a inputs dictionary for dynamic task descriptions using curly-brace placeholders.

from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Researcher",
    goal="Find comprehensive information",
    backstory="You are a thorough research specialist.",
)

writer = Agent(
    role="Writer",
    goal="Transform research into engaging content",
    backstory="You are a skilled content writer.",
)

task1 = Task(
    description="Research the benefits of containerization in cloud deployment",
    expected_output="A bullet-point summary of 5 key benefits with supporting evidence",
    agent=researcher,
)

task2 = Task(
    description="Write a 500-word blog post based on the research",
    expected_output="A well-structured blog post with introduction, body, and conclusion",
    agent=writer,
)

crew = Crew(
    agents=[researcher, writer],
    tasks=[task1, task2],
    process=Process.sequential,
    verbose=True,
)

result = crew.kickoff()
print(result)
Where you'll use itCrew instantiation is the wiring phase. Place agents in execution order in the agents list and tasks in execution order in the tasks list. Sequential process runs tasks top-to-bottom; hierarchical uses a manager to delegate dynamically.
Under the hoodkickoff() initializes each agent's LLM, builds the task execution queue, and runs the selected process. In sequential mode, each task's output is passed as context to the next task. The CrewOutput aggregates all task outputs and token usage metrics.

6Process.sequential Execution Flow

What & why. The sequential process runs tasks in the order they appear in the tasks list. Each agent completes its task before the next agent receives its task. Task outputs flow as context to subsequent tasks, creating a pipeline effect. This is the simplest and most predictable process. It works well when the workflow is linear and dependencies are clear: research then write then review.

from crewai import Agent, Task, Crew, Process

extractor = Agent(
    role="Data Extractor",
    goal="Extract key facts from raw text",
    backstory="You are precise at identifying factual claims.",
)

summarizer = Agent(
    role="Summarizer",
    goal="Condense facts into a concise brief",
    backstory="You excel at distilling complex information.",
)

reviewer = Agent(
    role="Reviewer",
    goal="Verify accuracy and flag issues",
    backstory="You are a careful fact-checker.",
)

t1 = Task(
    description="Extract all factual claims from: {input_text}",
    expected_output="Numbered list of factual claims",
    agent=extractor,
)

t2 = Task(
    description="Summarize the extracted facts into a 100-word brief",
    expected_output="A 100-word summary paragraph",
    agent=summarizer,
)

t3 = Task(
    description="Review the summary for accuracy and completeness",
    expected_output="Approval with notes or specific corrections needed",
    agent=reviewer,
)

crew = Crew(
    agents=[extractor, summarizer, reviewer],
    tasks=[t1, t2, t3],
    process=Process.sequential,
    verbose=True,
)

result = crew.kickoff(inputs={"input_text": "Sample text with facts..."})
Where you'll use itSequential process is the default choice for linear pipelines. Use it for ETL-style workflows, content production lines, and any scenario where step N's output feeds step N+1's input.
Under the hoodIn sequential mode, CrewAI maintains an ordered task queue. After each task completes, its output string is appended to a shared context list. The next agent's LLM prompt includes all prior task outputs, giving it full pipeline context.

7Verbose Logging and Reading Output

What & why. Setting verbose=True on agents and the crew produces detailed execution logs showing each agent's reasoning, tool calls, and task outputs. During development, verbose output is essential for debugging: you can see exactly what each agent received and produced. In production, verbose logs are piped to structured logging systems. The CrewOutput object from kickoff() contains the final output, token usage, and individual task outputs.

from crewai import Agent, Task, Crew, Process

agent = Agent(
    role="Analyst",
    goal="Provide analysis",
    backstory="You are a data analyst.",
    verbose=True,  # Logs agent reasoning steps
)

task = Task(
    description="Analyze the top trend in AI for 2025",
    expected_output="One paragraph analysis with supporting data",
    agent=agent,
)

crew = Crew(
    agents=[agent],
    tasks=[task],
    verbose=True,  # Logs crew-level orchestration
    process=Process.sequential,
)

result = crew.kickoff()

# CrewOutput contains structured results
print(f"Final Output: {result.raw}")          # Raw string output
print(f"Token Usage: {result.token_usage}")    # Token consumption dict
print(f"Tasks Output: {len(result.tasks_output)}")  # Individual task results

# Access individual task outputs
for task_output in result.tasks_output:
    print(f"Task: {task_output.description[:50]}...")
    print(f"Output: {task_output.raw[:100]}...")
Where you'll use itAlways run with verbose=True during development. For production, set verbose=False on agents but configure CrewAI's callback handlers to capture structured logs via LangChain callbacks.
Under the hoodVerbose output is printed via Python's logging module at the INFO level. CrewAI formats each log entry with the agent role, task description prefix, and truncated output. Token usage is aggregated across all LLM calls in the crew run.

8Output Formats: Raw String Basics

What & why. By default, CrewAI returns task outputs as raw strings. The result.raw attribute on CrewOutput contains the final text. Each TaskOutput in result.tasks_output also has a .raw field. For simple use cases, raw strings are sufficient. When you need structured data, you either parse the string yourself or use Pydantic-based expected outputs (covered in Tier 2). The raw format is always available regardless of output configuration.

from crewai import Agent, Task, Crew, Process

agent = Agent(
    role="Researcher",
    goal="Produce structured findings",
    backstory="You are a research analyst.",
)

task = Task(
    description="List 3 advantages of microservices vs monoliths",
    expected_output=(
        "1. Advantage one with explanation\n"
        "2. Advantage two with explanation\n"
        "3. Advantage three with explanation"
    ),
    agent=agent,
)

crew = Crew(
    agents=[agent],
    tasks=[task],
    process=Process.sequential,
)

result = crew.kickoff()

# Access raw string output
print(result.raw)

# The output is a plain string
# You can parse it manually
lines = result.raw.strip().split("\n")
for line in lines:
    if line.strip():
        print(f"Found: {line.strip()}")
Where you'll use itRaw string output is the baseline for all CrewAI runs. Use it when downstream consumers accept text, when you write to files, or when you pipe output to other systems. For structured extraction, see Pydantic output models in Tier 2.
Under the hoodThe raw field contains the last LLM response from the agent assigned to that task. CrewAI does not transform or validate this string unless you configure Pydantic output models. The raw string is exactly what the LLM generated.

9Simple Two-Agent Blog Outline Crew

What & why. A minimal end-to-end example demonstrates the full CrewAI workflow: define two agents, create sequential tasks, assemble a crew, and kick it off. The researcher agent gathers information, and the writer agent uses that information to produce an outline. This pattern scales to larger teams by adding agents and tasks in sequence.

from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Content Researcher",
    goal="Gather comprehensive information on the given topic",
    backstory=(
        "You are a meticulous researcher who finds credible sources "
        "and organizes findings by theme and importance."
    ),
    verbose=True,
    allow_delegation=False,
)

writer = Agent(
    role="Blog Outline Writer",
    goal="Create a structured, engaging blog post outline",
    backstory=(
        "You are a content strategist who creates outlines that "
        "balance SEO requirements with reader engagement."
    ),
    verbose=True,
    allow_delegation=False,
)

research_task = Task(
    description=(
        "Research the topic: {topic}. Find 3-5 key subtopics, "
        "supporting points for each, and 2-3 credible sources."
    ),
    expected_output=(
        "Organized research notes with: subtopic headings, "
        "bullet points under each, and source references."
    ),
    agent=researcher,
)

outline_task = Task(
    description=(
        "Using the research provided, create a blog post outline "
        "with: title, introduction hook, 4-5 main sections with "
        "sub-points, and a conclusion with CTA."
    ),
    expected_output=(
        "A numbered blog outline with title, intro, sections, "
        "and conclusion. Each section has 2-3 sub-points."
    ),
    agent=writer,
)

crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, outline_task],
    process=Process.sequential,
    verbose=True,
)

result = crew.kickoff(inputs={"topic": "Building AI Agents with CrewAI"})
print(result.raw)
Where you'll use itThis two-agent pattern is the foundation for content pipelines. Extend it by adding an editor agent after the writer, a fact-checker before publication, or a social media agent that repurposes the outline into post drafts.
Under the hoodThe researcher's task output becomes context for the writer's task. CrewAI automatically passes previous task outputs to subsequent agents. The writer LLM receives both the system prompt (role/goal/backstory) and the researcher's output as user context.

10Tools Assignment and SerperDevTool

What & why. Agents can be equipped with tools that extend their capabilities beyond text generation. Tools are Python functions or LangChain tools that agents can invoke during task execution. The crewai-tools package provides pre-built tools like SerperDevTool for web search. When an agent has tools, the LLM decides when to call them based on the task requirements. Tools give agents real-world access to search, APIs, file systems, and databases.

from crewai import Agent, Task, Crew, Process
from crewai_tools import SerperDevTool

# Create a search tool (requires SERPER_API_KEY env var)
search_tool = SerperDevTool()

researcher = Agent(
    role="Web Researcher",
    goal="Find the most current information using web search",
    backstory="You are an expert researcher who uses web search effectively.",
    tools=[search_tool],  # Agent can now search the web
    verbose=True,
    allow_delegation=False,
)

task = Task(
    description=(
        "Search for the latest developments in CrewAI as of 2025. "
        "Summarize the top 3 announcements or releases."
    ),
    expected_output="Three bullet points summarizing latest CrewAI developments",
    agent=researcher,
)

crew = Crew(
    agents=[researcher],
    tasks=[task],
    process=Process.sequential,
    verbose=True,
)

result = crew.kickoff()
Where you'll use itTools transform agents from text generators into active participants. Common tool assignments: search tools for researchers, file I/O for data processors, API clients for integration agents, and code executors for analytical agents.
Under the hoodCrewAI injects tool descriptions into the agent's system prompt as available functions. The LLM generates structured tool call responses, CrewAI executes them, and feeds the results back into the conversation. This follows the standard LangChain tool-calling protocol.

11Delegation Between Agents

What & why. When allow_delegation=True (the default), an agent can hand off subtasks to other agents in the crew. During execution, the agent's LLM may decide that another agent is better suited for a portion of its work and delegate. Delegation creates dynamic, non-linear workflows where agents collaborate in real time rather than following a fixed sequence. This is powerful but requires careful design to avoid loops.

from crewai import Agent, Task, Crew, Process

analyst = Agent(
    role="Data Analyst",
    goal="Analyze data and produce insights",
    backstory="You are a data analyst.",
    allow_delegation=True,  # Can delegate subtasks
    verbose=True,
)

writer = Agent(
    role="Report Writer",
    goal="Write polished reports from analysis",
    backstory="You are a report writer.",
    allow_delegation=False,  # Cannot delegate further
    verbose=True,
)

manager = Agent(
    role="Project Manager",
    goal="Coordinate the team and ensure quality",
    backstory="You are an experienced project manager.",
    allow_delegation=True,
    verbose=True,
)

analysis_task = Task(
    description="Analyze customer churn data and identify top 3 drivers",
    expected_output="Top 3 churn drivers with supporting metrics",
    agent=analyst,
)

report_task = Task(
    description="Write an executive summary based on the analysis",
    expected_output="A 200-word executive summary with key findings",
    agent=writer,
)

crew = Crew(
    agents=[analyst, writer, manager],
    tasks=[analysis_task, report_task],
    process=Process.sequential,
    verbose=True,
)

# Delegation allows agents to ask other agents for help
result = crew.kickoff()
Where you'll use itDelegation is most useful in hierarchical processes where a manager agent coordinates specialists. In sequential processes, delegation is less relevant because task flow is predetermined. Set allow_delegation=False on agents that should not spawn sub-conversations.
Under the hoodWhen delegation is enabled, CrewAI adds instructions to the agent's prompt describing how to delegate. If the LLM generates a delegation request, CrewAI pauses the current agent, spawns a sub-task with the target agent, and feeds the result back. Each delegation consumes additional LLM tokens.

12When CrewAI Fits and When It Does Not

What & why. CrewAI excels at role-based multi-agent workflows with clear task decomposition, sequential or manager-coordinated execution, and natural language interfaces. It fits content production pipelines, research workflows, analysis chains, and any scenario where distinct roles collaborate toward a shared output. It is less suitable for highly dynamic graph-based flows with complex conditional routing (use LangGraph), real-time event-driven systems (use Flows or custom orchestration), or applications requiring fine-grained control over LLM prompts per turn.

# CrewAI fits when: roles are stable and tasks are clear
# CrewAI struggles when: routing depends on runtime state at every step

from crewai import Agent, Task, Crew, Process

# GOOD FIT: Content pipeline with fixed roles
researcher = Agent(
    role="Researcher", goal="Gather facts", backstory="You research."
)
editor = Agent(
    role="Editor", goal="Polish content", backstory="You edit."
)
t1 = Task(
    description="Research topic: {topic}",
    expected_output="Fact list", agent=researcher
)
t2 = Task(
    description="Edit the research into article form",
    expected_output="Polished article", agent=editor
)
crew = Crew(
    agents=[researcher, editor],
    tasks=[t1, t2],
    process=Process.sequential,
)
result = crew.kickoff(inputs={"topic": "AI Trends"})

# CrewAI is less ideal for:
# - Complex conditional routing (use LangGraph)
# - Real-time streaming with fine-grained control
# - State machines with many possible transitions
Where you'll use itChoose CrewAI for team-style collaboration with clear roles. Choose LangGraph for state-heavy graphs with complex routing. Choose AutoGen for conversational multi-agent debugging. The frameworks are complementary, not competing.
Under the hoodCrewAI's process abstraction (sequential or hierarchical) is simpler than LangGraph's full graph model. This simplicity is a feature for most use cases but a limitation when you need arbitrary conditional edges, loops with complex state, or human-in-the-loop at every step.

Part II · IntermediateTier 2 — Hierarchical process, Pydantic outputs, memory, and guardrails

13Process.hierarchical: Manager-Led Delegation

What & why. The hierarchical process introduces a manager agent that dynamically assigns tasks to team agents. Instead of fixed sequential order, the manager evaluates each task and selects the best agent to execute it. This enables more flexible workflows where task assignment depends on content rather than position. The manager uses an LLM to make delegation decisions, adding intelligence to the orchestration layer.

from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Researcher",
    goal="Gather accurate information",
    backstory="You are an expert researcher.",
)

writer = Agent(
    role="Writer",
    goal="Create engaging content",
    backstory="You are a skilled writer.",
)

analyst = Agent(
    role="Analyst",
    goal="Provide data-driven insights",
    backstory="You are a data analyst.",
)

# Hierarchical process: manager assigns tasks dynamically
t1 = Task(
    description="Research the competitive landscape",
    expected_output="Competitor analysis with data",
    agent=researcher,
)

t2 = Task(
    description="Analyze market trends from the research",
    expected_output="Trend analysis with metrics",
    agent=analyst,
)

t3 = Task(
    description="Write an executive brief based on all findings",
    expected_output="Polished executive brief",
    agent=writer,
)

crew = Crew(
    agents=[researcher, writer, analyst],
    tasks=[t1, t2, t3],
    process=Process.hierarchical,
    manager_llm="gpt-4o",  # LLM for the manager agent
    verbose=True,
)

result = crew.kickoff()
Where you'll use itHierarchical process is ideal when task assignment should be dynamic: the manager can re-route if an agent struggles, assign follow-up tasks based on intermediate results, or parallelize independent work across agents.
Under the hoodCrewAI creates an internal manager agent that receives all pending tasks and available agents. The manager LLM evaluates each task's requirements against each agent's role description and selects the best match. This adds one extra LLM call per task assignment decision.

14Pydantic Expected Output Models

What & why. Instead of free-form text expected_output, you can pass a Pydantic model class as the expected_output parameter. CrewAI will instruct the agent to produce JSON matching that schema and will parse the output into a validated Pydantic object. This eliminates string parsing and ensures type-safe, structured results. Use Pydantic v2 models for schema validation and automatic field coercion.

from pydantic import BaseModel, Field
from crewai import Agent, Task, Crew, Process

class CompetitorAnalysis(BaseModel):
    competitor: str = Field(description="Competitor name")
    pricing: str = Field(description="Pricing model summary")
    strengths: list[str] = Field(description="Top 3 strengths")
    weaknesses: list[str] = Field(description="Top 3 weaknesses")
    threat_level: str = Field(description="Low, Medium, or High")

analyst = Agent(
    role="Competitive Analyst",
    goal="Produce structured competitor analysis",
    backstory="You are a market analyst.",
)

task = Task(
    description="Analyze competitor: {competitor_name}",
    expected_output=CompetitorAnalysis,  # Pydantic model, not string
    agent=analyst,
)

crew = Crew(
    agents=[analyst],
    tasks=[task],
    process=Process.sequential,
)

result = crew.kickoff()

# Output is a validated Pydantic object
analysis = result.tasks_output[0].pydantic
print(f"Competitor: {analysis.competitor}")
print(f"Threat: {analysis.threat_level}")
print(f"Strengths: {analysis.strengths}")
Where you'll use itPydantic outputs are essential for downstream automation: when the output feeds into databases, APIs, or other code that requires typed data. Use them for any task where the output has a predictable structure.
Under the hoodCrewAI adds the Pydantic model's JSON schema to the agent's system prompt. After the LLM generates a response, CrewAI parses the JSON and validates it against the model. Validation failures trigger a retry with an error message appended to the prompt.

15Callbacks on Task Completion

What & why. CrewAI supports callback functions that fire when a task completes or when the crew finishes. Callbacks enable side effects without modifying agent logic: logging results, sending notifications, storing outputs in databases, or triggering downstream processes. You can set callbacks at the task level (per-task) or crew level (on crew completion).

import json
from crewai import Agent, Task, Crew, Process

def on_task_complete(task_output):
    """Fires after each task completes."""
    print(f"Task completed: {task_output.description[:50]}")
    print(f"Output length: {len(task_output.raw)} chars")
    # Write to log file, send notification, etc.
    with open("task_log.jsonl", "a") as f:
        f.write(json.dumps({
            "task": task_output.description[:100],
            "output_preview": task_output.raw[:200],
        }) + "\n")

def on_crew_complete(crew_output):
    """Fires after the entire crew finishes."""
    print(f"Crew finished. Total tokens: {crew_output.token_usage}")

agent = Agent(
    role="Writer", goal="Write content", backstory="You write."
)

task = Task(
    description="Write a 100-word summary of AI agents",
    expected_output="100-word summary",
    agent=agent,
    callback=on_task_complete,  # Per-task callback
)

crew = Crew(
    agents=[agent],
    tasks=[task],
    process=Process.sequential,
)

result = crew.kickoff()
on_crew_complete(result)
Where you'll use itCallbacks are the primary mechanism for integrating CrewAI into larger systems: write results to a database, update a dashboard, trigger a deployment, or send a Slack notification when the crew completes.
Under the hoodCallbacks are simple Python callables that receive the TaskOutput or CrewOutput object. CrewAI calls them synchronously after the respective completion event. Callbacks run in the main thread and can raise exceptions to halt execution.

16Crew Memory: Short-Term, Long-Term, and Entity

What & why. CrewAI provides three memory layers that persist across crew runs. Short-term memory stores conversation context within a single run. 23CrewAI Flows: @start and @listen Event Graphs

What & why. Flows are CrewAI's event-driven orchestration layer. A Flow is a class where methods decorated with @start run on kickoff, and methods decorated with @listen fire when their specified upstream method completes. This creates a directed event graph where data flows between methods via return values. Flows wrap Crews, giving you event-driven control over when and how crews execute.

from crewai import Flow, listen, start, Crew, Agent, Task, Process

class ResearchFlow(Flow):
    @start()
    def gather_topic(self):
        return {"topic": "AI Agent Frameworks", "scope": "2025 landscape"}

    @listen(gather_topic)
    def run_research_crew(self, topic_data):
        researcher = Agent(
            role="Researcher", goal="Research thoroughly",
            backstory="You research AI trends.",
        )
        task = Task(
            description=f"Research: {topic_data['topic']}",
            expected_output="Structured research notes",
            agent=researcher,
        )
        crew = Crew(
            agents=[researcher], tasks=[task],
            process=Process.sequential,
        )
        result = crew.kickoff()
        return {"research": result.raw}

    @listen(run_research_crew)
    def publish(self, research_data):
        print(f"Publishing: {research_data['research'][:100]}...")
        return "Published"

flow = ResearchFlow()
result = flow.kickoff()
print(f"Flow result: {result}")
Where you'll use itFlows are ideal when you need branching logic, conditional crew execution, or event-driven architectures. Use them to build research pipelines that branch based on topic, approval workflows that pause for human input, or multi-stage processes where crew execution depends on upstream results.
Under the hoodFlows execute methods in topological order based on @listen dependencies. Return values from upstream methods are passed as arguments to downstream methods. The Flow class maintains internal state that persists across method calls within a single flow run.

24Flow State: Typed Persistence

What & why. Flows maintain typed state that persists across method executions within a single run. State is defined as a Pydantic BaseModel, and methods read and write to self.state. This eliminates the need to pass data through return values for shared state and makes the flow's data model explicit and inspectable.

25Router Conditions: Branching Flows

What & why. The @router decorator in Flows enables conditional branching based on method return values. A router method returns a string that maps to different downstream methods, allowing the flow to take different paths based on data analysis, classification results, or approval decisions. This turns linear flows into dynamic decision trees.

from crewai import Flow, listen, router, start, Crew, Agent, Task, Process

        return "handle_general"

27Custom Tools: BaseTool and Function Tools

What & why. CrewAI supports two approaches to custom tools: function tools (decorating a Python function with @tool) and class-based tools (subclassing BaseTool). Function tools are simpler for straightforward operations; class-based tools provide more control over the tool's schema, validation, and execution logic. Both approaches produce LangChain-compatible tools that agents can use during task execution.

from crewai.tools import tool, BaseTool
from pydantic import BaseModel, Field

# Function-based tool (simpler)
@tool("calculate")
def calculate(expression: str) -> str:
    """Evaluate a mathematical expression safely."""
    allowed = set("0123456789+-*/.() ")
    if not all(c in allowed for c in expression):
        return "Error: invalid characters in expression"
    try:
        result = eval(expression)  # Safe due to character filter
        return f"Result: {result}"
    except Exception as e:
        return f"Error: {e}"

# Class-based tool (more control)
class DatabaseQuery(BaseTool):
    name: str = "database_query"
    description: str = "Query the company database for customer information"

    def _run(self, query: str) -> str:
        # Custom logic with validation, logging, etc.
        return f"Query results for: {query}"

31Cost Tracking Per Crew Run

What & why. CrewAI's CrewOutput object includes token_usage data that tracks input and output tokens across all LLM calls in a crew run. By combining token counts with model pricing, you can calculate exact costs per crew execution. This is essential for budgeting, cost optimization, and billing in production systems.

from crewai import Agent, Task, Crew, Process

# Pricing per 1M tokens (as of 2025)
PRICING = {
    "gpt-4o": {"input": 2.50, "output": 10.00},
    "gpt-4o-mini": {"input": 0.15, "output": 0.60},
}

def calculate_cost(token_usage, model="gpt-4o"):
    """Calculate crew run cost from token usage."""
    if not token_usage:
        return 0.0
    input_cost = (token_usage.get("prompt_tokens", 0) / 1_000_000) * PRICING[model]["input"]
    output_cost = (token_usage.get("completion_tokens", 0) / 1_000_000) * PRICING[model]["output"]
    return input_cost + output_cost

agent = Agent(
    role="Analyst", goal="Analyze", backstory="You analyze.",
    llm="gpt-4o",
)

task = Task(

32Enterprise Patterns: Queue-Triggered Crews

What & why. In production, crews are triggered by events: messages on a queue, webhooks, scheduled intervals, or user actions. The queue-triggered pattern decouples crew execution from request handling. A message queue (Redis, RabbitMQ, SQS) receives job requests, a worker process picks them up and executes the appropriate crew, and results are published back to a response queue or database. This provides scalability, retry-on-failure, and separation of concerns.

import json
import redis
from crewai import Agent, Task, Crew, Process

r = redis.Redis(host="localhost", port=6379, db=0)

def process_job(job_data):
    """Execute crew based on job specification."""
    topic = job_data["topic"]
    agent = Agent(
        role="Researcher",
        goal=f"Research {topic}",
        backstory="You are a research specialist.",
    )
    task = Task(
        description=f"Research: {topic}",
        expected_output="Research summary",
        agent=agent,
    )
    crew = Crew(
        agents=[agent], tasks=[task],
        process=Process.sequential,
    )
    result = crew.kickoff()
    return {"status": "complete", "result": result.raw}

# Worker loop: poll queue and execute crews
while True:
    _, job_raw = r.brpop("crew_jobs")
    job = json.loads(job_raw)
    try:
        output = process_job(job)
        r.hset(f"job:{job['id']}", mapping=output)
    except Exception as e:
        r.hset(f"job:{job['id']}", "error", str(e))
Where you'll use itQueue-triggered crews are the standard production pattern. They enable horizontal scaling (multiple workers), job prioritization, retry logic, and monitoring. Use this for any CrewAI deployment that handles concurrent requests.
Under the hoodThe queue acts as a buffer between request producers and crew execution workers. Workers can run on separate machines, enabling horizontal scaling. Job results are stored in a database (Redis, PostgreSQL) for retrieval by the requesting system.

33Idempotent Reruns and Checkpoint Store

What & why. Crew execution can fail mid-run due to API timeouts, process crashes, or rate limits. Idempotent reruns ensure that re-executing a failed crew produces the same result without duplicating work. CrewAI's memory system provides basic checkpointing; for production, implement explicit checkpoint storage that records completed tasks and their outputs. On rerun, skip completed tasks and resume from the last checkpoint.

import json
import hashlib
from crewai import Agent, Task, Crew, Process

class CheckpointStore:
    def __init__(self, path="checkpoints.json"):
        self.path = path
        self.store = self._load()

    def _load(self):
        try:
            with open(self.path) as f:
                return json.load(f)
        except FileNotFoundError:
            return {}

    def _save(self):
        with open(self.path, "w") as f:
            json.dump(self.store, f)

    def get_completed(self, crew_id, task_desc):
        key = f"{crew_id}:{hashlib.md5(task_desc.encode()).hexdigest()}"
        return self.store.get(key)

    def mark_completed(self, crew_id, task_desc, output):
        key = f"{crew_id}:{hashlib.md5(task_desc.encode()).hexdigest()}"
        self.store[key] = output
        self._save()

store = CheckpointStore()
crew_id = "research-001"

agent = Agent(
    role="Researcher", goal="Research", backstory="You research.",
)

task_desc = "Research AI trends 2025"
task = Task(
    description=task_desc,
    expected_output="Research notes",
    agent=agent,
)

# Check if already completed
existing = store.get_completed(crew_id, task_desc)
if existing:
    print(f"Using cached result: {existing[:50]}")
else:
    crew = Crew(
        agents=[agent], tasks=[task],
        process=Process.sequential,
    )
    result = crew.kickoff()
    store.mark_completed(crew_id, task_desc, result.raw)
    print(f"New result stored: {result.raw[:50]}")
Where you'll use itIdempotent reruns are critical for reliability. In production, crews will fail and need to be restarted. Without checkpointing, you restart from scratch and waste tokens. With checkpoints, you resume from the last successful task.
Under the hoodA checkpoint store maps (crew_id, task_hash) to completed task outputs. Before executing each task, the crew checks the store. If the task is already completed, its output is used directly. This eliminates redundant LLM calls and ensures deterministic reruns.

34Security: Tool Credential Vaulting

What & why. Agents with tools need API keys, tokens, and credentials. Hardcoding these in agent definitions is a security risk. Credential vaulting stores secrets in a dedicated vault (AWS Secrets Manager, HashiCorp Vault, environment variables) and injects them at runtime. CrewAI tools should accept credentials as constructor parameters rather than reading from environment variables directly, enabling per-deployment credential management.

import os
from crewai import Agent, Task, Crew, Process
from crewai_tools import SerperDevTool

class CredentialVault:
    """Simple vault backed by environment variables.

    @staticmethod
    def get(secret_name):
        value = os.environ.get(secret_name)
        if not value:

Where you'll use itCredential vaulting is mandatory for any production CrewAI deployment. Never commit API keys to source code. Use vaulting to inject secrets at runtime and rotate them without code changes.
Under the hoodThe vault pattern separates secret storage from application code. In production, secrets are fetched from a vault service at startup or per-request. Environment variables are a simple vault; cloud-managed vaults add encryption, access control, and audit logging.

36Scaling: Concurrency and Worker Pools

What & why. CrewAI crews are CPU and API-bound. Scaling requires running multiple crews concurrently via worker pools. Each worker process handles one crew execution, and a pool of workers processes the job queue. For API-bound workloads (most CrewAI use cases), the bottleneck is LLM API rate limits, not CPU. Scale by increasing max_rpm and adding workers, or by using multiple API keys for load distribution.

import asyncio
from concurrent.futures import ProcessPoolExecutor
from crewai import Agent, Task, Crew, Process

def run_crew(topic):
    """Run a crew for a single topic (must be top-level for pickling)."""
    agent = Agent(
        role="Researcher",
        goal=f"Research {topic}",
        backstory="You are a researcher.",
    )
    task = Task(
        description=f"Research: {topic}",
        expected_output="Research summary",
        agent=agent,
    )
    crew = Crew(
        agents=[agent], tasks=[task],
        process=Process.sequential,
        max_rpm=20,
    )
    result = crew.kickoff()
    return {"topic": topic, "result": result.raw}

topics = ["AI Agents", "RAG Systems", "Fine-Tuning", "Embeddings", "Guardrails"]

# Process 3 crews concurrently

    futures = {executor.submit(run_crew, t): t for t in topics}
    for future in futures:
        result = future.result()
        print(f"Completed: {result['topic']}")
Where you'll use itWorker pools enable horizontal scaling of CrewAI executions. For production, use a task queue (Celery, RQ, or cloud-native) with auto-scaling workers. Match worker count to your LLM API rate limit budget.
Under the hoodCrewAI crews are stateless between runs, making them safe for concurrent execution. Each worker creates its own agent instances, LLM connections, and memory stores. The only shared resource is the LLM API rate limit.

38Migration: Crews to Flows Guidance

What & why. As CrewAI applications grow, migrating from pure Crew execution to Flow-based orchestration becomes necessary. Flows provide event-driven control, typed state, conditional routing, and better observability. The migration path: extract each crew into a Flow method, replace return-value passing with typed state, add routers for conditional logic, and implement callbacks for side effects. Crews remain the execution unit; Flows become the coordination layer.

Under the hoodThe migration is additive, not destructive. Flows wrap existing Crew logic in methods. The Crew's internal execution remains unchanged. What changes is the orchestration layer: Flows add state management, routing, and event handling on top of Crew execution.
