1Three Pillars Applied to GenAI: Traces, Logs, Metrics

What & why. Observability rests on three pillars: traces (structured records of a single request flowing through components), logs (timestamped event records), and metrics (numeric measurements aggregated over time). For GenAI systems, traces capture the full LLM call chain, logs record individual completions and errors, and metrics track token usage, latency, and cost in real time.

# Three pillars in a single LLM call
import logging, time

logger = logging.getLogger("genai")

def call_llm(prompt: str) -> dict:
    start = time.perf_counter()

    # TRACE: spans for each step
    with tracer.start_as_current_span("llm.request") as span:
        span.set_attribute("model", "gpt-4o")
        span.set_attribute("prompt_tokens", count_tokens(prompt))

        response = client.chat.completions.create(
            model="gpt-4o",
            messages=[{"role": "user", "content": prompt}]
        )

        span.set_attribute("completion_tokens",
                           response.usage.completion_tokens)
        span.set_attribute("total_tokens",
                           response.usage.total_tokens)
        span.set_attribute("latency_ms",
                           (time.perf_counter() - start) * 1000)

    # LOG: structured event
    logger.info("llm.completed", extra={
        "model": "gpt-4o",
        "tokens": response.usage.total_tokens,
        "latency_ms": (time.perf_counter() - start) * 1000,
    })

    # METRIC: aggregated for dashboards
    llm_tokens_counter.add(response.usage.total_tokens)
    llm_latency_histogram.record(time.perf_counter() - start)
    return response
Where you'll use itEvery production LLM application needs all three pillars. Traces debug individual failures, logs provide audit trails, and metrics drive alerts and capacity planning.
Under the hoodThe three pillars are complementary, not interchangeable. A metric tells you "P95 latency is 3 seconds." A trace tells you "this specific request spent 2.8 seconds in the retrieval step." A log tells you "this request failed with a timeout error."

2Span Hierarchy: Trace, Chain, LLM, Tool

What & why. A trace is a tree of spans representing a request's journey through your system. The root span represents the entire request. Child spans represent sub-operations: a chain (orchestration logic), an LLM call (model invocation), or a tool call (API lookup, database query). This hierarchy lets you pinpoint exactly where time is spent and where errors occur.

from opentelemetry import trace

tracer = trace.get_tracer("my-rag-app")

def rag_query(question: str) -> str:
    # Root span: entire RAG query
    with tracer.start_as_current_span("rag.query") as root:
        root.set_attribute("question", question[:100])

        # Child span: retrieval
        with tracer.start_as_current_span("rag.retrieve") as retriever:
            docs = vector_store.similarity_search(question, k=5)
            retriever.set_attribute("docs_found", len(docs))

        # Child span: LLM generation
        with tracer.start_as_current_span("rag.generate") as gen:
            gen.set_attribute("model", "gpt-4o")
            gen.set_attribute("context_docs", len(docs))
            response = client.chat.completions.create(
                model="gpt-4o",
                messages=[{
                    "role": "system",
                    "content": f"Answer based on: {format_docs(docs)}"
                }, {
                    "role": "user",
                    "content": question
                }]
            )
            gen.set_attribute("completion_tokens",
                              response.usage.completion_tokens)

        # Child span: post-processing
        with tracer.start_as_current_span("rag.postprocess") as post:
            citations = extract_citations(response, docs)
            post.set_attribute("citations_found", len(citations))

    return response.choices[0].message.content
Where you'll use itSpan hierarchy is the primary debugging tool for multi-step LLM systems. When a RAG query is slow, the span tree shows whether the bottleneck is retrieval, generation, or post-processing.
Under the hoodEach span carries a unique trace ID (shared across the whole request) and a span ID (unique to that operation). Parent-child relationships are encoded via parent_span_id, forming the tree.

3OpenTelemetry Concepts: Tracer, Span, Context

What & why. OpenTelemetry (OTel) is the vendor-neutral standard for generating and exporting telemetry data. A Tracer creates spans, a Span represents a unit of work, and Context Propagation ensures spans from different services are linked into a single trace. OTel's SDK handles sampling, batching, and export to any backend (Jaeger, Zipkin, Datadog, Grafana Tempo).

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import (
    OTLPSpanExporter
)

# Set up OTel SDK
provider = TracerProvider()
processor = BatchSpanProcessor(
    OTLPSpanExporter(endpoint="http://otel-collector:4317")
)
provider.add_span_processor(processor)
trace.set_tracer_provider(provider)

# Get a tracer and create spans
tracer = trace.get_tracer("my-app", "1.0.0")

def process_request(request_id: str, query: str):
    with tracer.start_as_current_span(
        "process_request",
        attributes={"request.id": request_id}
    ) as span:
        # Context automatically propagated to child spans
        result = call_llm(query)
        span.set_attribute("result.length", len(result))
        return result

# Sampling: only trace 10% of requests in production
from opentelemetry.sdk.trace.sampling import TraceIdRatioBased
sampler = TraceIdRatioBased(0.1)
provider = TracerProvider(sampler=sampler)
Where you'll use itOTel is the standard for instrumenting production systems. Its vendor neutrality means you can switch backends (from Jaeger to Datadog) without changing application code.
Under the hoodBatchSpanProcessor buffers spans in memory and exports them in batches, minimizing performance overhead. The default batch size is 512 spans or 5 seconds, whichever comes first.

4Langfuse Quickstart: Decorator-Based Observability

What & why. Langfuse is a purpose-built observability platform for LLM applications. Its Python SDK uses decorators to automatically capture function calls, LLM invocations, token usage, costs, and user feedback. Unlike raw OTel, Langfuse understands LLM-specific concepts like generations, embeddings, and prompt management.

from langfuse import Langfuse
from langfuse.decorators import observe, langfuse_context

langfuse = Langfuse(
    public_key="pk-lf-...",
    secret_key="sk-lf-...",
    host="https://cloud.langfuse.com"
)

@observe(as_type="generation")
def call_llm(messages, model="gpt-4o"):
    response = client.chat.completions.create(
        model=model,
        messages=messages
    )
    # Langfuse auto-captures: model, tokens, cost, latency
    return response.choices[0].message.content

@observe()  # creates a span in the trace
def answer_question(question: str) -> str:
    docs = retrieve(question)
    answer = call_llm(
        messages=[{
            "role": "system",
            "content": f"Use this context: {docs}"
        }, {
            "role": "user",
            "content": question
        }]
    )
    return answer

# Usage: automatic tracing
@observe()
def handle_request(user_id: str, question: str):
    answer = answer_question(question)
    # Attach user feedback
    langfuse_context.score_current_trace(
        name="user_feedback",
        value=1,  # thumbs up
        comment="Helpful answer"
    )
    return answer
Where you'll use itLangfuse is the fastest path to production-grade LLM observability. The decorator pattern requires minimal code changes and captures more detail than manual OTel instrumentation.
Under the hoodLangfuse's @observe decorator wraps functions with OTel-compatible spans. The as_type="generation" parameter tells Langfuse to treat the span as an LLM call, enabling model-specific metadata capture.

5Capturing Prompts, Completions, Tokens, and Cost

What & why. The core value of LLM observability is capturing what was sent to the model, what came back, how many tokens were consumed, and what it cost. This data enables debugging (what went wrong?), optimization (where are tokens wasted?), and chargeback (which feature consumed $X?).

import litellm
from dataclasses import dataclass, field

@dataclass
class LLMCallRecord:
    model: str
    messages: list[dict]
    response: str
    prompt_tokens: int
    completion_tokens: int
    total_tokens: int
    cost_usd: float
    latency_ms: float
    metadata: dict = field(default_factory=dict)

def tracked_llm_call(model: str, messages: list[dict],
                     **kwargs) -> LLMCallRecord:
    import time
    start = time.perf_counter()

    response = client.chat.completions.create(
        model=model, messages=messages, **kwargs
    )

    latency_ms = (time.perf_counter() - start) * 1000
    usage = response.usage

    # litellm provides cost calculation
    cost = litellm.completion_cost(
        model=model,
        prompt_tokens=usage.prompt_tokens,
        completion_tokens=usage.completion_tokens,
    )

    record = LLMCallRecord(
        model=model,
        messages=messages,
        response=response.choices[0].message.content,
        prompt_tokens=usage.prompt_tokens,
        completion_tokens=usage.completion_tokens,
        total_tokens=usage.total_tokens,
        cost_usd=cost,
        latency_ms=latency_ms,
    )

    # Send to observability backend
    langfuse.trace(
        name="llm_call",
        input=messages,
        output=record.response,
        model=model,
        usage={
            "promptTokens": usage.prompt_tokens,
            "completionTokens": usage.completion_tokens,
        },
        metadata={"cost_usd": cost, "latency_ms": latency_ms},
    )
    return record
Where you'll use itToken and cost tracking per call is essential for per-feature and per-tenant cost attribution. Without it, your monthly bill is a single number with no visibility into which features drove the cost.
Under the hoodlitellm.completion_cost uses published provider pricing tables. It handles model-specific pricing tiers (input vs. output tokens, context window pricing) automatically.

6Latency Waterfall Reading

What & why. A latency waterfall chart shows how a single request's time is distributed across components. For a RAG query, you can see that 60% of time was in vector search, 30% in LLM generation, and 10% in post-processing. This immediately identifies optimization targets â€” improving the slowest component has the highest impact.

import time
from dataclasses import dataclass

@dataclass
class SpanTiming:
    name: str
    start: float
    end: float
    children: list["SpanTiming"] = None

    @property
    def duration_ms(self) -> float:
        return (self.end - self.start) * 1000

def build_waterfall(spans: list[SpanTiming]) -> str:
    """Render a text-based latency waterfall."""
    total = spans[0].duration_ms
    lines = []
    for span in sorted(spans, key=lambda s: s.start):
        pct = (span.duration_ms / total) * 100
        bar = "#" * int(pct / 2)
        lines.append(
            f"  {span.name:<30s} {span.duration_ms:6.1f}ms "
            f"({pct:4.1f}%) {bar}"
        )
    return "\n".join(lines)

def trace_rag_query(question: str):
    spans = []
    t0 = time.perf_counter()

    with Timer("total", spans, t0):
        with Timer("retrieve", spans, t0):
            docs = vector_store.search(question)
        with Timer("generate", spans, t0):
            response = call_llm(question, docs)
        with Timer("postprocess", spans, t0):
            citations = extract_citations(response, docs)

    print(build_waterfall(spans))
    #   total                          2450.3ms (100.0%) ######################################
    #   retrieve                        980.1ms ( 40.0%) ################################
    #   generate                       1225.2ms ( 50.0%) ####################################
    #   postprocess                     245.0ms ( 10.0%) ####

class Timer:
    def __init__(self, name, spans, t0):
        self.name = name
        self.spans = spans
        self.t0 = t0
    def __enter__(self):
        self.start = time.perf_counter()
        return self
    def __exit__(self, *args):
        self.spans.append(SpanTiming(
            self.name, self.start, time.perf_counter()
        ))
Where you'll use itLatency waterfalls are the first thing to check when users report slowness. A waterfall that shows 80% of time in one component narrows the investigation immediately.
Under the hoodIn production, span timings are captured by OTel and rendered in trace viewers (Jaeger, Grafana Tempo, Langfuse). The text-based waterfall above is for local development debugging.

7Error Spans and Exception Recording

What & why. When an LLM call fails (rate limit, timeout, invalid response), the error must be recorded on the span with the exception type, message, and stack trace. This makes failures searchable and aggregateable: you can query "show me all timeout errors in the last hour" and get the full context.

from opentelemetry import trace
from opentelemetry.trace import StatusCode
import httpx

tracer = trace.get_tracer("llm-calls")

def call_llm_with_error_handling(prompt: str) -> str:
    with tracer.start_as_current_span("llm.call") as span:
        span.set_attribute("model", "gpt-4o")
        try:
            response = client.chat.completions.create(
                model="gpt-4o",
                messages=[{"role": "user", "content": prompt}],
                timeout=30.0,
            )
            span.set_status(StatusCode.OK)
            return response.choices[0].message.content

        except httpx.TimeoutException as e:
            span.set_status(StatusCode.ERROR, "Timeout")
            span.record_exception(e, attributes={
                "error.type": "timeout",
                "timeout.seconds": 30,
                "prompt_preview": prompt[:100],
            })
            # Fallback to smaller model
            return call_llm_fallback(prompt)

        except Exception as e:
            span.set_status(StatusCode.ERROR, str(e)[:200])
            span.record_exception(e, attributes={
                "error.type": type(e).__name__,
                "prompt_preview": prompt[:100],
            })
            raise
Where you'll use itError spans with exception recording enable "show me all errors for model X in the last 24 hours" queries. Without structured error recording, debugging production failures means grepping log files.
Under the hoodspan.record_exception() creates a span event with the exception details. These events are indexed by most trace backends, enabling faceted error analysis by type, model, and endpoint.

8Session Grouping: Tracking User Journeys

What & why. A single user interaction may involve multiple LLM calls: a clarifying question, a retrieval step, a generation, a self-critique, and a final answer. Session grouping links these into a single user journey using a session_id or user_id tag. This enables per-user debugging and journey-level metrics.

from langfuse import Langfuse
import uuid

langfuse = Langfuse()

def start_session(user_id: str) -> str:
    """Create a session ID linking all interactions."""
    return f"{user_id}:{uuid.uuid4().hex[:8]}"

def handle_conversation_turn(session_id: str, user_message: str):
    with langfuse.trace(
        name="conversation_turn",
        session_id=session_id,
        user_id=session_id.split(":")[0],
        tags=["conversation"],
    ) as trace:
        # Step 1: Classify intent
        intent = classify_intent(user_message)
        trace.span(
            name="intent_classification",
            output=intent,
            metadata={"intent": intent}
        )

        # Step 2: Retrieve context
        docs = retrieve_docs(user_message, intent)
        trace.span(
            name="retrieval",
            output=f"{len(docs)} documents",
            metadata={"doc_count": len(docs)}
        )

        # Step 3: Generate response
        response = generate_response(user_message, docs, intent)
        trace.generation(
            name="response_generation",
            model="gpt-4o",
            input=user_message,
            output=response,
        )

        return response

# Track full user session
session = start_session("user-123")
handle_conversation_turn(session, "How do I reset my password?")
handle_conversation_turn(session, "And what about 2FA?")
handle_conversation_turn(session, "Thanks, that worked!")
Where you'll use itSession grouping reveals multi-turn failure patterns: the first turn succeeds, but the third turn fails because context was lost. Without sessions, each turn appears as an isolated, passing interaction.
Under the hoodSession IDs are propagated through HTTP headers (X-Session-ID) or embedded in context objects. OTel uses baggage propagation for cross-service session linking.

10Sampling Strategies: What to Record

What & why. Recording every trace at full detail is expensive and noisy. Sampling strategies determine which traces to record and at what fidelity. Common strategies: head-based (decide at trace start), tail-based (decide after completion, keeping errors and slow traces), and adaptive (adjust rate based on traffic volume).

from opentelemetry.sdk.trace.sampling import (
    TraceIdRatioBased, ParentBasedTraceIdRatio
)

# Strategy 1: Head-based â€” sample 10% at trace start
sampler = TraceIdRatioBased(0.1)

# Strategy 2: Parent-based â€” respect parent's sampling decision
sampler = ParentBasedTraceIdRatio(rate=0.1)

# Strategy 3: Tail-based â€” implemented at collector level
# Keep: all errors, slow requests, random 5% of successes
TAIL_SAMPLING_CONFIG = {
    "policies": [
        {"name": "errors", "type": "status_code",
         "status_code": {"status_codes": ["ERROR"]}},
        {"name": "slow", "type": "latency",
         "latency": {"threshold_ms": 5000}},
        {"name": "random", "type": "probabilistic",
         "probabilistic": {"sampling_percentage": 5}},
    ]
}

# Strategy 4: Event-based â€” always sample important events
def should_sample(span) -> bool:
    if span.attributes.get("error"):
        return True  # always keep errors
    if span.attributes.get("latency_ms", 0) > 5000:
        return True  # always keep slow requests
    if span.attributes.get("user_feedback") is not None:
        return True  # always keep feedback-tagged traces
    return hash(span.trace_id) % 100 < 5  # 5% random
Where you'll use itSampling is a cost-quality tradeoff. Too aggressive: you miss issues. Too conservative: you drown in data. Start at 10% and adjust based on error rate and investigation needs.
Under the hoodTail-based sampling is more powerful but requires a collector to buffer spans before deciding. Head-based sampling is simpler but may miss errors (a slow trace might be sampled out before the error occurs).

11PII in Traces: What to Capture and What to Mask

What & why. Traces capture full prompts and completions, which may contain PII: names, emails, phone numbers, medical information, financial data. GDPR, CCPA, and internal policies require PII handling. The approach is to capture structured metadata (model, tokens, latency) while masking or excluding PII from trace payloads.

import re

# PII patterns to mask
PII_PATTERNS = {
    "email": r'\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b',
    "phone": r'\b\d{3}[-.]?\d{3}[-.]?\d{4}\b',
    "nric": r'\b[STFG]\d{7}[A-Z]\b',
    "credit_card": r'\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b',
}

def mask_pii(text: str) -> str:
    masked = text
    for pii_type, pattern in PII_PATTERNS.items():
        masked = re.sub(pattern, f"[REDACTED_{pii_type.upper()}]", masked)
    return masked

def safe_span_attributes(messages, response_text):
    """Create span attributes with PII masked."""
    masked_messages = [
        {**msg, "content": mask_pii(msg["content"])}
        for msg in messages
    ]
    return {
        "input_preview": mask_pii(str(messages[-1]["content"]))[:200],
        "output_preview": mask_pii(response_text)[:200],
        "messages_count": len(messages),
        # Never log full messages in attributes â€” use span events
    }

# In Langfuse with PII redaction
langfuse = Langfuse(
    mask=lambda data: mask_pii(str(data)) if isinstance(data, str)
    else data
)
Where you'll use itPII masking is a compliance requirement, not a nice-to-have. Every organization handling user data must implement trace-level PII protection before shipping observability to production.
Under the hoodRegex-based masking catches common PII formats but misses unstructured PII (names, addresses without standard formats). For high-compliance environments, combine regex with NER-based PII detection.

16Streaming Observability: TTFT and TBT

What & why. Streaming LLM responses require specialized metrics: Time to First Token (TTFT) measures how long until the user sees the first character, and Time Between Tokens (TBT) measures the streaming cadence. import time

def stream_with_metrics(prompt: str):
    ttft = None
    tbt_values = []
    prev_time = None
    full_response = []

    start = time.perf_counter()

        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        stream=True,

            yield chunk.choices[0].delta.content

    avg_tbt = sum(tbt_values) / len(tbt_values) if tbt_values else 0
    p95_tbt = sorted(tbt_values)[int(len(tbt_values) * 0.95)] if tbt_values else 0

    # Record metrics
    ttft_histogram.record(ttft)
    tbt_histogram.record(avg_tbt)

17Async Context Propagation in asyncio Tasks

What & why. In async Python applications, OTel context does not automatically propagate across asyncio.create_task boundaries. Without explicit propagation, child tasks create orphaned spans not linked to the parent trace. The opentelemetry-context package handles this, but you must use the correct async patterns.

import asyncio
from opentelemetry import context, trace

tracer = trace.get_tracer("async-app")

async def process_item(item_id: str):
    # Manually capture context before spawning task
    ctx = context.get_current()

    async def _process():
        # Restore context in child task
        token = context.attach(ctx)
        try:
            with tracer.start_as_current_span(
                f"process_item.{item_id}"
            ) as span:
                result = await llm_call(item_id)
                span.set_attribute("item_id", item_id)
                return result
        finally:
            context.detach(token)

    return await asyncio.create_task(_process())

async def process_batch(items: list[str]):
    with tracer.start_as_current_span("process_batch") as span:
        span.set_attribute("batch_size", len(items))

        # All child tasks are linked to this trace
        tasks = [process_item(item_id) for item_id in items]
        results = await asyncio.gather(*tasks)

        span.set_attribute("completed", len(results))
        return results

# Usage
asyncio.run(process_batch(["item-1", "item-2", "item-3"]))

def track_red(model: str, endpoint: str = "chat"):
    def decorator(func):
        def wrapper(*args, **kwargs):
            start = time.perf_counter()
            try:
                result = func(*args, **kwargs)
                llm_requests_total.labels(
                    model=model, endpoint=endpoint, status="success"
                ).inc()
                return result

                    model=model, endpoint=endpoint, status="error"

                raise
            finally:

                llm_request_duration_seconds.labels(
                    model=model, endpoint=endpoint
                ).observe(duration)
        return wrapper
    return decorator

28SLO Burn Rate Alerts: Multi-Window Approach

What & why. SLO (Service Level Objective) burn rate measures how fast you're consuming your error budget. A burn rate of 2x means you're burning budget twice as fast as normal. Multi-window burn rate alerts use two time windows (short + long) to catch both sudden incidents and slow-burning degradations without false positives.

def calculate_burn_rate(success_rate, slo_target=0.99):
    """Calculate error budget burn rate."""
    error_rate = 1 - success_rate
    allowed_error_rate = 1 - slo_target
    if error_rate == 0:
        return 0
    return error_rate / allowed_error_rate

def multi_window_alert(burn_rates):
    """
    Multi-window burn rate alerting:
    - Short window (1h): fast-burning incidents
    - Long window (6h): slow-burning degradations
    """
    alerts = []

    # Fast burn: burn rate > 14.4x for 1 hour
    if (burn_rates["1h"] > 14.4 and
        burn_rates["6h"] > 1.0):
        alerts.append({
            "type": "fast_burn",
            "severity": "critical",
            "message": f"Fast burn: {burn_rates['1h']:.1f}x "
                       f"(1h), {burn_rates['6h']:.1f}x (6h)",
        })

    # Slow burn: burn rate > 3x for 6 hours
    if burn_rates["6h"] > 3.0:
        alerts.append({
            "type": "slow_burn",
            "severity": "warning",
            "message": f"Slow burn: {burn_rates['6h']:.1f}x "
                       f"(6h window)",
        })

    # Budget exhaustion estimate
    if burn_rates["6h"] > 0:
        budget_remaining_hours = 72 / burn_rates["6h"]
        alerts.append({
            "type": "budget_status",
            "severity": "info",
            "message": f"Error budget exhausts in "
                       f"~{budget_remaining_hours:.0f}h "
                       f"at current burn rate",
        })

    return alerts
Where you'll use itMulti-window burn rate alerts are the industry standard for SLO-based alerting (popularized by Google SRE). They dramatically reduce false positives compared to single-metric alerts.
Under the hoodThe 14.4x multiplier for the 1h window corresponds to a 5-minute error budget exhaustion in 1 hour. The 3x multiplier for 6h catches gradual degradations that single-window alerts miss.

29Anomaly Detection on Traffic Patterns

What & why. Anomaly detection identifies unusual patterns in LLM traffic: sudden token spikes (prompt injection attack), unexpected error surges (provider outage), or unusual latency patterns (model degradation). Statistical methods (moving average, Z-score, IQR) detect anomalies without requiring labeled training data.

import numpy as np
from collections import deque

class AnomalyDetector:
    def __init__(self, window_size=100, threshold=3.0):
        self.window = deque(maxlen=window_size)
        self.threshold = threshold

    def update(self, value: float) -> dict:
        self.window.append(value)
        if len(self.window) < 20:
            return {"anomaly": False, "reason": "insufficient_data"}

        values = np.array(self.window)
        mean = np.mean(values)
        std = np.std(values)

        if std == 0:
            return {"anomaly": False, "reason": "zero_variance"}

        z_score = (value - mean) / std
        is_anomaly = abs(z_score) > self.threshold

        return {
            "anomaly": is_anomaly,
            "z_score": float(z_score),
            "value": value,

def reconstruct_agent_run(trace_id: str, spans: list[dict]):

TBD1Anomaly Detection on Traffic Patterns

What & why. Anomaly detection identifies unusual patterns in LLM traffic: sudden token spikes (prompt injection), unexpected error surges (provider outage), or unusual latency patterns. Statistical methods (Z-score, IQR) detect anomalies without labeled training data.

import numpy as np
from collections import deque

class AnomalyDetector:
    def __init__(self, window_size=100, threshold=3.0):
        self.window = deque(maxlen=window_size)
        self.threshold = threshold

    def update(self, value):
        self.window.append(value)
        if len(self.window) < 20:
            return {"anomaly": False}
        values = np.array(self.window)
        z_score = (value - np.mean(values)) / np.std(values)
        return {"anomaly": abs(z_score) > self.threshold,
                "z_score": float(z_score)}

33Economics of Telemetry: Volume vs Insight

What & why. More telemetry is not always better. Every additional span, attribute, and log line has a cost: collector processing, network bandwidth, storage, and query performance. The economics of telemetry require balancing insight granularity against operational cost, finding the point of diminishing returns.

def telemetry_cost_model(
    requests_per_day: int,
    spans_per_request: int,
    avg_span_size_bytes: int,
    sampling_rate: float,
    retention_days: int,
    storage_cost_per_gb: float = 0.023,
):
    daily_spans = requests_per_day * spans_per_request
    sampled_spans = daily_spans * sampling_rate
    daily_bytes = sampled_spans * avg_span_size_bytes
    daily_gb = daily_bytes / (1024**3)
    monthly_cost = daily_gb * retention_days * storage_cost_per_gb

    # Collector cost (estimated CPU)
    collector_cpu_millis = sampled_spans * 0.01  # 0.01ms per span
    collector_cost_monthly = collector_cpu_millis / 1000 * 730 * 0.04

    total = monthly_cost + collector_cost_monthly
    cost_per_request = total / (requests_per_day * 30)

    return {
        "daily_spans": daily_spans,
        "sampled_spans": sampled_spans,
        "storage_monthly_usd": monthly_cost,
        "collector_monthly_usd": collector_cost_monthly,
        "total_monthly_usd": total,
        "cost_per_request": cost_per_request,
    }

# Example: 10K requests/day, 5 spans/request, 2KB/span, 10% sampling

35Trace-Driven Auto-Optimization Loops

What & why. Use trace data to automatically optimize LLM system behavior: route slow queries to faster models, cache frequent prompts, adjust timeouts based on observed latency distributions, and trigger prompt optimization when quality scores drop. This creates a self-improving system that gets faster and cheaper over time.

class AutoOptimizer:
    def __init__(self, traces, config):
        self.traces = traces
        self.config = config

    def analyze_and_optimize(self):
        optimizations = []

        # 1. Route slow queries to faster model
        slow_queries = self._find_slow_queries(threshold_ms=5000)
        if slow_queries:
            optimizations.append({
                "type": "routing",
                "action": "redirect_to_fast_model",
                "queries": slow_queries,
                "estimated_savings_ms": sum(
                    q["latency_ms"] for q in slow_queries
                ) * 0.6,
            })

        # 2. Cache frequent prompts
        frequent = self._find_frequent_prompts(min_count=10)
        for prompt_pattern in frequent:
            optimizations.append({
                "type": "caching",
                "action": "add_to_cache",
                "pattern": prompt_pattern["pattern"],
                "estimated_savings_calls": prompt_pattern["count"],
            })

        # 3. Adjust timeouts based on P99
        p99_latency = self._calculate_p99_latency()
        if p99_latency > self.config.current_timeout * 0.8:
            new_timeout = p99_latency * 1.5
            optimizations.append({
                "type": "timeout",
                "action": "increase_timeout",
                "from": self.config.current_timeout,
                "to": new_timeout,
            })

        return optimizations

    def _find_slow_queries(self, threshold_ms):
        return [t for t in self.traces
                if t["latency_ms"] > threshold_ms]

    def _find_frequent_prompts(self, min_count):
        from collections import Counter
        patterns = Counter(
            t["prompt_pattern"] for t in self.traces
        )
        return [{"pattern": p, "count": c}
                for p, c in patterns.items() if c >= min_count]

    def _calculate_p99_latency(self):
        latencies = sorted(t["latency_ms"] for t in self.traces)
        return latencies[int(len(latencies) * 0.99)]
Where you'll use itAuto-optimization transforms observability from reactive (debugging) to proactive (improving). Each optimization is logged and its impact measured, creating a virtuous cycle.
Under the hoodAuto-optimization requires guardrails: never auto-optimize without human approval for high-risk changes (model routing), but do auto-optimize low-risk changes (caching, timeout adjustments).

What & why. Chaos observability combines chaos engineering (injecting failures) with observability (measuring the system's response). By deliberately failing components â€” killing a model provider, introducing latency, corrupting responses â€” and observing the trace data, you verify that fallback mechanisms, circuit breakers, and retry logic actually work.

import random, time

class ChaosInjector:
    def __init__(self):
        self.scenarios = {
            "provider_timeout": self._inject_timeout,
            "provider_error": self._inject_error,
            "high_latency": self._inject_latency,
            "partial_response": self._inject_partial,
        }

    def _inject_timeout(self, call_fn, *args, **kwargs):
        time.sleep(10)  # simulate timeout
        raise TimeoutError("Simulated provider timeout")

    def _inject_error(self, call_fn, *args, **kwargs):
        raise Exception("Simulated provider 500 error")

    def _inject_latency(self, call_fn, *args, **kwargs):
        time.sleep(2)  # add 2s latency
        return call_fn(*args, **kwargs)

    def _inject_partial(self, call_fn, *args, **kwargs):
        return None  # simulate empty response

    def run_chaos_test(self, scenario, system_fn, expected_fallback):
        injector = self.scenarios[scenario]
        start = time.perf_counter()
        try:
            result = injector(system_fn)
            latency = (time.perf_counter() - start) * 1000
            fallback_triggered = result == expected_fallback
            return {
                "scenario": scenario,
                "fallback_triggered": fallback_triggered,
                "latency_ms": latency,
                "passed": fallback_triggered,
            }
        except Exception as e:
            latency = (time.perf_counter() - start) * 1000
            return {
                "scenario": scenario,
                "error": str(e),
                "latency_ms": latency,
                "passed": False,
            }
